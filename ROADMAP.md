# Roadmap

The **living** execution tracker — what is in progress, what is next, what just shipped. It is updated in the same PR as the work (a definition-of-done item; see [`docs/conventions/documentation.md`](docs/conventions/documentation.md)).

This is **not** the white paper's _Build roadmap_, which is the stable **phase strategy** (Phase 0–7 and rationale). This file tracks execution against those phases and owns one thing: **narrative scope and ordering** — which stream is live, what it does next, what order the rest comes in, and why.

**It deliberately does not carry per-capability status.** [`docs/now.md`](docs/now.md) — the build register — is the complete inventory: every capability at its real status, the counts across all nine statuses, what is blocked on the owner, what is in build, what is queued, and how the counts have moved. It is generated from the [`roadmap.d/`](roadmap.d/) feature ledger and gated against it, so it cannot drift. Anything that is per-capability status is linked to here, never restated.

The other homes: per-slice stage (research → spec → plan → built → tested) in [`STATUS.md`](STATUS.md) · what shipped and when in [`CHANGELOG.md`](CHANGELOG.md) · decisions in [`docs/Decision-Log.md`](docs/Decision-Log.md) · subsystem design in [`docs/specs/`](docs/specs/) · integration adapters and their state in [`docs/integrations.md`](docs/integrations.md) · owner-side deploy and account actions in [`docs/deploy-queue.md`](docs/deploy-queue.md).

## Now — current focus

**Phase 2 is closing and Phases 3–6 are open at once.** The bullets below are the live streams, each with its current state in a sentence and its next step. Per-slice stage currency is in [`STATUS.md`](STATUS.md); per-capability completeness is in [`docs/now.md`](docs/now.md).

- **Matter document surface — the document loop is clickable.** A matter's Files page runs on the firm's own rows: list, add a document (from a file, or built from a template), save a new version, read the version history — all over routes that already existed, so the API contract did not move. The editor is now a screen: double-click, Enter and Open on a Word or plain-text document open `/documents/{id}/edit` in a new tab, where a word-processing format gets the Collabora frame with the WOPI token posted into it and a text document gets an in-app editor that saves a new version through the upload ceremony. A PDF opens too, at `/documents/{id}/view`, and it is the first consumer of the pure-Rust PDF engine in the browser: pages are rasterized in a Web Worker through `crates/pdf-core` compiled to WebAssembly, so only pixels reach the page and the reader needs no rendition engine, no container and no deploy. The engine had been built, tested and used by three workers, and nothing in the web application had ever loaded it. Honest gap: the browser editor's launch is real (co-editing state, audit row, signed single-version token) but its frame comes from the `magna-carta-edit` per-document container, a deploy-time activation, so it is empty locally and the screen says so; whether it fills on the deployed site is the next thing to verify. That gap used to be the second one — until 2026-08-19 none of the four `documents:*` permissions the chokepoint enforces was granted to any role, so the launch, the offline checkout, the check-in, the reconcile and the force-release answered 403 to every member of every firm; the seeds now exist and a `lint:ungranted-permissions` gate fails the next permission that ships without one. **Next:** a registered template in the development seed so build-from-template is clickable locally, then folders, rename and download.
- **Documents became a place you can go, and it is the firm's template library.** The sidebar row was a Soon stub while everything behind it was built: the template catalogue, registration, the merge-field dictionary and the assembly job have been on `main` since slice 2·6·1, reachable only from a matter's Files page one document at a time. `/documents` is the firm-side twin of that page — every template the firm has registered on the one table, with a derived standing (ready, being checked, archived) that says whether it can be built from today; New Template registers a Word document or a fillable PDF from the browser and renders the registration report as findings; and Add to Matters builds one template onto several matters in one go, one assembly job per matter under its own idempotency key, each reported on its own row so a refusal on one never hides what happened to the rest. **Next:** the field inspector over a version's manifest, adding a version from the library, and the mapping library's screen; then authoring in the browser.
- **Time became a place you can go.** `/time` reads the firm's time over a span of work dates, across every matter — the question the matter's Time tab and the one-day view could not answer between them. The sidebar row was a Soon stub for a structural reason rather than a cosmetic one: `GET /api/v1/time-entries` answered one timekeeper on one day or one matter entire, and returned an empty list for anything else, so the top bar's firm-wide Time Sheet was reading nothing at all. The third listing shape — a `from`/`to` span, narrowable to one timekeeper, matter or status, cursor-paged on the same `(work_date, id)` key the per-matter read walks — is what made flipping the row honest. Reading anybody's time but your own, the whole firm's included, takes `time:viewFirm`, and the control is absent rather than disabled without it. Six named spans plus a custom range, the span and the timekeeper both in the address so a supervisor's view is a link somebody can send, hours-and-money figures over what is in view, and any row opening the shared entry record. Deliberately no free-text search: the period pages, and a box that only looked at what had loaded would report a word missing from a month it never read — the columns' own filters narrow, and say what they left out. **Next:** the week grid, which is the other half of the personal-timesheet design and the fastest way to reconstruct a week that got away.

- **Discovery has screens.** Slice 5·1 was built end to end and completely invisible; the surface over its ingest half is now on `main`. Three addresses, one per reader: the matter's **Discovery** section lists that matter's corpora and starts one; `/discovery` lists every review set the member is on the ACCESS LIST for, across matters, which is the reader the wall is actually shaped for — a contract reviewer brought in for one production may hold no matter access at all; and the workspace at `/discovery/review-sets/<id>` leaves the matter chrome entirely, because the matter header mounts a consolidated search on every section by construction and that search must never reach a review set. ## UI roadmap — the deferred-surface build order

- **Every download registers, and Downloads became a register (2026-09-17).** `download_item` was built as a shelf of what the platform MADE you: `bundle` and `conversion` sat in its producer vocabulary from day one with no writer, and a file downloaded from a matter had nowhere to go at all — so "I downloaded something and it did not appear in Downloads" was the correct behaviour, which is the definition of a design that needs changing. - **Telemetry analytics tier (Iceberg-on-R2)** — register the redacted Logpush-in-R2 logs as R2 Data Catalog Iceberg tables for zero-egress querying, with compaction and snapshot-expiration maintenance. Analytics Engine remains the MVP path and the seam sits on data already written. _Gate: adopt when a trigger binds — retention past ~92 days, exact unsampled counts, rich joins, or cost at scale — and re-verify the open-beta limits at that point._ (ADR-0056, _Proposed_.)
- **Post-quantum signature migration** — passkeys/WebAuthn and the PAdES seal to ML-DSA/SLH-DSA, plus a PQC-capable external-KMS-rooted key hierarchy. Seamed today via algorithm versioning. _Gate: upstream standards (FIPS 204/205/206, COSE, ETSI PAdES, CA support)._ Verify Cloudflare hybrid PQC TLS is on for every hop and log any endpoint that will not negotiate it. (ADR-0046.)
- **Root-key rotation and customer-managed keys (BYOK).** Rotation is cheap by design — the root key wraps only the per-firm keys, never the field ciphertexts, so rotating it re-wraps N keys with zero data re-encryption; the ciphertext frame already reserves the version bytes. _Gate: before the first real client onboards, or sooner on a compromise or compliance trigger._ BYOK wraps a firm's key under the firm's own KMS instead, giving that firm a cryptographic kill-switch without breaking server-side processing — a future enterprise tier, not MVP, because the per-firm key is already the seam. True zero-knowledge encryption is explicitly out of scope; the only viable carve-out is a narrow opt-in sealed vault for fields that never need processing. (ADR-0046.)
- **Branded per-firm subdomains + the safe-delivery host model.** When firms get branded URLs the tenancy boundary becomes the subdomain, which reshapes both the preview delivery host and the session-cookie scope. Decided shape: one neutral, shared, cookieless delivery host embeddable by any firm subdomain via a wildcard `frame-ancestors` — which does not weaken authorization, because the signed firm-scoped token names one object and the embedding origin was never the gate. Session cookies stay host-only. Seamed now (the preview header builder emits the wildcard; a fitness test pins the cookie invariant). _Remaining when branded URLs are built: provision the wildcard host, move the app to per-firm subdomains, point `FILES_ORIGIN` at the real host (it is a placeholder today, so previews are inert until then), and bind the session's firm to the requested subdomain server-side._
- **Edge hardening (in-Worker)** — six request-handling improvements, all app/build work rather than dashboard config (the triage and the decision to skip Cloudflare Snippets are in [`operations.md`](docs/conventions/operations.md)). **(1) A security-header baseline is the one do-now gap** — no CSP, frame-options, content-type-options, referrer-policy or permissions-policy exists in the Worker or SPA today; add a global header middleware, with HSTS set at the zone. **(2) A deliberate CORS policy**, gated on the Tauri desktop client and the custom-hostname portal landing. **(3) Webhook HMAC verification and outbound request signing** in the integrations HttpClient seam, gated on the first signed integration. **(4) A maintenance-mode toggle.** **(5) Mining `request.cf`** for telemetry enrichment and bot-aware handling on sensitive routes. **(6) Honeypot / tarpit** — defense in depth, low priority, and tarpitting costs Worker duration.
