- id: conflicts.matching-engine
  name: Matching engine
  scope: Candidate generation over names and identifiers (exact identifier, exact normalized name, organization match keys, Double Metaphone, trigram) with related-party edge expansion, ordered by evidence tier.
  status: shipped
  slices: slice-4-1-conflicts
  adrs: ADR-0013
  spec: docs/specs/2026-07-09-slice-4-1-conflicts-design.md
  evidence: packages/conflicts/src/matching.ts runs six blocking channels over the Directory corpus — blind-index identifier equality with no decrypt, an exact normalized-display probe, the two organization match-key probes (normalized_match_key at tier 2, normalized_match_key_bare at tier 3, sharing one implementation with the exact-name probe so the three cannot come to scope differently), and the directory's phonetic and trigram channels — and matchPartyBatch runs each of them ONCE over a whole expanded closure through findDuplicateCandidatesBatch in packages/directory/src/search.ts, with readSubjectFactsBatch reading the closure's node rows in one query per table; packages/conflicts/src/expansion.ts walks related-party edges with a budget per edge class where corporate parent/subsidiary/successor hops cost nothing, and packages/conflicts/src/evidence.ts assigns each candidate its tier; packages/conflicts/src/run-check.ts composes them, held by matching.test.ts, expansion.test.ts matching-depth.test.ts and matcher-equivalence.test.ts in packages/conflicts/test — the last proving the batched matcher returns exactly the per-entity matcher's hit set over a real corpus carrying every channel's shape, and asserting per channel that it fired at all, which is what allows the batching to exist and what stops a dead channel reading as coverage.
  notes: Backend only, no screen. Deliberately scorer-free — a tier orders evidence and never filters, so raising strictness can only add hits; the under-specification the white paper flagged was answered by the two conflicts design specs rather than left open. One named gap remains and it is measured rather than assumed: the phonetic channel encodes ENGLISH pronunciation, so cross-origin surname variants (Nowak/Novak, Kowalczyk/Kovalchik) are structurally out of its reach. A Beider-Morse channel would close seven such pairs in a thirty-pair corpus; it is unbuilt because the only pure-TypeScript encoder compiles its rule tables in 20,377 ms inside workerd against 16 ms in Node, which is past the CPU limit. The follow-on is the Rust/WASM port, with that number as its flip condition.

- id: conflicts.matching-engine.strictness
  name: Configurable strictness
  scope: Balanced default with an over-inclusive fuzzy/phonetic/alias mode a firm can enable, and the name roles each band compares against as a firm setting recorded on the check row.
  status: shipped
  surface: screen
  slices: slice-4-1-conflicts
  evidence: The two levels are a typed vocabulary in packages/conflicts/src/types.ts; matchOptionsFor in packages/conflicts/src/matching.ts picks the channels and name roles each level sees, and over_inclusive is a structural superset by construction — it searches every name role and is deliberately not configurable, while ConflictsPolicy.balancedNameRoles in packages/conflicts/src/settings.ts makes the narrower band's role set a firm setting defaulting to current, former, maiden and alias, so a party who married and changed surname is found at the default band. The phonetic axis widens the same way: matchOptionsFor narrows balanced to the Double Metaphone PRIMARY code alone, while over_inclusive passes no scheme filter and so sees primary and secondary both. Beider-Morse runs at neither band — it is unbuilt, for the reason recorded on conflicts.matching-engine. resolveScope raises a per-run request to the firm's floor and records floorRaised, and runConflictsCheck writes inputs_json.matching with the name keys compared, the phonetic schemes that ran and the resolved roles, so a reader of an old row does not have to know what the preset word meant that day. Held by packages/conflicts/test/matching.test.ts, which drives the narrowed setting as well as the default.
  notes: The firm floor now has a write path and a screen. PUT /api/v1/firm/conflicts-policy on conflicts:configure — a permission of its own rather than conflicts:run, seeded to Owner and Admin alone, because this decides what every LATER check searches and no check row records that a person chose it. writeConflictsPolicy normalizes through normalizeConflictsPolicy, the same function the read repairs with, and STORES the normalized value: what is in the row is what runs, so the screen can render the row back and believe it. Settings, Conflicts stages every control until Save, shows party and current as locked controls carrying their reason rather than hiding them, and names each specific repair the platform made on the way in instead of describing the possibility. Held by packages/conflicts/test/policy-write.test.ts and apps/web/test/conflicts-policy-screen.test.ts.

- id: conflicts.read-surface
  name: Reading the log back
  scope: The reads the conflicts screens are built against — naming the party a hit is about, the full adjudication trail, the firm's own policy floor, the checks a firm has run, an earlier answer about the same party, and asking for a re-check on demand.
  status: shipped
  surface: screen
  spec: docs/specs/2026-09-02-conflicts-read-surface-design.md
  evidence: All six built. GET /api/v1/conflicts/checks/{checkId} now resolves every hit's entity through readEntityDisplayNames in packages/conflicts/src/subject-facts.ts and carries a `party` on each hit — the name the Directory holds today, resolved on the read rather than copied onto the append-only log. The same change replaced two N+1s: the handler was calling readCurrentDisposition per hit inside a Promise.all (readHitDispositionStates answers the whole check in one query, and its own comment names the per-hit loop as the mistake), and the checks screen was spending one Directory read per hit a reviewer opened. Held by packages/conflicts/test/entity-display-names.test.ts and two route tests, including the unresolved-entity path a merge makes reachable. GET /api/v1/conflicts/hits/{hitId}/dispositions then added the adjudication trail — readDispositionTrail in packages/conflicts/src/disposition.ts, oldest first with the same rowid tie-break readCurrentDisposition uses, so a reversed answer stays readable beside the one that replaced it. The hit's existence is checked so an empty trail can only mean nobody has answered it. POST /api/v1/matters/{matterId}/conflicts-rechecks then added the on-demand re-check on conflicts:run — no scope field, because the firm's floor is what runs and a scope field would invite a screen to compose a narrower search than the firm requires; no subject list, because runConflictsCheck reads the matter's live parties. GET /api/v1/firm/conflicts-policy serves readConflictsPolicy on conflicts:read, and the check runner states the floor rather than marking it unreadable. GET /api/v1/conflicts/checks then added the firm's check history — keyset-paged over (created_at, id) through selectConflictsChecksStatement, optionally narrowed by matter. Its load-profile plan probe measured the UNFILTERED listing as a full table scan of conflicts_check on the first run, exactly as the design predicted, because the existing index leads with subject_matter_id; conflicts_check_created_id_index was added in the same change and both shapes are now probed separately.
  notes: The sixth read closed the register: readPriorConclusions carries an earlier check's answer about the same party onto a hit as `previouslyAnswered`, a field deliberately separate from `disposition` so the hit stays UNANSWERED — the owner's ruling of 2026-09-02, decided on the case where a company cleared as a former client re-surfaces as a current client's subsidiary, which is a different question on a higher bar. It needed conflicts_hit_entity_created_index: conflicts_hit carried only (check_id), so matching a party across earlier checks scanned an append-only table. Since 2026-09-12 a check is a NUMBERED record with runs under it — conflicts_numbered_check and conflicts_check_run in packages/database/src/per-firm-schema.ts, opened by packages/conflicts/src/check-run.ts, executed after the response by apps/api-worker/src/conflicts/check-run-executor.ts — so POST /api/v1/conflicts/checks answers 202 with the number, GET /api/v1/conflicts/checks/{checkId} carries the runs and the selected run's record, POST .../{checkId}/runs opens a further run, PUT .../{checkId}/matter files the check on a matter, and GET /api/v1/conflicts/checks lists numbered checks one row each. The check's screen at apps/web/src/routes/(app)/conflicts/checks/[checkId] is titled by the number, follows a run in flight stage by stage, lists the runs, offers Run Again and File on a Matter, and carries exactly Print Report and Download Report (the printed sheet, rendered as a PDF through the export renderer). Held by apps/api-worker/test/conflicts-routes.test.ts, packages/conflicts/test/check-run.test.ts and apps/web/test/conflicts-run-progress.test.ts. What remains on conflicts-gaps.ts is the assembled report document filed on the matter, which is its own work.
