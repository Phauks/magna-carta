# Magna Carta — operating-cost register

**Status:** Living record · **Last updated:** 2026-08-14 · **Owner:** Trevor Goldsmith

The single home for the **money cost of running Magna Carta** — what _we_ pay (subscriptions, usage-metered platform spend, one-time charges) and, separately, what _customers_ pay and at what rates (pass-through + our take). As the program acquires services, every new cost gets a row here in the **same commit** that incurs or commits it (the docs-in-commit discipline). This register is _money_; the operational _setup steps_ for a service live in [`conventions/operations.md`](conventions/operations.md), and the _decision_ that adopted it lives in the [Decision Log](Decision-Log.md) — link, don't duplicate.

**All figures are estimates** (marked `~`) at 2026-06 list prices and **must be re-verified before relying on them** — vendor pricing drifts (e.g. Google's Jan-2025 +17–22% Gemini-bundle increase; Cloudflare's Dec-2025 Durable-Objects storage-billing change). Usage-metered lines have no fixed monthly figure; the cost is rate × volume, measured against the load-profile harness, not guessed.

**Cadence:** `monthly` · `annual` · `usage` (metered) · `per-txn` · `one-time`.
**Status:** `active` (billing now) · `committed` (decided, not yet billing) · `potential` (optional/upgrade or scale-triggered) · `deferred` (future/conditional) · `avoided` (a cost the architecture deliberately does _not_ incur).

**Browser Rendering has two cost axes, and only Live mode touches the second.** The static capture uses quick actions, billed by browser-hour alone. Live mode holds a Browser Session per member, which is billed by the hour **and** counts toward concurrency — the monthly average of each day's peak number of open browsers, ten included. Three controls bound it, all in the code rather than in policy: one session per member by construction (the session object is keyed firm and user), an idle alarm that closes a browser after three quiet minutes, and a fifteen-minute ceiling on any one browser's life. The concurrency line is the one to watch as firms adopt Live; the hour line stays small because a capture is seconds and a session is minutes.

**The editor container (folded into the Containers row above).** One `standard-1` instance per open document (half a vCPU, 4 GiB, 8 GB disk), started on first open and slept five minutes after the last view closes: about $0.04 an hour for memory while it runs and about $0.04 an hour for CPU while it is active, so under a dime per open-document hour. The owner settled this on 2026-09-20 after trying every size in a week: `standard-2` (one vCPU, 6 GiB, about twelve cents an hour) bought nothing the editor's server audit reads, since both sizes show it one thread, and `standard-4` (four vCPUs, 12 GiB, about forty cents an hour) cleared the audit's hardware warning (coolwsd sets it whenever the kernel shows it fewer than four threads, whatever `per_document.max_concurrency` says) and felt no different to use. The warning is therefore accepted as the stated consequence of the size, and the audit is switched off in the image so the warning's snackbar does not greet every member on every open (`containers/collabora/Dockerfile`, `disable_server_audit`). What four threads buy is burst compression of newly visible pages, so scroll and page-change latency, not typing; the sizes above, should a measurement call for one: `standard-2` at about $0.12 an active hour, a custom instance of 2 vCPUs and 6 GiB (the platform's floor for two cores, at least 3 GiB per vCPU) at about $0.20, or `standard-4`, the only size that clears the warning, at about $0.40.

**Engine container scaling (folded into the Containers row above).** Scan is the one exception that keeps a warm `standard-1` instance via a periodic poke (~$35–50/mo at MVP scale; see [`operations.md`](conventions/operations.md)). Recovery, file-repair, and **OCR** run with no warm-poke cron and scale to zero at idle, billing only while a job runs. The OCR container's cold start is slower than the others because it loads ~31 MB of baked-in PP-OCRv6 ONNX models at boot.

**Search split compaction (folded into the R2 row above), and it moves cost in both directions.** The discovery index publishes one split per document version, so an uncompacted matter's query fans out over every one of them — a measured 186,293 R2 range GETs (Class B) for one query over 5,000 documents, against 45 compacted. Compaction removes almost all of that recurring read cost and adds a bounded, occasional one: each pass reads its source splits and writes one merged object (Class A), and superseded objects sit in the firm's bucket for a one-hour grace period before collection, so storage briefly doubles for the merged set. The trade therefore depends on how often a corpus is searched versus written, which is why the thresholds are **per-firm settings** rather than platform constants — a firm that ingests constantly and searches rarely wants a higher threshold than one that does the reverse. Neither figure can be priced before the search Container is deployed; the read-side one is measured (`crates/search-eval`) and the write-side one is not.

**Vectorize bills the resident corpus, not just the queries — the line above is a factor of ~21 out if read as storage.** Cloudflare's _queried vector dimensions_ metric counts the vectors **already in the index**, once per month, as soon as one query is issued: the published formula is `((queried vectors + stored vectors) * dimensions * ($0.01/1,000,000)) + (stored vectors * dimensions * ($0.05/100,000,000))`, and the queried rate is 20x the stored rate per dimension. So an index that is queried at all costs about 21x its storage line, and the cost scales with corpus size rather than query volume. Worked against the discovery scale assumptions (250,000-document review set, ~20 passages/document, 1,024 dimensions): storage ~$2.56/mo, queried ~$51.25/mo, **total ~$53.81/mo** — against a **derived** ~$0.11/mo for the same corpus on the keyword half (measured 37–59 R2 range GETs per compacted query at the Class B rate above). The one-time **embedding** charge is the larger figure: 5,000,000 passages through the platform-pinned `@cf/baai/bge-large-en-v1.5` at **$0.204 / M input tokens** is roughly **$261–$522** depending on tokens per passage, repeated on every re-index. Two things about this line are **not** settled: whether a namespace-scoped query bills the namespace's resident vectors or the whole index's (undocumented — one query on first deployment settles it), and whether the semantic half is built at all (discovery flag D4, deferred). Derivation and labelling of every figure: [`research/2026-08-14-semantic-half-convergence-and-cost.md`](research/2026-08-14-semantic-half-convergence-and-cost.md).

## F. Deliberate cost-avoidance (architecture choices that are _not_ a bill)

Recorded so the register reads honestly — the absence of a common SaaS line is a decision, not an oversight:

- **No third-party error/observability SaaS** (no Sentry / Datadog). Error logging and telemetry are in-house and Cloudflare-native (golden rule 4; ADR-0017) — a privilege/confidentiality requirement, not only cost.
- **No third-party file-conversion / OCR / search SaaS** (no CloudConvert / Zamzar / VirusTotal for privileged bytes). Conversion, OCR, and full-text search run on our own Containers (ADR-0030) — _borrow expertise, never custody_.
- **No managed auth SaaS** (no Auth0 / Clerk). Better Auth, self-hosted on control-plane D1 (ADR-0004).
- **No turnkey legal-payments processor as primary** (LawPay kept only as a compliance fallback) — build on a raw interchange-plus processor to minimize fees (ADR-0032).

> When a potential/deferred line begins billing, move its row to **§A active/committed** and replace the estimate with the real figure in the same commit. When platform-subscription or processing-margin pricing is decided, fill the rate in **§E** and record the decision as an ADR.
