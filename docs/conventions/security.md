# Security conventions

**Status:** Active in part — the _Auth & secrets — operational facts_, _Untrusted file handling_, and _Post-quantum & crypto-agility_ sections bind now; the remaining scope below is filled in as the corresponding subsystems are built (white paper, _Tenancy_ and _Authentication, access control & encryption_; Phase 0).

**Scope (single home for):** the practitioner's how-to for building securely — isolation, access control, encryption usage, secrets handling, telemetry redaction, and payment scope.

**Authoritative context:** the [white paper](../Magna-Carta-White-Paper.md) — _Tenancy & data isolation_; _Authentication, access control & encryption_; _Observability & diagnostics_ (redact-by-default); _Payments_ (PCI SAQ A).

**Framework mapping:** which external requirement — SOC 2 / GDPR / PCI DSS / ISO 27001 — each control here answers, plus the compliance gap register, lives in [`compliance.md`](compliance.md). This file is the _how to build securely_; that one is the _which framework requirement it satisfies_ (one home per fact).

**To document:**

- **Firm-scoping:** every business query goes through the firm-scoped DAL; how the `member` mirror + `firm_id` join works; never cross firms.
- **RBAC + ethical walls:** how to gate an action; how a wall is honored in code. (Note: the access-control model itself is still under-specified — see the white paper's _Authentication, access control & encryption_ `Needs development` note and its forthcoming spec in [`../specs/`](../specs/).)
- **Encryption:** use the DAL `protected()` field type; the envelope-key model; blind-index matching; never hand-roll crypto or store plaintext secrets in core.
- **Secrets:** per-firm plugin credentials via `getSecret`/`putSecret`; plugins never see key material.
- **Telemetry redaction:** allowlist fields; Error IDs and breadcrumbs, never content.
- **Payments/PCI:** card capture through the processor's **hosted payment modal** (iframe) only — the app never sees or stores a PAN (never a CVV); keep the firm at **SAQ A** (`ADR-0181`); the payment surface stays free of third-party scripts (PCI v4.0.1); fees-never-touch-trust routing.
- Auth hardening: Argon2id, rate limiting, lockout, the immutable auth audit log.

> Firm-scoping and redact-by-default logging are **golden rules** (root [`CLAUDE.md`](../../CLAUDE.md)); `protected()`, secrets-isolation, and the trust/fee rules are **domain invariants** ([`invariants.md`](invariants.md)).

## Auth & secrets — operational facts (slice 0·4)

These bind now. The integration shape, rationale, and build findings live in **ADR-0073** (as amended) and the white paper (_Authentication, access control & encryption_; _Tenancy & data isolation_) — don't restate them here.

- **Membership is invitation-only.** There is no open signup: Better Auth runs with signup disabled (the public route always 4xxes — fitness-tested), so every user creation enters through the invitation flow and rides the idempotent write path.
- **Worker secrets — `wrangler secret put`, never `vars`.** Production secrets: `AUTH_SECRET` (Better Auth signing + at-rest encryption), `PLATFORM_ADMIN_KEY` (guards `POST /api/v1/firms`), `ROOT_KEK` (the root key-encryption key for protected fields — see below), and the `CLOUDFLARE_API_TOKEN_FIRM_PROVISIONER` + `CLOUDFLARE_ACCOUNT_ID` pair for the Cloudflare REST `FirmResourceProvider` adapter (Cloudflare API tokens are named `CLOUDFLARE_API_TOKEN_<purpose>` so each stays distinct and individually rotatable as more are added). `apps/api-worker/.dev.vars` is **committed with placeholder-only values** — enforced by a byte-identity fitness test (`apps/api-worker/test/dev-vars.test.ts`), so a real credential dropped into the file fails the suite. The Cloudflare pair is deliberately absent locally; its absence selects the dev pool-claiming adapter.
- **`ROOT_KEK` — the protected-field root key-encryption key.** 32 random bytes, base64-encoded, set as a Worker secret. It is an AES-KW key whose only powers are wrap/unwrap: it wraps the per-firm data keys minted at provisioning and unwraps them on demand into non-extractable HKDF base keys. It never encrypts application data directly and is never logged. The per-firm wrapped keys (not the root KEK) live in the control-plane `firm` table (`wrapped_firm_key`, `firm_key_version` — migration `0002_firm-key-columns`); the raw firm-key bytes are never persisted. Rotating `ROOT_KEK` is a rewrap of every firm's wrapped key, not a corpus re-encryption (the firm keys themselves do not change).
- **Better Auth `encryptionKeys` rotation array (the 2FA-secret encryption).** Better Auth encrypts the credentials it owns outside the firm-keyed chokepoint — most importantly the TOTP seed — under an auth-secret-derived keyset, configured as a version-tagged rotation array (element 0 the current encrypt key; every element a decrypt key, so a future rotation prepends a version and old seeds keep decrypting — a dual-read migration, never a flag day). A TOTP seed is a **user** credential read at login before any firm context exists, so it is deliberately not routed through the per-firm `protected()` chokepoint (a firm crypto-shred must never break a user's login). In the pinned Better Auth 1.6.16 this option is named **`secrets`**, not `encryptionKeys` — see the slice's deviation note in the Decision Log (ADR-0084). Configured in `apps/api-worker/src/auth.ts`; version 0 is the existing `AUTH_SECRET`, so already-stored seeds still decrypt.
- **Dev email stub.** Verification and reset links land in the terminal via the logging adapter behind the `sendEmail` port (nothing beyond the message fields is logged); slice 0·6 swaps in Cloudflare Email Service behind the same port (ADR-0074).
- **Dev firm-database binding pool.** Miniflare cannot create D1 databases at runtime, so local dev and tests claim from the pre-declared `DB_FIRM_POOL_*` bindings; a claimed firm's `database_identifier` **is** the binding name. Adding a pool member touches three places in lockstep: `wrangler.jsonc`, the `Bindings` type, and the resolver table in `apps/api-worker/src/firm-binding-resolver.ts`. An unknown identifier resolves to null → 404, never a 500 and never an existence oracle (ADR-0052).
- **TOTP seed handling.** Seeds are encrypted at rest by Better Auth under the auth-secret-derived `encryptionKeys`/`secrets` rotation array (see above). This is the final design, not a seam: slice 1·2 resolved (owner, 2026-06-12) that user-owned login credentials stay under Better Auth's own at-rest encryption rather than the per-firm `protected()` chokepoint — login precedes any firm context, and a firm crypto-shred must not break a user's login (ADR-0084 closing ADR-0026's open line).
- **Crypto-shred — irreversible per-firm key destruction.** `shredFirmKey` (`apps/api-worker/src/firm-key-shred.ts`) destroys a firm's data key in three ordered effects: it nulls `wrapped_firm_key` in the control-plane `firm` row (the whole mechanism — every purpose/index key derives from it, so once gone the firm's entire protected corpus is permanently unreadable and decrypts fail closed); it writes a `firm.key_shredded` audit row in the same atomic batch (which also distinguishes a shredded firm from a never-minted one, so the provisioning key-mint never re-mints for a deliberately shredded firm); and it calls the firm-key provider's `invalidate()`. The `invalidate()` step is required because the provider caches the unwrapped non-extractable HKDF handle per isolate — without it, the same isolate could keep serving a key whose wrapped form was just nulled (the same-isolate cache window). Function only this slice; the offboarding route that invokes it is a named seam.
- **Idempotency is auth-gated and tenant-scoped.** Session + permission checks run **before** the idempotency pre-decision (an unauthenticated caller can never replay a stored response or probe key existence), and stored keys are scoped `${firmId}:${clientKey}` (`platform:${clientKey}` on platform-admin routes), so a key can never replay or poison across firms (ADR-0073 amendment).
- **Deactivated members lose all permissions at the read path.** Both permission reads (role permissions and direct grants) gate on `member.status = 'active'` in SQL, so a deactivated member with a live session holds nothing anywhere the resolver is consulted; `GET /api/v1/me` answers a deactivated member with the ADR-0052 404 (absent — never a 403 that confirms the account exists but was switched off), while a never-mirrored user (the transient outbox sweep-lag window) still bootstraps 200 with empty permissions. The deactivation API itself is a later slice — the read path is correct ahead of it.
- **Platform-admin key comparison is constant-time.** `X-Platform-Admin-Key` is compared via SHA-256-folded `timingSafeEqual` (`apps/api-worker/src/constant-time.ts`) so neither content nor length leaks through timing; the secret guard itself is a named seam until a real platform-admin principal model exists (ADR-0073).
- **Dead-lettered outbox rows are revived by the requeue statement.** The relay marks a row `status='failed'` (dead-letter) terminally after max attempts — nothing re-dispatches it automatically. Recovery is an operator action: `requeueDeadLetteredMessageStatement` (`@magna-carta/data-access/outbox-statements`) flips a failed row back to `pending` (attempts reset) so the next sweep retries it. The guarded UPDATE only ever revives a genuinely failed row. A self-service admin surface is a later slice.

## A public repository

The repository is public (since 2026-11-13; licence: all rights reserved). Everything committed, including history, branch names, pull-request text and fixtures, is readable by anyone. Never commit a secret, a personal email address, a home or office IP address, or real client data; fixtures use invented names and reserved example domains. A secret that reaches a commit is rotated, not just removed, because history keeps it.

## Supply chain — what may enter the tree, and on what terms

Four gates, none of which needs a third-party service: the firm keeps its own dependency metadata on
its own compute.

- **Licenses are deny-by-default, in one policy read by two gates.** The platform is proprietary
  SaaS, so AGPL and SSPL are a hard prohibition — network interaction counts as distribution, which
  would force a source offer — and the allowlist is permissive licenses plus weak (file- and
  library-level) copyleft. The policy, the SPDX expression parser and its self-test live in
  [`tooling/license-policy/`](../../tooling/license-policy/); `pnpm run lint:licenses` reads the npm
  tree (701 versions) and `pnpm run lint:cargo-licenses` reads all ten Cargo workspaces (866 crate
  versions — the crates workspace plus every container). The Cargo half is new: the Rust supply chain
  had been vulnerability-scanned by the osv step for a year and license-checked by nothing.
  - The expression parser is a real parser, not a split on `OR`. The regex it replaced read
    `(MIT OR GPL-3.0) AND AGPL-3.0` as **allowed**, because it stripped the parentheses and found a
    permissive disjunct — a conjunct that binds the whole work waved through by precedence the
    classifier did not implement. It also denied three forms the Rust tree actually carries
    (`WITH` exceptions, the legacy `MIT/Apache-2.0` slash form, lowercase identifiers).
  - Adding an identifier to the allowlist is a deliberate policy act and binds both ecosystems.
- **A published version waits before it can be resolved.** `minimumReleaseAge` in
  `pnpm-workspace.yaml` holds new versions for three days, which is where a compromised release is
  caught — in public, by other people. It binds the weekly automated upgrades in particular. The
  override for a same-day security fix is in that file's own comment.
- **Vulnerabilities fail the gate at HIGH and above**, across every lockfile including the Rust ones
  (`pnpm gate`'s `audit` dimension, a pinned osv-scanner). An accepted advisory carries a cause and an expiry in
  [`osv-scanner.toml`](../../osv-scanner.toml); acceptance cannot silently become permanent.
- **A C or C++ dependency arrives only by consent** (golden rule 14 in the root
  [`CLAUDE.md`](../../CLAUDE.md)), and `pnpm run lint:native-builds` is the mechanism: the
  `onlyBuiltDependencies` grant in `pnpm-workspace.yaml` is an audited allowlist, and a native build
  step arriving without one fails. The consented exception is clamd in the scan container, which is
  network-isolated and documented where it runs.

**Nothing secret is committed.** `pnpm run lint:secrets` scans the tracked tree for credential shapes
— private key headers, provider tokens, and high-entropy literals bound to secret-shaped names — and
`pnpm run lint:containers` holds the Dockerfile properties that matter for images built from this
repository. Both are in-house scans for the same reason the license gate is.

## Untrusted file handling (uploads, processing & preview)

Every uploaded byte (File Manager, Client portal, Discovery ingest) is **untrusted** — Discovery and portal files arrive from external/adversarial parties. Rationale and the full threat model live in the [white paper](../Magna-Carta-White-Paper.md) (_Matters and File Manager_ `Needs development` note); don't restate them here. A malicious file is **inert at rest** (R2 cannot be corrupted/infected) — risk arises only when something **processes, serves, or forwards** it. **Containment is the primary defense; detection (AV) is a thinner layer.** Three threats, in priority order:

- **Server-side RCE (threat #1 — targets _us_).** Native parsers (LibreOffice, FFmpeg, libvips/ImageMagick, ghostscript, qpdf) have a recurring malformed-input RCE class. Run them **only** in **sandbox-hardened Containers**: **no egress** (`enableInternet = false`, or a tight `allowedHosts` allowlist); **least-privilege per job** — the instance gets the single file, never firm-wide R2 creds, D1, or any key (keys never enter the processing path); **ephemeral** (reset per job — no cross-job/cross-firm reuse); **resource caps + timeouts** (a spin/OOM file is contained, not a DoS); **assume-escape**. Where we author the parser, prefer the **Rust→WASM core** (memory-safe sandbox by construction). Home: white paper _Performance & concurrency model_.
- **Stored XSS on preview (threat #3 — targets other users' browsers).** A malicious SVG/HTML/scripted-PDF runs in the viewer's origin. Server sandboxing does **not** help — this is a client-side boundary. Serve untrusted bytes from a **separate, cookieless sandbox origin** (never `app.magnacarta.esq`), with **`Content-Disposition: attachment` + correct `Content-Type` + `X-Content-Type-Options: nosniff`**, a restrictive **CSP**, and — for inline render — exactly two mechanisms: an **`<iframe sandbox>`** (bare `sandbox`, never `allow-scripts`) for document formats, or a native **`<video>`/`<audio>`** **subresource** for verdict-confirmed inert media (`Content-Disposition: attachment` is still honored for a top-level navigation and ignored for the media subresource, so the file plays in place yet a direct hit on the raw bytes downloads); **never hand active formats raw to the browser** — preview a **derived safe rendition**. Home: white paper _Inline file preview_.
- **Distribution (threat #2 — targets downstream recipients).** Handing an infected file to a client/co-counsel/court. This is what the **malware scanner** mainly mitigates; with #1/#3 handled structurally it is defense-in-depth + a compliance/cyber-insurance expectation, not the linchpin.

**Scanning rules:** _borrow outside expertise, never outside custody_ — a commercial engine on our own compute is fine; a SaaS that holds privileged bytes (attachmentAV/VirusTotal) is not (same egress bar as in-house conversion/observability). Build the scanner as a **swappable port**; engine deferred. Pipeline: pre-acceptance gates (size/type allow-list, **magic-byte** check, decompression-bomb guards) → **quarantine-on-arrival** (object not servable until cleared; async via R2 event → Queue) → scan (verdict as file metadata) → optional **CDR rendition** (original preserved for evidence) → **re-scan sweep** on signature updates → **quarantine, never auto-delete** (infected files are evidence; destruction blocked by legal holds — the generic "delete-infected" default is wrong here). Files past the engine's scannable cap get an explicit _unscanned_ policy; desktop (Tauri) local pre-scan is the parity accelerator. Tracked in [`../../ROADMAP.md`](../../ROADMAP.md) _Hardening_; its own ADR when built.

**Re-scan is access-triggered, and a re-scan finding uses _informed access_ (not hard-quarantine).** A committed file is re-scanned when it is **accessed** (download/preview), not by a proactive sweep, and only when its recorded engine version is stale — so cost tracks attention, not corpus size, and a dormant file (which can harm no one until it is opened) is never re-scanned. Re-scans reuse a per-firm content-dedup cache keyed by `(content hash, engine version)`: identical content scanned once under an engine is never re-scanned under it again, and a signature-database update is a deliberate cache miss (never a stale clean). The `quarantine-on-arrival` rule above still holds for a **pending** upload (an infected upload never becomes visible). But when a re-scan flags an **already-committed, user-visible** version infected, the firm's own legal record is **not hidden or deleted** — for firm-controlled evidence, silent data-loss is worse than a controlled, consented risk. Instead: the version stays listed, a **safe preview** renders its content without exposing the raw payload, and the **raw download is gated** — it returns `409` carrying the signature until the member explicitly acknowledges the risk (`?acknowledgeMalware=true`), and every acknowledged override is audited (`file.downloaded_malware_acknowledged`). This is a deliberate, accepted, mitigated deviation from hard-quarantine DLP, justified by the firm-controlled, evidence-bearing nature of the data; stronger re-authentication on the override, and the notification to a file's users on a fresh finding, are follow-ups.

## Post-quantum & crypto-agility (ADR-0046)

These rules bind now, ahead of the full security write-up. Rationale and rejected options live in the [white paper](../Magna-Carta-White-Paper.md) (_Encryption and key management_ → _Post-quantum posture_) and **ADR-0046** — don't restate them here.

- **AES-256 everywhere.** All AES (AES-KW key-wrap + AES-GCM payloads) is 256-bit — never AES-128. This is the entire at-rest post-quantum story: symmetric crypto is not broken by quantum (Shor hits public-key; Grover only halves symmetric strength). KDF/HKDF and HMAC hashing use **SHA-384** where a choice exists (CNSA 2.0 margin).
- **Algorithm-versioned ciphertext & signatures.** Every ciphertext, wrapped key, and signature carries an explicit algorithm + version identifier in its envelope, so the scheme can rotate (e.g. to a hybrid ML-KEM wrap or an ML-DSA/SLH-DSA signature) without re-encrypting the corpus. Never emit a bare blob whose algorithm is implied only by the code that happens to read it.
- **Prefer symmetric.** Where a primitive can be symmetric, make it symmetric — session signing is HMAC, the blind index is HMAC. Reach for public-key only where the protocol requires it (TLS, WebAuthn, the PAdES seal).
- **Transport PQC is the platform's job — but verify it.** Cloudflare's hybrid X25519MLKEM768 covers inbound and Worker→origin egress; confirm it is on for every hop (including Containers / service bindings), and **log** any third-party plugin endpoint that won't negotiate PQC TLS (no silent caps — golden rule 10 / ADR-0017).
- **Signatures are deferred, not designed-out.** Passkey/WebAuthn and the e-signature PAdES seal migrate to ML-DSA/SLH-DSA when the upstream standards ship (FIPS 204/205/206, COSE algorithm IDs, ETSI PAdES); keep the e-signature port and certificate handling algorithm-pluggable so adoption is an adapter swap.
- **Never hand-roll PQC.** Use Workers Web Crypto and vetted platform/library implementations; a hybrid ML-KEM wrap or an ML-DSA signature arrives via the platform or a maintained library, never bespoke (golden rule 11 — verify current library docs first).

## Distribution & IP-protection posture (ADR-0090)

How the program's internals are protected once it is distributed. Full rationale, threat model, and rejected options live in **ADR-0090** — don't restate them here. The strategy: **treat everything shipped to a client as readable by an adversary; the moat is the server and the legal perimeter, not the bytes.** Most of this is a future seam built at distribution time; the rules below **bind now**.

- **Value lives server-side.** Anything embodying competitive value or correctness secret-sauce runs server-side (Workers / Containers / Durable Objects), never in the distributed client (the SPA bundle, the Rust→WASM core, the Tauri binary + webview — all treated as public). On any new client-shipped logic, ask: _does this value belong on the server?_ This composes with — does not override — the client-first-by-default placement for user-present compute (privileged bytes stay on the device; what ships there is generic engine logic, not proprietary product logic).
- **"Protected" is not "inline Worker."** Keeping something off the client never means relocating heavy _client-feasible_ compute onto a request handler to hide it — that adds CPU-ms billing and breaks golden rule 10. Heavy **and** protected work goes to a Container or Queue (golden rule 10; performance conventions).
- **No production source maps.** The client build ships minified, without source maps. Minification is the only client hardening — obfuscation/anti-tamper is rejected as a primary defense (revisitable per-hotspot at distribution time only on a concrete need).
- **Internal process docs are trade secrets.** The white paper, specs, ADRs, and research are not published. The open/closed line: generic engine primitives may be deliberately open-sourced (the upstreamed PDFium contributions); the proprietary product layer, firm data, and brand are protected.
- **The legal perimeter is owned outside engineering.** The public agreements, data-protection documents, security attestations, and IP/brand registrations are catalogued in [`../research/legal-perimeter.md`](../research/legal-perimeter.md) (the ADR-0090 point-3 perimeter); their generation is a distribution-gated owner/legal track tracked in [`../../ROADMAP.md`](../../ROADMAP.md), not an engineering deliverable.
- **Entitlement enforcement is server-side (deferred seam).** When licensing/entitlements are built, they are checked in a Worker; the client — desktop included — never enforces its own license. No offline crack surface for paid features.
- **Tenant-data exfiltration is already governed** by the firm-scoping, absence-not-existence, Container-sandboxing, and cookieless-preview-origin rules above — ADR-0090 adds nothing there.
