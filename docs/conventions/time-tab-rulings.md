# Matter time tab — the owner's standing rulings

> **Scope, as of round five: this ledger covers all four financial matter tabs — Time, Fees,
> Costs, and Billing.** Round five merged the four surfaces into one review artifact, The Matter
> Ledger (`scratchpad/unified/matter-ledger.html`), and the owner's rulings now land here for
> every one of them. Earlier rounds' rulings were issued on the Time surface; where a ruling
> generalizes (the one table machinery, the status register, the details-panel pattern, the
> dialog family, the footer grammar) it binds the other three tabs exactly as it binds Time.
> The file keeps its name and home so its history stays put.

Every ruling the owner has issued on the time surface, cumulative, newest round last. **A ruling
here is settled.** It is not re-derived, re-proposed, or re-litigated by a later round, and a round
that silently reverts one is a regression, not a redesign. The review surface is The Timesheet
mockup (The Matter Ledger from round five on); rulings bind the app screen when the design ports.

Read this file before changing the surface, and check the built surface against it after. Do not
rebuild the surface from scratch: edit it. Regeneration is what loses these.

Status values: `settled` (built in the mockup and confirmed) · `regressed` (was settled, a later
round undid it) · `open` (asked for, not yet built) · `superseded` (a later ruling replaced it,
with the pointer).

Rulings from the file manager's ledger that generalize beyond that surface
([`file-manager-rulings.md`](file-manager-rulings.md)) bind here too — Lucide-only icons, no inert
controls, say what a control will do, the person's name never "You", never "Just now", filter
controls inside the column header sharing one hover, active filters unmissable, consistent row
heights, dialogs capped at the viewport, selection presenting details in a panel while the reader
stays in the list (N22c).

## API gaps the mockup is honest about

Consolidated across rounds, in rough priority order. The per-matter listing and capture contracts
need:

1. **The two dates:** `createdAt` (the entered date) is stored but not served on the listing (TL8).
2. **Dual attribution:** delegated capture — the create route refuses a foreign
   `timekeeperUserId` today — plus a served enterer attribution; the audit trail already records
   `actorUserId`, so the capture half exists (TD9).
3. **Entry numbers:** no matter-scoped sequence exists on the record (TL7); the platform's
   sequence-numbering machinery (`@magna-carta/sequence-numbering`) is the natural home.
4. **Invoice linkage:** `time_entry.invoice_id` exists on the row but the listing serves neither
   it nor the invoice number a billed entry should name (TV2).
5. **Un-approve:** kick-back is submitted-only in the API; TS4 wants approved → draft as well.
6. **Status history:** no endpoint serves an entry's audit events (entered / submitted / approved
   / kicked back / billed / voided, each with actor and instant) — the details panel's History
   section renders exactly that (TV1), including the recorded kick-back reason (TV5).
7. **Unsubmit** (TS6): no route returns a submitted entry to draft at the timekeeper's own hand —
   kick-back is the reviewer's act, not the asserter's.
8. **Delete-draft** (TR1): the API has void only; the two-verb model needs a delete route scoped
   to never-submitted drafts, refused for anything with a review record.
9. **Optional kick-back reason** (TS8): the kick-back route requires a reason today; it must
   accept its absence and record it only when given.
10. **Enterer permission to work a draft** (TK2): the update route must accept the enterer of a
    delegated draft, not the timekeeper alone — the same dual-attribution gap as capture (gap 2).
11. Bulk submit / bulk approve (TL14, TR2) can compose from the per-entry routes client-side; a
    batch route is an optimization, not a blocker.
12. **Round five, cross-tab:** the invoice ADJUSTMENT model (BM1) has no route and CONFLICTS with
    the accepted finalized-is-immutable decision — a pending ADR must revise the billing model
    (finalized-and-unapplied is adjustable with recorded revisions; any application locks) before
    the routes (`PATCH .../invoices/{id}/lines/{n}` post-finalize + a revisions read) exist.
13. **Round five, costs:** an inline vendor-create for the payee path (CP1) — the capture flow
    needs a directory create, not only a typeahead read; the cost twin of the delete-draft gap
    (TR1) also holds — the cost API has void only; `receiptFileId` still unserved on the listing
    (CR1 renders it honestly).
14. **Round five, fees:** the From Entries modal (FD1) needs the per-line WIP-claim read
    (`invoice_wip_claim` served per line) — the fees spec's consolidation-read gap, now with a
    concrete consumer.
15. Carried from earlier rounds: the historical timekeeper name served forever (TK1's backend
    half — denormalize at capture); the resolved rate on the listing; `utbmsActivityCodeId` on the
    listing; a billable-side category vocabulary and column; the non-billable category on the
    listing; billing disposition beyond the boolean (TD2); an internal memo column (TD10); a
    permission on the rate override (TP4).
