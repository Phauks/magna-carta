**An upstream provider's severity comes from the components we depend on, never from its whole-page rollup.**

**Context:** The public status page polls each upstream provider's Atlassian Statuspage `summary.json` and read one field: `status.indicator`. That field is a rollup over *every* component the provider publishes, and providers differ enormously in what they publish. Cloudflare lists each edge location as its own component alongside its services — 472 components on a representative fetch, of which one group, "Cloudflare Sites and Services", holds everything this platform runs on (Workers, D1, R2, Queues, Durable Objects, Vectorize, Workers KV, Containers) and the other seven are continental buckets of points of presence.

Points of presence are re-routed constantly; it is Cloudflare's steady state, not an event. On the fetch that prompted this decision there were **zero unresolved incidents**, every component under "Cloudflare Sites and Services" was `operational`, 33 edge locations were `partial_outage` and 19 were `under_maintenance` — and `status.indicator` was `minor`. Cloudflare's own page headline read "All systems operational". Our page, reading only the indicator, showed Cloudflare degraded and raised an upstream advisory. The verdict band was never affected (an upstream provider does not set this platform's verdict), but a page whose entire job is to be believed was contradicting the provider it was quoting.

Two candidate explanations were ruled out by measurement rather than argument. The polling URL is not stale: `www.cloudflarestatus.com` and `new.cloudflarestatus.com` both return `200` with byte-equivalent payloads carrying the same Statuspage page id, so the host is not the difference. And the fetch is not failing: a failed or non-`200` fetch already yields `status_unavailable`, which raises no advisory and wears a neutral hue precisely so that an unreachable feed cannot read as an outage.

**Decision:** (1) **A provider definition may declare `serviceComponentGroups`** — the names of the top-level Statuspage component groups whose health this platform actually depends on. Cloudflare declares `["Cloudflare Sites and Services"]`. GitHub declares nothing: it publishes a dozen service components and no location components, so its page indicator is already the service verdict.

(2) **A scoped provider's severity is the worst of the in-scope components and the in-scope incidents.** Components are the group row itself plus its children. An unresolved incident counts when it names a component in scope, or when it names no components at all (a page-wide incident is about the whole provider and always counts). An incident confined to out-of-scope components is the same noise the component scoping exists to exclude.

(3) **A scope that matches nothing falls back to the whole-page indicator.** A group renamed on their side, or mistyped on ours, must not silently turn every future reading operational — the failure mode of a status page is always the false green, so a configuration error degrades to the pessimistic answer.

(4) **An unrecognized component status reads as `degraded`,** the same pessimism the indicator mapping already applies to an unknown value. A vocabulary we do not know is not evidence of health.

(5) **The human status page is carried explicitly on the provider row** (`statusPageUrl`, optional), rather than being derived from the origin of the polled feed. Cloudflare is currently serving its API from the long-standing host while directing readers to a new page at a different hostname, and the two need to be allowed to differ. When the derived origin is right, the field is simply absent.

**Consequences:** Our Cloudflare row now agrees with Cloudflare's own headline, and a real Cloudflare service incident still raises the advisory it always did. The scope is a per-provider judgement recorded in the registry with its reasoning, which means it has to be revisited if a provider reorganizes its page — the fallback in (3) makes that failure loud rather than silent, but it makes it *pessimistic*, so a stale scope shows as an unexplained degraded reading rather than as a false green. The severity computation is a pure function over the parsed payload and is unit-tested against a fixture trimmed from a real response, including the exact shape that produced the bug. Nothing about the rollup changed: an upstream provider still never sets this platform's verdict, and our own probes remain the only thing that can.
