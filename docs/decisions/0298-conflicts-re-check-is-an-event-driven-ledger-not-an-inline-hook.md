**A conflicts check fires when the corpus moves, through the transactional outbox and a durable re-check ledger — never inline on the write path, and never by dropping a cause to keep up.**

**Context:** ADR-0192 shipped API-only triggers with the reasoning that auto-firing on party-add would couple the Directory write path to the engine and need a queue consumer, and that a periodic re-scan had nobody to notify while reviewer UX was deferred. Both were correct then and both have expired: the notifications subsystem shipped with `conflicts` already in its category vocabulary and `conflictsCheck` already in its subject kinds, and the transactional outbox with per-firm queue consumers and a cron fan-out is now the platform's ordinary way to do exactly this. Meanwhile a check that only fires when a human asks is a photograph nobody retakes, and four ordinary events invalidate one: a party added months later, a Directory **merge** joining two separately-clean records, a corporate parent or spouse or principal-of link recorded later, and an identifier entered later that makes a tier-1 blind-index match possible where none could fire before. The merge case is the one the Directory's own duplicate-handling design exists to produce.

**Decision:** (1) **One path, and nothing heavy on it.** Each producing write commits exactly **one outbox row** in the batch it was already composing — no traversal, no matching, no query whose cost scales with corpus size executes in a request handler. The row commits if and only if the business write commits, so a trigger cannot be lost. (2) **A re-check ledger, not a direct queue-to-check hop.** `conflicts_recheck_request` records the matter, the cause topic, the cause reference, when the cause occurred, and — once satisfied — the check that answered it. It exists for three reasons a direct path does not serve: a pending re-check is **visible from the moment the cause commits**, so the platform never sits silently on a known-stale answer; it **coalesces without dropping**, collapsing several causes for one matter into one check that names them all; and it **bounds work honestly**, because a drain that runs out of budget leaves rows pending, and pending is a state a firm can see. Rows are never deleted and only the satisfaction columns are mutable, held by a `BEFORE UPDATE` trigger, so a cause and its timing cannot be rewritten after the fact. (3) **Request resolution and check execution are separate consumers**, so a slow check cannot back-pressure cause resolution. (4) **The trigger catalogue widens additively** — the `trigger` column's CHECK is `length > 0`, so no migration and no rebuild of an append-only table — and two nullable columns record `trigger_source` (`manual` / `event` / `schedule`) and `cause_json`. `actor_user_id` is already nullable, so an automated run leaves it null and the report reads "run automatically because entity X was merged", never attributing the run to a person. (5) **The non-triggers are decisions, not omissions**, and are recorded as such: entity creation with no link and no edge fires nothing (otherwise a two-thousand-row contact import re-checks the firm's whole open caseload for no possible new hit); party removal fires nothing (removing a party cannot create a conflict, and the prior hits stay on the record because what the firm knew at the time is the point); a disposition fires nothing; a closed matter is not re-checked, though its parties stay findable by every other matter's check; and a policy raise fires nothing, instead making the scope shortfall non-empty immediately and offering an explicit firm-wide re-scan. (6) **Storm control never drops.** A large fan-out still writes every ledger row; only the attempt is spread across invocations, with the cron pass as the backstop. No cause is ever discarded for being similar to a recent one. (7) **A periodic re-scan is the backstop for everything above** — a producer never wired, a matter that predates a trigger, a bug. A procedure with no backstop is a procedure that fails silently.

**Considered & rejected:** _calling the engine inline from the Directory write path_ (couples an ethics engine to every contact edit, puts a graph traversal in a request handler, and loses the check entirely if the request times out after the business write committed); _queue-to-check with no ledger_ (works until the queue falls behind, at which point the platform is silently sitting on a stale answer with nothing on the record to say so, and a redelivery either double-writes or needs the idempotency table to carry semantics that belong in a domain row); _deduplicating causes by recency_ (the second merge in an hour is exactly the one that matters); _firing on entity creation_ (an import storm with no possible new hit); _a Durable Object per firm to serialize re-checks_ (adds a hop and buys no correctness — there is no shared mutable state, and the ledger's partial unique index already makes redelivery a no-op).

**Consequences:** The white paper's stated trigger list — intake, party-add, optional periodic re-scan — is finally implemented, and three triggers it does not name (merge, relationship recorded, identifier recorded) are implemented too, because those are the ones that change an answer after it was given. A firm gains an auditable interval between a corpus change and the check that answered it, which is a stronger Rule 1.10(e) artifact than a check row alone can be. The costs are one new per-firm table, two queue consumers, one cron pass, and one outbox row on each of seven write paths. **F3** (re-scan cadence and whether it may be disabled) and **F8** (whether a conflicts notification escalates past the digest) remain owner decisions; both ship as settings. Deepens **ADR-0192**; builds on **ADR-0064** (outbox), **ADR-0050** (cron fan-out), **ADR-0039** (off the hot path), **ADR-0059** (notifications registry), **ADR-0086** (merge).
