**OCR engine — PP-OCR (PaddleOCR PP-OCRv5) _models_ consumed as ONNX through a Rust `ort` pipeline, never the PaddlePaddle framework; one engine + one pinned, versioned model set compiled native for both the server Container and the Tauri desktop, so the web/desktop "split" is a deployment _location_, not a divergent implementation.** **Context:** OCR was named as a pipeline stage in four places — _Discovery_ (`ingest → R2 → queue-driven extraction/OCR in Containers → index`), _PDF services_ (scanned-PDF→searchable-PDF, web server-side as a fallback to desktop-local), the _Delivery model_ parity table (Container OCR on web vs. on-device OCR on desktop), and the _Performance & concurrency model_ (heavy CPU work → native Rust in Containers + Queues + DO-per-job) — but **no engine was ever chosen** and no ADR owned it; the parity table read as if web and desktop might run _different_ OCR, which would fork results and double maintenance. **Hard constraints** narrowed the field decisively: **self-hosted / no third-party egress** (confidentiality — privileged bytes never reach a cloud OCR API, same logic as in-house conversion ADR-0030 and observability ADR-0038); **CPU-only** (Cloudflare Containers and user laptops have no GPU); **deterministic** (OCR text feeds both the Tantivy/Vectorize index _and_ discovery evidentiary hashing/chain-of-custody — same input must yield same output regardless of where it ran); **permissive license** (commercial multi-tenant SaaS — the AGPL/OpenRAIL wall of ADR-0030/ADR-0012); and **Rust-native** so the _scoped shared core_ parity story (ADR-0024) holds. **Decision:** (1) **Engine = PP-OCRv5 models via ONNX/`ort`.** Best accuracy of the permissive CPU-class engines (PP-OCRv5 ≈ top of non-VLM benchmarks; ~94.5% OmniDocBench v1.5 for the model family), 100+ languages incl. strong CJK, word-level bounding boxes for redaction — consumed as Apache-2.0 ONNX weights on neutral ONNX Runtime, which **sheds the PaddlePaddle runtime entirely** (the heavy, awkward, provenance-questionable part) and runs from one Rust crate native in **both** the web-path Container and the Tauri desktop. (2) **One engine, two locations, versioned model artifact.** The same crate + the **same pinned model version + config** run server-side and on-device; each produced text layer records the **model version** that produced it, and a model upgrade triggers re-OCR rather than silently diverging — this is what makes the desktop-local path (privacy: bytes never leave the device; speed: no upload of large scan sets; cost: offload off the Container bill; offline) a pure _location_ optimization with reproducible output, not a second implementation. Interrupted jobs retry under the at-least-once idempotent Queue/checkpoint model (ADR-0057/ADR-0039). (3) **Crate pick is a build-time spike:** `oar-ocr` leads (document-focused — bundles orientation detection + rectification that scanned exhibits need), with `retto` (proves desktop + WASM on `ort`) and `rust-paddle-ocr` (MNN backend, 100+ langs) as alternatives; the spike runs them head-to-head against **docTR/OnnxTR** on representative legal scans on the **one axis docTR could win — structured layout output** — the open question being whether docTR's block/line/word JSON beats `oar-ocr` enough to justify forfeiting the Rust-native desktop path and accepting a Python/C++ sidecar (same posture as the ADR-0022 library spike). (4) **Fallback = Tesseract 5** (Apache-2.0, ~10 MB, fastest, deterministic) as the conservative floor for clean typed scans; we rejected the _Stirling-PDF bundle_ (ADR-0030), not Tesseract itself. (5) **Escape hatch = `ocrs`** (RTen; MIT/Apache, **pure Rust, zero native deps, clean WASM**) — the only path to _browser-side_ OCR or a C++-free build, carried for that future but early-preview/Latin-only today. **Considered & rejected:** **the PaddlePaddle framework** (heavy second runtime, provenance — consume the models via ONNX instead); **Surya** (excellent + layout-aware, but model weights are **OpenRAIL-M with a commercial-revenue threshold** — a poison pill for commercial SaaS, the same wall as AGPL); **EasyOCR** (Apache-2.0 but 2026 benchmarks say skip for accuracy-critical work; heavy); **docTR as primary** (Apache-2.0 and best structured output, but Python/PyTorch with only partial ONNX export, weak multilingual, and **no Rust crate → breaks one-engine-two-targets parity**; kept only as the spike challenger for layout-heavy work); **VLM OCR** (olmOCR / dots.ocr / GLM-OCR / PaddleOCR-VL — the 2026 accuracy frontier, but **GPU-required** and **non-deterministic / prone to hallucinating plausible-but-absent text**, disqualified twice over: the CPU-Container/laptop constraint _and_ evidentiary determinism — classic det+rec OCR fails _visibly_, which is a feature for chain-of-custody; recorded as a possible **future web-only high-accuracy tier via Workers AI**, never on the evidentiary path); **any cloud OCR API** (egress — forbidden by confidentiality). **Consequences:** the OCR stage gains a concrete, permissive, CPU-friendly, deterministic engine and the parity table's "split" is reframed as one engine in two locations with a versioned model artifact — accurate search + reproducible hashes regardless of where a doc was processed; cost is carrying the ONNX-model artifacts, the model-version stamping/re-OCR discipline, and running the crate-vs-docTR spike before the Phase-4 build. OCR folds into the _scoped shared core_ "discovery extraction" already named in **ADR-0024**. Reuses **ADR-0012** (Discovery pipeline), **ADR-0024** (Rust scope / shared core), **ADR-0023** (web/desktop parity), **ADR-0030** (conversion orchestrator dispatches scanned-PDF→searchable-PDF to _this_ engine), **ADR-0039** (Containers + Queues + DO-per-job compute placement), **ADR-0057** (idempotent retry / checkpoints for interrupted jobs); bounded by **ADR-0003** (per-firm isolation) and the confidentiality discipline of **ADR-0038**. The specific crate and the docTR comparison resolve in the **Phase-4 Discovery** subsystem spec.
