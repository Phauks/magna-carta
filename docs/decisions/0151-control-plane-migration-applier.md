**Control-plane migrations apply via the scheduled handler, not a cold-start gate.** The per-firm D1 lineage is migrated at runtime via `perFirmMigrations()`, bundled into the worker and applied at provision time before a firm is ever served (`apps/worker/src/per-firm-migrations.ts`, `firm-provisioner-wiring.ts`). This decision adopts the same bundle-and-apply discipline for the control-plane lineage: `controlPlaneMigrations()` (`apps/worker/src/control-plane-migrations.ts`) mirrors `perFirmMigrations()`, and the scheduled handler (`apps/worker/src/scheduled.ts`) runs `runPendingMigrations(d1MigrationTarget(env.DB_CONTROL), controlPlaneMigrations())` as its first action on every cron tick.

**The sole runtime applier is the Cron handler — single-flight by construction.** Cloudflare fires a cron trigger as one invocation per tick. The runner at `packages/database/src/migration-runner.ts` is not safe to run concurrently for the same pending migration: each migration is one atomic `batch()` (in `packages/database/src/d1-migration-target.ts`) that concludes with `INSERT INTO _migrations(tag, …)`; `_migrations.tag` is `PRIMARY KEY`. If N isolates raced the same pending migration, exactly one batch would commit and the rest would throw (`UNIQUE constraint failed: _migrations.tag`), which the fail-loud runner propagates without catching. Using the cron — one invocation per tick — avoids this entirely.

**Cold-start migrate-before-serve rejected.** A gate that migrates before serving a request would require N isolates that cold-start after a deploy to coordinate, or to retry-and-recheck after a PK conflict. That needs a Durable Object coordinator or an optimistic-recheck wrapper — machinery whose cost outweighs its benefit when the cron + fail-safe discipline already close the window harmlessly.

**Additive migrations + fail-safe reads close the deploy window.** The cron applies a fresh migration within one `*/5` cycle (at most ~5 minutes). Request code that reads a new additive control-plane column must degrade to a safe default on absence rather than propagating an error. The `/me` session-bootstrap endpoint is the example: a failure to read `firm.release_channel` (column absent, or any read error) yields `channel: "stable"` and the default flag set, logged — the bootstrap never 500s fleet-wide. This is the same fail-safe-to-stable approach the feature already uses for an absent `FLAGS` binding, and it is a legitimate robustness property for a bootstrap endpoint independent of migrations.

**Deploy-time application — future zero-window hardening.** Running the migration runner in the Workers Builds command before `wrangler deploy` would be single-flight by construction (the build runs once, migrates, then deploys) and would eliminate the deploy window entirely — true migrate-before-serve, matching how per-firm migrations apply at provision time. This requires a D1-over-HTTP `MigrationTarget` adapter and an API token as a build secret. Documented as the future hardening to adopt when production firms make a zero-width schema window matter; not built now. The standard for this is in [`docs/conventions/operations.md`](../conventions/operations.md) § "Control-plane database migrations".
