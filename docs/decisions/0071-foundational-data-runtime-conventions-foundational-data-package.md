**Foundational-data package layout — the five slice 0·2 conventions are realized as four workspace packages split on the structure-vs-access seam: `@magna-carta/money` (all monetary math), `@magna-carta/identifiers` (identifier generation + prefix registry + branded id types), `@magna-carta/database` (how the database is defined and evolved — Drizzle schemas + fleet migration runner), and `@magna-carta/data-access` (how the database is safely reached — idempotency middleware + transactional outbox + relay; firm-scoping, `protected()`, and audit added as later layers); dependency graph is strictly acyclic: `data-access → database → identifiers`, `data-access → money`.** **Context:** the five §9 conventions (ADR-0061–0065) interlock across three concerns — pure arithmetic, schema definition, and safe runtime access — and were designed together but must be built and tested independently; the build order (money → identifiers → database → data-access) follows the dependency graph. The split needed a clear seam so each package could be a plain-Vitest, Cloudflare-runtime-free leaf where possible, with hard dependency edges enforced at module resolution (ADR-0070). **Decision:** (1) **`money` and `identifiers` are pure leaves** — no Cloudflare runtime, no repo inter-dependencies (only their external libraries: Dinero.js and nanoid respectively) — so they split cleanly, admit plain Vitest tests, and their boundaries are hard at module resolution. (2) **`database` vs. `data-access` splits on a genuine acyclic seam:** `database` owns _structure_ (Drizzle schema definitions, migration files, the fleet rollout orchestrator); `data-access` owns _access_ (all runtime queries go through it, carrying firm-scoping, `protected()`, audit, idempotency, and the outbox chokepoint). (3) **Idempotency and the transactional outbox are _not_ split into their own packages:** the idempotency row and the outbox row both commit in the same D1 transaction as the effect they guard (ADR-0063/ADR-0064), so separating them would require each to import the other's transaction handle — a genuine circular dependency. They live together inside `data-access`, separated by strict internal module boundaries and the fitness functions of ADR-0063/ADR-0064 rather than package edges. **Considered & rejected:** **one package for all five conventions** (no hard boundaries — the whole point of the split is enforcing the seam at module resolution per ADR-0070); **idempotency and outbox as separate packages** (forces a circular dependency through the shared D1 transaction — not a design smell, a real cycle); **`database` absorbing `data-access`** (mixes schema definition with runtime access, destroying the clean `database → data-access` edge and making it impossible to import schemas without pulling in the DAL). **Consequences:** four packages with hard, acyclic dependency edges; each can be independently versioned, tested, and evolved; `money` and `identifiers` are Cloudflare-runtime-free and admit plain Vitest (fast CI); `data-access` is the single runtime boundary that enforces all the cross-cutting invariants (firm-scoping, idempotency, outbox). Implementation structure detail in the _Foundational data conventions_ spec ([`docs/specs/2026-06-04-foundational-data-conventions-design.md`](specs/2026-06-04-foundational-data-conventions-design.md) §7). Builds on **ADR-0061–0065** (the conventions these packages implement), **ADR-0070** (no-barrel / exports-map package boundaries), **ADR-0051** (fitness functions at boundaries), **ADR-0003** (firm-scoped DAL).
