**A merge to `main` is a deploy, and there is no second gesture.**

**Context.** ADR-0171 moved the Workers Builds production branch from `main` to a dedicated `release` branch on every connected Worker, so that pushing to the trunk published code to GitHub without touching the live environment and a deploy was the explicit fast-forward `git push origin main:release`. That decoupling was correct for what it addressed — every trunk push, including a docs commit, had been deploying seven Workers — and it held for seven weeks.

What it cost only became visible once the owner began reviewing real screens rather than mockups. A screen correction is worth reviewing on the deployed site, the deployed site was `release`, and `release` moved only when somebody deliberately pushed it. Every round of UI review therefore carried a deploy gesture the owner had to remember and perform, which is the loop the standing direction on building UI in the repository (root `CLAUDE.md`, _How we work_) is meant to make fast.

**Decision.** On 2026-08-29 the owner set the Workers Builds production branch to **`main`** on **`magna-carta`** (the API Worker) and **`magna-carta-web`** (the single-page application). A merge to `main` builds and deploys both within minutes. `git push origin main:release` is retired; `release` survives as history and is not a deploy target. _Builds for non-production branches_ stays off, so a feature branch still builds nothing.

**Consequences.** A migration, an API-contract change, a binding change or a `wrangler.jsonc` edit reaches real users on the strength of whatever verification ran before it landed. There is no undeployed queue between the trunk and production, so the merge is the last point at which anything can be caught — and the GitHub Actions gate of record has started no billable job since 2026-08-05, which makes the pull-request tier the only standing net and leaves it not running. That billing step was housekeeping under ADR-0171; it is now the most consequential open owner action, recorded first in [`docs/deploy-queue.md`](../deploy-queue.md).

Three second-order effects follow, each recorded in its own home rather than here. Deploy ordering becomes a **merge-time** hazard: Cloudflare rejects a deploy whose service binding names a Worker that does not exist, so a pull request adding a `*_SERVICE` binding for a Worker nobody has stood up now fails the app Worker's build in production the moment it lands. Several soundness arguments in [`build-performance.md`](../conventions/build-performance.md) rested on a deliberate deploy push arriving after the nightly sweep and the post-merge lint tier, and no longer hold in that form. And a Watch Paths gap that used to be swept up by the large-push exemption — Workers Builds always builds a push of twenty or more commits — is now silent, because `main` receives one-merge pushes.

**Unverified, and named so it is not assumed.** The move covered the two Workers above. The other ten connected projects (scan, bundle, convert, recovery, file-repair, discovery, ocr, sign, status, edit) were on `release` at the last API-verified read, 2026-08-24, and whether any has since moved is unknown. A read of `GET /accounts/{account_id}/builds/workers/{script_tag}` per project settles it and nothing else does. Until then the fleet may be mixed, and a merge to `main` can ship an app Worker expecting a sibling change the sibling has not deployed.

**Supersedes ADR-0171.** What that decision established and this one keeps: `release` was never committed to directly, non-production branch builds stay off, and the per-Worker branch setting is read and written through the same build-configuration endpoint rather than trusted from a runbook. What it reverses is the branch, and with it the premise that the trunk can be read without saying anything about the running system.
