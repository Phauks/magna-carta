**lopdf is upgraded to 0.42.0 to clear the stack-overflow DoS advisory; the other three tracked advisories stay accepted because a clean fix is not yet available.** **Context:** when osv-scanner began auditing the Rust supply chain it surfaced four HIGH advisories, accepted-with-tracking (`ignoreUntil = 2026-10-14`) so the gate could protect against new advisories immediately while these were worked. This is the first remediation pass over that set. **Decision:** **lopdf** — the RUSTSEC-2026-0187 stack-overflow DoS is on the highest-risk surface (parsing untrusted PDFs), and lopdf 0.42.0 is the fixed release. Bumped the declared requirement to `0.42` in every first-party manifest (the `crates/` workspace dependency, `pdf-eval`, `recovery-core`, and the `scan` container) and updated all five affected lockfiles (`crates/` plus the `scan`/`ocr`/`recovery`/`file-repair` containers, the last three inheriting lopdf through their path-dependencies on the first-party crates). Held to 0.42.0 (the fix) rather than the newer 0.44.0 to keep the change minimal. Verified: the `crates/` workspace builds, and pdf-core / recovery-core / decryption-core and the scan container compile and test green against 0.42. The scan container's `heuristics::pdf` SIGABRT guards (the max-nesting pre-check and the object-stream routing away from `Document::load_mem`) are retained as defense-in-depth — clamd and yara still scan the raw bytes regardless — so abort-safety does not rest on the library fix alone. The lopdf entry is removed from `osv-scanner.toml`; the gate now enforces `>= 0.42.0` by failing if 0.41 ever reappears. **The three remaining advisories are kept accepted, with the reason on each rewritten to record why a bump is not clean:** **quick-xml** (RUSTSEC-2026-0194/0195) is reachable only transitively through `office-crypto` 0.2.0 — its *latest* published release (Nov 2025) — which pins quick-xml 0.38; there is no office-crypto release built on quick-xml >= 0.41, so reaching the fix would require patching a third-party crate's internals against a breaking quick-xml API on the document-decryption path, which is riskier than the tracked acceptance. **npm uuid** (GHSA-w5hq-g745-h8pq) is a transitive dev-tooling dependency of `postman-collection` 4.5.0 (API-contract test tooling), not on any production-runtime path; the advisory is a buffer-bounds issue in the `v3`/`v5`/`v6` builders when given caller-supplied output buffers, which that tool does not exercise with untrusted input, and a forced 8->11 major bump risks breaking it. Both keep the `ignoreUntil = 2026-10-14` forcing function so they re-surface for review against a newer upstream. **Considered & rejected:** forcing quick-xml to 0.41 with a `[patch]` (compiles office-crypto against an API it was not written for — a correctness risk on privileged bytes); a pnpm `overrides` bump of uuid to 11 (major-version break of a tool that works today, for a dev-only advisory); jumping lopdf to 0.44 (unnecessary surface for a security fix). **Consequences:** the scariest of the four advisories — the untrusted-PDF DoS — is gone from the actual dependency tree, not just tracked; the audit list shrinks from four entries to three, each now carrying an accurate upstream-blocker rationale so the next remediation pass does not re-investigate. Follow-ups: re-check quick-xml when office-crypto ships a release on 0.41+, and uuid when postman-collection moves off uuid 8. Realizes the _Vulnerability / dependency management_ control in [`docs/conventions/compliance.md`](../conventions/compliance.md); relates to golden rule 14 (memory-safe posture — this hardens the Rust dependencies that posture rests on).
