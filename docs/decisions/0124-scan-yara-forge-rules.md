**YARA rules come from YARA Forge — externally maintained, self-updating, FP-filtered — not hand-curated.** Extends **ADR-0081** (the inbound-upload scan path). 

**Context:** the scan engine shipped with an empty YARA corpus (`yara::build_rules(&[])`) — clamd + the structural heuristics carried detection while the rule source was decided. The owner's requirement is that detection **self-maintains**: we never hand-write or hand-curate rules; a maintained external provider supplies them and refreshes automatically. [YARA Forge](https://yarahq.github.io/) is that provider — it aggregates and normalizes the public YARA ecosystem, deduplicates, tags, quality/performance-analyses (`yaraQA`), applies FP tuning, and publishes versioned releases. A measured yara-x compatibility spike against the packages found the whole corpus compiles under yara-x 1.18 (only the imports `dotnet`/`hash`/`pe`/`math`/`string`/`console`/`elf`, all supported — all ~10.5k `extended` rules compile, 0 incompatible once the rule splitter brace-matches correctly).

**Decision:** (1) **Source YARA Forge at image build**, alongside the existing `freshclam` step; the nightly Deploy-Hook rebuild re-resolves the latest release, so rules self-update with zero runtime egress (the container stays `enableInternet = false`). (2) **Default tier `extended`** (`YARA_FORGE_TIER` ARG): it adds ~4,686 high-confidence malware rules over `core` (older/narrower threats, not lower quality), and its only real false-positive liability is a small pocket of heuristic `*_SUSP_*` structural rules (base64 PowerShell, odd-ZIP, OneNote tricks) that match legitimate-but-unusual documents. (3) **Drop that FP pocket at build time** (`build-yara-rules`): heuristic `_SUSP_` rules scoring below `YARA_MIN_SUSP_SCORE` (default 75) are removed, private rules always kept. Because the platform owns the compile step, this is a finer cut than any prebaked tier. (4) **Build-time compile + serialize, runtime deserialize:** rule problems fail the *build* loud (an empty/inconsistent package or a systemic compile collapse stops the image; a stray incompatible rule from a future release is skipped + logged), and the service deserializes the blob at boot with no startup recompile. A corrupt/unreadable baked blob is fatal at boot, never a silent fall-back to a rule-less scan. (5) **The `yara-rules` engine-version component is the Forge release tag** (was a rule count): it changes exactly when Forge publishes, so the access-triggered re-scan staleness gate re-scans the fleet on a real rules change and leaves it untouched on an unchanged nightly rebuild. (6) **A YARA hit is `infected`** — identical handling to a clamd signature hit, one quarantine workflow (no separate suspicious-for-YARA path); under this model the false-positive cost is what justifies the `core`/filter decisions above.

**Consequences:** the YARA layer is now live and self-maintaining with no hand-curation and no runtime egress. The `extended`-minus-FP-pocket corpus (~10.5k rules, 15 MB serialized) bakes in ~17 s. The verdict model is deliberately blunt (YARA = clamd = infected): it trades a richer suspicious tier for one quarantine path, so corpus precision (the tier + score floor) is the FP lever, tunable by ARG without code. New code: `containers/scan/src/forge.rs` (FP-pocket filter, unit-tested), `src/bin/build-yara-rules.rs` (build-time bundler, fail-loud like `build-atoms`), runtime load + tag-versioning in `yara.rs`/`main.rs`/`lib.rs`, the Dockerfile fetch step.
