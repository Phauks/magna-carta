**An edge cache in front of the status page.** Workers Cache is a cache tier ahead of a Worker entrypoint: on a hit the stored response is served and `fetch` never runs. `apps/status-worker` is the one place in this codebase where that is unambiguously correct, and the reason is the same property that makes the caching rule in [`docs/conventions/security.md`](../conventions/security.md) forbid it in `apps/worker`.

**(1) The cache key fully determines the body — here and only here.** An edge cache keys on entrypoint + path + query + Worker version, and on neither the request host nor the `Cookie` header. This worker has no session, no cookie, no `Authorization` header, and no per-firm content: `GET /` is the same bytes for every reader on Earth. `apps/worker` resolves the firm from a session cookie, so the identical config there would serve one firm's `/api/v1` reply to the next firm requesting the same path — which is why that worker carries a fitness guard rejecting the `cache` key outright. This decision does not weaken that rule; it is that rule applied to the one worker that satisfies its precondition.

**(2) The payoff is the incident.** A status page takes its traffic spike exactly when its dependencies are least healthy. On a hit the edge answers without invoking the worker and without reading `STATUS_KV`, so the page's availability stops depending on the availability of the one binding it holds. This *strengthens* the fate-isolation the worker exists for, and it adds no binding. `stale-while-revalidate=600` on the two 30-second responses extends that: when the KV read starts failing, the edge keeps handing out the last good page while a revalidation retries behind it, rather than every reader immediately falling through to the static stand-in.

**(3) Silence is not opt-out.** With caching enabled, a response carrying no `Cache-Control` is cached anyway, under RFC 9111 heuristic freshness — a `200` for two hours, a `404` for three minutes, a `405` for one. This worker's failure path returns `FALLBACK_HTML` as a **`200`**. Enabling the cache without touching the response code — which is how this change first looked — would have pinned "The status system is temporarily unavailable" at the edge for two hours after a single transient KV blip, on the one page whose entire purpose is to be truthful during an incident. So the rule is now structural here as it is in the app worker: every response either opts in with an explicit `max-age` or opts out with `no-store`, and the tests assert it for every route.

**(4) Purge crosses a worker boundary, so we do not purge.** `ctx.cache.purge()` is scoped to the entrypoint that issues it. Every writer of this data — the cron and the operator endpoints — lives in `apps/worker`, a different Worker, so no purge it could issue would touch anything this worker cached. An operator publishing an incident therefore waits out the 30-second window. That is accepted: thirty seconds is well inside the human latency of declaring an incident, and the alternative is giving a deliberately read-only, body-less worker a write-ish authenticated route, which its local conventions exist to prevent. The two snapshot responses carry `Cache-Tag: status-snapshot,…` so that a purge route on *this* worker remains a cheap option if that latency ever matters.

**(5) `cross_version_cache` stays off.** The Worker version remains part of the cache key, so each deploy starts from a cold cache and no page rendered by superseded code can be served. The cost is a hit-rate reset per deploy, which is nothing next to the guarantee that what the page says is what the live code and data say.

**Considered & rejected.** **A purge endpoint on the status worker** (option 2 of the handoff) — buys thirty seconds at the price of a write-ish route, an auth story, and a request body on a worker whose stated convention is to have none of the three; the tags make it reversible if that trade ever changes. **Leaving the fallback/404/405 without directives** — not a choice at all once heuristic freshness is understood, which is precisely why it is written down here. **`cross_version_cache: true`** — a warm cache across deploys, at the price of a status page that can serve a superseded version's answer.

**Consequences.** The status page now survives its own KV namespace being degraded, for the length of the stale window. Enabling the cache also makes static-asset requests and worker-to-worker invocations billable as standard requests; this worker has no `ASSETS` binding (it serves its two assets from its own code) and no service bindings, so the cost consequence that keeps the switch off in `apps/worker` does not arise. Requires Wrangler ≥ 4.69.0 (the repo pins 4.105.0). Not verified against a running deployment: purge scoping and the exact interaction between a `no-store` revalidation response and an existing stale entry come from Cloudflare's documentation, not from an observed deploy.
