**Adopt Cloudflare Workflows, scoped to compensate-on-partial-failure flows; pilot on firm provisioning.** ADR-0064 (transactional outbox) already chose "sagas via Workflows with compensating actions (Cloudflare's recommended path), built on the outbox + idempotency primitives" as the path for multi-step external flows, and deliberately deferred it — *"not expanded until a flow needs it."* Two things converge to graduate that deferred decision into a scoped adoption: **(a)** Cloudflare shipped first-class **saga step-rollbacks** for Workflows (2026-06-25) — a `rollback` handler registered per `step.do`, executed in reverse step-start order on terminal failure, durably replayed across engine crashes, with its own retry/timeout config; and **(b)** Phase 3 (Financial Core — payments, trust, costs) and firm provisioning are the first flows that genuinely need **cross-system** compensation, where one D1 transaction cannot cover steps that touch external systems. Before this primitive, even those flows would have meant hand-rolling compensation in catch blocks (the error-prone status quo); the primitive makes *correct* multi-step money movement cheap enough to commit to — which matters most in exactly the domain (trust/billing) where correctness is non-negotiable.

**(1) Scope — orchestration of the few flows that must unwind on partial failure.** Cloudflare Workflows is the orchestrator for multi-step external flows where step *N* failing means earlier steps must be **undone**, not merely retried: **payment capture** (ADR-0032: authorize at processor → post to the trust/operating ledger → emit receipt/notification; rollback = void/refund on the processor), **trust disbursements** (debit the trust subledger → record the disbursement → pay out → notify; rollback restores trust integrity — a half-applied transfer is a compliance event, not a bug), and **firm provisioning** (ADR-0073: create the per-firm database → seed schema → create the R2 prefix → register the control-plane row → welcome; rollback deletes the half-created resources). Each external step's side effect lives inside `step.do` with a registered `rollback`; rollbacks must be idempotent.

**(2) Composition, not replacement — Workflows sits ON the outbox + idempotency floor.** The chokepoint (ADR-0051) still binds: a handler that wrote D1 may not call external directly — it writes an `outbox` row in the same batch, the relay publishes to Queues, and the consumer **starts a Workflow instance** for the multi-step flow. The outbox stays the atomic D1-handoff; the idempotency keys of ADR-0063 are **reused** as the external idempotency keys that both forward steps and their rollbacks dedupe on. Critically, a Workflow's durable step history is **not a ledger** — D1 + ledger + audit remain the system of record (ADR-0064's scope rule binds unchanged; Workflows is delivery/orchestration, not the source of truth).

**(3) Pilot on firm provisioning first.** Firm provisioning is the **planned first build**: high value (a failed provision today can leak half-created resources) and lower blast radius than client money. It proves the new runtime surface — a `[[workflows]]` binding plus a `WorkflowEntrypoint` class exported from the worker (the same "introduce once, narrowly, with its own tests" move the first Durable Object, `BundleBuildCoordinator`, established) — and the crash-replay compensation semantics in production, **before** trust-account disbursements depend on it.

**(4) Explicitly NOT migrated — the forward-only pipelines stay as they are.** Ingest, scan, bundle-build, and inference stay on Queues + Durable-Object coordinators. They are **retry-forward** (a failed scan does not need un-scanning), so the rollback primitive buys nothing; migrating them would be lateral machinery against the measure-first discipline. Workflows is added where compensation is needed, nowhere else.

**(5) Failures fold into the one error pipeline.** Workflow instance failures and exhausted rollbacks report through the standardized, redacted error pipeline (golden rule 4; ADR-0017/0038), correlated by ID with a user-facing Error ID — never a separate, un-redacted Workflows dashboard as the error surface.

**(6) Terminology correction (ADR-0064).** The built outbox relay is a plain Cron `scheduled` handler (`apps/worker/src/scheduled.ts`) invoking the `sweepOutbox` library, wired through `triggers.crons` — **not** a Cloudflare Workflow; no `WorkflowEntrypoint` or `[[workflows]]` binding backs it. ADR-0064's "Cron-Workflow relay" / "Cron-triggered Workflow" labeling is corrected by an amendment to that ADR. This adoption is the **first real use of Cloudflare Workflows (the product) in the codebase.**

**Considered & rejected.** **Migrating the existing forward-only pipelines onto Workflows** — machinery without payoff; they are retry-forward and already coordinated by Queues + DOs. **Hand-rolled compensation in catch blocks** — the pre-2026-06-25 status quo; error-prone and without durable replay, superseded by the first-class primitive. **Trusting trust-account disbursements to a day-old feature first** — blast radius; provisioning pilots it, and the outbox + idempotency floor is the documented fallback if the feature proves immature (it shipped sequential-rollback-only — no `waitForEvent` rollback, no parallel rollback, no Python yet). **Workflows as a system of record / event-sourcing** — out of scope, the same rejection ADR-0064 records; Workflows orchestrates, the ledger is truth.

**Consequences.** Multi-step money movement and resource provisioning gain durable, reverse-ordered, idempotent compensation without distributed transactions, on the existing outbox/idempotency primitives. A new runtime surface (the `[[workflows]]` binding + a per-flow `WorkflowEntrypoint`) and a determinism discipline (side effects only inside `step.do`; step definitions replay on recovery to rebuild rollback stubs) enter the codebase — both mirroring the Durable-Object precedent contributors already live with. Cloudflare lock-in deepens, but the stack is already all-in on Workers/D1/R2/Queues/DO and parity (ADR-0023) governs web/desktop, not cloud portability — so no new portability concern. The adoption is pilot-gated: firm provisioning ships first; payments and trust adopt once the pilot validates crash-replay compensation in production. Reuses **ADR-0064** (outbox — amended here for the relay-wording correction), **ADR-0063** (idempotency/dedup, reused for rollback idempotency), **ADR-0051** (chokepoint), **ADR-0050** (cross-firm cron fan-out), **ADR-0039** (Queues/DO placement — where the forward-only pipelines stay); serves **ADR-0032** (payment capture — the canonical saga) and **ADR-0073** (firm provisioning — the pilot); folds failures into **ADR-0017/0038** (error pipeline).
