**PDF settles on one PDFium-WASM engine across every runtime (via EmbedPDF, MIT), an AGPL/SSPL prohibition is made a hard repo-wide rule, and content-level redaction is un-deferred onto that engine's off-the-shelf true-redaction plugin targeting Adobe parity — refining ADR-0045's provisional design.** **Context:** ADR-0045 (Proposed) sketched an in-house PDF service hand-composed from permissive engines and **deferred true content-level redaction** to Phase-4 citing AGPL engines. A first pass this cycle proposed a five-library spread (PDFium + pdf.js + pdf-lib + qpdf); further research (owner-pushed — "fragmented vs. Collabora; there should be a real one out there") found the integrated SDK that pass missed and a **spike empirically confirmed server-side execution**. Analysis + spike evidence on file at [`docs/research/pdf-tooling.md`](research/pdf-tooling.md). **Decision:** (1) **One engine across all runtimes — EmbedPDF over PDFium-WASM.** The ecosystem has only two comprehensive engines — **MuPDF (AGPL, excluded)** and **PDFium (BSD-3)**; every permissive option is a binding over PDFium. **EmbedPDF** (MIT; PDFium bundled Apache-2.0) is the integrated, plugin-composable SDK over it: `@embedpdf/pdfium` (low-level WASM) → `@embedpdf/engines` (`PdfEngine`, 100% TS) → framework packages incl. **first-class Svelte** + `@embedpdf/snippet` UI. It **runs in browser, Node, and serverless** — so the _same_ PDFium WASM engine serves the interactive Svelte viewer, server/Container batch work, and (size-permitting) light Worker ops, realizing the ADR-0024/ADR-0039 one-engine-WASM+native model off the shelf rather than approximated. **Spike (2026-06-13, on file):** `@embedpdf/pdfium` v2.14.4 runs headless in pure Node (init ~41 ms, load+parse ~4.3 ms, correct page count/dims); `pdfium.wasm` is 4.6 MB raw / **~2.05 MB gzip** — under the Workers paid 10 MB bundle limit (ADR-0074), so Worker _size_ is fine and CPU placement (edge vs. Container) is a load-harness measurement (ADR-0083), not a guess. Capabilities are **plugins** (install only what is used): Viewer, Annotation, **Redaction**, Forms, Stamp, Search, Selection, **Metadata** (read+edit), **Export/Save**, Signature, Thumbnail, Print, Bookmark, Attachment, Layout-Analysis, plus an AI package. **pdf.js and pdf-lib are dropped** (EmbedPDF covers viewer + create/modify/save); the standalone `pdfium-render` binding is likely unnecessary (the engine runs PDFium-WASM in Node). (2) **AGPL/SSPL is a hard prohibition** — including **transitive** deps and **isolated-service** use — because the platform is proprietary SaaS and AGPL §13 treats network use as distribution; categorical, to avoid relying on the contested process-isolation boundary (consistent with Documenso/DocuSeal in ADR-0045, self-hosted-Sentry in ADR-0038, Jasmin-as-fallback-only in ADR-0047). A **license-scanning CI gate** (permissive allowlist; AGPL/SSPL denied; reads the _as-used_ license of dual-licensed packages) joins the ADR-0048 OSV/audit pipeline. (3) **OCR is Tesseract-direct, not OCRmyPDF** — OCRmyPDF requires **Ghostscript (AGPL)**, transitive copyleft one import deep; OCR = Tesseract (Apache-2.0) + EmbedPDF/PDFium or qpdf for rasterize/reassemble, refining ADR-0030. (4) **Redaction un-deferred, Adobe parity largely off the shelf.** EmbedPDF's **Redaction plugin is true content removal** (destructive, alters the content stream, original unrecoverable, optional fill of any color) — the vector-level capability the first pass planned to _build_ on PDFium, now an MIT plugin, removing the maintenance burden the owner was wary of and giving Adobe-class text-native output. Two thin shells stay ours for legal defensibility: a **sanitize pass** (confirm Metadata+Redaction strip every hidden vector; keep **qpdf** as belt-and-suspenders if not) and a **verification gate** that re-extracts and **refuses to emit** if any content survives under a mark (most real-world leaks are operators who only boxed text — a pipeline that cannot emit an unverified redaction is a defensibility edge competitors lack). The raster-rebuild flatten is retained as a documented _fallback_ only. (5) **Placement = client-first by default.** The one WASM engine runs in browser, Worker, Container, and Tauri; interactive single-document user-present work (view/annotate/redact/fill/stamp/extract/metadata/export) runs **on the user's device** (browser WASM / Tauri native), privileged bytes never leaving it — ADR-0045's client-side-by-default sharpened into the default, matching the ADR-0023/0024 parity model; the result still uploads to R2 (ADR-0081, compute client-side / artifact server-stored). **Only four cases are irreducibly server-side:** no-user-present generation; bulk/batch over a corpus; native engines (OCR/LibreOffice); and trust/authority (the PAdES seal, and the authoritative redaction+verification for an evidence/discovery production). That server tier is **mostly Container with the Worker as orchestrator** — the light-Worker-PDF-compute tier largely collapses into the client. **Device variance for interactive work is the user's concern** (owner, 2026-06-13 — no required server fallback for large interactive docs; batch remains server-side regardless). **Shared review/markup and its coordinating Durable Object are DEFERRED** (owner, 2026-06-13) — v1 markup is single-user, client-side, persisted as firm-scoped annotation data on save (no real-time coordination, no markup DO in the near-term design); collaborative _document_ editing stays Collabora on the source `.docx` (ADR-0010), not the PDF. (6) **Upstream-first engine-extension policy (scoped to metadata and signing).** Generic PDF-engine capability we need but EmbedPDF lacks is built to be **contributed upstream** (fork + PR under EmbedPDF's MIT terms — verify any CLA/DCO at first contribution), **shipped locally in parallel** via `pnpm patch` or a pinned fork so no slice blocks on the merge, and **collapsed to upstream — dropping the external dependency — if/when accepted** (rejected/stalled → keep the patch indefinitely, which MIT permits). Two named targets: **signing** — EmbedPDF/PDFium _verifies_ signatures but cannot _create_ a PAdES seal (spike #2), which otherwise forces the external **`@signpdf`**; build seal-creation for upstreaming and drop `@signpdf` if merged (the textbook dependency-elimination case). **Metadata** — read/write/strip is _already_ in-engine via EmbedPDF's `EPDF_*` extensions (spike #3), so there is **no dependency to eliminate**; the contribution is gap-filling (most likely full-document _sanitization_ of non-metadata hidden vectors for redaction defensibility). **Boundary:** only the _generic engine primitive_ is upstreamed; the proprietary product layer stays in-tree — the **ESIGN/UETA attribution workflow + Certificate of Completion** (ADR-0045) around the signer, and the **redaction verification gate** around sanitization. Designing for upstreamability also forces a clean engine-vs-product seam (ADR-0051), and becoming an active contributor **upgrades this ADR's bus-factor mitigation from "we could fork" to "we know the codebase well enough to fork."** Generalizable to other strategic OSS dependencies later. **Considered & rejected:** **MuPDF / `mupdf.js`** (the only single-library rival; does everything incl. true vector redaction — but **AGPL**, excluded entirely, not even a fallback; EmbedPDF is the permissive equivalent); **OCRmyPDF** (transitive Ghostscript AGPL); **paying Artifex** for commercial MuPDF/Ghostscript (owner prefers not to pay); **the first pass's five-library hand-composition** (PDFium+pdf.js+pdf-lib+qpdf — fragmented vs. a single SDK, and pdf.js/pdf-lib are now redundant); **building Tier-2 vector redaction ourselves** on PDFium (the EmbedPDF Redaction plugin already provides it); **commercial suites** Apryse/Nutrient/Syncfusion (paid). **Consequences:** the stack collapses to one engine in two runtimes (EmbedPDF/PDFium-WASM, browser + Node/Container) plus orthogonal services (LibreOffice convert, Tesseract OCR) and an optional qpdf sanitize backstop — uniformly permissive (MIT/BSD-3/Apache-2.0/MPL-2.0); Adobe-parity redaction arrives off the shelf with our defensibility shell on top; a license gate makes a future AGPL dependency unmergeable; cost is a single-org dependency (bus-factor — mitigated by MIT + thin-over-PDFium, escape hatch to raw `@embedpdf/pdfium`/`pdfium-render`) and the open verifications below. **Status Accepted** — validated since the proposal: the four-vector document-sanitization contribution (the §J metadata target) was built CI-green and submitted upstream (issue embedpdf/embed-pdf-viewer#673; PRs embedpdf/pdfium#27 + #28 and embedpdf/embed-pdf-viewer#674 + #675), the item-2 license gate is implemented (`tooling/lint-licenses.mjs` + a CI governance step; weak copyleft MPL/LGPL allowed, AGPL/SSPL denied), and fork consumption is settled in ADR-0089. The five build-time questions were **spiked 2026-06-13** (evidence on file): render CPU ~2.9–6.6 ms/page (single-page Worker-feasible, bulk → Container; WASM ~2.05 MB gzip under the Workers paid limit); **signature = verify only → `@signpdf` stays for the PAdES seal** (the one firm constraint); **metadata read+write/strip confirmed in-engine** via EmbedPDF's `EPDF_SetMetaText` extensions + a working verification-gate text-extraction primitive (qpdf needed only for non-metadata hidden vectors, if at all); **`FPDF_SaveAsCopy` round-trips** a valid PDF headless in Node; Bates feasible (APIs present, save round-trips — drive content mutation through the high-level `@embedpdf/engines` API, as raw FPDF string marshaling is inconsistent). No blocker found. Refines **ADR-0045** (PDF services + redaction-deferral; pdf.js/pdf-lib/`@signpdf` re-scoped), **ADR-0030** (OCR = Tesseract-direct); realizes **ADR-0024**/**ADR-0039** (one WASM+native engine, placement); builds on **ADR-0010** (Collabora source editing), **ADR-0048** (CI gains the license gate), **ADR-0083** (placement measurement), **ADR-0074** (Workers paid limit); competitive gap in [`docs/research/competitive-analysis.md`](research/competitive-analysis.md).
