**Integration-platform decoupling: each integration package exports one declarative `IntegrationManifest`; the core holds a central registry that enumerates manifests and drives all wiring (route mounting, per-request adapter resolution) from them — inverting the previous model where the core contained direct knowledge of each plugin. `app.ts` stops naming individual plugins; routes are mounted via a manifest-driven loop through the unchanged ADR-0067 chokepoint. `PluginRuntime` is introduced as the uniform dependency seam (firm-scoped capabilities handed to every plugin's route handler), replacing bespoke per-plugin `CreateAppOptions` fields. Shipping (credentialed) is migrated as the proof of correctness; parcels and property-links (credential-less) gain catalog-only manifests establishing both integration types in the registry from day one. Intrinsic shared-resource concerns — migrations, permission registrations, and identifier prefixes — remain core-side: they cannot be plugin-private. Accidental coupling (route wiring, dependency injection, catalog knowledge) is removed. A well-formedness + decoupling fitness guard (unique `id`/`category` per manifest; `permission` in the access-control registry or null; `app.ts` imports no individual plugin route module by name) runs in CI, making regression a build failure.** **Context:** the shipping slice (ADR-0094/0095) landed the first credentialed adapter, at which point the core accumulated bespoke wiring in roughly a dozen places per plugin. Adding a second plugin at the same cost would compound that coupling exponentially; the manifest model was the obvious inversion. The ADR-0091 port-system spec already anticipated this: "Isolation = in-process first-party modules now, with the in-process → service-binding → Workers-for-Platforms split as the documented, contract-stable marketplace seam." The manifest is exactly that contract. **Decision:** `IntegrationManifest` is a pure-data struct carrying `id`, `category`, `displayName`, `summary`, `vendorUrl`, `credential` (kind/scope, reusing `CredentialRequirement` from ADR-0091), `capability` (reusing `CapabilityDescriptor`), `permission` (a known `KnownPermission` or null), `defaultEnablement`, `connectSchema`/`settingsSchema` (Spec-2 marketplace fields declared now so the contract is whole), `registerRoutes` (the plugin's own Hono route wiring, optional), and `adapter` (the Port adapter, for credentialed resolution). The Spec-2 fields are declared now but read only by the marketplace (Spec 2), not by the current core. The central registry (`listManifests()` / `manifestFor(category)`) is the single place the core learns a plugin exists; adding a plugin = write its manifest + add one line. `PluginRuntime { httpClient, secretStoreForFirm }` is the uniform seam: built once in `createApp`, injected into every `registerRoutes` call, and — crucially — this is the exact seam the C boundary (ADR-0097) later replaces with RPC. The emitted OpenAPI contract and committed snapshot are regenerated; routes are byte-identical to before (only mounting became data-driven). **Intrinsic boundary:** migrations, permission registrations, and identifier prefixes stay in the core because they are genuine shared-resource concerns: a per-firm migration lineage is applied by the provisioner (one lineage, not per-plugin); a permission key lives in the one access-control registry and is referenced by name in the manifest; identifier prefixes live in the one identifier registry. Moving any of these to a plugin package would require cross-package coordination at provisioning time. **Considered & rejected:** a per-plugin Worker now (deferred to ADR-0097 — the trigger condition is not met; the manifest is the contract that survives that move); a plugin options bag growing per plugin (the status quo — inverting it is the decision); pulling permission/migration registration into the manifest (these are shared-resource registrations, not plugin-private declarations — they cannot be owned by the plugin package). **Consequences:** adding or removing a plugin touches only that plugin's package plus one registry line; the core enforces the chokepoint for every plugin route without naming them; the fitness guard keeps the decoupling from regressing; shipping, parcels, and property-links all live under the same manifest-driven model from day one. Builds on **ADR-0091** (port framework), **ADR-0092** (connection model), **ADR-0067** (chokepoint), **ADR-0071** (package seam); sets the stage for **ADR-0097** (C-transition seam).
