**Template registration reports what it found in every case; it rewrites merge fields only when asked, and strips macros without asking — because the two transforms fail in opposite directions.**

**Context:** Registering a `.docx` template can require changing the firm's own document, and slice 2·6·1 met two such transforms. A firm migrating from Word mail merge has templates built from `MERGEFIELD` field constructs, which this engine does not fill in. A firm migrating from an older practice-management system has macro-bearing templates, which carry executable code into a system that runs templates against privileged client data. The product-wide posture (ADR-0214) settles the general shape — detection and reporting always on, the rewrite opt-in, guidance at the decision. What remained was this subsystem's realization of it, and one place the posture's default is deliberately inverted.

**Decision:** (1) **Merge fields: detect always, convert on request.** The registration pass finds every Word merge field and reports each — the field name as Word recorded it, how many times it appears, which document part it sits in, the merge-field key it would become, and whether that key is a field this firm actually has. The rewrite runs only when the request sets `convertMergeFields`, whose contract description states that the document registered will not be the document uploaded.

(2) **Without the opt-in, a merge-field template is REFUSED, not registered inert.** This is the load-bearing choice and the softer alternative is the dangerous one. Left as authored, a merge field is invisible to the assembly engine: it is not a placeholder, so nothing substitutes it and nothing reports it missing — the assembled document silently carries whatever text Word last cached in the field. That is the silently-wrong-document failure the absence model exists to prevent, and the absence model structurally cannot see it, because there is no placeholder to be absent. The refusal carries the full field list, so the caller presents a choice (convert, or edit in Word) rather than a dead end.

(3) **Macros: strip without asking, and report.** The posture's opt-in default is inverted here, deliberately. The two transforms fail in opposite directions: converting a merge field changes what a document *says*, so it needs consent; removing a macro removes what a document *does*, and cannot make it assert anything untrue. Refusing macro templates outright — the design's original recommendation — leaves the firm to strip them by hand and re-upload: the same outcome, more work, and no record of what was removed. So a macro-bearing template is accepted, its VBA project and every content-type and relationship declaration referencing it are removed, the macro-enabled main-document declaration is demoted to its macro-free equivalent, and the count of removed parts is reported on the registration response.

(4) **Macro detection reads the declarations, not the file names**, and the stripped package is re-verified by an independent scan over the bytes that will actually be stored, after the metadata scrub. Any residue refuses the registration outright.

(5) **The Word-name-to-key mapping is an injectable resolver**, the identity mapping today.

**Considered & rejected:** *Automatic merge-field conversion* (the design's original recommendation) — the convenient happy path, but an author who later opens the registered template finds their field codes gone; superseded by the product posture. *Registering a merge-field template with the fields left inert* — the softest option and the most dangerous, for the reason in (2). *Refusing macro-bearing templates* (the design's original recommendation) — defensible on security grounds, rejected on migration grounds per (3). *Applying the opt-in default to macros as well* — consistent, and wrong: it would mean asking a firm's permission to remove code from a document that is about to be executed against its clients' data, where the only safe answer is the one we would take anyway. *Guessing a mapping for an unrecognized field name* — a `ClientName` that becomes `client.displayName` because it looked close is a silent binding decision on privileged content; an unmapped name is reported as one.

**Consequences:** A mail-merge migration costs a round trip — the first registration reports, the second converts — which is the price of the decision being a decision. The identity resolver means a firm whose Word fields are not named the way the dictionary is receives a full list of unmapped names rather than a working template; that is honest, and it is the shape that makes the **per-firm field-mapping library** the obvious next build. It is a named seam here, not built: it plugs into the resolver and nothing downstream changes, because everything past the conversion pass already works in dictionary keys. The macro path means the platform now stores templates whose bytes differ from what was uploaded in a way the firm did not individually approve — accepted, because the difference is reported, is only ever a removal, and the alternative is a template that can run code. Refines the placeholder-form half of the template-model decision (ADR-0211), which recorded conversion as automatic.
