**Identifier strategy — one opaque, type-prefixed, CSPRNG-random, URL-safe handle per row that is also its primary key; purely random (never time-encoded), ~126-bit guess-resistant, UNIQUE+retry for guaranteed non-overlap, branded TS id types; integer-PK-plus-handle split rejected at per-firm scale.** **Context:** ADR-0052 established that matters carry an immutable, always-resolvable opaque handle (and that documents/Directory/events "stay opaque"), but the id format, its relation to the database key, and the generation/crypto details were unspecified; fixtures (ADR-0034) require seeded deterministic id generation, and per-firm D1 (ADR-0003) means ids need only be unique within a firm. The handle is security-sensitive — it is the enumeration/IDOR surface the server-side-only access gate (ADR-0052, 404-not-403) assumes is closed. **Decision:** (1) **One handle per row, serving as both primary key and public id** — a **type-prefixed, CSPRNG-random, URL-safe token** (`mat_`, `doc_`, `dir_`, `inv_`, `evt_`, `pgr_`, `usr_`, `firm_`…) — this _is_ ADR-0052's opaque handle. (2) **Purely random, never time-encoded** — **UUIDv7/ULID/Snowflake rejected** because their embedded timestamp leaks record-creation time, growth rate, and predictability, a real confidentiality leak; generation through a **CSPRNG** (`crypto.getRandomValues`, available in Workers), with a **seeded PRNG injected in fixtures** so ADR-0034 determinism survives. (3) **Entropy sized for guess-resistance (~126 bits, nanoid-21 class)**, not merely collision-avoidance — the IDOR/unguessability bar. (4) **Non-overlap is a correctness guarantee, not a probability:** type-prefix space partitioning + per-firm-D1 scoping + a `UNIQUE` constraint with **retry-on-collision** in the generator. (5) **Prefixes are a registry** (ADR-0051) — self-describing in logs/Error-ID trail (ADR-0038), defense-in-depth against id-type confusion — reinforced by **branded TypeScript id types** (`MatterId` ≠ `DocumentId`). (6) **Cross-database references** (control-plane `usr_`/`firm_` referenced by per-firm `member` rows, ADR-0003) use the same handle scheme, since random handles cross DB boundaries where integer keys cannot. (7) The **matter number** stays a separate human/mutable alias with redirect aliasing (ADR-0052/ADR-0007), never the key. **Considered & rejected:** **integer-PK + separate handle column** (the textbook SQLite max-performance pattern, but its edge is negligible/speculative at per-firm scale where bulk content is in R2 — _measure before optimizing_, ADR-0039 — while it taxes every API boundary with handle↔key translation and an N+1 risk; if scale ever demands it, the handle being the stable external ref makes it a pure internal migration that breaks no URL/contract); **integer rowid PK + handle** (loses self-describing ids and still needs the handle layer); **UUIDv7/ULID as the handle** (time-leak — the decisive security rejection); **the SQLite "random PK fragments the B-tree" fear** (a myth — D1's hidden rowid is the clustered index). **Consequences:** one id per row, enumeration/IDOR-safe by randomness, self-describing, debuggable, type-safe; the confidentiality story (ADR-0052) holds and the id itself leaks nothing; cost is slightly larger TEXT keys/FKs (negligible at per-firm scale) and the prefix-registry + branded-type discipline. Reuses **ADR-0034** (seeded RNG), **ADR-0051** (prefix registry/fitness), **ADR-0038** (Error-ID); underpins **ADR-0052** (opaque handle), **ADR-0003** (cross-DB refs), and the _Idempotency_/_Outbox_ UNIQUE-insert idiom (ADR-0063/ADR-0064). Implementation detail in the _Foundational data conventions_ spec. **Amendment (2026-06-13, slice 1·1 build):** the type prefix is now the **entity type spelled out in full**, in camelCase, identical to the registry key — `matter_`, `document_`, `ledgerAccount_`, `fileVersion_`, `idempotencyRecord_`, `auditLog_`, … — replacing the original abbreviations (`mat_`/`doc_`/`acct_`/`usr_`/…). The owner's call: golden rule 12 (no shorthand) governs identifiers too, and the abbreviated prefixes were an unflagged exception to it. The handle shape `<prefix>_<token>` and the single-`_` separator are **unchanged**; the prefix is **camelCase, not snake_case**, deliberately — our token alphabet already contains `_`, so a snake*case prefix would make the prefix/token boundary ambiguous, whereas camelCase keeps exactly one separating `*`(the recognized TypeID standard assumes an underscore-free suffix, which we do not have). The prefix validator was relaxed from`^[a-z]+$` to camelCase; the registry is now an identity map (prefix === key). No production rows carried handles (only the control-plane schema is live, with no seeded handle rows), so this was a code + committed-seed-literal + test change, not a data migration.
