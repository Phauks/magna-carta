**A conflicts check is a numbered record with runs under it; opening it answers at once, and the search reports on itself until it settles.**

**Context:** A check was one row written by one synchronous request: POST ran the whole search and answered the finished check. That gave it no number — the opaque handle in the address did the work of a reference — no history (running again produced an unrelated row in the log), no way to be filed on a matter after it ran, and no running state to show, because there was none. The owner's rulings of 2026-09-11 ask for all four: a number the firm refers to a check by, a history of its re-runs on the check, filing from the check's own screen, and a screen that says where a running search is and what it has checked so far. A walk to closure (the companion decision) is also the search that cannot be promised to finish inside one request.

**Decision:** Two tables beside the append-only log, both in the per-firm lineage. `conflicts_numbered_check` is the check a person refers to: its sequence and rendered number (`CC-` and four digits, rendered by `renderCheckNumber`), the matter it is filed on, who opened it, and its latest run. `conflicts_check_run` is one search under it: ordinal, status (queued, running, completed, failed), stage, progress counts, the stored request, what started it and who asked, a heartbeat, and a failure sentence. The existing `conflicts_check` row is a run's RECORD — its id is the run's id — and stays append-only exactly as it was.

Identity is settled without a new identifier kind: a numbered check's id is its first run's handle, and every run's id is the `conflicts_check.id` its record writes, so the address a check had before this change resolves to the same check, and either a check's or a run's handle finds the check. The number is `MAX(check_sequence) + 1` under a unique index with a bounded retry on collision — not a counter table, which would have needed a schema-conformance entry outside this surface and buys nothing a unique index does not.

Opening is one small batch that draws the number and inserts the queued run, and the route answers 202 with the check's id, number, run id and ordinal. Execution runs after the response through `runInBackground` — the request's own background allowance — claiming the run, reporting each stage (sources, walking, matching, candidates) with what it has counted, and finishing with the record, the hits and the completion in one effect; a throw settles the run as failed with a sentence a person can act on. A run whose heartbeat is older than two minutes is settled as failed by the next read, because the runtime abandons post-response work after thirty seconds and a run it abandoned must not sit in flight forever. Re-running opens a further run under the same number with the check's stored request against the matter as it stands now; an automatic re-check opens under the matter's latest numbered check; filing a check on a matter moves no record and makes the next run search with the matter's parties. The log lists numbered checks, one row each, carrying the latest run's facts and the run count.

The idempotency record stores the same body every opening route sends, so a replayed key answers in the shape the first request did.

**Considered and rejected:** **A third numbering-scheme purpose** — the matter and consultation schemes are the firm's own choice of shape, and a check's number is a plain firm-wide sequence nobody asked to configure; the settings round can revisit that together with the scheme screen without a schema change. **A queue from the first day** — the per-firm queue dispatch table lives outside this surface and the outbox relay is a five-minute cron; the background allowance is honest today, the stale rule covers what it cannot finish, and the executor is one function that a consumer can call unchanged. **Runs as unrelated log rows with a shared number** — the whole point of the history is that a check's runs belong to it, which is a foreign key and not a column.
