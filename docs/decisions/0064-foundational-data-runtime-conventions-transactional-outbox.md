**Transactional outbox — write the intended effect to an `outbox` row in the same D1 transaction as the business change; a Cron-Workflow relay (DO-poke latency seam) publishes to at-least-once Cloudflare Queues; idempotent consumers; chokepoint-enforced; sagas via Workflows for multi-step.** **Context:** a committed D1 change often must trigger an external effect (payment capture ADR-0032, outbound email/SMS/voice ADR-0047, conflicts re-check ADR-0013, search-index/projection updates), but **a D1 transaction spans a single database only** (no D1+Queues/R2/external atomicity — Cloudflare-confirmed), the classic dual-write problem; ADR-0057 (durability on close) names the outbox as a dependency. Cloudflare's own docs endorse the outbox pattern (publish to Queues from a Durable Object). A §9 member. **Decision:** (1) **Atomic write** — the effect is written as an **`outbox` row in the same D1 transaction** as the business change (and the audit row): `id` (ADR-0062 handle) + topic + payload + status + attempts + aggregate*key + seq + timestamps — recorded iff the change commits. (2) **Chokepoint** (ADR-0051) — a handler that wrote to D1 may **not** enqueue/call-external directly; it goes through the outbox, a boundary fitness function failing CI on any bypass (genuinely independent async work whose job row \_is* its state may enqueue directly). (3) **Relay** — a **Cron-triggered Workflow** sweeps each firm's outbox and publishes pending rows to **Cloudflare Queues** (the cross-firm fan-out of ADR-0050) as the **correctness floor**, with a **post-commit poke to a per-firm relay Durable Object (alarm-driven)** as a **latency seam** on top — prompt drain, but correctness never depends on the poke. Ship the sweep first (measure-first, ADR-0039). (4) **Consumers** — Queue-consumer Workers perform the effect (payment, comms ports, conflicts, indexing/projections) **idempotently**, deduping on the outbox id (reusing ADR-0063); since Queues are **at-least-once and unordered**, ordering-sensitive topics apply by `aggregate_key`+`seq` (skip-stale); max-attempts → **dead-letter** to observability (ADR-0038). (5) **Scope** — the outbox is a **reliable async-dispatch primitive, not event-sourcing**; D1 tables + ledger + audit stay the system of record. **Multi-step external flows** (charge → post → receipt) compose as **sagas via Workflows** with compensating actions (Cloudflare's recommended path), built on the outbox + idempotency primitives, not expanded until a flow needs it. **Considered & rejected:** **direct enqueue/external-call after the D1 write** (the dual-write bug — an effect lost or duplicated when one side fails); **Cron-sweep only with no poke** (correct but adds latency to money/comms — the poke is the bounded enhancement); **DO-storage outbox** (business data is in D1, so the outbox must be in D1 to share the transaction — a DO can't co-write with D1); **event-sourcing as the persistence model** (out of scope — no ADR mandates it; the outbox is delivery, not the source of truth). **Consequences:** state changes and their side effects are consistent without distributed transactions; with inbound idempotency (ADR-0063) the system is effectively-once end to end; cost is the outbox table + relay + idempotent-consumer discipline and at-least-once redelivery. Reuses **ADR-0050** (Cron-Workflow fan-out), **ADR-0039** (Queues/DO compute placement), **ADR-0063** (consumer dedup), **ADR-0062** (ids), **ADR-0051** (chokepoint/fitness); serves **ADR-0032**/**ADR-0047**/**ADR-0013** and depended on by **ADR-0057** (durability). Implementation detail in the _Foundational data conventions_ spec. **Amendment (2026-06-09):** "the same D1 transaction" is realized as the single-`batch()` write path of the ADR-0063 amendment — outbox rows ride the same batch as the business change and the idempotency record, so the row exists iff the change committed. Per-aggregate `seq` is computed **inside the INSERT** (a `MAX(seq)+1` subselect — batch statements cannot share JS-side results but run sequentially in one transaction). The relay **floor shipped as a library** (`sweepOutbox`: publish-**then**-mark for at-least-once, per-row failure isolation, `attempts` tracking, dead-letter callback at max attempts); the Cron-Workflow sweep wiring and the per-firm relay-DO latency poke land with `apps/worker`.
