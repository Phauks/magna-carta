**A race that only happens when the scheduler cooperates is not tested by hoping it cooperates: the interleaving is chosen, named, and asserted to have happened.**

**Context:** there is no interactive transaction on this substrate. A domain mutation reads its precondition in one round trip and commits its batch in another, and the batch's atomicity says nothing about the gap between them — two callers can both read the same pre-state and both commit. What actually holds the line is never that atomicity. It is a UNIQUE or CHECK constraint that aborts the batch, or a guarded UPDATE whose WHERE repeats the precondition so a stale caller changes no rows.

That makes the guard the thing a verifier has to exercise, and the read in front of it is what makes this hard: the code reads correct either way. A service that checks the status and then commits looks like it enforces the status. Delete the `AND status = 'draft'` from the statement and every existing test still passes, because no test ever arranged for the status to change in between.

Two ways to arrange it. Fire both operations with `Promise.all` and let the runtime interleave them — which works where the contended state is inside a Durable Object that serializes the two calls, and is how the per-firm database and live-timer verifiers are written. Or place the competing writer at a chosen point inside the operation. For a read-then-commit service the second is the only honest option: the two promises interleave however that run happened to schedule them, so the test passes for a reason nobody chose and stops failing for a reason nobody notices.

The technique was already here, invented once, in `packages/matters/test/matter-service.test.ts` as a nine-line `interleaveBeforeFirstCommit`. Fourteen other service files have the same window and no such test.

**Decision:** one shared harness at `@magna-carta/data-access/interleave`, and it is what the seven-angle review's concurrency angle instantiates to for a read-then-commit service.

**Where it lives is decided by what it wraps.** The harness wraps a `BatchDatabase`, which `effect-batch.ts` defines, and every domain package already depends on data-access — so it adds no edge to the build graph. It is dev/test-only code in `src/` behind an exports path, which is the `@magna-carta/database/node-sqlite` pattern, carrying the same header saying so.

**Two points, because the domain layer has two shapes.** `beforeCommit(nth)` fires before the operation's nth batch, and is right whenever the precondition is read and committed in the same call. `afterRead(matching, occurrence)` fires once a read whose SQL contains given text resolves, and is for an operation that does other work between the read and the commit — the re-rate that makes one rate-resolution round trip per candidate before committing them all, where the window is not the commit but the whole span. Both count occurrences, so a later commit or a mid-loop read can be the one raced.

**It refuses to pass vacuously, and that is the load-bearing part.** `runInterleaved` throws `InterleaveNotReachedError` when the point was never reached, whether the operation succeeded or failed. The failing case is the dangerous one: a test that asserts a rejection and gets one from a precondition the operation never got past reads as a passing concurrency test and is not one. The operation's own failure travels on the error as `operationFailure`, so nothing is lost. The harness carries its own verifier proving it can still see a commit and a read, on the same argument the background-work barrier's test makes: a gate that has quietly stopped firing does not fail, it passes everything handed to it.

**A finding the guard does not cover is pinned, not fixed in passing.** Applying it recorded two: a member whose guarded edit matched no row is told it succeeded, because the affected-row count never leaves the batch seam and the route answers 200; and an audit row rides the same batch as the guarded write without a guard of its own, so a refused edit still leaves an event behind. Both are protected where the money is — no invoiced amount moves — and both misreport. Surfacing the row count out of the batch means an API contract change, and making the audit row conditional changes what the audit trail means. Those are the owner's calls, so the tests state today's behaviour and say why it is pinned rather than endorsed.
