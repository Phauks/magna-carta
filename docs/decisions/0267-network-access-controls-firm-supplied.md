**Network and device controls are the firm's to enforce and ours to accept — federation, not infrastructure; and the hotel-wifi problem is answered by a package, not a tunnel.**

**Context:** The owner asked for both a network control protecting access to Magna Carta and a VPN we operate. The second is refused in [`no-platform-operated-vpn`](no-platform-operated-vpn.md). This decision settles the first, and settles what we ship instead to meet the goal he actually named: _"I want to assist firms in accessing their files securely over insecure wifi."_

**Decision:** (1) **There is no private network to tunnel into, and this shapes everything.** Our surface is four public Cloudflare hostnames — `app`, `api`, `portal`, and the marketing origin — served by Workers static assets and a Hono Worker, with per-firm data behind the `FirmDatabase` Durable Object and per-firm R2. There is no VPC, no subnet, no origin behind a firewall at an RFC 1918 address. Cloudflare Tunnel exists to connect **private infrastructure** to the edge; we have none. Cloudflare's documentation is explicit that protecting a public hostname needs neither a tunnel nor a private network — _"You do not need to install anything on the user's device — authentication happens entirely in the browser."_ The platform **is** the edge, and any proposal phrased as "a VPN into Magna Carta" should be read as a request for **policy before session creation**, which is a different and cheaper thing.

(2) **We become a SAML 2.0 / OIDC service provider. This is the highest-leverage item and the correct division of labour.** Cloudflare Access's SaaS application type exists precisely for _"applications your team relies on that are not hosted by your organization,"_ federating over SAML or OIDC — and the same protocols serve Okta, Entra and JumpCloud, so the interface is the standard, not a vendor. The firm buys its own Zero Trust or identity seats, installs the WARP client if it wants posture signals, and writes the policy: this person, on a managed laptop, disk encryption on, from an approved country. We accept the assertion and create a session. The firm gets device posture, conditional access and a managed tunnel if it wants one; **we hold no network logs, no device inventory and no posture telemetry**, which is the whole point and the reason this is strictly better than operating anything. Better Auth's SSO plugin is the service-provider implementation. This is **not** a small piece of work and needs its own spec — assertion validation is a notorious source of critical authentication bugs, and Better Auth's own recent hardening (rejecting assertions whose audience, bearer recipient or destination does not match the configured service provider) is evidence of how sharp those edges are.

(3) **The hotel-wifi goal is answered by a package, because the real threats are not network eavesdropping.** Ranked: credential phishing, session-cookie theft by infostealer, device compromise, shoulder-surfing, and only then eavesdropping — which TLS already handles. A tunnel defeats none of the top three. The package does: **passkeys as the default second factor** (already in the stack via Better Auth; a WebAuthn credential is origin-bound and will not present itself to a lookalike domain, which is the only control on the list a convincing fake login page cannot defeat — the work is defaulting and onboarding, not building); **Device Bound Session Credentials** (two server endpoints and a response header, generally available in Chrome on Windows since Chrome 145/146 with macOS Secure Enclave announced, binding the session to a TPM-held key so an exfiltrated cookie cannot be refreshed off-device — the direct answer to the threat that secondary reporting attributes 80% of MFA-bypass breaches to, and which MFA by construction does not cover, degrading gracefully to today's behaviour where unsupported); **short re-authentication windows**; and **an accurate `docs/user/` guidance article** on working from hotels and airports, which is what makes ABA Formal Opinion 498's _"consider using virtual private networks"_ a decision the firm makes knowingly rather than a box a vendor ticks. We should also emit our own `Strict-Transport-Security` header despite `.esq` being preloaded at the TLD level, because preload covers browsers and not the Tauri shell or SDK consumers.

(4) **Per-firm IP allowlisting ships opt-in, off by default, with unusually blunt warnings.** The Worker already sees `CF-Connecting-IP`, so a nullable allowlist on the firm's settings enforced at the existing chokepoint — beside tenancy and authentication, never in a handler — is a small vertical slice. It earns its place because an insurer or a corporate client's outside-counsel guidelines occasionally demand it. It must default off because in 2026 it breaks more than it protects: carrier-grade NAT, mobile work, and — self-defeatingly — a lawyer whose own VPN egresses from a rotating pool. A firm that wants it to work reliably needs a stable egress IP, which on Cloudflare means dedicated egress IPs: **Enterprise-only, minimum two addresses in two cities, bought by the firm**. Enforcement must evaluate **per request** rather than pinning a session to an address, and must fail with a distinct error so support can tell "your firm's allowlist rejected this address" from "your session expired."

(5) **mTLS with Cloudflare-issued client certificates is a named backlog seam, not near-roadmap.** Cloudflare can act as a CA, issue client certificates and enforce mutual TLS per hostname, exposing the verdict to a Worker as `cf.tls_client_auth.cert_verified`. It is the strongest device-binding control available **in our own account** without a client agent, and the honest answer for a firm with a hard firm-issued-laptops-only requirement and no appetite for Zero Trust seats. It is also operationally heavy — enrollment, lifecycle, revocation, and the support burden of a lawyer whose certificate expired the morning of a hearing — so it is recorded as a seam rather than scheduled.

(6) **Coexistence is a testable obligation, not a feature.** Most firms with any IT maturity are already behind a corporate VPN, an agent or a filtering proxy, and the failure modes are specific: a session must never bind to a source IP, because WARP and corporate VPNs re-home between data centres and would otherwise log a lawyer out mid-deposition; a TLS-inspecting middlebox must not silently break the two push-progress WebSocket surfaces (bundle builds and conversion jobs) — the poll fallback exists by design and needs a test proving it engages on a blocked upgrade rather than leaving a spinner; and a firm's geo-restriction policy must not make R2 presigned URLs or Container-backed services fail opaquely. The user-docs article should name which hostnames a firm's administrator must allow.

(7) **The client portal takes no network control, ever.** Portal recipients are clients, co-counsel, experts and adjusters on devices we will never manage; the problem there is the inverse of the staff problem — not "is the network trustworthy" but "is this person who they claim to be, on a device nobody vetted." The designed answer is already correct: per-grant assurance levels up to account-plus-2FA, short-lived signed URLs, instant revocation, quarantined uploads requiring staff acceptance, and metadata-only audit. A future proposal to add a network control to the portal should be read as a symptom that the assurance model is not being used properly.

(8) **The Tauri shell is where connection integrity becomes possible, within parity.** The browser cannot pin certificates (HPKP is removed); a Tauri app controls its own HTTP client and can, which is the correct answer to the trusted-rogue-CA attack and is meaningfully stronger than a tunnel because it fails closed against exactly the interception a tunnel on a compromised device does not stop. Add an honest connection-integrity indicator (pinned, TLS 1.3, no interception detected) alongside the network-medium readout the white paper already routes to the desktop-avenues note, and OS-keychain-held credentials as the desktop expression of the same anti-session-theft goal DBSC serves on the web. All three satisfy ADR-0023: the web path is complete and the desktop adds a local hardening that degrades to it.

**Considered & rejected:** **operating any network infrastructure ourselves** (see the companion decision); **requiring the WARP client for staff access** (an agent rollout forced on every firm for a benefit TLS already provides, contradicting the finding that the firm's identity provider is the right enforcement point); **mandatory or default-on IP allowlisting** (breaks carrier-grade NAT, mobile work and lawyers already using their own VPN); **binding sessions to a source IP as a security control** (guarantees mid-deposition logouts on any re-homing tunnel, for protection a bound session credential provides properly); **building a bespoke device-posture agent** (duplicates what the firm's identity provider already reports as assertion claims, and would make us hold device telemetry we have no reason to hold); **shipping mTLS in the near roadmap** (right control, wrong time — the enrollment and revocation burden needs its own design); **any network control on the client portal** (incoherent against unmanaged external recipients); and **treating "consider using a VPN" in ABA Formal Opinion 498 as a product requirement** (the opinion addresses the lawyer's own router, laptop, passwords and surroundings, leaves the VPN decision to the lawyer's discretion, and is not a specification for what a practice-management vendor must operate — and it is ABA guidance, not binding authority; Nevada's RPC 1.6 as adopted is the operative rule). Extends **ADR-0068** (the trusted-insider model and the one chokepoint — an allowlist is another chokepoint check, never a second authorization system) and **ADR-0067** (route meta and the single enforcement point); respects **ADR-0023** (parity) and **ADR-0003** (per-firm isolation — an allowlist is per-firm settings data inside the boundary).
