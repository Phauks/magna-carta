**The conversion orchestrator's scanned-PDF→searchable-PDF edge (reserved by ADR-0030) is wired: OCR is a conversion engine, behind a distinct `searchable-pdf` format node, resolved per-engineId to the OCR service binding.**

**Context:** The OCR engine and its searchable-PDF writer shipped and are reachable directly at `POST /api/v1/ocr/searchable`. ADR-0030 reserved an edge for the conversion orchestrator to dispatch scanned-PDF→searchable-PDF to that engine, so the same "convert this file" surface, job coordinator, queue, and polling that serve every other conversion also serve OCR — rather than OCR being a separate one-off endpoint. The conversion subsystem was built and dormant only on the engine port; the executor already resolves each hop's engine per `engineId`, but the worker collapsed every hop to one shared port.

**Decision:** (1) **A new engine `ocr`** in `@magna-carta/conversion`, server-only in the placement map. (2) **A distinct `searchable-pdf` format node**, same `application/pdf` media type and `.pdf` extension as `pdf`, and listed after `pdf` so format detection of a `.pdf` file still resolves to `pdf`. It is a separate node rather than a `pdf→pdf` edge because pathfinding treats `from === to` as no-path, and "make this searchable" is a real, selectable target. (3) **A single edge `pdf → searchable-pdf` (engine `ocr`).** (4) **A per-engineId resolver in the worker:** `resolveEnginePort` now returns an `EngineResolver` that routes the `ocr` hop to the `OCR_SERVICE` binding's `/ocr/searchable` (body only, no recipe headers) and every other hop to the `CONVERT` binding; a hop whose service is unbound resolves to the deferred port (`engine-not-implemented`). This is why OCR works today without the dedicated conversion worker — it is its own already-deployed service — while the convert-worker engines stay dormant until that worker is deployed. (5) **A scanned image reaches `searchable-pdf` by composition, not a direct edge:** the searchable writer appends an invisible text layer onto an existing PDF and the OCR service refuses a bare image (`not-a-pdf`), so an image is first wrapped into a PDF by the `image-pdf` engine and then recognized — `image → pdf → searchable-pdf`. A direct image edge would duplicate the image-to-PDF engine inside OCR and break one-engine-per-edge. That path executes once the raster/image-pdf engine is deployed; `pdf → searchable-pdf` executes now.

**Fitness tests:** the registry declares exactly one `ocr` edge, `pdf → searchable-pdf`, and it is well-formed (registered endpoints, positive weight, a placement entry); `findPath("pdf","searchable-pdf")` is a single `ocr` hop and `availableConversions("pdf")` includes it; the conversion runs server-only (`canConvertLocally` is false); the worker resolver routes `ocr` to `OCR_SERVICE` `/ocr/searchable` and everything else to `CONVERT`, resolves `ocr` to the deferred port (never `CONVERT`) when `OCR_SERVICE` is unbound, and maps a non-2xx or thrown transport error to `adapter-error`; the submit route accepts `pdf`→`searchable-pdf` (validated by `getFormat` + `findPath`, no format enum, so the API contract is unchanged).

**Realizes ADR-0030** (in-app file conversion; it names discovery OCR among the engines the orchestrator dispatches to). **Builds on** the OCR engine and searchable-PDF writer decisions (`docs/decisions/pending/ocr-engine-model-and-determinism.md`, `docs/specs/2026-07-14-searchable-pdf-writer-design.md`) and the conversion port/registry (`packages/conversion`). Bounded by **ADR-0003** (per-firm isolation — the OCR service is firm-agnostic; the worker owns firm scoping).
