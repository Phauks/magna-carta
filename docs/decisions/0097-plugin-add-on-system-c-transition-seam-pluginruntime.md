**The C-transition seam: `PluginRuntime` is the boundary contract that makes the in-process integration model transport-agnostic. The transport progression under one unchanged manifest is: (C0, current) in-process — plugin `registerRoutes` runs in the same Worker, `PluginRuntime` is direct function calls; (C1) service bindings — a per-plugin Worker, `PluginRuntime` becomes RPC over a service binding, sub-millisecond, same-DC; (C2) Workers for Platforms — per-untrusted-plugin Workers in a dispatch namespace, the full third-party marketplace isolation model confirmed as Cloudflare's supported path. Authors code against `PluginRuntime` identically at every stage. The trigger for advancing past C0 is the first untrusted/third-party plugin, or the first plugin needing an independent deploy cadence or sandbox — not a calendar date. This is recorded now, not built — the hard problems below are documented so they are not improvised at trigger time. Hard problems C must solve: (1) per-firm D1 across Workers — bindings are set per-Worker by `database_id` at deploy time; a plugin Worker cannot receive the core's runtime-resolved firm DB connection across the boundary, so the resolution mechanism (capability token, proxy Worker, or similar) must be designed; (2) firm-key / credential custody — the `CredentialStore` and per-firm `firm_secret` encryption root live in the platform Worker, not the plugin; crossing the boundary requires a defined, audited handoff; (3) distributed migration ownership — the current model has one per-firm migration lineage applied by the provisioner; an isolated plugin Worker cannot safely manage its own migrations against the firm D1 without coordination; likely resolution is plugins _declaring_ schema fragments that the platform applies to the single lineage, not per-Worker migrations; (4) chokepoint-across-boundary — C1: the platform enforces tenancy/authn/RBAC then forwards a trusted context header to the plugin Worker; C2: per-Worker sandbox plus a re-check inside the plugin Worker (the platform cannot trust the plugin's enforcement in the untrusted model); (5) aggregated OpenAPI — the single committed contract must aggregate operations from Workers that are separately deployed; (6) multi-Worker dev/test/deploy complexity and Workers-for-Platforms dispatch-namespace pricing. What stays platform-owned at every stage regardless of transport: tenancy resolution, the single ADR-0067 chokepoint, the per-firm migration lineage, and the encryption custody root. The manifest (`IntegrationManifest`) is the stable interface all three stages share; it is defined whole in ADR-0096 (including the Spec-2 marketplace fields) precisely so the C boundary does not reshape it.** **Context:** the in-process model (ADR-0096, ADR-0091) is deliberate and correct for first-party integrations where trust is inherent and inter-Worker overhead would be gratuitous. The C seam documents why isolation is deferred and exactly what must be solved before it is triggered — avoiding both premature complexity and improvised architecture at trigger time. ADR-0091 named the seam ("Workers-for-Platforms split as the documented, contract-stable marketplace seam") without specifying it; this ADR specifies it. **Considered & rejected:** building C1/C2 now (no trigger condition met; the manifest and `PluginRuntime` seam cost nothing today and preserve the option); leaving the boundary unspecified (risks improvising it under time pressure when a third-party plugin first appears); per-plugin D1 databases (isolation at the cost of cross-plugin queries and the provisioner complexity — not adopted; the shared per-firm lineage is the invariant). **Consequences:** the hard problems are named and searchable before they become urgent; the trigger is explicit (untrusted/third-party plugin or independent-deploy need) so advancement is event-driven, not calendar-driven; the platform retains its invariants (tenancy, chokepoint, migration lineage, encryption root) in all three stages. Builds on **ADR-0096** (manifest + `PluginRuntime` seam), **ADR-0067** (chokepoint), **ADR-0003** (tenancy + per-firm isolation), **ADR-0084** (encryption custody), **ADR-0091** (port framework). Not built — recorded only. Spec: [`docs/specs/2026-06-17-integration-platform-foundation-design.md`](specs/2026-06-17-integration-platform-foundation-design.md).
