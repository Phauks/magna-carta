**Access-control model — a trusted-insider RBAC: anyone logged in is an authorized firm member, so information is open among insiders and RBAC governs _actions_ not _visibility_; permissions are a per-subsystem registry, roles are editable data (defaults seeded, role-editor UI a later seam), effective permissions = roles ∪ direct grants, action-denials are request-able (403 + access request → direct grant); location is a view/reporting filter (not a gate); 404 is reserved for cross-firm isolation; ethical walls and external-principal enforcement are deferred (named seams, no design yet).** **Context:** ADR-0004 named "RBAC + ethical walls" but left the model thin, and the API route-metadata chokepoint (ADR-0067) needs the `permission` set defined; the owner's working assumption is a small, mutually-trusted firm where every login is an authorized member who may access and assist. Captured at the **white-paper level — no separate spec** (owner's call; a subsystem spec is written only when walls or portal-enforcement is actually built). **Decision:** (1) **Trusted-insider posture** — information is open among insiders; RBAC gates _actions_, not _reading_; the only hard boundary is firm isolation (ADR-0003), so **within a firm every denial is 403** and **404 is reserved for the cross-firm/other-database case** — clarifying ADR-0052 (its 404-not-403 now applies to cross-firm isolation, not to within-firm screening). (2) **Permissions = fixed registry, one namespace per subsystem** (`<subsystem>:<action>`, mirroring the per-subsystem route modules + frontend areas, ADR-0067); the `Permission` union is generated from it and a conformance fitness function (ADR-0051) cross-checks every route's `permission` and that a route's namespace matches its module. (3) **Roles = data, not enums** — `role→permission` + `member→role` rows seeded with editable defaults (Owner/Admin, Attorney, Paralegal, Billing, Read-only); role-editor UI is a later additive seam (design-for-the-superset); **effective permissions = roles ∪ direct grants**. (4) **Access requests** — a visible-but-action-denied 403 routes to a `users:`/`roles:` approver who writes an optionally time-boxed **direct grant**; reuses Notifications (ADR-0059) + audit. (5) **Location is a filter, not a gate** — **supersedes** the white-paper "per-location scoping = access control" text (_Locations_); data is firm-wide, users filter by office; **hard per-location separation is a reserved seam**. (6) **Deferred (named seams, no design):** **ethical walls** (future content-screening overlay — visible header, locked contents — built only when a real use case appears; the resolver's `resource` field is the reserved seam), the **external-principal/portal enforcement** detail (the zero-trust grant model of _Client portal_), and dual-control / sealed-matter variants. **Considered & rejected:** **need-to-know / assignment-based matter access** (wrong for a small trusted firm — overhead without benefit; reserved seam); **per-location access restriction now** (owner wants office as a filter, not a barrier); **designing ethical walls now** (no concrete use case — building unused mechanism violates YAGNI; the seam is preserved); **a full RBAC subsystem spec now** (the model fits at white-paper level; a spec is earned when walls/portal-enforcement are built). **Consequences:** RBAC ships as action-gating over open information — cheap and fast for a single trusted firm — with the expensive-to-change parts (permission registry, roles-as-data, the route seam) future-proofed; walls and portal-enforcement attach later as overlays on the same resolver with no retrofit. Refines **ADR-0004** (does not supersede), clarifies **ADR-0052** (404 = cross-firm), builds on **ADR-0067** (route `permission`/`resource` seam), **ADR-0003** (isolation/`member`), **ADR-0026** (`protected()` reuses the same permission check), **ADR-0059** (access-request notifications), **ADR-0051** (registry/fitness); revises the _Locations_ per-location-scoping text.
