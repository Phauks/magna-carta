**Duplicate handling (slice 1·3): entry-time prevention + non-destructive merge now; automated unmerge deferred to the LEAP slice as a guarded operation. Prevention = a recall-biased "possible duplicate?" candidate list (phonetic-block ∪ trigram ∪ blind-index equality) surfaced on entry. Merge is non-destructive — the subordinate is archived (`status = merged_into` + master id, never deleted), all inbound references (matter_party, edges, categories, contact/identifier rows) are repointed to the master because every reference is a real indexed column, and an append-only `entity_merge` event records the survivorship choices + the exact repoint list (table/row/old→new); the subordinate's names + identifier blind indexes stay master-resolved in the matching corpus (a merged-away alias must still trigger a conflict hit). Field-level survivorship for standard fields (prior values recorded for restore); multi-valued child rows are unioned.** **Context:** duplicates arise in ordinary operation, not only at LEAP (the same person entered as a beneficiary in a second matter), so 1·3 must merge; the research ([`docs/research/directory-mechanics.md`](research/directory-mechanics.md) §B) found no mainstream true unmerge and offered three tiers. **The unmerge tenability finding (the deferral rationale):** unmerge is well-defined only as "reverse a specific, recent, still-clean merge." If A and B merge then C is added against the unified entity, deterministic replay cannot re-attribute C to a former side — that information was never captured (one entity to everyone who touched it). So **unconditional deterministic unmerge is rejected** (it silently misattributes post-merge data — a footgun); whenever unmerge is built it **must be guarded** (offered only while the merge is clean — no post-merge references/edits — then locked to a manual path); and because merge is non-destructive with the full `entity_merge` event, the data to reverse always exists, so the guarded automated button is a deferral, not a retrofit over lost data. **Considered & rejected:** prevention-only with merge deferred to LEAP (duplicates are real pre-LEAP — owner scenario); merge + true unmerge built in 1·3 (the post-merge-attribution problem makes a general split ill-posed; the safety net is non-destructiveness, not an undo button); hard-delete-the-subordinate merge (industry norm — destroys the conflicts corpus + audit). **Consequences:** the white-paper "unmerge/split safety net" line is amended to non-destructive merge + guarded unmerge (defer-with-seam; nothing irrecoverable now); the conflicts-corpus rule binds the merge path; reference-kind custom-field values (slice 1·4) extend this relink set in-area. Serves **ADR-0006/0013**; builds on **ADR-0085** (the model), the slice-0·2 atomic batch, and the 1·1 `audit_log`.
