**AcroForm read/fill/flatten with engine-generated Helvetica appearances (no NeedAppearances reliance) and flatten-into-content; AcroForm-only, XFA/signature/rich-text out of scope; forms is not redaction.**

**Context:** Firms regularly complete government and court-mandated forms — the IRS W-9, standard pleading templates, discovery checklists, and similar documents — and must produce versions with permanent, everywhere-renderable values for filing, service, and archive. A form that only carries `/V` values and relies on the viewer to generate the visual appearance is fragile: different viewers apply `/NeedAppearances` inconsistently, and a flattened raster image of a form that was never rendered correctly is useless. The engine must own the full rendering pipeline.

**Decision — generated appearances, not NeedAppearances.** When a field is filled, the engine generates a real PDF Form XObject (`/AP /N`) in Helvetica for every widget annotation. The generated appearance exactly matches the value that will be visible in every compliant viewer, because the engine writes the glyph stream itself rather than asking the viewer to draw it. Helvetica is chosen because it is one of the fourteen standard base fonts guaranteed to be present without embedding; the appearance references only a three-key font dictionary, adding no font file to the document. Font size is parsed from the field's `/DA` (default appearance) entry; when the specified size is zero the engine auto-fits to the widget height.

**Flatten bakes into content.** When `flatten: true` is passed, each widget's selected appearance (`/AP /N`) is drawn into the page content stream via a `Do` operator at the widget's display rectangle, with a `cm` transform to map the appearance's coordinate system to the page. Page resources are merged non-destructively — existing font and XObject resource dictionaries are cloned and the new entries appended, so no existing resource is dropped. Widget annotations are then removed from the page's `/Annots` array and the `/AcroForm` entry is removed from the document catalog. After a successful flatten, `readForm` returns an empty array: the form is gone, replaced by ordinary drawn content.

**Field model — terminal-field walk with inheritance.** The engine performs a depth-first walk of the `/Fields` array in `/AcroForm`, collecting terminal fields (nodes that carry an effective `/FT` and have no field-type child nodes). For each terminal field, `/FT`, `/Ff`, `/DA`, `/V`, and `/Opt` are resolved by ascending the parent chain when the field dict does not carry them directly, matching the inheritance rules in the PDF specification. The fully-qualified name is built by joining `/T` values with `"."` from root to leaf. Widget annotations (`/Subtype /Widget`) referencing the field are collected via the `/Kids` array and cross-referenced with the page `/Annots` lists.

**Fillable kinds: text, checkbox, radio, choice.** Text (`/FT /Tx`) and choice (`/FT /Ch`) fields receive a Helvetica text stream. Checkbox (`/FT /Btn`, non-radio) widgets toggle between their on-state export name and `/Off` based on a boolean value. Radio group widgets set the chosen `/Kids` widget to its export name and all others to `/Off`. Push-button (`/FT /Btn` with the pushbutton flag set) and signature (`/FT /Sig`) fields are enumerated by `readForm` but are read-only in v1 — no fill action is taken. Unknown field types are also passed through read-only.

**Not redaction.** `fillForm` and `flattenForm` are additive or value-edit operations. They write visible field values and optionally bake the resulting appearances into page content. They do not remove hidden content, orphaned text, metadata, attachments, optional-content layers, or any other surface that may carry sensitive information. Redaction and sanitization are separate, explicitly destructive operations (`redact`, `sanitize`) that must be applied independently when content removal is required. These two concerns must never be conflated.

**Boundaries — deferred.** The following are explicitly out of scope for this version: XFA-only documents (the call returns `"document has no interactive form"` when no `/AcroForm` is present); digital-signature creation and signing (PAdES); rich-text and multiline appearances; `/MK` widget border and background styling in generated appearances; encrypted or permission-locked forms (the secure-forms half). These are candidates for later work driven by production demand.
