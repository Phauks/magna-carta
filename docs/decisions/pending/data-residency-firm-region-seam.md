**A `region`/`jurisdiction` attribute is added to the control-plane firm registry now as a designed seam, so a firm's per-firm D1 and R2 can be placed in — and pinned to — an allowed jurisdiction (EU/UK/Canada/US), with provisioning honoring it via Cloudflare location/jurisdiction hints and a fitness test asserting a region-tagged firm never instantiates storage outside its allowed set; only the launch region runs at GA, but the attribute and the placement seam ship up front because retrofitting residency across every already-provisioned per-firm database and bucket is the expensive path.** **Context:** the target market is global/enterprise with US primary plus Canada and EU/UK. GDPR/UK GDPR restrict international transfers (Art. 44 et seq.; post-Schrems II this rides SCCs/IDTA, which flow through Cloudflare and the payment processor), and Canadian PIPEDA / several provincial law-society rules expect Canadian-resident data. Today there is **no** per-firm residency control: per-firm D1/R2 are created in the account's default region, and the only "where does data physically live" lever is the deferred off-Cloudflare DR export seam (ADR-0050) — which is catastrophe recovery, not residency. The firm is already the unit of tenancy, isolation, and crypto-shred (ADR-0003), so region is a natural firm attribute, not a new axis. This is a "build the cheap seam when in the area" case (ADR-0078): the column and placement hook are cheap now; a data migration across every firm's database and bucket after launch is not. **Decision (proposed):** add `region`/`jurisdiction` to the control-plane `firm` row; the `FirmProvisioner` reads it when selecting D1/R2 location; the default value is `us` (the primary market); a fitness test pins the invariant (an `eu`-tagged firm places no storage outside the EU set); regional Terms-of-Service variants (legal-perimeter.md) key off the same attribute. **Considered & rejected:** retrofit residency later (a schema + data migration across every per-firm database and bucket — precisely the expensive-to-retrofit foundation this avoids); treat the off-Cloudflare DR seam as the residency mechanism (wrong tool — it is disaster recovery, and it is deferred); a separate residency registry decoupled from the firm (needless — residency is a firm property). **Resolved (2026-07-02, design accepted):** the column is `firm.data_region` (`us | eu`, extensible; `canada` reserved; `us` the primary-market default, backfilled onto existing firms), immutable after provisioning. Note `eu` is a *hard* Cloudflare jurisdiction lock while `us` is North-America placement via location hint — Cloudflare has no general US jurisdiction primitive (only FedRAMP), which is adequate since no GDPR-style transfer restriction binds US-resident data. The `eu` path is built on Cloudflare's `eu` jurisdiction for **both** the R2 bucket (a hard EU-storage guarantee, threaded through the single `createBucket` call) and the per-firm database Durable Object (addressed via `namespace.jurisdiction('eu').idFromName(firmId)` at the `firm-database-proxy.ts` chokepoint) — **set once at provisioning, no cross-region moves**, because a jurisdiction-bound DO id differs from the bare id (re-addressing under a different jurisdiction would point at a different, empty DO). Canada has no Cloudflare jurisdiction and is **reserved, not built** (interim: US placement + SCCs). The off-Cloudflare export seam (ADR-0050) is disaster recovery, out of scope here. Spec: [`docs/specs/2026-07-02-data-subject-attribution-erasure-residency-design.md`](../specs/2026-07-02-data-subject-attribution-erasure-residency-design.md). **Consequences:** the attribute and seam ship now; actual multi-region placement is built when the first firm with a residency obligation signs; pairs with **ADR-subject-level-erasure-dsar** (both are the GDPR/PIPEDA data-lifecycle gap). Builds on **ADR-0003** (per-firm isolation) and **ADR-0050** (the DR export seam); mapped in [`docs/conventions/compliance.md`](../conventions/compliance.md).
