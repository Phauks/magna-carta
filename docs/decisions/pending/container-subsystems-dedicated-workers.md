**Container-backed subsystems extract to dedicated Workers.** Magna Carta runs several subsystems on heavy native runtimes inside Cloudflare Containers (malware scanning; document editing via Collabora, ADR-0010; file conversion via LibreOffice + libvips, ADR-0030; OCR, ADR-0060; the pure-Rust PDF engine, ADR-0089). The question this decision settles, generally and once: does such a subsystem live **inside** the main `magna-carta` app Worker, or as its **own** Worker? The answer is its own Worker, by the rubric below — generalizing the per-integration worker isolation of ADR-0015/ADR-0096 from outbound integrations to inbound heavy compute, and concretizing the off-the-hot-path mandate of ADR-0039.

**The rubric — five properties.** A subsystem extracts when it scores high on ①–④ **and** clears ⑤:

1. **Heavy native / Container runtime** — its work runs in a Dockerfile-built Container Durable Object, not in the Worker isolate.
2. **Independent deploy cadence** — its image rebuilds on a schedule decoupled from app deploys (e.g. scan's daily signature refresh; Collabora's security-patch cadence).
3. **Distinct scaling profile** — it wants its own `max_instances`/`instance_type` and must not contend with, or starve, the app Worker's request handling.
4. **Containment / blast-radius** — it processes untrusted bytes and wants `enableInternet = false`, no public surface, and reachability **only** via service binding from the app Worker.
5. **Stateless compute (the seam test)** — the work that moves into the dedicated Worker holds **no firm state**. This is the decisive property: it is what let scanning split cleanly, and it is where the others differ.

**The compute-vs-coordination seam.** Only stateless compute crosses the boundary. The firm-state-bearing coordination stays in the app Worker, behind the data-access layer (ADR-0003) and the route chokepoint (ADR-0067):

- **Scanning** — clean split, no coordinator: the whole engine is the Container; nothing firm-scoped lives with it. (`apps/scan-worker`, realized.)
- **Editing (2·2)** — the **coolwsd Container compute** extracts; the **`DocumentSession` DO** (participants, WOPI lock, working-object metadata) stays in the app Worker, because it is coordination coupled to document/file logic, not stateless compute. Moving it would only relocate coupling across a network hop.
- **Conversion (2·4)** — the **heavy engine bodies** (LibreOffice, OCR, native libvips, future PDF) extract behind the existing `ConversionPort` seam (a container adapter is just one more `ConversionPort` implementation); the **`ConversionJob` DO**, the `CONVERSION` queue, and the pure-TS `registry`/`pathfinding`/`placement` logic stay in the app Worker. Light WASM engines (wasm-vips for small rasters) may stay in-process as a fast-path — the multi-candidate registry already models "in-worker WASM" vs "container native" as two engines in the graph.

**Failing the rubric — durable per-firm state is a different design.** A subsystem whose state **is** a durable, per-firm dataset fails ⑤ and is **not** this pattern. Full-text search (Tantivy, ADR-0012) is the example: its index is firm data, not stateless compute; extracting it raises index storage, per-tenant isolation, and rebuild questions that this rubric does not answer. It gets its own spec as a **stateful service** when search is scheduled, and must not be modeled as "scan again."

**The worker template (the realized form).** A dedicated Container Worker mirrors `apps/scan-worker`: `workers_dev:false` + `preview_urls:false` (no public surface), reached only by a service binding from `magna-carta`, owning the Container DO via a `new_sqlite_classes` migration, `enableInternet = false`, and its own crons (a `*/20` warm-poke to keep one instance and its resident state hot; a daily image rebuild where the runtime needs no egress, e.g. signature refresh). The full rubric and template live as a cited convention in [`docs/conventions/operations.md`](../conventions/operations.md) (§ "Container subsystems → dedicated workers"); specs and code reference that path, not this ADR.

**Considered & rejected.** *Wire each Container into the app Worker* (the pre-extraction shape, still described inline in operations.md §11 for scan) — rejected: it couples the app's deploy cadence and blast radius to the heaviest, most-frequently-patched, untrusted-byte runtimes, and the local worker test pool cannot host container bindings at all (`@cloudflare/vitest-pool-workers`, workers-sdk#10408), so an in-app Container forces an awkward absent-binding seam on the whole app. *One shared "compute" Worker owning every Container class* — rejected as the blanket rule: it re-couples independent deploy cadences (signatures vs. Collabora vs. LibreOffice) and scaling profiles that property ②/③ say should move independently; grouping is allowed only where engines genuinely share one pipeline and cadence (e.g. conversion's LibreOffice + OCR), decided per-candidate. *Extract the coordination DOs too* — rejected: `DocumentSession`/`ConversionJob` are firm-state coordination that belongs with the document logic and behind the data-access layer; relocating them buys no isolation and adds a network hop to every state mutation.

**Consequences.** The Container family converges on one structure instead of re-litigating placement per slice: scanning is realized (`magna-carta-scan`); editing (2·2) has agreed to extract the coolwsd compute; conversion (2·4) is evaluating the same split at its `ConversionPort` seam; search (Tantivy) is explicitly out of this pattern as a future stateful service. New caveats are named for future builders: a *pluggable* engine that needs outbound network (e.g. a cloud OCR/conversion engine) cannot share scan-grade `enableInternet = false` containment and needs its own policy lane — a real fork for conversion's pluggable-engine set. Builds on **ADR-0010** (Collabora on Containers), **ADR-0012** (search on Tantivy), **ADR-0030** (file conversion), **ADR-0039** (deliberate-compute / off the hot path), **ADR-0060** (OCR engine), **ADR-0069** (Worker delivery architecture); generalizes **ADR-0015**/**ADR-0096** (worker-per-integration) from outbound integrations to inbound heavy compute; respects **ADR-0003** (firm-scoped data access) and **ADR-0067** (route chokepoint) at the seam.
