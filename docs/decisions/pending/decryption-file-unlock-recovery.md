**File unlock & password recovery — one pure-Rust core, two operations, a hash-only recovery boundary.** The firm needs to open encrypted client files: sometimes the password is known (open it), sometimes it is lost (recover it). Both are handled by a single in-house engine rather than shelling out to `qpdf`/`hashcat`/`John` or a SaaS.

**(1) One core behind a format trait.** `crates/decryption-core` implements a `FormatAdapter` trait over v1 formats **PDF, ZIP, OOXML** (7-Zip, legacy Office, RAR deferred): magic-byte `detect()`, `strip_with_key(password)` (unlock), `extract_hash()` (produce a hashcat-compatible `$pdf$`/`$zip2$`/`$office$` hash + mode), and `verify_guess()`. The crate is pure Rust and compiles two ways — to **WebAssembly** (`packages/decryption`, mirroring `packages/pdf`) so unlock and hash-extraction run *inside* the app Worker with no container, and to **native** for the recovery search shards where rayon parallelism is available (`cfg(not(wasm32))`). Crypto correctness is cross-validated against real hashcat `example_hashes` vectors *and* independent fixtures, not just self-consistency.

**(2) Pure-Rust, no C/C++ (golden rule 14).** The dependency set is chosen to avoid native code even at some cost in format breadth: `lopdf` (workspace-pinned), `zip 2` with default features off (aes-crypto + deflate only), `cfb`, `office-crypto`, RustCrypto 0.10/0.4 generation. A memory-unsafe library parsing untrusted, privileged encrypted bytes is a confidentiality risk even inside a sandbox; the pure-Rust path is preferred and the trade recorded.

**(3) The confidentiality keystone.** Two operations, one hard rule: the password and the decrypted plaintext must never appear in any audit row, log line, or problem detail. Unlock returns the cleartext file only in its own success response to the caller who supplied the password. **Recovery never sees the file at all** — the route extracts the hash in the Worker and only the *hash* enters the job, the queue, and the search shard; the file bytes are never stored or forwarded. Audit rows record the outcome and a SHA-256 of the *encrypted input*, never the hash-secret or the password. Malformed attacker-influenced input (bad base64, a non-encrypted file, an unparseable hash) returns 400, never a 500/panic.

**(4) Button-initiated, permission-gated, attested.** Nothing decrypts or cracks automatically. Every call requires the `tools:decryption` permission (registry entry + a per-firm seed migration) and an explicit per-file authorization attestation that the requester is entitled to the file. The tool is registered in the `@magna-carta/tools` catalog under the `documents` group.

**(5) A backend port for heavier compute.** Recovery escalates along a ladder — Cloudflare CPU (built) → desktop GPU → cloud GPU → an external-forensic seam — expressed as a `RecoveryBackend` port so the coordinator is backend-agnostic and later rungs plug in without coordinator rework.

**Considered & rejected.** **Shelling out to `qpdf`/`hashcat`/`John`** — pulls in C/C++ parsing untrusted privileged bytes (golden rule 14) and a heavier operational surface; rejected for the in-house pure-Rust core. **A decryption SaaS** — sends privileged client files or their hashes to a third party; rejected outright for a confidentiality product. **Two separate engines for unlock vs recover** — the format handling (detect, parse, key-derive) is shared, so one `FormatAdapter` core serves both. **Running the search in the app Worker** — CPU-bound brute force does not belong on a request isolate; it runs in native shards off the hot path.

**Consequences.** Unlock and hash-extraction run in-Worker with no container cold-start; the recovery muscle is native and horizontally shardable. Confidentiality is structural: the file never leaves the boundary for recovery, and the secret material has exactly one egress path. Deferred: additional formats (7-Zip, legacy Office, RAR), the GPU escalation rungs, and the end-user UI. The recovery orchestration (the fan-out coordinator over the search shards) is the companion `decryption-recovery-orchestration` decision.
