**Fast builds are a foundation, not a measure-first optimization.**

**Context:** the scan Container was deliberately built for fast, cheap builds (multi-stage image, lean `.dockerignore`, committed `Cargo.lock`, signature DB and compiled YARA-rule blob baked at build time). Nothing else that builds repeatedly had the same care, and there was no written standard requiring it. The build/deploy pipeline is Cloudflare Workers Builds (ADR-deploy-model-cloudflare-workers-builds), and it was running each build from a cold cache — re-downloading the pnpm store and rebuilding outputs on every push.

**Decision:** treat build-time performance as a standing foundation under the "Build when in the area" principle (ADR-0078), not under golden rule 10's measure-first gate. A cache, a path scope, and build-time baking are cheap-from-the-getgo and expensive-to-retrofit, so they are added up front by default for anything that builds repeatedly in the cloud. The standard lives in a new `docs/conventions/build-performance.md` (the single home), is referenced from the root `CLAUDE.md` "Build when in the area" bullet, and carries a checklist applied whenever something new that builds is added. Concrete levers, in order of leverage: enable Workers Builds **Build Caching** (deps + outputs cached across builds) for `magna-carta` and `magna-carta-scan`; set **Build Watch Paths** per Worker so an unrelated change does not rebuild every Worker; and add BuildKit cache mounts on the Cargo registry, git cache, and crate `target/` in the scan `Dockerfile` (copying the built binaries out to a non-mounted path so the cross-stage `COPY` still works). Build Caching and Watch Paths are dashboard settings (operator steps in `docs/conventions/operations.md`); the Dockerfile change is in code.

**Scope:** this governs build/CI wall-clock and the developer feedback loop only. Runtime/request-time performance stays with golden rule 10 and `performance.md` (measure-first); reclaiming dead build output to keep the disk from filling stays with the post-merge auto-clean sweep (a separate decision). The throwaway validation Dockerfiles (`Dockerfile.buildatoms-check`, `Dockerfile.validate-prefilter`) are not part of the pipeline and are left unchanged. No build-time budgets or a build-wall-clock regression signal are set yet; those are deferred until there is a baseline worth holding.

**Consequences:** with Build Caching on and Watch Paths scoped, Workers Builds restores dependencies and skips unchanged outputs instead of rebuilding from zero, and only the affected Worker rebuilds on a given change; the scan image reuses an unchanged Cargo dependency graph via the cache mounts. The standard makes "is this fast to build?" a default question for every new Worker, Container, or generation step, and applies directly to the queued Container subsystems (editing, conversion, OCR, search, office) as they are built. One known limitation: BuildKit cache mounts are build-local and not persisted across Workers Builds runs, so a cold Rust dependency compile can still occur after a `Cargo.lock` change; persisting the mounts (a cache-mount export) is the documented upgrade path if that becomes the bottleneck.
