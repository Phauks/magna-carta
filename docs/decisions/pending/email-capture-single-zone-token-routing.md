**Forward/CC capture routes on one zone-level catch-all with an opaque local-part token, resolved firm-first against a control-plane token index — not on a per-firm subdomain.**

**Context:** The forward/CC capture entrance ([`docs/specs/2026-07-14-email-filing-record-and-forward-capture-design.md`](../specs/2026-07-14-email-filing-record-and-forward-capture-design.md)) delivers a forwarded or CC'd message to the `apps/email-worker` Cloudflare Email Worker, which stages the raw MIME and enqueues the capture job. The worker holds no per-firm database handle — firm resolution is a control-plane read. The initial implementation encoded the firm in a subdomain label (`<token>@<firmId>.in.magnacarta.esq`) and resolved it against the control-plane `firm` table. Cloudflare Email Routing, however, supports exactly **one zone-level catch-all rule** per zone — there is no per-subdomain catch-all and no wildcard `*.in.magnacarta.esq` inbound routing — so that address shape could not have been provisioned at all, and it also contradicted the accepted design's own `<token>@in.magnacarta.esq` address form (single subdomain, token in the local part).

**Decision:** (1) **One zone-level catch-all.** A single catch-all rule on `in.magnacarta.esq` sends every inbound capture message to the worker. The firm is **not** in the subdomain. (2) **The local part is the opaque routing token.** An address is `<token>@in.magnacarta.esq`; the whole local part is a server-minted, client-unguessable token. The worker lower-cases it to match the minted form and treats it as opaque — no prefix parsing. (3) **A control-plane `email_capture_route` index maps token→firm.** A new control-plane table keyed by `token` (its natural identity, like `setting` keyed by its key) carries `firm_id`, an `active` flag, and `created_at`/`revoked_at`. The worker resolves a token to its firm with one JOIN to `firm` (carrying the R2 bucket the MIME stages into); an unminted or revoked token does not route and the sender is bounced. (4) **Firm-first, then matter.** The worker resolves only the firm; the token rides to the capture consumer, which — now holding the firm's database handle — resolves it to a candidate matter against that firm's own `email_capture_address` store (a per-matter token proposes its matter; a firm catch-all token lands with no matter). The two-store split keeps the control plane holding only the routing fact (token→firm) and each firm's D1 holding the matter mapping — no cross-firm data in the control plane beyond the routing key.

**Considered & rejected:** the per-firm subdomain (`<firmId>.in.magnacarta.esq`) — unprovisionable, since Email Routing has no per-subdomain catch-all, and it leaks the firm id into the address; denormalizing `bucket_name` onto the route row to save the firm JOIN (the bucket is stable per firm and the JOIN is one indexed read — normalization wins over a staleness risk); a per-matter row in the control plane (the control plane holds only token→firm; the matter mapping stays in the firm's own D1, so no matter identity crosses the tenancy boundary).

**Consequences:** The forward path is now provisionable with a single Email Routing catch-all and aligned with the accepted address form. The `emails:manageCaptureAddresses` mint/rotate route — which writes a token into **both** the control-plane `email_capture_route` index and the per-firm `email_capture_address` store — is the remaining fast-follow; until it ships the index is empty and every capture address bounces (the API entrance is unaffected). Revocation is a single `active` flip on the route row, effective on the next message with no per-firm read. Realizes the parent design's reserved capture-address routing model.
