**Directory role merge sources are platform-declared and role-matched by normalization; ambiguity resolves to nothing with a reason, and the many case is a collection.**

**Context:** A matter records who it is about through `matter_party` links — a Directory entity plus the role it plays. `client.displayName` has always been readable because a matter carries its client on its own row; every other role was reachable only by walking `matter.parties` and reading the role out of each item, which is not a thing a paralegal can write in a pleading caption. The named seam was `opposing.*` / `counsel.*`. Three questions had to be settled before a key could exist: which roles the platform names, how a key finds a link when the stored role is free text, and what happens when the matter has more than one party in the role.

**Decision:**

1. **A closed platform-declared set of roles, not a per-firm derivation.** `opposingParty`, `opposingCounsel`, `guardian`, and `witness` — each a role this repository already models. The tempting alternative is the custom-field pattern: derive an entry per row of the firm's `directory_party_role` catalogue, as `custom.<handle>` entries are derived from `custom_field`. It does not transfer. A custom field binds by a MINTED handle precisely because its name is firm-typed text; a party role has no handle, only the name a firm typed, and "Opposing party (2nd chair)" is neither a token an expression can lex as one atom nor one anybody types from memory. A role a firm uses that no source covers remains reachable through `matter.parties`, whose items carry their role.

2. **The role is the key with the punctuation taken out.** `matter_party.role` is free text — the catalogue is what a screen lists from, not a constraint on the column — so one firm writes `opposing_party`, the next `Opposing Party`, a third `opposing-party`. Both sides are lowercased with every non-alphanumeric character removed, and a link matches when the two agree. Removing the separators rather than normalizing to one is the point: the separator is exactly what two firms recording the same role do not agree on. The consequence is a rule that no two shipped sources may normalize alike, which is a fitness test rather than a matter of care.

3. **Ambiguity resolves to NOTHING, with a reason naming the count.** Two opposing parties means there is no single one to name, so `opposingParty.displayName` is an absence rather than the first link by created-at. Choosing would produce a document that is wrong in a way nobody catches by reading it — the failure mode this whole subsystem is organized against. Zero is an absence too, and the two say which they are, because "the matter links nobody in this role" and "the matter links three" call for opposite repairs.

4. **The many case is the repeat machinery that already exists.** `<role>.all` is an ordinary list-valued dictionary entry with the same item fields, so `{{#each opposingParty.all}}` binds items as `opposingParty.all.displayName` — the same `<collectionKey>.<field>` binding `matter.parties` produces, under the same items-per-repeat bound. Nothing new iterates, and the ambiguity reason names the collection by key so the way out is in the message.

5. **A reason is a new channel on the merge context, and it is not persisted.** `MergeContext.absenceReasons` and `AssemblyAbsence.reason` carry a sentence per unresolvable key, and it reaches the failure text of a condition that could not be worked out. It is deliberately absent from the assembly provenance row and from the assembly-status response: the row's contract is that it records absent KEYS and never what the matter held, and a count of a matter's opposing parties is the matter's data. The sentence is engine-visible today and reaches a person through the authoring and field-list surfaces when those ship; the redacted telemetry carries only an enum-like `cause`, never the sentence.

6. **No new read.** Every role is derived from the one party-collection read the merge context already issues for `matter.parties`. Filtering by role in SQL was considered and rejected in both forms — one narrowed read per role is the same N+1 the batching rule forbids, and a single read with a role `IN` list buys nothing over the collection a repeat already walks whole. A template naming four roles costs exactly what one naming a single role costs.

**Consequences:** The shipped dictionary grows by twelve entries with no migration, no statement change, and no index. The load profile's generator changes (the probe matter's party links now lay down one client, one opposing party, and one opposing counsel, so the measured merge context exercises the resolving path rather than only the ambiguous one), which bumps `GENERATOR_VERSION`. A fifth role is one row in `DIRECTORY_ROLE_SOURCES`. The bare-key condition form `{{#if opposingParty.displayName}}` reads as `has(…)` and therefore answers **no** on an ambiguous matter rather than failing — that is the existing and correct meaning of `has`, and a template that must not silently drop the clause writes a condition that reads the value.
