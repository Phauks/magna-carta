**Firm-user email becomes matter data through one convergent capture pipeline and one record. The capture posture is add-in-led and CASA-free; the forward/CC Email Worker and the authenticated file-to-matter API are the two entrances this slice builds; mailbox sync is the later credentialed tier.**

**Context:** The white paper's _Communications layer_ specified email as outbound + logging only and framed OAuth mailbox sync as "the email integration." The subsystem brainstorm ([`docs/specs/2026-06-16-email-filing-design.md`](../specs/2026-06-16-email-filing-design.md)) reframed the higher-value direction: capturing each firm's *own* email correspondence *into* matters as first-class, thread-aware records — the product is not an email host and never builds webmail or an IMAP server. Three capture mechanisms were weighed against the competitive analysis and the Outlook/Gmail add-in + CASA research: a native add-in "Save & File", forward/CC to a capture address, and full mailbox sync. The load-bearing finding: the add-in "Save & File" UX is both the best experience *and* CASA-free — Outlook reads the open message via `getAsFileAsync` (no CASA exists) and Gmail's `current.message.readonly` is sensitive, not restricted (verification, no CASA audit). CASA only bites at full-mailbox scopes (sync). The email parse core ([`docs/decisions/0173-email-core-parse-engine.md`](0173-email-core-parse-engine.md)) and the inbound upload / quarantine pipeline ([ADR-0081](0081-documents-file-handling-inbound-upload-path.md)) shipped ahead of this, so the parser and the chokepoint are reuse, not new build.

**Decision:** (1) **One convergent pipeline.** Inbound email is a *source on the existing source-agnostic ingest / quarantine chokepoint*, not a parallel path — stage → parse → dedup → stage-onto-matter → staff-accept. Every capture mechanism converges on one `captureEmail` operation in a new `@magna-carta/email-filing` package and produces the same staged record; there is never a second parser or a second data path. (2) **Two entrances now, add-in and sync later.** This slice builds the **forward/CC entrance** (a Cloudflare Email Worker, `apps/email-worker`, resolving a per-matter token address or the firm catch-all to a firm and candidate matter) and the **authenticated API entrance** (`POST /api/v1/matters/{matterId}/emails`, the "file this MIME to matter" endpoint). The forward path is the universal any-client fallback; the API is the shared target the later add-in slice and the manual `.eml`/`.msg` uploader both post to. (3) **Add-in-led, CASA-free posture** — the hero add-in UX and full mailbox sync are later slices; the add-in is client work against this settled server contract, and sync is the CASA-gated credentialed adapter on the integration port system feeding the *same* record and dedup, adding no parallel data path. Front-loading the CASA-free entrances defers the procurement gate. (4) **Staff-accept by default.** Capture lands **staged**; a person confirms onto matter(s). The API entrance, already authenticated to a specific matter with `emails:file`, may stage-and-accept in one step per firm policy; the Email Worker entrance always lands staged. Guardrailed auto-file rules are a fast-follow, gated on the DKIM verdict seam. (5) **Off the hot path** ([ADR-0039](0039-performance-performance-concurrency-model-deliberate-compute.md)) — parse / hash / attachment-extract run on a Queue consumer; the entrances enqueue and return. (6) **The Email Routing ceiling** (~25–40 MiB) bounds the forward path; over it the worker records a `capture_oversize` outcome and does not silently drop — the add-in path handles larger messages later.

**Considered & rejected:** mailbox sync as the first/primary integration (its CASA + Microsoft-verification gate is procurement lead-time, and it reaches the firm nothing the CASA-free entrances don't while the add-in lands the hero UX first); a bespoke inbound-email data path parallel to the file ingest chokepoint (duplicates scanning, hashing, and quarantine, and diverges the two untrusted-bytes pipelines that must stay identical); a TypeScript MIME parser (e.g. PostalMime) for capture with the Rust engine reserved for later (two parsers, two `ParsedMessage` shapes — the email-core engine already serves the Email Inspector and is the one parser); silent auto-file on arrival (the LEAP/Smokeball wrong-matter mass-file failure mode — staff confirm, structurally).

**Consequences:** The add-in slice is pure client work against the `file this MIME to matter` contract and the "already filed" read, both built here. The mailbox-sync slice feeds this record model and dedup with no new data path. Discovery's email-as-evidence stands on this record model. The white paper's _Communications layer_ email section is amended to add the inbound-capture entrances and reconcile the "sync is the integration" framing (sync is the later credentialed tier). **Realizes** the parent design's reserved subsystem-architecture ADR for the forward/API entrances; the add-in and sync entrances extend it in their own slices.
