**Visibility beats refusal for a merge field nobody converted, and the macro strip gets the same consent the merge-field conversion has.**

**Context:** Slice 2·6·1 shipped two registration transforms of the firm's own uploaded document under the consensual-guided-data-conversion posture (ADR-0214), recorded as ADR-0217, and settled each differently: Word merge fields were detected always and converted only on request, with a template that used them **refused** without the opt-in; macros were detected always and **stripped unconditionally**, with the removal reported. Both settlements were defensible on the reasoning recorded at the time, and both were reviewed by the owner on the evening of 2026-08-04 with the built system in front of them. Both were changed.

**Decision (1) — an unconverted merge field is recorded, not refused.** The refusal was guarding a real failure: an unconverted `MERGEFIELD` is not a placeholder, so nothing substitutes it and nothing reports it missing, and the assembled document silently carries whatever text Word last cached in the field. That is the silently-wrong-document failure, and the argument for refusing was that the absence model structurally cannot see it, because there is no placeholder to be absent.

The premise is what changed: the absence model **can** see it, if registration writes it down. So registration now records each construct on the **field manifest** — name, part, occurrences, mapped key, whether that key exists for this firm, and the frozen cached text the field will print — and the template registers. Every later reader then has the fact: the registration response lists it, the field inspector shows it with the words the document will actually print, and an assembly reports the field names in its response and on the `document_assembly` row and completes `succeeded_with_absences`, because a field printing stale text is the same class of "this needs a human before it is filed" as a blank. The frozen text is recorded because a name alone cannot make the statement that matters — an author deciding whether to convert has to see the words their document will print.

The trade is stated plainly: the platform now stores templates that will produce documents with stale text in them. That is worse than a template that was converted and better than the refusal, because a refused template is one **nobody can inspect** — the firm cannot see the field list in context, cannot compare it against the dictionary, and cannot register the document at all while it decides. Refusal removed the failure from the product by removing the template from the product. Recording keeps both, and puts the failure in front of the same model that catches every other hole in an assembled document.

**Decision (2) — the macro strip becomes opt-in, and a macro-bearing upload without it is refused.** The merged behaviour inverted the posture's default deliberately, on the reasoning that the two transforms fail in opposite directions: converting a merge field changes what a document *says* and so needs consent, while removing a macro removes what a document *does* and cannot make it assert anything untrue. That reasoning survives; what does not is the conclusion that it licenses acting unasked. A firm that uploads a `.docm` and gets back a `.docx` whose bytes differ from what it sent has had its document rewritten without being asked, and "the rewrite was only ever a removal" is a reason the rewrite is *safe*, not a reason it needed no consent. Consent parity is the rule; the strip is a transform of the firm's data like any other.

So: detection still always runs and always reports. The strip runs only when the request sets `stripMacros`. And an upload carrying macro content **without** the opt-in is refused — because unlike a merge field, there is no third state worth having. Recording "this template contains live macros" and storing it anyway would mean a package with executable code sitting in the catalogue waiting to be run against privileged client data; there is no manifest entry that makes that safe. The refusal therefore names **both** ways through, so it is a decision rather than a dead end: opt in to the removal, or upload a macro-free copy of the file. The adversarial detection (content-types map and relationship types, never file names), the declaration repair, and the independent re-verification over the bytes that will actually be stored are all unchanged — only the trigger moved.

**Decision (3) — the per-firm field-mapping library is built.** It was a named seam behind `MergeFieldNameResolver`, and decision (1) makes it due: a firm migrating from Word mail merge now registers its templates immediately and sees a list of Word names, most of which mean something the dictionary has under a different spelling. A firm-scoped `document_template_field_mapping` table records each confirmed name-to-key mapping, written in the same commit as the registration whose conversion confirmed it, and read **once** per registration into the resolver — one read, never a lookup per field, the same batching rule the merge context follows. A detection reports whether its key came from the library or from the name matching a dictionary key outright, because those are different facts to put in front of the person deciding. The library is visible and editable per ADR-0214: list and delete routes under `templates:manage`, because a mapping nobody can see is one nobody can correct and it silently steers every later import. Nothing guesses: a name the firm has not confirmed is reported unmapped rather than matched by resemblance.

**Considered & rejected:** *Keeping the refusal and adding the manifest entry only for converted-then-reverted cases* — the manifest entry is what makes registration safe, so gating it behind a state that cannot occur keeps the cost and drops the benefit. *Registering a macro-bearing template with a manifest entry, symmetrically with (1)* — the symmetry is superficial: a recorded merge field renders wrong text a human can catch, a recorded macro is executable code, and no amount of reporting makes storing it acceptable. *Making the assembly of a frozen-field template fail rather than complete with a report* — that is the refusal moved to the point where a user is waiting and the template can no longer be inspected, which is strictly the worse place for it. *Auto-confirming a mapping by resemblance* (`ClientName` → `client.displayName`) — a silent binding decision on privileged content; an unmapped name stays unmapped. *Archiving withdrawn mappings instead of deleting them* — nothing downstream depends on the row (a registered version's bytes and manifest are immutable, and a mapping acts only at the moment of conversion), so a tombstone would preserve nothing and make the library harder to read.

**Consequences:** Amends ADR-0211's two registration behaviours and ADR-0217, which realized them; the placeholder model, the catalogue and version model, and the ingest chokepoint are untouched. A mail-merge migration no longer costs a mandatory round trip — the first registration succeeds and reports — but a firm that ignores the report can now file a document with frozen text in it, which is why the report is repeated at assembly and lands in the outcome rather than only in a warning list. A macro migration now costs the round trip the merge-field path just gave up, which is the price of the consent being a consent. `document_assembly` gains a frozen-field count and name list beside its absent-key columns, on the same terms: names only, never content. The `documentAssembly.frozenMergeField` counter is the drift instrument, dimensioned on the construct's form rather than the field's name, for the same reason a merge-field key is not a dimension.
