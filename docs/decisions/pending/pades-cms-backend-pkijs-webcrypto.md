**The PAdES seal's CMS/PKCS#7 is produced in TypeScript with pkijs over WebCrypto in the Worker; the pure-Rust engine owns the PDF structure and consumes the CMS as an opaque blob.** **Context:** the e-signature core needs a detached CMS (`/SubFilter /ETSI.CAdES.detached`) over the signature's `/ByteRange`, with the firm's signing key. The engine now produces the PDF signature structure in Rust (`pdf-core`: `prepare_signature` writes a prefix-preserving incremental update with an exact `/ByteRange` and a reserved `/Contents`; `signed_bytes` yields the digest input; `embed_signature` splices the CMS in). What remained undecided was where the CMS itself is assembled and signed. Two routes were weighed against the current ecosystem (verified this cycle, golden rule 11). **Decision:** build the CMS in TypeScript with **pkijs 3.4 over WebCrypto**, inside the forthcoming `@magna-carta/signing` package, running in the Worker (or a Container for a future HSM path). (1) **The key stays host-side and non-extractable.** The firm key is a WebCrypto `CryptoKey` in the Worker — never extractable, never on the client — doing only a raw signature over the CMS SignedAttributes digest; this matches the platform's "the seal runs server-side with the firm key" placement and the "thin host signer" framing. (2) **CMS is orthogonal to PDF bytes.** The Rust engine already owns the byte layout end to end and takes the CMS as an opaque reservation, so the CMS producer belongs in the product/host layer, not the engine — no new dependency enters the engine and the two concerns stay cleanly seamed. (3) **pkijs fits the runtime and the roadmap.** It is pure JavaScript on WebCrypto (memory-safe, golden rule 14 — no owner consent needed), Cloudflare Workers implement the full WebCrypto surface it needs (RSASSA-PKCS1-v1_5 / RSA-PSS / ECDSA), it has a maintained detached-CMS path, and it ships the TSP/OCSP/CRL primitives the B-T → B-LT → B-LTA levels will need — unlike `@signpdf` (PAdES-B-B only, node-forge). **Considered & rejected:** the **RustCrypto `cms` crate in the engine** — pure Rust and attractive for "one engine owns everything," but its builder has no first-class external/async-signer hook (keeping the key host-side means hand-assembling `SignerInfo`) and no ESS `signing-certificate-v2` helper, and it buys nothing the opaque-blob seam does not already give us; **`@signpdf`** — kept only as a documented PAdES-B-B fallback (no native LTV path); a **Container-hosted native Rust signer** — deferred to a future HSM/native requirement, since Worker + WebCrypto avoids the extra hop for the common case. **Consequences:** the seal's crypto is a maintained, memory-safe, WebCrypto-native TypeScript component with a clear path to timestamped/LTV levels; the engine stays crypto-free; the firm key never leaves the host or becomes extractable. Costs: a TypeScript PKI dependency (pkijs + asn1js, well under the Workers bundle limit), and PAdES/CAdES conformance must still be confirmed against an **independent validator** (pyHanko / DSS) before onboarding — not just our own parsers. **Proven this cycle:** a workerd (vitest-pool-workers) test builds a detached CMS with signed attributes (contentType, messageDigest, signingTime) over an external byte range, and it verifies and correctly rejects a tampered range. Builds on the pure-Rust PDF engine (which owns the seal structure) and the e-signature product design (ESIGN/UETA workflow, Certificate of Completion, attribution spectrum) that this backend serves.
