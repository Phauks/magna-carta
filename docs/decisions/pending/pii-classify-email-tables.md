**The email-filing record model is classified in the PII/erasure registry with a retain-under-matter action on the message, participant, and matter-link rows, and the participant/sender address string is admitted as a subject key alongside the resolved entity id.**

**Context:** The email filing record model added six per-firm tables. The registry's coverage fitness function forces every per-firm table into one of two halves, so the tables landed unclassified and the check was red. Two of them do not fit the registry's existing shapes cleanly. `email_participant` freezes each from/to/cc/bcc address as-at receipt — the frozen string is deliberately the evidentiary record, not a pointer into a shadow address book — and its `directory_entity_id` is nullable enrichment, resolved through the Directory reverse address lookup only where a match exists. `email_message` denormalizes the sender's display name and address onto the message row with no id column of any kind. Every subject key in the registry until now was an id column (`entity_id`, a `user_id`, a parent row's key) or `self`.

**Decision:** (1) **`email_message` → `from_address`, retain-under-matter.** A captured message is correspondence on the matter file; its retention basis is the matter corpus, and the subject-side scrub happens at the Directory entity, the same discipline `matter_party` follows. The subject line and the verbatim R2 original are content-level residue for the residue report, not structured columns this registry erases. (2) **`email_participant` → two entries, `directory_entity_id` and `address`, both retain-under-matter** — the two-entry idiom `directory_edge` and `custom_field_value` already use for a row reachable by more than one column. (3) **The frozen address string is a legitimate subject key.** The capture core itself resolves an address to an entity through the Directory reverse address lookup, so the orchestrator can gather these rows for a subject by expanding the subject's Directory email addresses. Keying only on `directory_entity_id` would leave exactly the unresolved participants — the people with no Directory record to scrub in the first place — unreachable by erasure. (4) **`email_matter_link` → `linked_by`, retain-under-matter.** Which firm member filed a message to a matter, and when, is the filing's provenance on that matter record, the same treatment `time_entry.timekeeper_user_id` gets as a billing record. (5) **`email_thread`, `email_attachment`, `email_capture_address` → non-PII.** A thread row is a grouping key plus a normalized-subject fallback (a subject line is message content, as `matter.description` is a business record); an attachment row is a link to a File Manager document whose matter-corpus retention is expressed by the `file` entry, mirroring `file_version`; a capture address is a firm-owned, server-minted opaque routing token — not a person's mailbox — whose `created_by` is administrative provenance on a configuration row, current state rather than an activity record about the member, the line `integration_connection` and `scoped_setting` already sit on.

**Considered & rejected:** classifying `email_message` non-PII on the grounds that the sender is also recorded in `email_participant` (the row literally stores the sender's name and address; a denormalized copy is still personal data that must be scrubbed); registering `email_participant` on `directory_entity_id` alone (silently drops every unresolved participant, the exact population with the weakest Directory footprint); `pseudonymize-keep` for `email_matter_link.linked_by` (the row is mutable — unlink flips state — and the retention question is a matter-record question, not an append-only-log question); `email_capture_address` as PII on `created_by` (that would make every administrator-stamped configuration row an activity record and erase the line the registry draws at `integration_connection`).

**Consequences:** The registry now carries value-keyed subject keys as well as id-keyed ones, which the deferred `eraseDataSubject` orchestrator must handle: gathering rows for a subject means expanding the subject's known email addresses, not only traversing id references. That expansion is address-matching over data the firm holds, so it inherits the reverse lookup's normalization rules and its false-positive profile (a shared or role address matches more than one person) — a reason these rows are retained and reported rather than auto-erased. Realizes the classification half of the erasure seam for the email subsystem; nothing about the erasure action set or the fitness function changes.
