**A protected merge field is the existing decrypt path with a document on the end of it — not a second way to read an encrypted column.**

**Context:** Document assembly shipped with a `sensitivity` axis on every dictionary entry and no entry using it, deliberately: an entry marked `protected` without a route through the protected-field chokepoint would have been a silent downgrade of the invariant rather than an implementation of it. The values a legal document actually needs — a client's tax identifier on a retainer, a date of birth on an affidavit — are exactly the values the platform seals, and the firms asking for them are asking for them in documents. What made this worth care is that assembly is asynchronous: the job runs after the request that submitted it, in a queue consumer with no session, and the naive wiring either carries a decided permission answer on the message (an unexpiring grant travelling through a queue) or skips the gate because there is no session to gate.

**Decision:**

1. **One read path, and it is the chokepoint's.** Resolution holds no ciphertext column name, derives no key, and decrypts nothing. It takes an injected reader — wired at the composition root to the directory's `readIdentifier`, which is `readProtected`: permission gate, audit row committed before any plaintext, AAD-bound decrypt, inseparable and in that order. The refusal the resolver turns into an absence is the chokepoint's own `ProtectedReadForbiddenError`, caught by identity rather than re-derived from a permission set, so there is no second copy of the rule that decides who may read a client's sealed details.

2. **No assembly-specific audit reason code.** A decrypt performed to fill a merge field writes the same `protected.decrypt` row, with the same subject (the identifier row the AAD binds the ciphertext to), the same field identity in its metadata, and the acting member as actor. The conservative reading was taken deliberately: what a firm asks after the fact is who saw this value and when, and an answer split across two record shapes by the reason it was read is a worse answer, not a richer one. If assembly context turns out to be worth recording, the way to record it is a field on the one composition, never a second event.

3. **Refusal is a declared absence.** The assembly completes, the document carries the visible marker the absence model already produces, and the reason names the field and the permission the member would need. The alternatives were both refused: aborting makes one unreadable detail cost the whole document, and a silent blank files a document that reads as complete. The reason names the field and the permission and nothing else — never a value, and never anything about it.

4. **Permissions are re-derived at consume time.** The queue message carries the requesting member's identity; the firm's database supplies what that identity may do, read when the first protected key is reached. A permission revoked between submit and consume therefore bites. A job with no requesting member decrypts nothing — there is no principal to gate, and "nobody" cannot hold a permission.

5. **The decrypt count is bounded, not batched.** Each sealed value is bound to its own row by its AAD and commits its own audit record, so there is no batch form of the chokepoint to reach for and inventing one would mean bypassing it. The ceiling is instead fixed by the template: one decrypt per protected key the manifest names, deduplicated before any value is touched, and a refusal costs exactly one attempt because the permission guarding one sealed identifier guards them all. The row read the subject is identified from is the party read the merge context already issues.

6. **The subject is the matter's single client, and ambiguity decrypts nothing.** A matter linking no client, or more than one, resolves every protected key to an absence whose reason names the count — the same answer the ambiguous-role sources give, for the same reason: a document stating the wrong person's tax identifier is wrong in a way nobody catches by reading it. Other parties' sealed identifiers are not bound at all; that is a wider disclosure surface than a document has been asked for.

7. **Registration is unrestricted; the field list marks the field.** Binding a protected field names a key, not a value, so a template registers whatever the registrant may decrypt. Both field-list surfaces now carry the entry's sensitivity, which is what lets an authoring surface say what has been bound before anything is assembled.

**Consequences:** The protected merge sources are the Directory identifier types, because those are the values the platform holds encrypted today. A protected CUSTOM field — a firm declaring one of its own fields sealed — is a separate decision: it needs a column on `custom_field` and a ciphertext column on `custom_field_value` that do not exist, and the derivation in `custom-field-bindings.ts` is the one line that would read the declaration once they do. The keys are a total mapping over the identifier catalogue, so a type the Directory gains cannot quietly acquire no merge binding. `@magna-carta/document-assembly` gains two allowed externals — the chokepoint module whose refusal it catches, and the identifier-type catalogue — each recorded in its purity fitness function with the reason.
