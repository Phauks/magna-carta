**Communications** — **The email parse core is a pure-Rust engine on the engine-host seam; it parses only, and rendering plus DKIM verification live outside it.**

**Context:** Nothing in the codebase can read an email. The upload policy accepts `message/rfc822` and `application/vnd.ms-outlook`, and the conversion registry declares `eml→pdf` and `msg→pdf` edges, but no MIME parser exists in the workspace and the `email` conversion engine is an unimplemented stub. An uploaded `.eml` is stored as an inert blob. Meanwhile the draft email-filing design assumes **PostalMime** (TypeScript) parses the forward/CC path in a Cloudflare Email Worker — a choice that would leave bulk mbox parsing, `.msg` MAPI decoding, and the desktop shell needing a second, Rust implementation later.

**Decision:** Build **`crates/email-core`** as the third engine on the [engine-host seam](../conventions/engine-host-seam.md), after `pdf-core` and `decryption-core`. It is I/O-free and serde-free — bytes in, a `ParsedMessage` record out — reading `.eml` (RFC 5322/MIME via `mail-parser`), `.msg` (CFB/MAPI via `msg_parser` over the already-pinned `cfb` crate), and mbox (a framing iterator over the `.eml` lane). It compiles twice: WASM as the default Worker lane, native as the heavy Container lane, making placement a routing decision rather than a rewrite. Every dependency is pure Rust and the `r2` feature stays off, so the crate carries no C in its closure and needs no golden-rule-14 consent.

The core is **parse-only**. Rendering (`email→pdf`) and DKIM signature verification are consumers standing on it, not parts of it: the record captures `DKIM-Signature`, `Authentication-Results`, and the `Received` chain **verbatim with no verdict attached**, following the scan engine's "raw facts in the engine, the verdict in the app" rule. This keeps a crypto dependency out of a parsing engine and keeps the WASM edge light.

Two shapes in the record are load-bearing. **Extraction is two-phase** — `parse` returns part descriptors carrying byte ranges, and `extract_part` materializes one part on demand — so a Worker never holds an mbox's whole attachment set in an isolate and Discovery never pays for payload bytes it discards. And **`message_id` records its provenance** (`from_header` / `from_mapi` / `absent`) rather than flattening to a string, because a `.msg` carries RFC 5322 headers only when `PidTagTransportMessageHeaders` survived — so for `.msg` sources the capture design's content-hash dedup fallback is the common case, not the exception, and a synthesized identifier must never be mistaken for the real one.

This **supersedes the PostalMime assumption** in the draft email-filing design: the Email Worker calls `email-core` through its WASM edge. Taken now because the capture spec is still Draft and the override costs a paragraph; taken later it would cost a migration.

**Considered & rejected:** a **TypeScript `@magna-carta/email` package** (postal-mime + a JS CFB reader) — fastest to a working `.eml` path and consistent with the existing spec, but `.msg` MAPI decoding is materially weaker in TypeScript, bulk mbox parsing on the isolate is the hot-path work golden rule 10 forbids, and Discovery plus the desktop shell would force a second Rust implementation regardless, yielding two parsers and two records. A **hybrid** (TypeScript MIME on the Worker path, Rust for `.msg`/mbox in a Container) — the path of least resistance from today's spec, rejected because it institutionalizes exactly that divergence while the seam already delivers dual-target hosting without it.

**Consequences:** One parser and one output record serve capture, file upload, conversion, metadata, and Discovery. The conversion registry's `eml→pdf` / `msg→pdf` edges **stay unimplemented** after this work — closing them is a render slice. `.msg` files whose only body is RTF yield no text body until that renderer exists. `msg_parser` is the one dependency taking untrusted bytes whose maturity is unestablished; it is audited before adoption, with direct MAPI stream reading over `cfb` as the fallback.
