**Bates stamping is implemented as an additive text overlay using base-14 Helvetica with rotation-aware corner placement, non-destructive resource merge, and continuous set numbering; single-PDF merge and from-scratch page generation are explicitly deferred.**

**Context:** Legal productions, discovery sets, and court filings require Bates numbering — a sequential identifying label on every page of every document — to create an unambiguous page reference across potentially thousands of files spanning multiple parties. The label must be visible, selectable, and consistent regardless of the viewer or printing system used.

**Decision — additive overlay, not redaction.** The stamp is a new PDF content stream appended last on each page, so it renders on top of existing content. No existing text, images, vector graphics, XObjects, annotations, or metadata are modified or removed. The caller receives the same document with one additional content stream per page and one additional font resource per document. This is architecturally distinct from the redaction path (`redact`), which intentionally destroys content; the two operations must never be conflated.

**Base-14 Helvetica — no font embedding needed.** The label is rendered in Helvetica, one of the fourteen fonts guaranteed to be present in every conforming PDF viewer without embedding. This means the stamp font dictionary is a three-key reference (`/Type /Font /Subtype /Type1 /BaseFont /Helvetica`) — no font file, no subsetting, no ToUnicode mapping. The document grows by only one such dictionary regardless of page count. Glyph advance widths are computed from the built-in Helvetica metrics table in `crates/pdf-core/src/standard_fonts_data.rs`, giving exact label-width measurements for placement without touching the font file.

**Non-destructive resource merge.** Each stamped page needs the stamp font in its effective `/Resources /Font` dictionary. Rather than overwriting the page's existing resources, the engine resolves the page's current effective resource dictionary (including resources inherited from ancestor `/Pages` nodes), clones the `/Font` subdictionary, adds the stamp font reference under the name `MagnaCartaBates`, and writes the merged dictionary back onto the page dict. This ensures no existing font resource is dropped and no page that relied on inherited resources loses its fonts.

**Rotation-aware corner placement.** PDF pages may carry a `/Rotate` entry (0, 90, 180, or 270 degrees) that viewers apply before display. The engine resolves the effective rotation and computes a text matrix (`Tm`) that counter-rotates the glyph direction so the label reads upright in the displayed frame, and maps the requested corner of the displayed page back into unrotated user space. Placement is computed in the displayed frame (swapping width and height for quarter-turn rotations), then transformed into the coordinate system the PDF content stream expects.

**Continuous set numbering.** `stamp_document` accepts a `start` counter and returns a `BatesRange` (`start`, `end`, `page_count`). Callers stamp a set of documents by threading `end + 1` of one document as the `start` of the next. `stamp_set` encapsulates this loop for the single-call case. The `BatesOptions.start_number` field seeds the range for a standalone call; for a set, the caller controls threading.

**Deferred — single-PDF merge and from-scratch page generation.** Merging multiple PDFs into one before stamping (so the Bates range spans a single output file) requires a PDF writer that can concatenate page trees from multiple input documents. Similarly, adding a blank separator page between documents requires generating a new page from scratch. Neither is part of this version: the deferred operations would require a PDF-writer dependency not yet present in `crates/pdf-core`, and the per-document call-and-thread pattern covers all current production use cases without it. This decision is revisited if the safe-delivery sandbox or a court-filing export feature requires merged output.

**Consequences.** Each stamped page gains one appended content stream (the label) and the page's resource dictionary is expanded to include `MagnaCartaBates`. A multi-page document gains exactly one font object. Output size growth is proportional to label text length and page count, not to page content complexity. The stamp is selectable text: a PDF reader's copy-and-paste picks up the label. The label cannot be removed by extracting page content streams because it is not embedded in the original streams; it is a separate stream appended to the page's `/Contents` array. Overwriting a page's content streams with a new version (as the redaction path does) would remove the stamp, which is the correct behavior for a workflow that stamps then redacts.
