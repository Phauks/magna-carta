**Cloudflare Flagship as the feature-flag engine.** The release-channel system needs a flag engine that can target flags to cohorts, ramp gradually with consistent hashing, track audit history, and support typed variants — all without an outbound HTTP call on the request hot path. Flagship delivers these natively as a Worker binding (`env.FLAGS`), evaluating against KV and Durable Objects in-process with no egress, which is the right shape for the performance model in _Performance and concurrency model_ (no heavy work on the hot path).

**The `@magna-carta/feature-flags` wrapper.** Rather than scattering Flagship calls across the codebase, a thin package wraps the native binding behind a minimal typed interface (`getBooleanValue(flagKey, default, context)` and typed siblings). The wrapper is not a swappable-provider abstraction — the firm has committed to Flagship and cross-provider portability is a non-goal — but it still earns its keep: it centralizes evaluation-context construction and safe-default enforcement in one place, and it lets tests substitute a `defaultOffEvaluator` (all flags off) or a `recordingEvaluator` (in-memory overrides) without a live binding. Tests that need specific flag values inject a `FlagEvaluator` fake; no mocking library required.

**Flag catalog.** All feature flags are declared in a `FLAG_CATALOG` export from `@magna-carta/feature-flags`. Each catalog entry carries a `stage` field (`alpha | beta | stable`), which is the enabling metadata for the in-app stage-labeled alpha/beta visibility markers (the UI treatment is deferred to the frontend release-channels slice; the metadata is a backend rails concern).

**Evaluation context.** The context sent to Flagship is built from non-privileged session fields: `{ firmId, channel, role, userId }`. No client content, matter data, or privileged identifiers travel to the flag provider. This is consistent with Flagship's own guidance on evaluation context and with the confidentiality model in _Tenancy and data isolation_.

**Fail-safe defaults — the invariant.** Every call to `getBooleanValue` (and its typed siblings) supplies a default equal to the stable-behavior value (feature off). If Flagship is unreachable, the binding is absent (local Miniflare: the optional binding shape means no error, just the default), or a flag key is not in the dashboard, the default wins. A flag service outage is invisible to users — they see stable behavior. This is both a correctness property and a security property: no outage can accidentally activate unfinished code for a firm that did not opt in.

**Local Miniflare note.** The `env.FLAGS` binding requires a production deploy-time wiring step (the Flagship account binding in `wrangler.jsonc`). The local Miniflare test pool does not support the Flagship binding shape; the optional binding declaration in `wrangler.jsonc` means the binding is `undefined` in tests, and `resolveFlagEvaluator` falls back to the `defaultOffEvaluator` (all flags off, the stable default) automatically. No test setup is needed for flag-safe paths; a test that needs a specific flag on injects a `FlagEvaluator` fake.

**Considered and rejected.** An in-house feature-flag engine from scratch — rejected: targeting, gradual rollout, audit history, and a management dashboard are real work that Flagship delivers natively. An OpenFeature SDK layer over Flagship — rejected: cross-provider portability is a non-goal, and the SDK layer adds indirection without benefit given the firm has committed to Flagship. A Cloudflare Worker-level experiment (gradual percent rollout via `wrangler versions`) — rejected: percentage-based and not cohort-pinned; cannot express "all firms in channel beta see this flag" without a custom targeting layer that duplicates what Flagship already does. Relates to _Release channels_ (white paper) and the firm's Cloudflare Workers deployment model in _Delivery model_.
