---

**Converting a firm's uploaded template is a change to the firm's document, so the product asks; removing code from one is a safety act, so the product acts and says so.**

**Context:** Registering a `.docx` template can require changing it. Two transforms came up in slice 2·6·1. A firm migrating from Word mail merge has templates built from `MERGEFIELD` field constructs, which this engine does not fill in — they would render Word's cached result text, frozen at whatever it was when the template was authored. A firm migrating from an older practice system has macro-bearing templates, which carry executable code into a system that runs templates against privileged client data. The original design recommended converting merge fields automatically and refusing macro templates outright. Both defaults were reconsidered against one principle: **when data conversion into our system takes place or may take place, the product owes the user input, guidance, and feedback.** Silent rewriting of a firm's own document is the failure mode to avoid — a firm should never discover that the template it uploaded is not the template we stored.

**Decision:** (1) **Detection is unconditional; conversion is opt-in.** The registration pass always finds every Word merge field and reports each one — the field name as Word recorded it, how many times it appears, which document part it sits in, the merge-field key it would map to, and whether that key is a field this firm actually has. The rewrite happens only when the registration request sets `convertMergeFields`, whose contract description states plainly what conversion does and that the document registered will not be the document uploaded. (2) **Without the opt-in, a template that uses merge fields is REFUSED, not registered.** The alternative — registering it with those fields inert — was rejected: an unconverted merge field is invisible to the assembly engine, so the assembled document would carry stale cached text and look finished. That is precisely the silently-wrong-document failure the absence model exists to prevent, and the absence model cannot see it because there is no placeholder to be absent. The refusal is a `template-normalization-failed` problem carrying the full field list, so the caller presents a choice (convert, or edit in Word) rather than a dead end. (3) **Macro-bearing templates are accepted and stripped, under the same feedback rule.** A firm migrating in has these and will ask; refusing outright makes the platform the obstacle. The VBA project, its content-type declarations, and its relationships are removed, the macro-enabled main-document declaration is demoted to its macro-free equivalent, and the count of removed parts is reported on the registration response. Detection is driven by the content-types map and the relationship types, not by file name — a project parked at `word/embeddings/printerSettings.bin` is exactly as macro-bearing as one at the conventional name. (4) **The stripped package is re-verified independently before it can register.** A second, separate scan runs over the bytes that will actually be stored, after the metadata scrub, and any residue refuses the registration: the stripper asserting its own success is the failure mode the gate exists to catch. (5) **The Word-name-to-key mapping is an injectable resolver**, the identity mapping today.

**Considered & rejected:** *Automatic conversion (the design's original recommendation)* — cheapest to build and the most convenient happy path, but it changes a firm's document without telling them, and an author who later opens the registered template finds their field codes gone. *Registering a merge-field template with the fields left inert* — the softest option and the most dangerous, for the reason in (2). *Refusing macro templates outright (the design's original recommendation)* — defensible on security grounds but not on migration grounds: the firm's answer is to strip the macros by hand and re-upload, which is the same outcome with more work and no record of what was removed. *Guessing a mapping for an unrecognized field name* — a `ClientName` that becomes `client.displayName` because it looked close is a silent binding decision on privileged content; the resolver maps by exact confirmation or not at all, and an unmapped name is reported as one.

**Consequences:** A firm always knows what its uploaded template contained and what happened to it: fields found, fields converted, macro parts removed. The merge-field opt-in costs a round trip for a mail-merge migration — the first registration reports, the second converts — which is the deliberate price of the decision being a decision. The identity resolver means a firm whose Word fields are not named the way the dictionary is gets a full list of unmapped names rather than a working template, which is honest but is also the shape that makes the follow-on obvious: **a per-firm field-mapping library** — a firm-scoped store of confirmed name-to-key mappings that accumulates as an administrator confirms them, so a second template import reuses what the first established. That store is a named seam here, not built: it plugs into the resolver and nothing downstream changes, because everything past the conversion pass already works in dictionary keys. Refines the placeholder-form half of the template-model decision (ADR-0211), which recorded conversion as automatic.
