**Settings precedence — first realization.** The white paper (_Settings → Scope & resolution_) describes a precedence chain — entity (matter/client) → user → location → firm → system — but no resolver exists: the `setting` seam (`packages/data-access/src/setting-statements.ts`) resolves a single firm-level row (`SELECT value … WHERE key = ?`) with no scope dimension, and its own header calls it "the storage seam a full settings framework will later formalize." Slice 3·1 needs scoped resolution for its increment/rounding settings — not as gold-plating but because the white paper's *own* "increments are firm default with **per-client/per-matter override**" (and the owner's per-timekeeper extension, 2026-06-22) cannot be expressed by the flat seam. The 3·1 spec's adversarial review surfaced that the spec had wrongly claimed this as "reuse." **Decision:** 3·1 lands a minimal **`scoped_setting`** table `(key, scope_tier, scoped_id, value, updated_at)` (`scope_tier` ∈ matter/client/user/location/firm; firm rows have null `scoped_id`; system defaults stay in code) and **`resolveScopedSetting`** walking most-specific-first, in `@magna-carta/data-access`. A firm that sets only the firm-level value behaves exactly like the flat seam. **Considered & rejected:** *descope to firm-only rounding for 3·1* (rejected by the owner, who wants per-timekeeper rounding — a real differentiator vs PracticePanther); *build a full general settings framework now* (deferred — build only the tiers time needs, generalize on the second consumer, the promote-on-second-consumer rule). **Consequences:** cheap-from-the-getgo (ADR-0078); the flat `setting` seam stays for firm-level-only knobs; later settings (theme, etc.) reuse the resolver; the `scoped_setting` migration is coordinated like the shared migration slot.
