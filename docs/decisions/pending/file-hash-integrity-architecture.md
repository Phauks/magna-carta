**File Hash & Integrity tool architecture.** The tool computes cryptographic digests and verifies file integrity. The key architectural choices:

**(1) Pure streaming multi-digest core — one read, five digests.** The `hashAll` function in `@magna-carta/file-integrity` fans every chunk from one `ReadableStream<Uint8Array>` into one `DigestSink` per algorithm simultaneously. A single pass over the bytes produces MD5, SHA-1, SHA-256, SHA-384, and SHA-512 together. Buffering nothing beyond the current chunk means memory cost is O(chunk) not O(file). The digest backend is injected (`CreateDigestSink`) so the package is pure and node-testable; the Worker backs it with `crypto.DigestStream` and the tests back it with `node:crypto`.

**(2) Server-side compute on every surface.** Hashing runs in the Cloudflare Worker on every call — for the `hash` route over the streamed request body, and for the `verify` route over the bytes read from R2. Server-side computation is necessary for forensic attestability: the server observes the bytes and signs the result with a chain-of-custody audit row, so the digest is not merely what the client claims. MD5 and SHA-1 are retained for eDiscovery and legacy interoperability (load files and opposing-party tooling still specify them) and are explicitly labelled legacy-interop, not security-grade, in the metadata and receipt.

**(3) Verification against the ingest baseline, recorded to audit_log.** The `verify` route reads the file's current clean version from D1 via `readCurrentVersionForIntegrityBaseline` in `@magna-carta/file-manager`, re-fetches the bytes from R2, computes all five digests, and compares the computed SHA-256 against the `content_sha256` stored at ingest. The outcome (`match` / `mismatch` / `no-baseline`) is written as a `file.integrity_verified` audit row and returned with the full digest set and a downloadable hash receipt. This makes every verification a permanent chain-of-custody record — the same model used throughout the audit subsystem.

**(4) New "file" context tag.** The `file` context tag is added to `@magna-carta/tools`, making the File Hash & Integrity tool the first per-file contextual action — a tool surface that appears in the context of a specific file, not just in the Tools sidebar. This establishes the pattern for future per-file tools.

**Deferred seams (measured-trigger, not built).**

- **Async large-file verify via Container.** The verify route streams bytes through the Worker for files under the Worker's request-body size cap. For files above that cap, a Container-backed async verify path is the named seam — built when large-file verification is measured to be needed.
- **Client-side standalone hashing.** A client-side WASM or WebCrypto path for hashing a local file before upload — a pure UX improvement that does not replace server-side attestation. Deferred until the UI shell (slice 0·7a) provides the surface to build on.
- **Signed/PDF receipts.** The receipt is currently a plain-text attestation block. A cryptographically signed receipt (using the slice 1·2 signing seam) or a PDF receipt (using the PDF engine) are named future evolutions, deferred to when downstream consumers (Discovery production, e-signature) make them necessary.

**Considered and rejected.** Client-only hashing without server attestation — rejected because it cannot produce a chain-of-custody record (the server cannot attest to bytes it did not observe). Storing each digest in D1 as a permanent record — rejected because the ingest-baseline SHA-256 already exists on `file_version.content_sha256`; duplicating it into a separate integrity table adds a sync surface with no benefit. Per-algorithm parallelism — rejected in favour of the fan-into-one-read pattern; the chunk fan-out achieves all five digests in one I/O pass, which is the bottleneck.

**Consequences.** Every file integrity verification is a permanent audit-log entry — the system knows who verified what, when, and what the outcome was, without storing the file's content or name in the log. The pure `@magna-carta/file-integrity` package is independently testable in the node pool and re-usable by any future consumer (Discovery production Bates-and-hash, the file export pipeline). The `file` context tag establishes a new class of contextual Tools actions that surface alongside a specific file in the UI.

**Adversarial review (six independent angles: tenancy, redaction, integrity semantics, streaming core, resource exhaustion, migration/merge).** Tenancy holds (firm-scoped database + server-resolved R2 key + parameter-bound branded `fileId`; no cross-firm read, no permission bypass, no version-steering); redaction holds (audit metadata and receipt carry only ids/digests/sizes/timestamps; `file.name` is null on verify; the R2 key is ids-only); integrity semantics are sound (no false match/mismatch; the audit row is written exactly once, unconditionally); the streaming core is correct; the migration/merge resolution is consistent. One Important finding was fixed: a clean `file_version` may carry a null `size_bytes` (no `NOT NULL` constraint, not tied to `status='clean'`), so the verify route now **refuses** a null-size version (404) rather than skipping the size cap — closing an uncapped-R2-read vector. The streaming core now also aborts its digest sinks on a mid-stream error.

**Known limitations & forward dependencies (accepted for v1).**

- **The broad role grant is safe only under the current firm-level read model.** Migration `0022` grants `tools:fileIntegrity` to every default role; this exposes strictly less than the existing `permission: null` file reads (`files.download`/`files.versions` already return bytes and `content_sha256` to any firm member). If a real `files:read` capability or matter-level ethical wall is ever introduced, the `verify` route becomes a firm-scope digest+size oracle that bypasses that wall — so whoever builds matter-level access must revisit this grant set **and** add a handler/query-level matter gate to `verify`.
- **Verify does not gate on `scan_verdict`.** It will hash an infected-flagged current version and return its digests (no bytes are delivered to the client, so this is not malware delivery — and verifying a quarantined file's hash against its flagged baseline is arguably desirable). Left ungated deliberately; revisit if a policy reason emerges.
- **Audit rows duplicate on client retry.** The route's idempotency is `optional`, so a network retry writes a second (individually truthful) `file.integrity_verified` row. Accepted as an append-only "a verification ran" log; switch to `idempotency: "required"` if single-entry-per-action is later wanted.
- **Late-failing verifications are not recorded.** A 413 (oversize) or a 404 (R2 bytes missing — e.g. a tamper that deletes the object) returns before any audit row is written, leaving no trace that a verify was attempted. Recording an attempt row for the bytes-unavailable case is a forensic-completeness follow-up.
- **Defense-in-depth on metadata logging.** `refuseUnredactedMetadata` only refuses keys containing "password", and the telemetry message scrubber does not cover filenames or R2 keys. Today nothing privileged reaches either path, but a future edit that added a filename to the audit metadata or an error message would not be caught by the guard — call-site discipline is the real defense.
- **Content-Length cap bypass on the `hash` route.** A spoofed/absent Content-Length skips the pre-check; this is a CPU-only consideration (the streaming digest never buffers) bounded by the Worker CPU limit and the route rate limit — identical to the established `scan-diagnose` stance, to be tightened in both routes together if ever.
