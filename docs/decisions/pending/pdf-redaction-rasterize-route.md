**PDF redaction uses rasterize-and-reassemble — render the page to a pixel image, burn the redaction region onto that image, replace the original page content with the image — rather than content-stream surgery, and enforces a hard verification gate that fails closed on any text-extraction anomaly.**

**Context:** Redacting a PDF page requires permanently removing the underlying content (text, vector graphics, embedded objects) so that it cannot be recovered — whether by copying, searching, or inspecting the raw bytes. Two broad implementation strategies exist: (1) content-stream surgery, which parses the page's PDF operators and removes or replaces only the operators that draw within the redacted region; (2) rasterize-and-reassemble, which renders the entire page to a pixel image, paints the redaction over the image, then replaces the page's content stream and resource dictionary entirely with the image. Content-stream surgery is more complex to implement correctly because it must handle every operator type, every font encoding, and every resource reference without accidentally preserving a reference to the removed content; any gap is a silent data-survival bug. Rasterize-and-reassemble eliminates that surface: the original operators are gone by construction.

**Decision:** Use rasterize-and-reassemble as the sole redaction path. The page is rendered via the hayro render pipeline to an RGBA pixel buffer at the configured DPI (default 300). The redaction region (expressed in rendered display-space pixels) is painted with the configured fill colour (default black). The resulting image is compressed with FlateDecode and written as a new image XObject; the page's content stream is replaced with a single `Do` operator referencing that XObject; all other resource entries (fonts, form XObjects, annotations) are removed from the page dictionary. lopdf then serialises the document with orphaned objects pruned so that the original bytes do not survive in unused cross-reference entries.

**Verification gate:** After reassembly, the implementation calls a hard gate before returning the output PDF. The gate extracts text from the output using lopdf's text-extraction path and fails closed if: (1) the extract itself returns an error (structural anomaly — treat as unknown survival, not a pass); (2) any of the caller-supplied `redacted_text` strings appear in the extracted text; (3) any of those strings appear as a raw byte subsequence in the emitted PDF bytes. A gate failure is a hard error (`RedactError::GateFailed`) — the function never returns an output PDF in that case. This makes the redaction operation fail-loud rather than silently deliver a document with surviving content.

**Text-position surgery deferred:** Fine-grained content-stream surgery (removing only the individual text-drawing operators whose glyphs fall within the redacted region, leaving the rest of the page's text and vector content intact as PDF operators) is a useful future capability — it preserves searchability for unredacted text and avoids degrading the whole page to a raster. That capability requires a complete PDF text-position primitive (glyph-to-display-space mapping, font encoding table, operator sequencer) which is not built yet. It is explicitly deferred to the slice that introduces that primitive. Until then, rasterize-and-reassemble is the only supported mode; it is correct-by-construction and passes the hard gate.

**Consequences:** Every redacted page becomes a raster image, which means the redacted output loses searchability for any text on that page (not only the redacted region). This is acceptable for the safe-delivery use-case (a locked-down viewer rendition) and for legal redaction (where a raster rendition is often preferred precisely because it prevents text extraction). The DPI parameter lets callers trade file size against image quality; 300 DPI is chosen as the default because it exceeds typical court-filing requirements without producing unreasonably large files. The hard gate adds a small but bounded cost (one round-trip through the text extractor) on every call; this cost is preferable to a silent correctness failure.
