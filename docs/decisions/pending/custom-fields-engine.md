**Custom-fields engine realization (slice 1·4): the shared typed-EAV engine `@magna-carta/custom-fields` serving both the matter-type axis (1·1) and the entity-category axis (1·3), on three per-firm tables — `custom_field` definitions (a stable `customField_` handle PK + a _separate mutable_ `name` label; the twelve-kind catalog as a CHECK; `target` matter|entity; nullable `attachment_id` to a matter-type/entity-category with null=all; `required`/`archived`/`converting`/`position`/`number_scale` + a reserved `template_field_key`), `picklist_option` (handle-keyed child, renamable/archivable), and `custom_field_value` (five typed columns `value_text`/`value_number` integer-minor per ADR-0061/`value_date`/`value_option_id`/`value_reference_id`, an exactly-one-non-null CHECK, and append-and-flip temporal history under a partial `UNIQUE(target_row_id, field_id) WHERE is_current=1`). Identity is the handle, never the label — values, picks, the 2·6 document-automation merge binding, and future reporting/search all bind by handle, so a rename is a one-column UPDATE with zero cascade. Value history is full-temporal (the directory `name-history` append-and-flip); audit is split — who/when in `audit_log`, what-it-was in the value rows — because golden rule 4 keeps `audit_log.metadata` null and a field value can be privileged content. Reference-kind values are real indexed handles (never JSON); 1·4 extends the directory merge (ADR-0086) by adding two `REPOINT_TARGETS` entries (+ matching `fitness.ts` probes) that name `custom_field_value` by string — the table lives in `@magna-carta/database`, so `@magna-carta/directory` imports nothing from `@magna-carta/custom-fields` (sibling packages, no cycle) — plus one new per-target `onCollision` mode (`archive-to-history` for content-bearing custom values vs the existing `delete` for content-less links), giving field-level survivorship on entity merge.** **Context:** ADR-0087 promoted the engine to slice 1·4 and settled the typed-EAV _shape_ in the 1·3 spec §9.3 but deferred field _identity_, the merge-extension mechanism, and value history to this slice. The codebase already answered the owner's rename-cascade concern: every directory entity uses an immutable `newIdentifier` handle + a mutable label with all references by handle (`categories.ts`/`merge.ts`/`name-history.ts`), so custom fields follow that proven pattern. **Considered & rejected:** identifying a field by its mutable name or a (target,name) tuple (renames cascade into stored values, automation, reports — the exact failure the owner flagged); JSON-column value storage (breaks merge relink + field-level audit/temporal history — the §9.3 platform invariants, re-affirmed); storing old values in `audit_log.metadata` for history (violates redact-by-default — privileged content in the observability pillar; history belongs in firm business data); a boolean or per-kind extra value column (the five typed columns cover all twelve kinds — checkbox rides `value_number` 0/1); overwrite-in-place values with an audit-only trail (loses the prior _value_ the owner needs, and which is what makes retype safe). **Consequences:** the rename-cascade and automation-coupling risks are closed by construction; reference values stay whole through merge with no dangling pointers (CI-guarded); the document-automation handle→definition resolve contract is fixed for 2·6; the load harness gains a custom-fields volume profile (accretion rule). Realizes the §9.3 seed; builds on **ADR-0087** (promotion + seed), **ADR-0085/0086** (directory model + non-destructive merge/relink), **ADR-0061** (integer-minor, no floats), **ADR-0062** (handles), **ADR-0071** (package seam), **ADR-0084** (protected-field reuse for sensitive custom fields), **ADR-0003** (per-firm isolation).
