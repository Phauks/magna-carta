**The bad-redaction detector uses a shared observing-Device text-position primitive and a high-recall divergence model (extractable ∧ not-visible) covering all seven categories; no detectors are deferred.**

**Context:** Detecting bad redactions in a PDF requires comparing two views of the same document: what a text extractor can recover and what a renderer actually draws. Where those two views diverge — content is extractable but not visible — there is a potential bad redaction. Two families of detector arise from this: geometric detectors that work over a rendered page observation (where glyphs landed, what paint-order covers them) and structural detectors that work over the object model (metadata surfaces, unreachable objects). Both families share a common need: a lightweight primitive that observes a page — recording glyph positions, text, render modes, and opaque covers — without committing to a full rendering pipeline or imposing a cost on the redaction path.

**The observing-Device primitive:** The `textpos` module provides a rendering Device (`PageObservation`) that records, for each glyph, its bounding box in device space, its paint order, its text content, whether it is invisible (text rendering mode 3), and its RGBA colour at draw time. It also records `CoverMark` — opaque rectangular fills, with the same paint order and colour tracking. This primitive is read-only and stateless: it observes a page without modifying it. It is the substrate both for the v1 detector and, in a future content-stream surgery slice, for selective glyph removal (the surgery pass needs the same position map). The `textpos::observe_page` entry point runs a hayro page through the observing Device and returns a `PageObservation`; pages that the renderer cannot interpret return `None` and are recorded in `DetectionReport.pages_unreadable`.

**The high-recall divergence model:** The v1 detector uses a deliberately high-recall strategy: flag any case where text is extractable but not drawn in the expected way. This produces some benign positives (most `InvisibleText` findings are OCR text-layers over scanned images) in exchange for not missing a true bad redaction. The `DetectionReport` conveys severity to let callers triage: Critical for the most unambiguous patterns (opaque cover over text), High for patterns that are suspicious but more often benign (invisible text, whiteout, orphaned text), and Medium for metadata leaks (which are always worth knowing about but are rarely safety-critical on their own). The report explicitly does not say a document is clean — an empty findings list means these mechanisms detected nothing, not a guarantee.

**Decision — seven detectors:**

- **CoveredText (Critical):** A glyph with extractable text has a paint-order-later opaque fill covering its geometric center. The cover and text are not the same colour (that would be whiteout). The detector groups covered glyphs by the cover that hides them, so each finding describes a contiguous covered run rather than individual characters. Severity is Critical because this is the most unambiguous bad-redaction pattern: the content is visually hidden but structurally present and extractable.

- **InvisibleText (High):** A glyph is drawn with text rendering mode 3 (PDF "invisible" mode). The text is extractable by any PDF library but not rendered to the display. Severity is High rather than Critical because this pattern is overwhelmingly benign in practice — OCR workflows place invisible text layers over scanned images to enable search and selection. The finding is still raised because invisible text on a document that is supposed to have no text layer is suspicious; the high-recall model flags it and the caller applies judgement.

- **WhiteoutText (High):** A glyph's draw colour and the opaque cover over it are both near-white (R, G, B ≥ 200), and they match each other within a tolerance of 8 per channel. This identifies the pattern where white or near-white text is painted under a white or near-white fill — a same-color concealment that is visually indistinguishable from a blank region but is textually recoverable. Severity is High because the concealment is intentional in form even if the content may be benign.

- **RemovableAnnotation (Critical):** A glyph with extractable text has its center falling within the bounding rectangle of an annotation whose subtype is one of: Redact, Square, Circle, Polygon, FreeText, Stamp, Highlight, or Ink. Annotations of these subtypes can be stripped by a PDF editor to expose the underlying text. The detector is structural — it works from the annotation object model, not from the paint-order observation. Severity is Critical because the content is visually concealed by a layer that an editor can delete in one operation without touching the page content stream.

- **HiddenLayer (High):** Text extracted from a page region that is enclosed by a marked-content sequence (`BMC`/`EMC` or `BDC`/`EMC`) whose optional-content group is off by default (the default visibility state in `/OCProperties` resolves the group to hidden). These glyphs are present in the content stream and are extractable, but a conforming viewer does not render them. The detector resolves the group by a `/Properties` resource name in the page's resource dictionary. Findings are page-level with `region: null` — the text is recovered but per-glyph geometry is not available. Severity is High because the content is selectively suppressed at the document level in a way that survives casual review.

- **MetadataLeak (Medium):** The document's information dictionary (`/Info`), XMP metadata stream (`/Metadata`), bookmark outline titles (`/Outlines` tree), or AcroForm field values (`/V`) carry text content. These surfaces are document-level — they do not correspond to a specific page location — so `page` and `region` are `null` in the finding. Severity is Medium: metadata leaks are always worth surfacing but are rarely the safety-critical path (the page-level geometric patterns are more dangerous). The minimum string length for a structural finding is 3 characters, filtering incidental single-character values.

- **OrphanedText (High):** The detector's structural pass calls `lopdf::Document::traverse_objects` to collect all object IDs reachable from the trailer. Any object not in that reachable set but present in the cross-reference table is orphaned: it is not part of the document's live structure but its bytes remain in the file and are recoverable by a tool that reads the raw cross-reference table. Orphaned text findings are also document-level (`page` and `region` are `null`). Severity is High because the content is irrecoverable by the viewer but extractable from the file bytes.

**Consequences:** The detector now covers all seven known bad-redaction patterns — from the classic opaque-box-over-text failure through annotation-layer concealment, hidden optional-content groups, metadata surfaces, and orphaned objects. The `pages_unreadable` field in `DetectionReport` is the honest signal that some pages were not examined; callers must not treat an empty `findings` list as clean for those pages. The covered-text geometry is glyph-center based against the cover's axis-aligned bounding box: a glyph more than half outside the cover, or a rotated/non-rectangular cover, may not be flagged. Covers that fully contain the text they hide — the usual redaction case — are caught reliably. RemovableAnnotation's high-recall subtype list flags annotation-concealed text even when the annotation is transparent; this may surface benign annotations of those subtypes where the annotation happens to sit over text (the caller should apply judgement as with InvisibleText). HiddenLayer findings do not carry per-glyph geometry and do not resolve inline optional-content dictionaries without a `/Properties` resource name — a rare but valid PDF encoding.
