**The matter-number draw is backed by a per-firm allocation table keyed by {scope_key, drawn_value}, not by the uniqueness of the rendered number.**

**Context:** A number draw reads the counter for its scope, renders the number, and commits [ensure counter row, guarded increment, matter write] as one batch. The guarded increment (`WHERE scope_key = ? AND next_value = ?`) is how a concurrent draw is detected — but a zero-row UPDATE is not an error in SQLite, so it does not abort anything on its own. The design leaned on the `matter_number` UNIQUE index to abort the losing batch. That index constrains the rendered STRING. Counter scope is derived from the segments a scheme marks `scoping`, and any variable segment may be left unmarked, which is a legitimate configuration: a client code, staff initials, or a matter-type code that appears in the number without resetting the counter. Two matters opened concurrently under such a scheme read the same counter value and render `ACME-0001` and `BRIGHTON-0001` — two distinct strings, no index violation, both batches commit, and the counter advances once. Two matters then hold the same position in the firm's sequence with nothing recording it, and the counter cannot be reconciled after the fact. D1 has no interactive transaction, so there is no read-and-hold alternative available inside the service.

**Decision:** Add a per-firm `matter_number_allocation` table — `scope_key`, `drawn_value`, `matter_id` (foreign key), `allocated_at` — with `PRIMARY KEY (scope_key, drawn_value)`. Every drawing batch inserts the value it consumed. The losing draw now aborts on that composite key, and the bounded retry that already existed for a `matter_number` collision handles it unchanged: advance the counter out of band (a no-op when the winner already advanced it), re-read, re-render. The `matter_number` UNIQUE index is retained for what it genuinely covers — a rendered number colliding with a manually assigned court or legacy number, which draws no counter and so has no allocation row. The table is keyed by what it reserves, no identifier handle, the same natural-key exception `matter_number_counter` holds; `drawn_value` is INTEGER because constraining the number (not a string spelling of it, where `01` and `1` would both be drawable) is the entire point. The allocation statement is composed last in the batch, after the matter write, because `matter_id` is a foreign key and a create-and-open draw inserts its matter in the same batch.

**Considered & rejected:** widening the counter scope to include every variable segment (silently changes what firms' numbers mean — a client-code segment would restart the sequence per client, which is a different numbering policy, not a bug fix); requiring every variable segment to be marked scoping (same, and it removes a configuration the numbering engine deliberately offers); checking `meta.changes` on the guarded increment (the shared effect-batch chokepoint commits and discards per-statement results by design, and a post-commit check cannot un-draw a committed number); a `UNIQUE(matter_id)` on the allocation table as a second guard against a matter drawing twice (it would fire on the retry path of a legitimately racing draw whose earlier attempt committed an allocation row, turning a recoverable race into a permanently unopenable matter).

**Consequences:** Number draws now cost one extra INSERT per attempt, and the allocation table grows one row per drawn number (plus a stranded row per losing attempt, which is what makes the retry gap visible rather than silent). Gaps in the counter sequence remain possible and expected — a losing attempt consumes a value — which was already true of the retry-past-a-parked-manual-number path. The allocation rows are also the first durable record of which matter consumed which position, so a firm's sequence can be reconciled after the fact, which was impossible before. Nothing about existing numbers changes: the table starts empty and constrains only new draws.
