**Deploying is a `release` fast-forward, not a push to `main`.**

**Context:** ADR-0144 recorded the as-built pipeline: Cloudflare Workers Builds, connected to the GitHub repository, building and deploying each Worker on push to `main`. That fused two unrelated cadences. Every push to the trunk — a docs commit, a merged branch, a sync — was also a production deploy of seven Workers, and the only way to get code onto GitHub was to change what was running. Watch Paths narrowed _which_ Workers rebuilt, but not _whether_ a push deployed at all; the single `main` push on 2026-07-04 triggered builds on all seven connected Workers. The trunk could not be used as a trunk.

**Decision:** make the Workers Builds **production branch** `release` on all seven connected Workers (`magna-carta`, `magna-carta-scan`, `magna-carta-bundle`, `magna-carta-recovery`, `magna-carta-file-repair`, `magna-carta-status`, `magna-carta-edit`), and leave _Builds for non-production branches_ **off**. `main` becomes an ordinary trunk that builds nothing. A deploy is a deliberate fast-forward, `git push origin main:release`, after which Watch Paths select the Workers that actually rebuild. `release` is never committed to directly, so what is deployed is always a commit that exists on `main`. Both settings are per-Worker dashboard settings under **Settings → Build → Branch control**; ordering matters on adoption — create `release` at the currently-deployed commit _before_ flipping the setting, or the flip queues a build of unshipped trunk work.

**Rejected:** changing each deploy command to `wrangler versions upload` (a version uploads but is never promoted). It leaves the live environment alone, but every push to `main` still runs seven builds — paying the wall-clock and build minutes this decision exists to stop — and it drops `wrangler deploy`'s trigger and Durable Object migration handling, which the recovery and file-repair Workers depend on to apply their Container DO migrations. Also rejected: disconnecting the git integration and deploying by hand, which breaks the scan Worker's nightly deploy-hook signature refresh (that hook builds the production branch and needs the repository connection).

**Consequences:** `main` and production diverge on purpose, and `git log --oneline release..main` is the undeployed queue — "what is live" is `release`, and reading the trunk is no longer a statement about the running system. The `pre-push` hook (ADR-0144) fires on both pushes, so the quality gate still runs before a deploy rather than only before a merge; it now also runs on pushes that deploy nothing, which is cheap. The scan Worker's nightly `0 7 * * *` deploy hook now rebuilds `release` instead of `main`, which is the intended behaviour: signatures refresh without shipping untested trunk code. Two facts surfaced while auditing the connected Workers and are recorded in the runbook rather than fixed here: `magna-carta-edit` has failed every `main` build since 2026-06-28 (so the live editing Worker predates the trunk), and it carries a build from a non-production branch, meaning that checkbox must be verified per Worker rather than assumed off.
