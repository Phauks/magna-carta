**Per-document-version splits with derived identity make the search write pipeline converge on retry; a deferred engine parks a job rather than failing it.**

**Context:** The search subsystem was wired-but-dormant: the engine core (`crates/search-core`), the per-firm split catalog (`index_split`), the `SearchIndexPort`, and the keyword/hybrid query composition all existed and were green, but **nothing turned documents into splits**. A query resolved a matter's live splits from the catalog and found none, because no catalog row was ever written. Two design questions had to be answered before the write half could be built, and both are about failure rather than the happy path. First, **what is the unit of a split?** A split per ingest *batch* is the shape Quickwit uses and the shape compaction ultimately wants, but a batch has no stable identity: a retried batch job builds a *different* split covering the same documents, so the catalog accumulates duplicates and a query counts documents twice — in e-discovery, a wrong count, not just wasted bytes. Second, **what happens when an engine is not there?** Neither engine is deployed: the index Container (`apps/search-worker`) is unbuilt, and text extraction reaches the recognition service. A queue consumer that treats "engine not deployed" as an ordinary failure will retry each message until it exhausts its attempts and dead-letters — turning a *scheduling* fact into a *lost document*, which is the exact defensibility failure the pipeline exists to prevent.

**Decision:** (1) **One split per document version**, chosen over per-batch for idempotency. (2) **The split id is derived, not minted** — a content-addressed handle over `documentId + version` (`deriveIdentifier` in `@magna-carta/identifiers`: SHA-256 → base64url, truncated to the standard token length, so a derived handle is indistinguishable in shape from a minted one and passes the same validation). The id fixes the R2 key (`search/<matterId>/splits/<splitId>.split`), so **identity and location are both reproducible from the inputs alone**: every attempt at a version writes the *same* object and targets the *same* row. Idempotency is structural — nothing has to know whether a previous attempt ran. (3) **Publishing is delete-then-insert, in one atomic batch** through the standard write chokepoint: a re-index at any version leaves exactly one live row however far a previous attempt got. Delete rather than supersede, because a per-document split has no reader to protect — the replacement covers the same document. (4) **A partial unique index** on `(document_id, version)` where `document_id IS NOT NULL AND superseded_at IS NULL` is the last line of defence against a duplicate delivery that races past the delete. Partial by design: `document_id`/`version` are **nullable**, and the many-document splits a later compaction publishes carry NULL, so compaction is not boxed out by a constraint written for the per-document case. (5) **Superseded R2 objects are deleted before their catalog rows** — the other order leaves unreferenced bytes in the firm's bucket that nothing will collect, while this order at worst leaves a row pointing at a deleted object, which the next index run replaces. (6) **A deferred engine parks the job.** The consumer's outcomes are three: `indexed`; `deferred` (an engine reported `engine-not-implemented` — the message is **acked**, the state recorded on the job's Durable Object, and the job is **re-startable**, so deploying an engine and replaying the enqueue drains the backlog); and `failed` (terminal-and-acked for bytes nothing can read, or rethrown so the queue retries and finally dead-letters). The dead-letter queue is load-bearing rather than hygiene: a message that lands there *is* the record that a document is missing from the corpus. (7) **The trigger is the clean ingest commit**, gated by a new per-firm `search.indexing_enabled` setting (off by default) read at enqueue time. (8) **`TextExtractionPort` is a second, separate port** from `SearchIndexPort`, because the two are separate services with separate deploy states and the consumer must distinguish "not extracted yet" from "not indexed yet"; its three failure reasons (`engine-not-implemented`, `unextractable`, `adapter-error`) are exactly the three things the pipeline does differently.

**Considered & rejected:** *Per-batch splits* — the shape compaction wants, but a batch has no reproducible identity, so a retry duplicates; per-document splits are the smaller unit and compaction merges them later, which the catalog design already anticipates. *A minted (random) split id* — every retry becomes a new split and every failure an orphaned R2 object; deriving the id is what makes the retry path free. *Upsert on the catalog row instead of delete-then-insert* — an upsert converges only for the *same* version; a new version would leave the old version's split live and still answering queries. *A non-partial unique index* — would forbid a second compacted (many-document) split for a matter, boxing out compaction for a constraint that only concerns per-document splits. *Retrying a deferred engine* — burns each message's attempts against an engine that is not built and dead-letters documents that were merely early; parking makes the backlog a queryable state rather than an error rate. *Failing the ingest when the enqueue fails* — re-running ingest means re-scanning and re-committing an already-committed version; the enqueue is best-effort and the deferred/replay path is the repair mechanism. *Triggering off the OCR or conversion completion path* — would only catch documents that happened to pass through those tools, so a plainly uploaded PDF would never become searchable; ingest commit is the one seam every document crosses. *Gating on the engine binding alone* — binding presence is a platform fact; whether a firm wants its corpus indexed is a separate, per-firm question, so the gate is a firm setting.

**Consequences:** Documents now produce splits, which makes the deploy-gated engine runtime the only remaining blocker to real search usage: deploying `apps/search-worker` turns the parked `deferred` jobs into real splits with no code change here. The pipeline is safe to run before that deploy — every document is either indexed, parked, or recorded as failed, never silently dropped. Turning `search.indexing_enabled` on for an existing firm indexes documents committed from that point; re-indexing the existing corpus is a replay over the same queue, which the derived split ids make safe to run twice. **A known gap:** the recognition engine skips a page that already carries a text layer, so a born-digital PDF currently extracts to nothing and is recorded `unextractable` rather than indexed empty — an empty index entry would assert "this document contains no text", the one answer discovery must never give wrongly. Closing it needs a PDF text-extraction edge that `crates/pdf-core` has internally (`page_text_glyphs`) but does not expose through `packages/pdf`; it drops in behind the same `TextExtractionPort` with no other change. Also of note, the `SearchIndexPort`'s document handle moved from the unused `DocumentId` entity to `FileId`, the handle the File Manager actually mints for a corpus document, so the pipeline is type-safe end to end against the real tables. Builds on **ADR-0003** (firm-scoped data access), **ADR-0039** (off the hot path), and the stateful-service design (`docs/specs/2026-07-17-discovery-search-index-stateful-service-design.md`), whose write-pipeline stage this implements.
