**Joining is three anonymous routes and one authenticated one, and the enumeration defence is in the storage shape rather than in the handlers.**

**Context:** The sign-in screens shipped ahead of their backend and carried an honest register of nine things the Worker could not do. Three of those blocked the product outright: `disableSignUp: true` meant no registration could succeed at all, invitation redemption had no route, and a throttled request answered with a bare 429 carrying no budget — so the remaining-attempts line and the lockout countdown the screens render had no source and were left deliberately unwired rather than fed an invented number.

The hard part is not the routes. It is that registration and redemption are the platform's only anonymous writes, and for a legal practice the confidential fact is frequently the mere association: that a named person has an account here, or was invited to a named firm. A form that distinguishes "unknown code" from "right code, wrong date of birth" is a machine for confirming exactly that, one guess at a time.

**Decision:**

1. **Three doors, one of which creates anything.** Registration takes a declared role. *Client of a law firm* and *works at a law firm* answer `{ next: "redeemInvitation" }` and write nothing and read nothing — in particular they do not look the address up, because a lookup is an oracle with a timing signature even when its result is discarded. Membership of an existing firm is that firm's decision, never a stranger's.

2. **Registration is two stages, and the split is the primary anti-abuse control.** Stage one writes ONE `registration` row and sends one email: no bucket, no key mint, no Durable Object, no entry in the fleet-wide cron enumeration. A spam run buys a row per attempt and nothing that costs money. Stage two — following the emailed link — commits a `firm.provision` outbox row with the status flip, and a control-plane consumer runs the existing `provisionFirm` orchestration. That reuse is the whole reason this is cheap: `provisionFirm` was already step-guarded and resume-safe for crash recovery, which is exactly the contract an at-least-once consumer needs.

3. **A self-serve firm's `name` is the registration handle; the human name is `display_name`.** `firm.name` is UNIQUE because it is the provisioner's resume identity. A human name in that column would refuse the second firm called Smith Law, would let anyone probe for a named firm's existence by trying to register it, and would make squatting a real firm's name cost one email address. The operator door is unchanged and stays name-keyed.

4. **One answer, always.** Registering a free address and a taken one both answer `202 { next: "checkEmail" }`. The difference is only in the mail, which goes to the address in question — telling the *account holder* their address was used is the opposite of an oracle, and costs an attacker nothing they did not already know. No registration row is written for a taken address, so the uniform answer is uniform underneath as well as on the wire.

5. **Redemption's neutrality is structural, not a discipline.** The `invitation` row stores `verifier_hash` = SHA-256 over the code, the normalised surname and the date of birth together. There is no surname column and no date-of-birth column, so there is nothing to compare separately and the handler *cannot* know which fact was wrong. One problem type, one title, one detail covers an unknown code, a wrong surname, a wrong date of birth, an already-redeemed or revoked or expired invitation, and an address that turns out to already have an account. The not-found path runs the same digest comparison against an unmatchable constant rather than returning early, so the two are indistinguishable in time as well as in content.

6. **Two composed budgets.** The caller-keyed limit bounds breadth; the invitation's own `attempt_count` and `locked_until` bound depth, because an address-keyed limit alone does not stop a patient attacker walking a date of birth from a rented range. Once an invitation locks, the *correct* combination is refused too — otherwise the lockout hands back one oracle bit per request.

7. **One shared credential ladder, published.** The password, the two-factor code and the recovery code spend the same budget: three ways of asking one question, and an attacker who gets a fresh five tries by switching fields has not been limited. It is enforced by a middleware over the Better Auth base path, because those endpoints are deliberately outside the `/api/v1` chokepoint and the chokepoint's bucket is per-route and firm-keyed — the wrong shape for a signed-out visitor. It rides on response *headers* rather than a rewritten body, so it does not couple to Better Auth's error shape. The chokepoint's own 429 gained `attemptsRemaining` and `retryAfterSeconds` in the body, so a client reads one shape wherever it was throttled.

8. **The budget is keyed on the caller's address, never on the address being tried.** Keying on the email would let anyone lock a colleague out by failing five sign-ins against them, and would make the ladder itself report which addresses have one in progress.

9. **Redemption ends at a mailbox, not a session.** A successful redemption creates an unverified, credential-less user and sends the password-setting link — the same activation path an invited member already travels. Guessing all three facts is therefore not by itself a way in.

10. **Recovery codes are `MC`-prefixed** via Better Auth's `customBackupCodesGenerate`, over an alphabet excluding `I l 1 O 0`. The prefix adds no entropy, so the random part stays at the library default's ten characters rather than being shortened to pay for it.

**Consequences:** `disableSignUp: true` STAYS. Better Auth's own signup route must remain closed, because our registration route is the door that enforces the role fork, the verification gate and the two-stage split — an open library signup would bypass all three. The per-isolate ladder shares the honest limitation of the existing rate limiter: state is not shared across isolates, so a distributed attacker gets more than five tries overall. It fails in the safe direction (a fresh isolate reports the full budget, which is true of that isolate) and moves behind the same interface when a Durable Object limiter lands. An office behind one egress address shares a sign-in ladder, which is why the window is minutes rather than a long lockout. Turnstile is *not* built here and is not faked: it remains an operations item, and until it is stood up the IP-keyed limit is what stands between the registration endpoint and a script.
