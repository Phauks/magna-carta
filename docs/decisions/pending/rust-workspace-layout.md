**Rust crates live in a single Cargo workspace at `crates/` beside the pnpm workspace; the two build systems are independent and share no package manager — Cargo owns the Rust graph, pnpm owns the TypeScript graph, and the WASM artefact is the only artifact that crosses the boundary.**

**Context:** Magna Carta uses pnpm workspaces for its TypeScript/JavaScript packages and Cloudflare Workers deployment. Adding a Rust/WASM component introduces a second build graph. The options for integrating Rust into the monorepo are: (a) a single `Cargo.toml` at the root alongside `pnpm-workspace.yaml`, (b) a dedicated `crates/` subdirectory with its own workspace root, or (c) a separate repository. The project already has a `tooling/` convention for non-package tooling; a `crates/` convention mirrors it cleanly.

**Decision:** The Rust workspace root is `crates/Cargo.toml`. All Rust crates are members of that workspace. The pnpm workspace (`pnpm-workspace.yaml`) does not include `crates/`. The two workspaces are independent: running `cargo` commands requires either `cd crates/` or `--manifest-path crates/Cargo.toml`; running `pnpm` commands operates on the TypeScript packages. The wasm-pack build command produces its output into `packages/pdf/src/pkg/`, which is the only crossing point between the two graphs: Cargo builds the `.wasm` + JS glue, pnpm bundles it. `packages/pdf/src/pkg/` is gitignored except for its `package.json` (generated by wasm-pack and imported by the TypeScript wrapper); the `.wasm` binary is never committed. The `rust-wasm-build` vp task and the `rust-pdf-core` CI job own the build and verification of the WASM artefact.

**Future crates:** Rust crates for the Tantivy search engine, the OCR pipeline, and the Tauri shell will join the same `crates/` workspace when those slices open. The workspace layout (one `[workspace]` root, per-crate `Cargo.toml`s as members) keeps the build graph unified and avoids scattered `Cargo.lock` files.
