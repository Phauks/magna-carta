**The per-firm database is a SQLite-backed Durable Object, not a per-firm D1.** ADR-0003 set tenancy as control-plane D1 + **per-firm D1** + per-firm R2, with the per-firm D1 reached through a static Worker binding. That binding model does not scale: a Worker holds at most ~5,000 bindings, and every firm beyond a pre-declared pool needs a config commit + redeploy to bind its database. Slice 0·4 named this and deferred it ("dynamic dispatch / Workers for Platforms — revisit when firm #2+ makes it real"). This decision settles it: the per-firm database becomes **one `FirmDatabase` Durable Object class, addressed `idFromName(firmId)`** — binding-free, created on first access, no redeploy, scaling to millions of instances. **Control-plane D1 and all per-firm R2 are unchanged**; the firm-scoped data-access layer (ADR-0003) is untouched at the interface.

**Why DO-SQLite over the alternatives.**

- *Bindingless D1 over the HTTP API* — rejected, not even an interim: there is no runtime dynamic-D1-binding mechanism, and the only bindingless transport (the D1 REST API) is capped at ~1,200 req / 5 min (~4 req/s) globally — unusable for serving.
- *Workers for Platforms* — rejected as the answer to **this** problem: it works and is inexpensive ($25/mo self-serve, not Enterprise-gated) and keeps a native per-firm D1 binding on each user Worker with no dispatcher redeploy, but it exists to run **different per-tenant code**, while every firm here runs **identical** code — making a per-firm user Worker either pure overhead (a thin shim) or a per-release per-tenant bundle tax. Earmarked as the home for a future tenant-supplied-code capability; this decision forecloses nothing there.
- *Per-firm DO-SQLite* — chosen: binding-free unlimited addressing, **stronger** ledger transactions than D1 (interactive `transactionSync` vs D1's transaction-less `batch()`), no new product tier, and a domain layer already abstracted for it.

**Validated, not assumed.** The domain layer (~185 query sites across 6 packages) targets an abstract `SqlDatabase`/`SqlStatement`/`BatchDatabase` shape; concrete `D1Database` lives only in the migration seam and the worker edge. A throwaway spike (`spike/per-firm-do-sqlite`) ran the **real** per-firm migration lineage and a **real, unmodified** statement module against `ctx.storage.sql`: 18 migrations self-applied on wake (`blockConcurrencyWhile` + the target-agnostic runner), `meta.changes` mapped faithfully via `SELECT changes()`, and `isIdempotencyKeyConflict` matched DO SQLite's UNIQUE-message with `transactionSync` rolling the batch back. The port is two ~100-LOC adapters plus worker wiring, not a DAL rewrite.

**Considered & rejected within the chosen path.** *A worker-side proxy that throws conflicts across RPC* — rejected in favor of the DO returning a **typed** commit outcome, so conflict detection never depends on error-message identity surviving serialization. *The per-firm cron relay* — shipped as the **central cron sweep re-pointed at the DO** (`scheduled.ts` enumerates active firms and resolves each via `firmDatabaseFor(env.FIRM_DATABASE, firmId)`); per-firm failure isolation is preserved by the loop's existing per-firm quarantine. The **per-DO alarm self-sweep** (each firm sweeps its own outbox/idempotency/uploads, eliminating the central O(firms) fan-out) is kept as a **named scale-seam** to swap in when firm count makes the per-tick fan-out matter — off-hot-path machinery is optimized when measured, not pre-emptively. *A dual-run DO-for-new / D1-for-existing flag* — unnecessary: there are no live firms, so the per-firm D1 pool is retired outright and the demo firm is re-provisioned onto a DO (a clean cut).

**Consequences.** Onboarding a firm is binding-free and redeploy-free; `firm-binding-resolver.ts` + the `DB_FIRM_POOL_*` bindings + the config-commit-and-deploy step, `fleet-rollout.ts`'s central iteration, the REST adapter's per-firm `createDatabase`, and `firm.database_identifier`-as-binding-pointer all become obsolete (the DO name **is** `firmId`). New constraints to honor: **10 GB per firm** (ample for core practice-management metadata; high-volume discovery/custodian metadata and append-only audit logs are a deferred separate decision — per-matter shard / D1 / search index — not pre-decided here); **single-writer per firm** (push bulk writes to Queues off the interactive path); and **no read replicas + sticky homing** (set `locationHint` from the firm's region at creation and control first-access). Supersedes the per-firm-D1 element of **ADR-0003** (the control-plane-D1 and per-firm-R2 elements stand); respects **ADR-0039** (off the hot path) and **ADR-0067** (route chokepoint) at the data-plane seam; relates to **ADR-0069** (Worker delivery architecture).
