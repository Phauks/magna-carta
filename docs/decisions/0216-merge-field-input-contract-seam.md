**The field-input interface is built against a catalog contract with a mock provider, the design system takes structural shapes rather than domain types, and a detected placeholder is a proposal with no applied state.**

**Context:** Document automation's user-facing half is where a person picks merge fields from the firm's dictionary rather than typing `{{matter.responsibleAttorney}}` from memory, and fills in the placeholders a template declares that the firm's data cannot supply. That interface is buildable well before the backend it eventually reads from: the dictionary endpoint, the template field-manifest endpoint, and the assembly job are all still being built, on a separate branch. Building the interface against nothing means either waiting, or building it against a shape invented ad hoc in the page and retrofitted later — the second of which is how a UI ends up with a data model that no endpoint actually produces. There is also a boundary question that gets answered by default if it is not answered deliberately: the design system currently depends on no workspace package but `@magna-carta/design-tokens`, and a merge-field picker is the first component with an obvious pull toward importing a domain type. Finally, an authoring surface that reads a Word `MERGEFIELD` out of an uploaded template and maps it to a dictionary key is a surface that can very easily imply a conversion has already been performed on the firm's document, which it has not.

**Decision:** (1) **The contract is its own package**, `@magna-carta/merge-field-catalog-contract`: the catalog entry (key, human label, group, value type, example rendering, availability and its note, sensitivity, legal formats), the template field manifest, the detected-conversion record, and the `MergeFieldCatalogProvider` read seam — plus a realistic fixture catalog and a mock provider over it. It holds no data access and no assembly logic. (2) **Consumers take the provider, never import the mock.** The mock is constructed at one composition root in the app; switching to a provider that calls the live endpoints is an edit to that file and no other. (3) **The mock is asynchronous and takes a latency option**, because a surface built against an instant answer grows loading states that never run. (4) **The design system takes structural shapes.** The picker's option and the review list's row are types declared in the components' own folders — label, group, value-type label, description — and the app maps catalog entries into them in one adapter module. The design system gains no workspace dependency. (5) **A detected placeholder is a proposal.** `DetectedFieldConversion` and the review row carry a `confirmed` flag owned by the consumer and deliberately have **no** applied/converted state, so no surface can render a conversion as a completed action; the review component's standing guidance says plainly that nothing has been changed. (6) **The input area's model is pure and separate from its rendering**: which fields get a control, which block the assembly when empty, and whether typed text is the kind of value the field takes are decided in a testable module, not in a component.

**Considered & rejected:** *Putting the dictionary types in the assembly package the backend owns* — correct eventually for the resolution engine's own types, but it makes the interface's progress depend on another branch's file layout and hands two agents the same files. The contract package is a read shape; when the assembly package exports its own dictionary, this one narrows to a re-export or disappears. *Importing domain types into the design system* — the smaller amount of code today, but it binds every merge-field component to one producer's shape and breaks the package's only-tokens dependency rule for a convenience; one adapter module is the whole cost of keeping it. *Holding form values as typed objects (money, dates) rather than text* — a form's fields carry text, interpreting it is a step rather than an assumption, and a string-keyed values map keeps a half-filled form serializable for drafts and hand-off. *Blocking the assembly on every empty field* — a conditional field left empty may still be covered by the matter's own data, so blocking on it stops people assembling documents that are in fact complete; empty required fields error, empty conditional fields warn and name what will happen. *Auto-applying an exact-confidence conversion and asking only about the uncertain ones* — the confidence is ours, the document is the firm's, and a surface that silently rewrites a template for the high-confidence cases teaches people it rewrites templates.

**Consequences:** The field picker, the field chip, the detected-field review list, and the assembly input area are all built and tested end to end with no backend, and none of them changes when the endpoints land — the one file that changes is the composition root. The fixture catalog carries at least one protected entry, one template with an unrecognized placeholder, and one with conversion proposals, so every state a surface must render has a case to render it from, and a test asserts the fixtures stay consistent with each other. The interface's visual design is explicitly unfinished and left for owner review; what is settled here is the contract, the seam, and the posture. Builds on **ADR-0076** (all UI through the design system) and the document automation design (`docs/specs/2026-08-04-document-automation-design.md`), whose user-interface seams this serves.
