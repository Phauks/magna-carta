**The office-crypto dependency is replaced by an in-house implementation of the MS-OFFCRYPTO package decryption loop, because replacing the carrier was the only remediation that existed for the two quick-xml advisories it brought in.**

**Context:** `crates/decryption-core` decrypts password-protected Office documents on the untrusted-upload path. It already owned the ECMA-376 agile password verifier, the iterative SHA-512 password hash, block-key derivation, its own descriptor parser (used by hash extraction), and the compound-file structural validation. `office-crypto` 0.2 supplied one remaining piece: the package decryption loop — unwrapping the session key from `encryptedKeyValue`, then walking the `EncryptedPackage` ciphertext in 4096-byte segments. It also brought `quick-xml` 0.38, whose two high-severity advisories (`RUSTSEC-2026-0194`, quadratic duplicate-attribute scan, reachable; `RUSTSEC-2026-0195`, unbounded namespace allocation, unreachable) were accepted with a time-box to 2027-02-14. The acceptance reason named this replacement as the exit: quick-xml 0.41 fixes both, `office-crypto` 0.3 (its newest release) still requires `^0.38.4`, `[patch.crates-io]` cannot lift a version requirement, and forking a 15 000-line XML parser under a falsified version number would trade a bounded exposure for an unaudited one. Beyond the advisories, `office-crypto` carried three panic-or-hang paths on attacker-supplied bytes: an unsigned `total_size - 4096` with no bounds check, a bare `.unwrap()` on its XML reader for a malformed descriptor, and an uncapped `spinCount` read straight off an uploaded document. The first was already guarded upstream in this adapter; the third was not guarded on the decryption path at all.

**Decision:** implement the package decryption loop in `decryption-core` and drop `office-crypto` entirely. The loop is the specification's, not the carrier's: each 4096-byte plaintext segment is an independent AES-CBC chain whose initialization vector is `SHA512(keyData salt ‖ LE_u32(segment index))` truncated to the cipher block size, so a segment is decrypted at its true index and the bytes of two segments are never run together as one chain. It reads only the cipher blocks each segment's plaintext needs, so the final short segment cannot pull its successor's bytes into its own chain. Every arithmetic step is checked or saturating, the size prefix is read as the 64-bit quantity the format defines and converted with `try_from` rather than cast (usize is 32-bit on the wasm32 target), and a prefix promising more plaintext than there is ciphertext is refused before any segment is decrypted. No dependency is added — `aes`, `cbc`, `sha1`, and `sha2` were already direct dependencies, and AES-ECB is driven through the `aes` crate's block API rather than pulling in the `ecb` crate. All existing guards are kept and re-documented against the in-house parser they now protect: the 64 KiB `EncryptionInfo` cap, the size-prefix floor, and the compound-file structural checks. Two guards are added: a stream whose declared length exceeds the file that contains it is refused before it is read, and the `spinCount` cap that already protected hash extraction now protects decryption.

**On capability — nothing is dropped silently.** `office-crypto` covered three things. (1) **ECMA-376 agile encryption** — reimplemented, and now verified byte-identically across the segment and cipher-block boundaries. (2) **ECMA-376 standard encryption** (Office 2007: AES-ECB under a 50 000-round SHA-1 key derivation) — this was reachable through this adapter, so it is **ported**, including its verifier, and now supports AES-128/192/256 where the carrier hardcoded AES-128 and would have panicked on a 256-bit key. Its **RC4 CryptoAPI** variant is refused with a named `Unsupported` error, which is exactly what the carrier did (`Unimplemented("RC4")`) — no regression, and implementing a 40-to-128-bit stream cipher no supported Office version writes is not worth presenting as a supported format. (3) **Word-97 binary RC4 CryptoAPI** (`.doc`) — confirmed **unreachable** from this adapter both before and after: `strip_with_key` returns `NotEncrypted` when the compound file has no `EncryptionInfo` stream, which is precisely the `.doc` shape, so the carrier's `doc97` path was never entered. Hash extraction for standard-encrypted documents remains unsupported, unchanged: the `$office$*2013*` format encodes a SHA-512 agile derivation and cannot express a SHA-1 one.

**Two behavioral improvements fall out.** A wrong password is refused by the ECMA-376 verifier before any package byte is decrypted, rather than inferred afterwards from the absence of the ZIP magic — the limitation the previous implementation documented. Consequently a genuinely corrupt document that decrypts to non-archive bytes is now reported as `Malformed` rather than as a wrong password. And the carrier had a real correctness bug the replacement fixes: its loop compared a stream offset against a plaintext length off by the eight-byte size prefix, so for any package whose plaintext length modulo 4096 fell between 1 and 8, the final tail was decrypted under the previous segment's initialization vector and chain — a corrupt archive trailer on roughly one document in five hundred. The boundary sweep in the test suite covers exactly those lengths.

**Considered & rejected:** *extending the `ignoreUntil` again* — the acceptance was explicitly time-boxed against this work, and an accepted advisory that is renewed rather than retired is how a forcing function becomes a formality. *Waiting for an office-crypto release on quick-xml 0.41* — no schedule exists, and the crate's last release predates the advisories. *Vendoring a patched quick-xml* — trades a bounded, analyzed exposure for a parser fork the scanner can no longer identify. *Implementing only the agile loop and refusing standard encryption* — smaller, and it would have silently stopped opening Office 2007 documents that open today; a capability is not dropped because it was inconvenient to port. *Implementing RC4 standard encryption for completeness* — the primitive is in the workspace, but nothing produces such documents and the carrier refused them too; a named refusal is honest and an implementation would not be exercised.

**Consequences:** sixteen crates leave the dependency graph (`office-crypto`, `quick-xml`, `base64`, `bytemuck`, `derivative`, `ecb`, `packed_struct` and its proc-macro, `bitvec`/`funty`/`radium`/`tap`/`wyz`, `serde` and `serde_core`, `syn` 1.x) and none are added; `osv-scanner.toml` now carries no accepted Rust advisory. The confidentiality-sensitive parsing of privileged bytes moves from a third-party crate to code this repository reviews and tests, which is the memory-safe-by-default posture applied to a dependency rather than to a language. The cost is ownership: the MS-OFFCRYPTO agile and standard schemes are now this codebase's to maintain, which is why the test suite covers both round-trips byte-identically, sweeps every plaintext length adjacent to the segment and block boundaries, and drives a deterministic mutation sweep for panics. The public API and the WASM export surface are unchanged. Realizes the _Vulnerability / dependency management_ control in [`docs/conventions/compliance.md`](../conventions/compliance.md); completes the remediation begun in ADR-0201 and relates to golden rule 14.
