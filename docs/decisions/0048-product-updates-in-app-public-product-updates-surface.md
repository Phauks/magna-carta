**In-app + public product-updates surface (changelog, release notes, roadmap) + live status; bundle the versioned content, centralize only the live content.** **Context:** users want in-app access to the changelog, release notes, and roadmap, and the question was raised whether to serve this from a central SQL database or bundle it with the app — and how it relates to the deferred _Community & feedback forum_ (ADR-0044), which also lists changelog/roadmap/known-issues. **Decision:** (1) **Split by mutability, not by surface** — versioned content (changelog, release notes, roadmap) **ships with the build** as a structured `product-updates.json` static asset (the in-app read path); only the **live** known-issues / service-status banner lives in **control-plane KV**, written via an owner/admin RBAC-gated endpoint (and propose-only by the diagnostics/maintenance agents), no deploy needed. (2) **Repo stays the single home** — `CHANGELOG.md`/`ROADMAP.md` (ADR-0037) are the authoring source; a tool-agnostic build step derives the artifact (parser now, or the Phase-0 release tool — git-cliff/changesets — emitting it later; the _schema is the contract_, malformed input fails CI). **No CMS**; authoring stays in git/PR via the changelog/roadmap maintenance agent (ADR-0016). This gives **version-accuracy by construction** (a build can't advertise features it lacks) and **offline-native parity** (web + Tauri). (3) **KV, not D1**, for the live content — platform-level, read-mostly, edge-replicated config; keeping status off the off-Cloudflare forum host means the banner survives an incident that takes the forum down. (4) **Public-by-default** read surfaces rendered as **Workers static pages** from the same artifact + KV status (transparency + acquisition, SEO), so the canonical public changelog/roadmap does **not** depend on the unchosen forum tool; the forum is scoped to login-gated requests/votes/discussion and **links to** our pages / **mirrors** our status. (5) **Single system of record per content type** — we own changelog/roadmap/status, the forum owns requests/votes/discussion — wired by **seams** (native SSO deep-links, optional read-only vote-count enrichment on roadmap items, the one-way private-report→feature-request escalation bridge of ADR-0038), built when the forum tool is chosen; the surface is fully functional standalone until then. (6) **Per-user `lastSeenProductUpdate`** marker registered in the Settings framework (ADR-0040, control-plane storage) drives the "What's New" unread badge. (7) The internal **roadmap is shown as-is** now (sole tenant); the artifact reserves an optional `audience` field as a non-breaking seam for an internal/public filter at multi-firm. **Considered & rejected:** **central SQL (D1) + a CMS** as the system of record (creates a second home for the changelog against _one home per fact_, can drift ahead of the deployed build, abandons the git/agent authoring flow, and is the most infra for the worst fit); **pure-bundle with no central seam** (forecloses the live status banner the owner wants and a shared public/forum source); **delegating the public changelog/roadmap to the forum tool's own modules** (weak/inconsistent presentation, ties canonical content to an off-Cloudflare, not-yet-chosen tool). **Consequences:** a small, mostly-static surface that ships early and works offline; the only authored-without-deploy content is the live status; the forum integration is reduced to thin seams. Extends **ADR-0037** (living docs) and **ADR-0044** (community forum); reuses **ADR-0040** (settings), **ADR-0016** (maintenance agents), and the _Cloudflare primitive mapping_ (KV). Distinct from per-entity audit/temporal history (ADR-0006) and not a per-firm activity feed.
