**Recovery orchestration — a keyspace-split coordinator that fans out, first-hit-cancels, and never persists the secret.** Given an extracted password hash and a CPU-crackable format, the app must search a large candidate space across a fleet of isolated compute shards, return the password the instant it is found, and do so without ever writing the secret down. This is the Slice-2 companion to the `decryption-file-unlock-recovery` engine decision.

**(1) A Durable Object coordinator, state in DO SQLite.** `RecoveryJobCoordinator` (keyed `firmId:jobId`) owns one job's lifecycle — `queued → running → found | exhausted | needsGpu | cancelled` with progress (candidates tried, shards done, shard count). State lives in **DO storage, not a new D1 table** (mirroring `BundleBuildCoordinator`/`ConversionJob`): the job is transient and the DO *is* its store. `start()` splits the keyspace and enqueues one message per shard on a recovery **Queue**; the queue consumer dispatches each shard to a **distinct** `apps/recovery-worker` container instance (addressed per `jobId:shardIndex`, so shards actually fan out across containers rather than colliding on one) via a service binding, and reports the outcome back. The coordinator aggregates and, on the **first hit, cancels the rest** — a later shard's result can never overwrite a password already surfaced.

**(2) The tier router — don't grind on what a CPU can't crack.** A classifier maps (format, mode) to `cfCapable` (fan out N shards on the Cloudflare-CPU lane) or `gpuRequired` (modern slow key-derivation — return terminal `needsGpu` with zero shards enqueued, filling the seam a later GPU rung plugs into). An unknown format defaults to `gpuRequired` — the safe direction (never claim to have exhausted a space we did not search).

**(3) Shard-by-count, self-splitting containers.** The Worker cannot run the keyspace split itself (the wasm surface has no rayon), so the container receives `(shardIndex, shardCount)` and self-splits its baked wordlist contiguously — complete, non-overlapping, dropping the empty tail — with the range validated and clamped (a bad range → 400, never a panic). CF v1 uses a **modest real shard count** (a few containers) to prove the coordinator; it is a tunable throughput knob, not a bound on the keyspace a job can search.

**(4) At-least-once safety.** Cloudflare Queues deliver at least once, so a shard can report more than once. The coordinator dedups per shard index before counting, so a redelivery never double-counts `shardsDone`/`candidatesTried` or prematurely flips a job to `exhausted` (which would drop a genuinely-later `found`). A stuck fan-out (a container that never reports) fails **closed** — `exhausted`, never a fabricated password — via a watchdog alarm that is **re-armed on every reported shard**, so its deadline measures time-since-last-progress and never guillotines a shard still legitimately searching within its own request budget.

**(5) Password-confidentiality lifecycle.** The recovered password is the most sensitive material in the subsystem. It is surfaced **once**, only to the user who **started** the job (the status route records `startedByUserId` and 404s any other caller — indistinguishable from an unknown job, so existence never leaks), is **never** written to an audit row/log/problem detail, and is **purged** from DO storage after a bounded retention window (the alarm, repurposed on `found`, nulls it; the job stays `found`, the route simply stops returning it). The started/cancelled audit rows carry actor + encrypted-input digest + tier + counts only.

**(6) Recovery is the FIRST fan-out consumer — the generic primitive is deferred.** No platform-generic fan-out/join utility exists today, and building one speculatively for a single consumer would be guessing at the abstraction. The generic primitive is therefore **not** built here; the coordinator carries the pattern (split → enqueue → dispatch → aggregate → first-hit-cancel) inline, and the **next non-recovery domain that needs container fan-out extracts it from this coordinator** rather than rolling its own.

**Considered & rejected.** **A D1 table for job state** — the job is transient and single-writer; a DO's own storage is the right home and avoids a per-firm schema migration (matches the bundle/conversion coordinators). **One container instance for all shards** — collapses the fan-out to serial work on a single container; rejected for distinct per-shard instance addressing. **`>=` completion checks / trusting the consumer to be idempotent** — an exact `===` after per-shard dedup is strictly safer and defends even a non-idempotent consumer. **A fixed stuck-job deadline from job start** — shorter than a shard's own request budget, it guillotines legitimately-slow shards and drops real hits; rejected for the re-armed, time-since-last-progress watchdog. **Building the generic fan-out primitive now** — premature abstraction from a sample size of one; deferred to the second consumer. **Running slow-KDF formats on CPU anyway** — burns the sharded budget to reach a foregone `exhausted`; rejected for the `needsGpu` triage.

**Consequences.** Recovery is callable end-to-end (button → tier router → fan-out → first-hit → password) on the CPU lane, with the GPU rungs plugging into the same `needsGpu` seam and `RecoveryBackend` port later. The confidentiality keystone holds across every boundary. Deferred: the GPU rungs, the end-user UI, and the extraction of the generic fan-out primitive at its second consumer. **Owner-owed activation:** the `magna-carta-recovery` Worker must be connected to Workers Builds (build root `apps/recovery-worker`) — until then the container is inert and the consumer reports honest zero-count misses (jobs terminate `exhausted`, never a false hit). Companion to `decryption-file-unlock-recovery`.
