**The expression ceiling grows to computed expressions, and the line that does not move is that an expression is never executable code — a closed, total, statically checked grammar rather than a sandboxed one.**

**Context:** _Owner decision, 2026-08-04 evening._ The document-automation design fixed the expression ceiling at presence, negation, and equality against a literal, and named the widening as owner flag F6. That ceiling braided two arguments together. The first is a product argument: a template language rich enough to need a developer produces a firm-wide dependency on whoever wrote the templates, which is the road HotDocs authoring went down — and its own documentation directs authors out of the inline field editor and into a component studio once expressions get real, which is the moment a paralegal stops being able to maintain the firm's templates. The second is a security argument: the templating libraries that offer richer expressions do so by evaluating code from the template, turning a firm-authored `.docx` into an execution surface inside a Worker that holds privileged client data. The two arguments have different answers. The product argument is answered by keeping the language small, closed, and total rather than by keeping it incapable — a paralegal who can write a spreadsheet formula can write a date comparison, and what they must never be able to write is a program. The security argument does not move at all. Meanwhile the real templates a firm files want arithmetic: a settlement statement that splits a recovery, a fee agreement that states a cap, a notice that computes a deadline thirty days out, an exhibit index that says "Exhibit" or "Exhibits" correctly. Refusing those pushes the firm back to a calculator and a typed-in number, which is both the error-prone path and the one with no record.

**Decision:** (1) **The ceiling grows to computed expressions** — arithmetic over money and numbers, date math, comparisons, boolean composition, and a catalog of formatting, pluralization, ordinal, and case helpers — for conditional blocks, repeating blocks, and a new computed-field placeholder `{{= expression}}`. One grammar serves all three; the alternative is two languages to keep consistent and two places for a security property to hold.

(2) **An expression is never executable template-supplied code.** This is the invariant, stated as a property of the grammar rather than of a runtime: there is no production for a function definition, a property access, an index, an assignment, a lambda, a regular expression, a template include, or a call to anything but a fixed allowlist compiled into our source. The evaluator is a switch over a closed set of node kinds; a call node carries a catalog identifier resolved at parse time, so by evaluation the only callable things in existence are functions we wrote. There is no `eval`, no `new Function`, no dynamic `import`, no `with`, no `Reflect`, and no regular expression built from template text.

(3) **A merge key is ONE atom, not a traversal.** `matter.number` is a single lexical token whose dot is part of the identifier; names resolve by exact match through `Map.get` against the merge context and the loop scope. This is the structural difference from a sandboxed JavaScript expression evaluator, where `a.b.c` is real property traversal over a host object and the sandbox is therefore a denylist over that object graph — the shape that failed as CVE-2020-5219 and again as CVE-2024-54152, where `compile("__proto__.constructor")` returned an object and a longer payload reached arbitrary code execution. With no traversal production, `__proto__.constructor` is one atom, absent from the map, and reported at registration as an unknown merge field. **Ours is an allowlist over a language that cannot express the escape; theirs is a denylist over a language that can express everything.**

(4) **Termination is structural, not a timeout.** No loop, no recursion, no self-reference, no template include; a finite tree with a bounded depth walked once in post order; the only variadic-cost construct is `{{#each}}`, which iterates a finite list resolved from the firm's own data under an item cap. **`{{#each}}` iterates data; expressions do not iterate** — there is no `map`, `filter`, `reduce`, comprehension, or aggregate written by the author. The per-assembly step budget is a second line of defence against the product of the other bounds, not the guarantee.

(5) **Money arithmetic is integer-exact and division is not an operator.** No floating point anywhere in the evaluator; every intermediate is checked against the safe-integer range before the operation, so the money package's own guard throw is unreachable and a breach is a typed refusal. Mixed currencies refuse and name both keys; there is no currency conversion in this language, ever. `/` has no production — the lexer recognizes it only to name the three replacements: `divideExact` (the exact quotient or a refusal), `divideRounded` / `applyRate` / `percentOf` (**banker's rounding, half to even**, through `@magna-carta/money`'s existing `roundLedger`), and `allocate` (largest-remainder parts that sum exactly to the input, through the money package's existing `allocate`). Banker's rounding is the only rounding mode template authors see.

(6) **Date math is over calendar dates in the matter's office time zone**, through the existing `timeZoneForLocation` seam. There is no instant type in the language, so time-of-day arithmetic is not expressible and a filing date cannot depend on the hour a job ran. Month arithmetic clamps at end of month, stated rather than assumed. No business-day or court-deadline helper ships: that needs a maintained per-jurisdiction holiday calendar, and a wrong answer from one is a missed filing.

(7) **Static type checking happens at registration.** Lex, parse, resolve names against the dictionary and loop scope, type-check, check the format suffix against the shipped legal-formats table, check limits — and a failure is a registration error carrying part, paragraph, and character offset, surfaced through the existing field-inspector route. The manifest stores the expression SOURCE, not a serialized tree: assembly re-parses and re-checks, which costs microseconds and is the only thing that catches dictionary drift when a bound custom field is archived three months after the template registered.

(8) **Absence and refusal are distinguished, with a deliberate asymmetry.** An unresolved CONDITION fails the assembly by default, because a wrong branch is invisible — nobody reads a contract and notices the paragraph that is not there. An unresolved COMPUTED FIELD renders a visible placeholder by default, the same bias the absence model already takes. `has(key)` is the total presence form, so the safe reading is one word away and the dangerous one cannot be reached by accident. A refusal — currency mismatch, magnitude breach, inexact `divideExact`, budget exhaustion — always fails the assembly naming the location and the reason, and never becomes `false`, blank, or a rounded guess.

(9) **The claim carries a fuzzing obligation, in the slice, not after it.** Structure-aware generation over the grammar and byte-level generation of arbitrary strings, both seeded reproducibly; a committed denied-construct corpus in which every hostile input must fail at PARSE OR CHECK and never reach evaluation; a pretty-print-and-reparse property for parser ambiguity; an arithmetic oracle proving half-to-even on the tie cases in both signs and `allocate`'s parts summing to the input; one bound-hitting test per limit; and a permanent corpus regression for anything ever found.

**Considered & rejected:** *Holding the narrow ceiling* (the design's recommendation) — safest and the status quo, rejected because it does not actually buy the security property, which comes from the grammar being closed rather than from it being small, and it pushes real arithmetic onto a calculator and a typed-in number with no record. *Adopting docxtemplater's Angular parser and hardening it* — the fastest route to every operator a firm could want, and precisely the architecture we refuse: a general-purpose JavaScript expression evaluator whose sandbox is a denylist, whose documented mitigations (pin the parser, enable `csp: true` to avoid `new Function`, disable `CallExpression`, harden the runtime) are the mitigations a permeable first line needs, and whose own guidance says you are impacted if the parser is enabled and the templates are written by untrusted people. Our templates are written by firm administrators, which is the *good* case, and it is still an execution surface reachable by anyone who can get a `.docx` in front of one. *A general expression language run under a restricted interpreter of our own* — the same denylist shape with our name on it, and a much worse place to discover the first escape. *Allowing user-defined named computations reusable across templates* — the genuinely useful next step, and the exact mechanism by which HotDocs authoring became a specialist job; deferred as an owner flag rather than taken. *Infix `/` with a documented default rounding* — one operator instead of three helpers, rejected because a money engine that hides its rounding behind an operator is lying about the part that matters, and "the settlement split three ways lost a penny" is discovered in a reconciliation months later. *Aggregates such as `sum(disbursements.amount)`* — genuinely wanted by a settlement statement and genuinely safe (bounded by the data, exactly as `{{#each}}` is), but it is iteration inside an expression, which is the line drawn here; recorded as a flagged seam rather than smuggled in. *Pronoun and verb agreement as a helper* — expressible now that helpers exist, and it requires recording a gender attribute on a party, which is the part we do not want; `choose` lets an author write it explicitly and visibly.

**Consequences:** Template authoring gains real capability and gains a new failure surface — a paralegal can now write an expression that does not type-check, and the answer is that they find out at registration with a character offset rather than at a filing deadline with a wrong number. The build slice grows from two tasks to five and reorders so the language is proven as a language before it meets an OOXML package: grammar, evaluator, conditionals, repeats, computed fields, each testable alone. The engine takes on a permanent obligation it did not have — a fuzz harness and a denied-construct corpus that must keep passing, which is the cost of making a structural security claim rather than a procedural one. Every expression's merge keys join the field manifest, so the one-batched-read-per-source rule survives a template whose conditions read anything the dictionary has. A firm will eventually want a helper the catalog does not have, and the answer is a catalog entry we write, review, and test — slower than a template that computes it, and the reason a bug in this evaluator is a wrong number in a document rather than a foothold in a Worker. Supersedes the expression-ceiling recommendation in the document-automation design (`docs/specs/2026-08-04-document-automation-design.md`) and answers its owner flag F6; builds on ADR-0210 and ADR-0211 (the engine and template model shipped in slice 2·6·1).
