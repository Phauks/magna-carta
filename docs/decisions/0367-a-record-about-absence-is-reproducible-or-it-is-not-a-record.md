---

**A manifest and an exception report are documents about a corpus, handed to people who did not
build the corpus. The only thing that makes them worth handing over is that they do not change.**

**Context.** The design placed both artifacts in R2, written once at load completion, never
regenerated. It did not say what "never regenerated" has to be true of, and the obvious
implementation — read the rows, render, write — has a defect that only shows up years later: it
reads a clock. Run it twice and you get two documents that disagree about when they were true, over a
corpus that may itself have moved. A firm asked to produce the report it produced in 2026 would
produce a different document and have no way to explain the difference.

The same slice had to settle deduplication and container families, both of which decide what a
reviewer sees, and both of which the design gave a recommendation and not a mechanism.

---

**Decision 1 — reproducibility is a property of the generator, held three ways.**

The renderers in `packages/discovery/src/manifest.ts` are pure: no binding, no bucket, no database,
and **no clock**. Everything they state is handed to them.

- **The knowledge instant is an argument**, and it is the load row's `updated_at` — the moment its
  last counter moved, which is the moment the last document in it reached a terminal state. Nothing
  advances it afterwards, so a second run reads the same instant. Taking `now` instead is the
  difference between a record and a snapshot.
- **Every set arrives ordered by identifier.** The document walk and the exception walk are both
  keyset-paged and both ordered; the code counts are grouped in code order. No set is rendered in
  whatever order a planner chose that day.
- **Nothing is derived from the environment** — no hostname, no build identifier, no locale-shaped
  number or date. A test renders twice and compares bytes; a source scan fails the module on
  `Date.now` or `new Date(`.

The keys are derived, so a retry overwrites its own object with the same bytes rather than leaving a
second differently-named record beside the first, and the completion write is guarded on
`state = 'processing'` so the load leaves that state exactly once.

**Decision 2 — the report is refused while the load does not reconcile, and it is checked twice.**

The load's counters are advanced relatively as documents finish; the artifact writer also counts the
rows themselves. **Both must agree** before anything is written. A report reconciled against the
number it was drawn from would reconcile with anything.

**Decision 3 — deduplication groups on an identity, never on a similarity score.**

The group is derived — `content-sha256:<hex>` for a file, `email-dedup-key:<key>` for a message, the
kinds kept in separate spaces so they cannot collide by coincidence — which lets every copy compute
the same group with no coordination and no read. A raw-bytes hash of an email is the wrong identity
because two copies differ in their transport headers, and the email subsystem already solved that.

The near-duplicate fingerprint that the extraction pass computes on the same row is **deliberately
not read here**. It is a similarity score that collides by design, and suppressing a document from
review on the strength of one would be deciding, on a heuristic, that a reviewer never sees a
document. Clustering over it is the review slice's job and it shows documents rather than hiding
them.

A document with no recorded hash gets **no group at all** — not a group of one. The platform declines
to assert anything about bytes nobody hashed; the cost is an extraction that might have been avoided,
and the alternative cost is evidence suppressed on a guess.

**Decision 4 — primacy is taken once, held by the database, and never moves.**

One statement whose `WHERE NOT EXISTS` refuses the claim while another member holds it, and a partial
unique index on `(review_set_id, dedup_group_id) WHERE dedup_group_id IS NOT NULL AND
is_dedup_primary = 1` as the same rule held for the write path nobody has written yet. A copy that
finds primacy taken reads the group back rather than trusting a row count, so the answer is the same
whether this process wrote the holder or a concurrent one did. A copy that finds a holder which has
not finished yet **parks and throws** — the queue redelivers, and since dispatch walks in identifier
order the primary is almost always one redelivery away.

**Decision 5 — the duplicate keeps everything except the extraction.**

The row survives, marked non-primary, with its own custodian and its own load, and an occurrence row
names the primary it sits behind. It reaches its own terminal state by mirroring the primary: a copy
of a document that was read is `processed` pointing at the **primary's** text object (a derived key,
so nothing is written twice); a copy of a document that could not be read is `excepted` carrying the
primary's **named codes on its own row**, with a detail saying the reason is that document's. That
last part matters for the report: the custodian who held an encrypted document is counted as having
held one rather than collapsing onto whichever copy the queue reached first.

**Decision 6 — a container family, bounded to one level, through the ordinary gate.**

Every entry re-enters the ingest chokepoint — presigned session, magic-byte sniff, content hash,
malware scan — by the same path an email attachment takes; there is no discovery bypass and no second
way to put bytes in a firm's bucket. Entries are sorted by path before they are numbered, so a
re-processing gives the same entry the same family sequence. The archive becomes the family head and
is `processed` with **no text object**: writing an empty text object for a container would assert it
holds no words, which is the assertion the whole exception vocabulary exists to avoid; the entry
listing goes in its sidecar.

**Expansion is one level per review document, absolutely, and not by counting.** The engine already
recursed to its own nesting ceiling and returned the tree flattened, so a child that is itself a
container is one the engine declined to open — re-expanding it here would walk straight past the
guard that stopped it. Such a child is recorded `container-not-expanded`.

Entries the engine described rather than opened become **one exception per kind, not per entry**:
`encrypted-container-entry` and `container-guard-tripped`, each carrying a count and a kind and
**never a path**. A path inside an opposing party's production is free text somebody writes a name
into; the paths live in the sidecar, which is a record rather than an error message.

---

**Three deviations from the design, deliberate and recorded.**

**1. The manifest carries three digests, not five.** The design asks for the five-algorithm set. The
shipped `review_document` table has three digest columns — SHA-256, MD5, SHA-1 — and adding two more
to the largest table in a firm's database, at a quarter of a million rows, to carry values no
e-discovery load-file specification asks for, is not a trade worth making. The three that are carried
are the three that are asked for, each labelled: SHA-256 as the identity, MD5 and SHA-1 as
legacy-interop exactly as `packages/file-integrity` labels them. MD5 and SHA-1 now reach the row from
the engine's own pass over the bytes, which is the only pass that would ever compute them; SHA-256
stays the ingest gate's value, because two authorities on whether two documents are the same document
is one too many.

**2. Engine VERSION pinning is replaced by the routes the corpus observed.** The design wants the
manifest to record the discovery core's version, the recognition model set's version, and the
conversion engine's version. **No engine reports a version over its service binding today**, and
inventing one would be worse than omitting it. What the manifest states instead is drawn from the
corpus itself: the distinct extraction routes its documents actually recorded, plus the per-document
route on every entry. That is a weaker claim than a version pin and a true one. When an engine grows
a version endpoint, the manifest gains the field.

**3. An exception row may sit on a document whose terminal state is `processed`.** The model said the
presence of a terminal-coded exception is what makes a document `excepted`. A container that expanded
fifty entries and skipped two encrypted ones is the counter-example: it processed, and it still owes
the reader a sentence about the two. Rather than invent an advisory-code list, the **report renders
the document's terminal state beside every reason**, so a reader can tell the two apart without
inferring anything, and the reconciliation is untouched because it counts states rather than
exception rows.

---

**Considered and rejected:** *rendering the manifest with a generated-at timestamp* (makes every
rebuild a different document); *clustering over the near-duplicate fingerprint to group duplicates*
(a heuristic deciding what a reviewer never sees); *deleting the duplicate row and keeping only an
occurrence* (destroys the answer to a question asked under oath, and breaks the load's arithmetic);
*picking the primary by lowest identifier across the whole group* (a later load adding a
lower-identifier copy would move primacy after the fact, which means re-extracting a corpus to keep a
tie-break rule); *letting a suppressed copy write its own text object* (doubles the largest derived
storage line to hold byte-identical bytes); *one exception row per skipped archive entry* (four
hundred rows drown the report they are written for); *putting entry paths in an exception detail* (a
redaction failure wearing an error message); *a second queue for load completion* (a pair of
production resources to create before the worker deploys at all, to carry one message per load);
*building the manifest in memory* (a load at the ceiling is far past an isolate's memory, hence the
fixed-part multipart writer).

**Consequences:** one additive per-firm migration (the dedup primacy index, the exception row's load
column and its index); the discovery lane's message becomes a two-kind union with the absent `kind`
still reading as a document, so messages in flight across a deploy still route; a document waiting on
the scan gate now parks **and throws** so the queue looks again, which is what a container's children
require and what the previous ack-and-forget path could never deliver; and the record artifacts carry
their own object class so a lifecycle rule cannot sweep the evidence with the cache.
