**The email parse core is a pure-Rust engine on the engine-host seam; it parses only, and rendering plus DKIM verification live outside it.**

**Context:** Nothing in the codebase can read an email. The upload policy accepts `message/rfc822` and `application/vnd.ms-outlook`, and the conversion registry declares `eml→pdf` and `msg→pdf` edges, but no MIME parser exists in the workspace and the `email` conversion engine is an unimplemented stub. An uploaded `.eml` is stored as an inert blob. Meanwhile the draft email-filing design assumes **PostalMime** (TypeScript) parses the forward/CC path in a Cloudflare Email Worker — a choice that would leave bulk mbox parsing, `.msg` MAPI decoding, and the desktop shell needing a second, Rust implementation later.

**Decision:** Build **`crates/email-core`** as the third engine on the [engine-host seam](../conventions/engine-host-seam.md), after `pdf-core` and `decryption-core`. It is I/O-free — bytes in, a `ParsedMessage` record out — reading `.eml` (RFC 5322/MIME via `mail-parser`), `.msg` (the CFB/OLE2 container via the `cfb` crate, with the MAPI property-stream decoding on top written and bounded by us), and mbox (a framing iterator over the `.eml` lane). It compiles twice: WASM as the default Worker lane, native as the heavy Container lane, making placement a routing decision rather than a rewrite — though only the WASM lane is built now, since nothing yet consumes the native one. Every dependency is pure Rust and the `r2` feature stays off, so the crate carries no C in its closure and needs no golden-rule-14 consent. (`cfb` is pinned per-crate at 0.14, matching `recovery-core`; it is not a workspace dependency.)

The core is **parse-only**. Rendering (`email→pdf`) and DKIM signature verification are consumers standing on it, not parts of it: the record captures `DKIM-Signature`, `Authentication-Results`, and the `Received` chain **verbatim with no verdict attached**, following the scan engine's "raw facts in the engine, the verdict in the app" rule. This keeps a crypto dependency out of a parsing engine and keeps the WASM edge light.

Two shapes in the record are load-bearing. **Extraction is two-phase** — `parse` returns part descriptors that name where a part's bytes live but do not carry them, and `extract_part` materializes one part on demand — so a Worker never holds an mbox's whole attachment set in an isolate and Discovery never pays for payload bytes it discards. A part's location is a typed `PartLocator`, not a bare byte range: `InputRange` for a MIME part (a contiguous span of the input), `MapiStream` for a `.msg` attachment (a stream reassembled from scattered compound-file sectors, which no span of the input denotes) — so a `.msg` part can never be mistaken for a slice of the buffer and extracted as the wrong bytes. And **the message identifier records its provenance** (`FromHeader` / `FromMapi` / `Absent`) rather than flattening to a string, because a `.msg` carries RFC 5322 headers only when `PidTagTransportMessageHeaders` survived — so for `.msg` sources the capture design's content-hash dedup fallback is the common case, not the exception, and a synthesized identifier must never be mistaken for the real one.

This **supersedes the PostalMime assumption** in the draft email-filing design: the Email Worker calls `email-core` through its WASM edge. Taken now because the capture spec is still Draft and the override costs a paragraph; taken later it would cost a migration.

**Considered & rejected:** a **TypeScript `@magna-carta/email` package** (postal-mime + a JS CFB reader) — fastest to a working `.eml` path and consistent with the existing spec, but `.msg` MAPI decoding is materially weaker in TypeScript, bulk mbox parsing on the isolate is the hot-path work golden rule 10 forbids, and Discovery plus the desktop shell would force a second Rust implementation regardless, yielding two parsers and two records. A **hybrid** (TypeScript MIME on the Worker path, Rust for `.msg`/mbox in a Container) — rejected because it institutionalizes exactly that divergence while the seam already delivers dual-target hosting without it. The **`msg_parser` crate** as the `.msg` reader — it looked like the obvious dependency, but an audit found a release-profile out-of-bounds panic reachable from its public entry point on crafted input (its sector-index loop is bounded by the input length, not the array length); on the WASM runtime, which cannot unwind, that aborts the whole isolate. It also carries no fuzz target, was dormant for roughly three years before an eleven-release burst over two days, and drags `regex` and `serde` into the bundle. Rejected in favor of the actively-maintained, heavily-exercised `cfb` (which is panic-free on malformed input across a fuzz sweep, and already a production dependency here) plus MAPI decoding we own and can bound.

**Consequences:** One parser and one output record serve capture, file upload, conversion, metadata, and Discovery. The conversion registry's `eml→pdf` / `msg→pdf` edges **stay unimplemented** after this work — closing them is a render slice. `.msg` files whose only body is compressed RTF yield no text body until an LZFu decoder is added. Owning the MAPI decoder is the cost of not trusting an unsafe dependency with privileged bytes on an unwind-less runtime: the decoder is written defensively (every input-derived index bounds-checked, no panic on malformed input, embedded-message recursion capped) and carries fuzz targets, so the confidentiality risk golden rule 14 warns about is met by construction rather than by a third party's diligence.
