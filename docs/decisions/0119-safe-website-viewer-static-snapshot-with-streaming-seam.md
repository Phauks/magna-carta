**The Safe Website Viewer uses Cloudflare Browser Rendering's `env.BROWSER` quick actions to capture a static snapshot — screenshot, redirect chain from a guarded redirect-probe, page title, extracted text, and outbound links — and returns only inert data to the user. The live page never loads in the user's browser. Interactive pixel-streaming is a documented future seam, not built.** Builds on ADR-0101 (the Tools layer), the shared SSRF guard (see `outbound-fetch-ssrf-guard-invariant`), and ADR-0017/ADR-0038 (redacted error logging).

**Context.** The hygiene use case is: a user receives a link they do not trust and wants to know what it leads to, without risk to their own device or browser session. The core safety property must be that no code from the suspect page executes in the user's browser. Two implementation paths exist: (1) a **static snapshot** — a headless browser visits the page remotely, takes a screenshot and extracts metadata, and the user receives only inert data (an image and text); (2) **interactive pixel-streaming** — a persistent headless browser session runs remotely, CDP events stream frames to the user's browser canvas, and the user's input is forwarded back. Option (2) provides a live, clickable session but requires Browser Sessions, a Durable Object per session, WebSocket frame streaming, input forwarding, and significant operational surface (concurrency limits, session lifecycle, teardown). Option (1) is sufficient for the hygiene use case and its non-interactivity is itself the strongest safety property — even if the remote browser were compromised, only image and text would cross back to the user.

**Decision.** (1) **Static snapshot via `env.BROWSER` quick actions.** The Worker route calls the Browser Rendering `env.BROWSER` binding (a Workers binding — no API token required). The quick actions (`/screenshot`, `/content`, `/markdown`, `/links`) return the rendered HTML screenshot, page content, markdown, and links. The `BROWSER` binding is added to the Worker's wrangler config. (2) **Redirect chain and response headers via a guarded redirect-probe.** The `env.BROWSER` quick actions follow redirects internally but do not expose the intermediate URLs or response headers. To surface the redirect chain and response headers — both critical for identifying phishing and cloaking — the route performs a guarded `fetch()` with redirect tracking before the browser render, passing every intermediate and final URL through `assertPublicTarget`. This data is returned alongside the snapshot. (3) **Only inert data is returned.** The screenshot is returned as an image; extracted text, redirect chain, response headers, page title, and outbound links are returned as structured data. Fetched HTML is never re-rendered as live markup in the application — it is shown only as escaped text or structured fields. (4) **Transient by default.** The screenshot is streamed through the Worker to the client and not persisted. This avoids accumulating hostile-site captures and matches the hygiene (not evidence) use case. A short-TTL content-hash cache to avoid re-rendering the same URL within a session is a noted optimisation, not built. (5) **Interactive streaming is a documented future seam, not built.** The seam: Browser Sessions (Puppeteer/Playwright + CDP `connect()`) for a persistent session; a Durable Object per session holding the CDP connection and enforcing lifecycle/idle-timeout/teardown; `Page.startScreencast` → JPEG frames over a WebSocket to a client canvas with throttling and backpressure; `Input.dispatch*` for mouse/keyboard/scroll forwarding; SSRF re-checked on every navigation. This is approximately 3–5× the build of the static path and a substantially larger operational surface; it is deferred. The static snapshot fully serves the hygiene use case, and its non-interactivity is the stronger safety posture.

**Consequences.** No hostile code from a suspect page can reach the user's browser — only a screenshot (an image) and structured text cross back. The `env.BROWSER` binding is sufficient and requires no API token. The redirect-chain/response-header data requires a separate guarded redirect-probe fetch because the quick actions do not expose it; this is the correct seam (Quick Actions for render, guarded fetch for headers/chain). The interactive-streaming seam is recorded with its full technical shape so the decision to defer it, and what building it entails, is unambiguous. When the streaming seam is built, the SSRF guard re-application on every navigation is a mandatory inherited constraint.
