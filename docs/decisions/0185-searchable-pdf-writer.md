**The searchable-PDF writer is a `pdf-core` function that writes recognized OCR text as an invisible, additive text layer, using a single non-embedded Type0/Identity-H font with a ToUnicode CMap.**

**Context:** The OCR engine reads a scanned page into per-page facts — line text and word boxes in PDF user space — but nothing writes those facts back into the document, so the PDF a reviewer opens is still an unsearchable picture. The OCR engine decision named this the natural next step: an invisible text layer "belongs in `pdf-core` beside the Bates content-append path, consuming exactly the word boxes this slice produces." This realizes the scanned-to-searchable edge the conversion orchestrator already routes to this engine.

**Decision:** (1) **Location and shape.** `pdf_core::write_searchable_text_layer(pdf, &[PageTextLayer])` reuses the Bates additive-append rule verbatim: guard the input, resolve page geometry, merge one shared font into each page's resources under a collision-safe name, and append a *new* content stream drawn last — never rewriting an existing stream, so every untouched byte is byte-identical. `pdf-core` takes a native input type (`PageTextLayer`/`TextRun`), so it depends on no OCR types; the container adapts `PageFacts` into it. (2) **Invisible, additive, deterministic.** Each run is drawn in text render mode 3 (neither filled nor stroked), placed by a text matrix at its box with a horizontal scale fitting the run to the box width. A page that already carries visible text is never given a layer; a re-run of the same inputs is byte-identical, the property re-OCR discipline needs. The written text reads back through the page observer as present-but-invisible, so the OCR skip-gate still treats the page as a scan and redaction can still find and remove it. (3) **Font — non-embedded Type0/Identity-H + ToUnicode.** The two-byte codes are the text's UTF-16BE code units, with `CIDToGIDMap /Identity` and a constructed `ToUnicode` CMap. Because the layer is invisible, the font's glyph program is never executed — extraction rides the ToUnicode CMap and selection geometry rides the widths and text matrix — so the font need not be embedded, avoiding a vendored glyphless-font binary while covering everything the engine reads (Latin, CJK, Greek; all BMP). Embedding a small glyphless font is a documented fast-follow if a target viewer ever needs a rendered selection glyph; PDF/A conformance is a separate, later concern. (4) **Placement granularity.** Where a line's whitespace-split word count matches its per-word boxes, each word is placed at its own box (word-level selection); otherwise the whole line is placed at the line box — still searchable, only coarser. (5) **Deferred seams (not built):** the delivery path (the `ocr-worker` forward, a main-worker route, the `tools:ocr` reach, and the OpenAPI contract for `/ocr/searchable`); the conversion-orchestrator dispatch; ingest-time wiring (queues, per-job Durable Object, search index); rotated/skewed-quad placement beyond axis-aligned bounds; and the UI.

**Fitness tests:** the written layer round-trips through the page observer as extractable text yet reads as zero visible-text coverage; Latin, CJK, and Greek all recover through the ToUnicode CMap; the same inputs produce byte-identical output; a page with no runs (or one that already has text) is returned unchanged down to the byte; a bare image is refused by `/ocr/searchable` rather than returned unchanged; the input decompression-bomb guard rejects oversize input.

**Builds on the OCR engine decision** (the raw facts this consumes) and **ADR-0030** (the conversion orchestrator dispatches scanned-PDF-to-searchable-PDF to this engine). Reuses the Bates content-append and redaction observation machinery. Bounded by **ADR-0003** (the container is firm-agnostic; the worker owns firm scoping).
