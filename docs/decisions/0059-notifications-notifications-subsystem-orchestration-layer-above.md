**Notifications subsystem — an orchestration layer above the Communications transport: one notification-type registry owns the _decision_ (event → who → which channel → wanted? → read?) and the in-app center; external delivery is delegated to the Communications ports; realtime stays deliberately minimal (durable rows + refetch/poll, per-user push a seam).** **Context:** notifications were anticipated everywhere but designed nowhere — a _Delivery model_ parity row (web vs. native), a _Communications layer_ "trigger engine" (deadline/payment/report-ready reminders), a _Settings_ "My Account → notifications" category, a job-completion "completion notification" (ADR-0030), a _Tasks and workflows_ "notification/escalation" Needs-development note, _Calendar/docketing_ reminders, _Safe Custody_ release reminders, and the diagnostics-agent "acknowledge the user in-app/portal" (ADR-0038) — plus _Architectural integrity & coherence_ (ADR-0051) explicitly naming "notification templates" as an anticipated registry category, while ADR-0054 **rejected a global server-push layer for v1**. Eight subsystems depend on a thing with no home, no event model, and no ADR. **Decision:** make Notifications a first-class subsystem that **separates the decision from the delivery** and owns the decision. (1) **Boundary — orchestration above transport.** Notifications owns the event model, recipient resolution, per-recipient routing preferences, and the in-app notification center; it **delegates external delivery (email/SMS/voice) to the _Communications layer_ ports** (ADR-0047), which becomes pure channel transport — the trigger-engine _brain_ relocates here (**ADR-0047 amended**). Rejected: _fold into Communications_ (overloads external/client transport with internal/staff concerns and telecom-compliance domains it does not share) and _in-app-center-only_ (splits routing across two homes — the registry anti-pattern). (2) **Registry-first** (ADR-0051/ADR-0040): every notification is a declarative **type** (`key`, `category`, **audience** internal-`member`/external-_Directory_-entity, `severity`, `mandatory` vs opt-out-able, eligible `channels` + default routing, channel-aware `templates` from the glossary, `cadence` immediate/scheduled/digest, `audited`), the single `audience` field unifying the staff bell and the client appointment-reminder under one model; conformance is a **fitness function** (every declared channel has a template; mandatory categories declare no opt-out; a notifiable event not routed through the registry is flagged). (3) **Preferences** are a _Settings_ My-Account category resolving user → firm → system (ADR-0040), with **mandatory categories (security, trust-compliance) non-silenceable** and external routing additionally gated by the ports' **STOP/HELP + TCPA** state. (4) **Delivery is always durable** — a **per-firm D1 row** the instant the event fires (IDs + non-sensitive fields only, never privileged content; a canonical deep-link per ADR-0052) — so the realtime question governs only how fast an _already-stored_ row surfaces. **v1 channels:** in-app (the center), email + SMS via the Comms ports; **seams:** web push (VAPID/Push API on the app-shell SW), desktop-native/tray (rides Tauri, in-app fallback — parity per ADR-0023), digest rollup. (5) **Realtime stays minimal (honors ADR-0054):** v1 freshness = **refetch-on-focus + cross-tab BroadcastChannel + a cheap unread-count poll** (no global push); **job-completion rides the existing per-job Durable Object channel** (ADR-0030/ADR-0039) for instant delivery; a **per-user DO push channel is the documented seam** (extends the named DO-per-job primitive), adoptable later behind the same call sites. Rejected: _build the per-user push channel now_ (the infra ADR-0054 deliberately deferred; no sub-second need justifies it). (6) **Raise as a chokepoint seam** (ADR-0051): one `notify(type, context)` port, but the high-value raises are **co-located with an existing unbypassable path** — money/sensitive notifications raise from **the same write that lands the audit-log entry**, task assignment from the task write path, conflicts/portal/deadline/job from their own seams — and fan-out runs **off the hot path** via Queues (ADR-0039). **Scheduled** reminders are materialized by a **Cron-triggered Workflow** sweeping due reminders per firm (the ADR-0050 fan-out), deadline dates computed in the **court's zone** (ADR-0055). (7) **Confidentiality** inherits the observability discipline (ADR-0038): external channels carry **no privileged content** (reference + deep link, allowlist-assembled), in-app may show more behind RBAC/ethical-walls but **re-checks access at read time** in the firm-scoped DAL (a stale/walled row is filtered, never an existence oracle — the 404-not-403 logic of ADR-0052); rows are per-firm + recipient-scoped; preference changes and audited-category dispatch are audited (metadata only). **Considered & rejected:** _fold into the Communications layer_; _in-app-center-only_; _build the global server-push layer now_; _embed content in notifications_ (a leak surface — references only). **Consequences:** the scattered triggers and the _Tasks_ escalation / _docketing_ reminder Needs-development notes gain one home and become notification types; the Communications layer simplifies to transport; v1 ships durable in-app + email/SMS + scheduled reminders without premature realtime infra; cost is the registry + in-app center + the on-raise seam discipline. **Amends ADR-0047** (Comms = transport); reuses **ADR-0040** (settings/preferences), **ADR-0051** (registry/seam/fitness), **ADR-0054** (freshness model + per-user-push seam), **ADR-0030**/**ADR-0039** (DO-per-job reuse, off-hot-path), **ADR-0050** (Cron-Workflow fan-out), **ADR-0055** (court-zone deadlines), **ADR-0038** (redaction), **ADR-0003**/**ADR-0052** (isolation, access-gated read, deep-links), **ADR-0023** (parity). A full subsystem spec (the type catalog, the raise-seam inventory, and the in-app-center UI archetype) is the planned next step.
