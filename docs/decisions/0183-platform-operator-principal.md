**A minimal `platform_operator` principal — the first global, cross-firm authorization axis.** Status authoring (declaring a service event, posting a rolling update, setting a component override) is a repeated, attributed, human action performed during incidents, and neither of the two authorization mechanisms already in the codebase fits it.

**(1) Why not the existing shared secret.** Firm-provisioning is gated by `PLATFORM_ADMIN_KEY`, a constant-time-compared shared header secret. It authenticates a **request**, not a **person** — it has no identity to record as an event's author, yet an incident timeline's whole value is "who said what, when." It suits a rare, machine-ish call (minting a firm), not a repeated human one under stress: handing every operator the same shared secret to paste means secret sprawl, no per-person revocation, and a rotation that locks everyone out at once. It also conflates "platform automation gate" with "which humans may speak for the platform." The secret's own code comment already named a real platform-admin principal as a later seam; this is that seam, built for status.

**(2) Why not `platform_staff`.** The support-access framework (ADR-0157) already introduced a control-plane `platform_staff` principal, but it is a different shape by design: it is the **reach-into-one-customer-firm** identity — credential-less, belongs to no firm, and only ever yields a single-`firmId`, grant-scoped, time-boxed session redeemed from a firm member's support grant. It has **no global session**, and a cross-firm surface is explicitly out of its model. Status authoring is a global action by a logged-in human acting on no single firm — the opposite shape. Growing `platform_staff` a global session to cover it would contradict its by-design firm scoping and entangle status with the support subsystem. The two tables are parallel and hand-seeded, conceptually adjacent ("people who run the platform"), but kept as separate axes; a future unified platform principal could subsume both, but that convergence is its own project.

**(3) The principal.** A `platform_operator` table in the **control-plane** database: `{ user_id, granted_at, granted_by_user_id, expires_at (nullable), note }`. It is a distinct **platform** authorization axis, separate from per-firm RBAC (which stays per-firm and does not gain a global role). `expires_at` mirrors the per-firm `direct_grant` time-boxing pattern: `NULL` is standing membership, a timestamp is a grant that lapses automatically. Membership is seeded by hand for now — no self-service grant UI in this slice.

**(4) The guard.** `platformOperatorGuard` middleware in `apps/worker` reuses the Better Auth session the chokepoint already resolves, and requires the session's `userId` to be an active, unexpired `platform_operator` row (`expires_at IS NULL OR expires_at > now`). It runs as a route-level guard on the status write group, on the platform axis — not the per-firm RBAC permission check. Unauthenticated requests get 401; non-members and lapsed grants get 403 (with a distinct `not-operator` vs. `mfa-required` denial cause recorded in telemetry). Every write is stamped with the session `userId` as `authorUserId`, so attribution and audit fall out for free — public exposure of that identity is prevented separately by the service-status design's audience-scoped merge, not by this guard.

**(5) MFA is required, not optional.** Because a platform operator can publish public-facing status and is the seam a later cleanup may extend to provisioning, the guard additionally requires the account's Better Auth `twoFactorEnabled` flag. This matches the support-access framework's "MFA mandatory" posture for `platform_staff` — a platform-trust identity should not rest on a password alone. A member without two-factor enabled gets 403 with an "enable two-factor" detail, distinct from the not-a-member 403.

**Considered & rejected.** **Reusing `PLATFORM_ADMIN_KEY` for status writes** — no per-person identity, no revocation, wrong shape for a repeated human action; rejected (see (1)). **Growing `platform_staff` a global session** — contradicts its deliberate firm-scoped, grant-redeemed design and would entangle two unrelated subsystems; rejected (see (2)). **A per-firm RBAC permission for status** — there is no firm to scope it to; status is a platform-wide fact, not a firm's data; rejected in favor of a distinct platform axis. **A self-service grant-management UI in this slice** — deferred; membership is hand-seeded until a management surface is built.

**Consequences.** The platform gains its first real cross-firm authorization axis, cleanly separated from per-firm RBAC and from the support-access principal, with MFA and per-person time-boxed grants built in from the start. `PLATFORM_ADMIN_KEY` is unchanged and remains firm-provisioning's gate — migrating provisioning onto `platform_operator` is a natural, named follow-on cleanup, not done here. Deferred: self-service membership management, and any AI/agent principal on this axis.
