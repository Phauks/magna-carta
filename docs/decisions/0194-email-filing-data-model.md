**The matter-email record is five per-firm tables — message, thread DAG, multi-matter junction, participant, attachment — deduped by Message-ID with a content-hash fallback, metadata in D1 and bytes in R2, reconstructed by link + DAG rather than copied per reply.**

**Context:** The subsystem brainstorm ([`docs/specs/2026-06-16-email-filing-design.md`](../specs/2026-06-16-email-filing-design.md)) settled that email should be a first-class, thread-aware, multi-matter record rather than a folder-file or a loose "communications" list (the differentiator every incumbent leaves open). The parse engine ([ADR-0173](0173-email-core-parse-engine.md)) surfaces a typed `ParsedMessage` with a `MessageIdentifier` that carries provenance (`header` | `mapi` | `absent`) and never flattens it — a `.msg` MAPI-synthesized identifier is not the same bytes another recipient's `.eml` copy carries. The File Manager stores blobs under per-version keys, not content-addressed keys, so attachment dedup lives at the version/scan-cache layer. Directory address→entity resolution merged after the gate check (`findEntitiesByEmailAddress`), so participant resolution can light up now rather than stay deferred.

**Decision:** (1) **`email_message` — one row per unique message, the unit of truth.** It carries `message_id_value` + `message_id_provenance` (never flattened, mirroring the engine's typed identifier), subject, sent/received UTC instants ([ADR-0055](0055-foundational-data-runtime-conventions-time-dates.md)), from display/address frozen as-at receipt, `thread_id`, `in_reply_to`, `content_sha256` ([ADR-0078](0078-documents-tenancy-data-isolation-storage-foundation-follow-ups.md)), `dedup_key`, `original_r2_key` (the verbatim original), `references_remote_content`, the captured `integrity` facts stored verbatim with no verdict, `dkim_verdict` defaulted `unverified`, `source_format`, and `captured_via` provenance. **Unique on `(dedup_key)`** (the table is already per-firm). (2) **Dedup identity is `Message-ID` (+ firm)** — identical in every recipient's copy, so cross-user/cross-inbox capture converges to one row. When the identifier is absent or rewritten, the `dedup_key` falls back to a SHA-256 over normalized headers (canonical casing/order, value-trimmed) + the first text body, whitespace-collapsed. A second capture updates provenance ("also confirmed"), never inserts a second message; it may add a new link but never a second `email_message`. (3) **`email_thread` — the conversation as a DAG, not a line.** Edges are carried on `email_message.thread_id` + `in_reply_to`/`references` (a separate edge table is deferred with the integrity/tamper-diff work); forks and late-surfacing messages are edges. A matter's email view is reconstructed from all messages linked to that matter, deduped by `dedup_key`, ordered by the DAG + time — **never a re-saved per-reply blob** (the storage lever: store each unique message once, thread = links). (4) **`email_matter_link` — the multi-matter junction, stored once and linked many.** `(email_message × matter)`, **unique on the pair** (can't double-file to the same matter, can link to many), carrying `state` (`staged` | `filed` | `unlinked`), `linked_by`, `linked_at`, per-matter tags, and the capture entrance. Access is per-link/per-matter; unlink is not delete (the last link removed orphans the message, retained per policy + legal hold). (5) **`email_participant` — each from/to/cc/bcc frozen as-at receipt.** The frozen address string is the record (no shadow address list); a nullable `directory_entity_id` enriches it, resolved through the Directory reverse lookup where a match exists and left null otherwise (graceful degradation, not a fake). (6) **`email_attachment` — the link, not the bytes.** Real attachments are extracted into the matter's File Manager as first-class `file`/`file_version` documents through the existing untrusted-file quarantine chokepoint ([ADR-0081](0081-documents-file-handling-inbound-upload-path.md)); this row ties the `file_id` back to the message + thread with the part's declared filename/media type, `disposition` (`attachment` | `inline`), and whether it was promoted from an inline image. Decorative `cid:` inline images are recorded `inline` and not made documents (a later "promote" is a data change, not a re-parse). (7) **Metadata in per-firm D1, bulk bytes in per-firm R2** ([ADR-0003](0003-tenancy-isolation-tenancy-control-plane-d1-per-firm.md), golden rule 3); no query crosses firms; sensitive bodies/identifiers wrap `protected()` where the firm flags them ([ADR-0084](0084-encryption-keys-protected-concretization-envelope-context.md)).

**Considered & rejected:** keying dedup on a content hash alone (a Message-ID is identical across every recipient's copy and free; a content hash is the *fallback* for stripped identifiers, not the primary key); flattening message-id provenance into a single string (collapses the header-vs-MAPI distinction the engine deliberately preserves, so a `.msg` and `.eml` copy of the same logical mail would falsely appear identical or falsely distinct); copying a message per matter (the LEAP/Clio duplicate-across-matters bug — the junction stores once, links many); a per-reply re-saved thread blob (N copies of quoted history; reconstruct from links + DAG instead); content-addressed single-blob attachment storage in this slice (the File Manager keys by version, not content — true single-blob storage is a named enhancement, not free from the current store); modeling participants as a firm-wide shadow address book (the frozen string is the evidentiary record; the Directory link is enrichment).

**Consequences:** The record is discovery-ready now (content hash, verbatim original, immutable capture audit). The add-in and mailbox-sync slices feed this exact model and dedup with no parallel path. Turning on richer participant resolution or the DKIM verdict later is a backfill + a wiring step, not a schema change. The thread edge table, tamper-diff, and "unauthenticated — from quote" markers are later slices the DAG columns already anticipate. **Realizes** the parent design's reserved data-model ADR.
