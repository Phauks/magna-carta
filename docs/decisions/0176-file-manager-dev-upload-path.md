**The local development upload path is a Worker route gated on real-credential absence, not a production flag or a new wrangler binding.**

**Context:** Production upload is a four-step direct-to-R2 ceremony (`uploads.initiate` → presigned PUT or multipart `signPart` → `uploads.complete` → an R2 object-create event feeds the files-ingest queue, which commits or quarantines the version). Locally this cannot run: `apps/worker/.dev.vars` deliberately omits `CLOUDFLARE_ACCOUNT_ID`, so `presignerForEnv` selected a dev presigner that minted `https://r2.dev.local/...` — a host that does not resolve. No bytes reached storage, no R2 event fired, ingest never ran, so the whole upload-and-ingest surface was unobservable off production.

**Decision:** Off production — when the real R2 S3 credential set is absent — the dev presigner points its **upload** URLs (`presignPut`, `presignUploadPart`, and the server-side multipart create/complete/abort) back at the Worker itself, and a development-only route (`apps/worker/src/routes/dev-r2-upload.ts`, bare `app.put` under `/api/__dev`, never a `/api/v1` operation and never in the OpenAPI contract) accepts those writes to the Miniflare `R2` binding and **enqueues the files-ingest message directly**, standing in for the R2 event notification local storage does not emit. The client runs the identical ceremony in both environments; nothing is stubbed client-side. Download/preview presigning is left on its existing non-network dev stub (that path is out of scope and needs a bound `FILES_ORIGIN`).

**The registration guard is credential-absence, not a binding.** An earlier design gated the route on a development-only `wrangler` binding; that was rejected. Named `wrangler` environments do not inherit bindings, so a `dev`-environment binding would force duplicating every production binding to run the route — a config-drift machine — and a binding declared to gate one route is still configuration a deploy could mis-set. Instead the route registers on exactly the condition that already selects the dev presigner: the absence of `CLOUDFLARE_ACCOUNT_ID` / `R2_S3_ACCESS_KEY_ID` / `R2_S3_SECRET_ACCESS_KEY` (`devUploadEmulationActive`, the single shared predicate in `presigner-wiring.ts`). Production cannot sign a real presigned upload without those credentials, so "the dev presigner is in use" already implies "real presigned upload is dead" — a **fail-closed, self-enforcing** signal costing no new configuration. Wherever the route could activate, no working production upload surface exists to expose.

**Defence in depth (two more guards, both required):** (1) the route sits behind the normal chokepoint — session, then `files:upload` — so even reachable it is never an unauthenticated write; (2) it writes only the object key the firm's own `uploads.initiate` minted (the key must resolve to a still-pending version in this firm via `loadPendingVersionForIngest`), so an arbitrary or cross-firm key is refused.

**What this route cannot prove.** It is **same-origin**, so it exercises no CORS. The most likely production upload failure — a bucket with no `AllowedOrigins`, or multipart unable to read the `ETag` response header — is invisible to every local run against it. The dev route is therefore explicitly **not** the acceptance gate. The acceptance gate is one real upload against a real bucket in a preview environment, including a file large enough to take the multipart path. To make that reachable, the first R2 bucket CORS configuration in the repo is checked in (`apps/worker/r2-cors.json`: app-origin `AllowedOrigins`, `GET`/`PUT`, `content-type`, and `ExposeHeaders: [ETag]`) with its runbook step in `docs/conventions/operations.md` — applied out-of-band against the bucket by the owner, never by CI.

**Fitness tests:** the dev route refuses to serve (bare 404) when the full R2 S3 credential set is present, and is otherwise wired (a 401 under the same request without a session); an unauthenticated request 401s; a key no upload session minted is refused (404) while the key `uploads.initiate` minted is accepted and its bytes land in the `R2` binding. The upload-ceremony integration suite runs the worker-origin single-shot and multipart paths (sign part → stage the part through the dev route → complete assembles the staged parts) end to end.
