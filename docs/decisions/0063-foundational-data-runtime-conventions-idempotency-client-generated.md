**Idempotency — client-generated IETF `Idempotency-Key` with Stripe semantics; atomic dedup via a UNIQUE idempotency-row insert committed in the same D1 transaction as the effect; chokepoint-enforced and required on side-effectful routes; processor pass-through.** **Context:** exactly-once money movement under retries/double-clicks/network failure is a crown-jewel correctness property binding the append-only ledger (ADR-0008), payments (ADR-0032), and the client's optimistic-mutation/retry behavior (ADR-0054); ADR-0057 (durability on close) already names idempotency as a dependency. A §9 member. **Decision:** (1) **Standard surface** — mutations accept a client-generated **`Idempotency-Key`** header (IETF `draft-ietf-httpapi-idempotency-key-header`, the WG draft standardizing exactly this; Stripe semantics): the SvelteKit client (TanStack Query, ADR-0054) mints one key per _logical_ operation and reuses it on retry; the public API (ADR-0022) takes the same header from third parties. (2) **Mechanism** — a per-firm D1 `idempotency_key` table stores key + request fingerprint (method+path+body hash) + status (`in_progress`/`completed`) + captured response (status+body). Repeat resolution: **completed+same-fingerprint → replay stored response, no re-execute**; **in-progress+same-fingerprint → `409`**; **same-key+different-fingerprint → `422`** (client bug surfaced). (3) **Atomicity** — the idempotency row and the effect (ledger postings) **commit in one D1 transaction**, and the row's `UNIQUE` key **is** the concurrency guard (two simultaneous identical requests race to insert; one wins, the other is served as a duplicate) — exactly-once with no separate lock, reusing the UNIQUE-insert idiom of ADR-0062. (4) **Chokepoint-enforced** (ADR-0051) — idempotency lives in the API/DAL mutation middleware; each mutating route declares `idempotency: required | optional` in metadata (**required** on money/trust/payment/outbound-comms routes), a conformance fitness function asserting every side-effectful route requires it. (5) **Scope/lifecycle** — per-firm; the fingerprint includes the endpoint so cross-endpoint reuse trips the mismatch; **~24h TTL**, a Cron job purges expired rows (ephemeral dedup state, not the record of truth — the append-only ledger is). (6) **Processor pass-through** — the same key is passed to Helcim/Stripe (which honor idempotency keys) so the external charge dedups too; reliable _outbound_ delivery is the transactional outbox (ADR-0064). Inbound dedup + outbox + idempotent consumers = end-to-end **effectively-once**. **Considered & rejected:** **server-generated keys** (idempotency is inherently client-keyed across retries); **require a key on all mutations** (uniform but taxes every trivial write — required only where irreversible); **a separate distributed lock for concurrency** (the UNIQUE-insert in the single-DB transaction already serializes — simpler, no extra infra); **storing only success responses** (Stripe stores success _and_ failure — a failed-then-retried op must replay the failure, not silently re-run). **Consequences:** money posts exactly once under any retry; double-submit and network-uncertainty are safe; cost is the per-firm idempotency table + TTL sweep + the route-metadata discipline. Reuses **ADR-0062** (UNIQUE-insert idiom), **ADR-0051** (chokepoint/conformance), **ADR-0054** (client mutation keys); binds **ADR-0008**/**ADR-0032** (ledger, payments); paired with **ADR-0064** (outbox) and depended on by **ADR-0057** (durability). Implementation detail in the _Foundational data conventions_ spec. **Amendment (2026-06-09):** D1 has **no interactive transactions** (`BEGIN` is rejected at runtime; the upstream feature request is closed-not-planned; the 2025 Sessions API is read-replication consistency only — no transaction semantics), so "the same D1 transaction" is realized as **one `D1Database.batch()`** — Cloudflare executes a batch as a single all-or-nothing transaction. The `@magna-carta/data-access` write path is: pre-check `SELECT` (fast replay/409/422), **speculative** handler effect (it produces statements and outbox messages, committing nothing — safe because handlers never call external services directly; that is the ADR-0064 chokepoint), then one batch ordered `[INSERT idempotency record, …business statements, outbox rows]`. The UNIQUE(key) insert remains the concurrency guard: a losing duplicate's **entire batch rolls back**, and it re-reads and replays the winner's stored response. The record is written **directly as `completed` with the captured response in the same batch as the effect**, so crash-between-effect-and-record is impossible by construction; `in_progress` is retained as a reserved state (a future long-running/external-call path) and still yields 409 when encountered. All primary keys are minted client-side (ADR-0062), which is what makes up-front batch binding possible.
