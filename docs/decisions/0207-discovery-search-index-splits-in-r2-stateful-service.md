**The discovery search index is durable per-firm state, so it is built as a stateful service: Tantivy indexes as immutable splits in per-firm R2, pruned + range-read from an always-warm Container, cataloged in the firm DO; Vectorize namespace-partitioned per firm; both behind one swappable port.**

**Context:** ADR-0012 accepted Tantivy (keyword) + Vectorize (semantic) as the discovery search engines, "full production workflow, large-scale designed-out-but-deferred." ADR-0167 then set the Container-subsystem pattern (heavy native runtime → dedicated stateless Worker reached by service binding) and explicitly carved search **out** of it: a subsystem whose state *is* a durable per-firm dataset fails the statelessness test and "gets its own spec as a stateful service when search is scheduled, and must not be modeled as 'scan again'" — leaving index storage, per-tenant isolation, and rebuild as named open questions. `roadmap.d/discovery.md` records every `discovery.search.*` node not-started (no Tantivy crate, no Vectorize wiring on the tree); the embedding substrate exists (`packages/inference`: `InferencePort.embed`, platform-fixed `@cf/baai/bge-large-en-v1.5` pinned to Vectorize index v1). This decision answers the deferred questions and unblocks the build.

**Decision:** (1) **Search is a stateful service, not the scan pattern.** The index is firm state; the search Worker owns durable per-firm data (splits in R2, catalog in the firm DO) and a **warm** Container that keeps hot index state resident between queries — the inverse of scan's spun-per-request statelessness. It takes the `apps/scan-worker` *shape* (no public surface, service-binding-only, `enableInternet = false`, warm-poke cron) but not its stateless *seam*. (2) **The Tantivy index is stored as immutable splits in R2.** A split is a self-contained bundle of Tantivy segment files plus a footer (term-dictionary offsets, per-field metadata, doc range), written once to `firms/<firmId>/search/<matterId>/splits/<splitId>.split` and never mutated; new documents make new splits, splits are only added, compacted, or deleted whole (large splits use multipart `put`). This is the Quickwit split model over R2 via an object-store-backed Tantivy `Directory`. (3) **Query is footer-pruning + ranged reads.** The query enumerates a matter's live splits from the catalog, reads each split's **footer** (small ranged GET or warm-cache hit), prunes splits whose terms/range exclude the query without touching their postings, then issues HTTP **range GETs** for exactly the postings and doc-store blocks the surviving splits' query walks — so per-query I/O scales with **query selectivity, not corpus size**. That is the whole answer to "search large, growing corpora continuously": the index grows, the per-query read does not. (4) **An NVMe warm cache** in the Container (LRU by matter, footers first, postings second), kept resident by the warm-poke cron, makes the common query a local read; R2 is the durable backing store, the cache is the latency layer. (5) **The per-firm split catalog** lives in the `FirmDatabase` DO lineage (behind the data-access layer, ADR-0003) and is the **sole** authority the query path enumerates splits from — never an R2 `LIST` — so a query is structurally confined to its own firm's splits, and compaction swaps catalog rows transactionally while immutable splits keep in-flight queries correct. (6) **Vectorize is namespace-partitioned per firm** (never one flat index): 1024-dim vectors from `bge-large-en-v1.5` via `InferencePort.embed`, `{documentId, matterId, chunkId, page}` in ≤10 KiB metadata (chunk text stays in R2/the doc-store, not Vectorize), topK ≤ 100. The ~5M-dimension/index ceiling is designed against up front — namespace-per-matter within a firm index, or index-per-firm for large corpora, sized at build against the load-profile fixtures. (7) **Hybrid ranking by reciprocal rank fusion** — BM25 and cosine lists combine by `Σ 1/(k+rank)`, needing no cross-engine score calibration and degrading gracefully when one half is empty; de-duplicated by `documentId`, hydrated through the data-access layer. (8) **One swappable `SearchIndexPort`** (`index` / `remove` / `query` with a `keyword | semantic | hybrid` mode) is the single chokepoint, in the shape of `InferencePort`/`ConversionPort`; the Tantivy schema/build/read is a pure `crates/search-core` Rust crate (port-free, like `pdf-core`, memory-safe with no C dependency — golden rule 14) the Container drives. (9) **The index is a derived cache.** Documents durably live in R2; splits and vectors are rebuildable from source at any time, deletion is **provable** (catalog entry removed + Vectorize vectors deleted by id + tombstone → compaction physically drops), and an index-generation version gates schema changes so a query never mixes versions — the defensibility e-discovery requires. (10) **Large-scale is a widening, not a rewrite** — Container sharding routes split-ranges to more instances and merges partials with the same prune→range-read→merge path; parallel OCR is a queue-concurrency knob; desktop-local indexing implements the same port over the same crate with the server as fallback. Each is built when the load harness measures the moderate-scale design out of headroom (golden rule 10); the seams that are expensive to retrofit — the split boundary, the catalog, namespace partitioning, the port, generation versioning — are built up front.

**Considered & rejected:** *Model search on the scan/OCR Container pattern* (ADR-0167 rejects this by name — the index is state, not stateless compute; a per-request Container would rebuild the working set every query and own no durable index). *Keep the whole index memory-resident in a Durable Object or the Container* — rejected: a matter's index is far larger than DO/Container memory, and it must survive restarts and shard; R2 is the only home that scales and persists. *Query by loading whole index files from R2* — rejected: it makes per-query cost scale with corpus size, the opposite of the requirement; footer-pruning + ranged reads is the mechanism that decouples them. *One flat Vectorize index for all firms* — rejected: no structural firm isolation and the ~5M-dim ceiling is hit almost immediately; namespaces are mandatory. *Store chunk text in Vectorize metadata* — rejected: 10 KiB/vector is a pointer budget, not a document store, and it would duplicate the doc-store. *Calibrate BM25 and cosine into a shared score* — rejected: score spaces are incomparable and calibration is brittle; RRF fuses ranks without it. *Put the index in D1* — rejected: bulk index content is exactly the "bulk content to R2, never D1" rule (golden rule 3); D1 holds the small catalog, not the postings. *A Tantivy candidate-generation path for conflicts* is a separate, already-closed question (conflicts uses shipped D1-native blocking; this index is the discovery corpus, not the Directory). *Build sharding / parallel OCR now* — rejected as speculative machinery (golden rule 10); the split model makes them additive.

**Consequences:** The discovery search subsystem has a buildable design that needs no new subscription (marginal cost: R2 split storage as an expirable derived cache, R2 Class B bounded by query selectivity, existing Vectorize + Workers-AI-embedding lines, one warm search-Worker instance). The open questions ADR-0167 deferred are closed: storage = splits in per-firm R2; isolation = firm R2 prefix + firm-DO catalog + Vectorize namespace; rebuild = replay the write pipeline from source. `crates/search-core` is the first buildable slice and needs no Cloudflare; steps 2–6 of the spec build and test the port, catalog, both index halves, and the write pipeline while `apps/search-worker` stays dormant (the conversion subsystem's wired-but-dormant model). Highlight-offset fidelity ties search correctness to the searchable-PDF writer's placement (the rotated-page gap in `crates/pdf-core/src/searchable.rs` is a search-correctness dependency, not only a display one). **Serves ADR-0012** (the engine choice) and **completes the stateful-service seam ADR-0167** left open; builds on **ADR-0003** (firm-scoped data access), **ADR-0039** (off the hot path), **ADR-0060** (OCR engine), the searchable-PDF writer, and `packages/inference` (the pinned embedding substrate).
