**Decompression-bomb guard — a crate-wide raw-bytes pre-flight, not a parser fork.**

**Context:** every `pdf-core` operation inflates compressed PDF streams with no size bound. lopdf 0.41's `LoadOptions` exposes no size or decode limit, and its `Stream::decompress_zlib` reads a `ZlibDecoder` to completion into an unbounded `Vec` — a path our own `decompressed_content()` call sites hit, and one that also runs *inside* `load_mem` itself when `ObjectStream::new` decompresses an object stream (ObjStm) to enumerate its packed objects, before any of our code runs. hayro is a second, independent parser (`Document::load`) with its own unbounded internal decompression. An input-byte cap alone is not sufficient: a single zlib stream tops out near 1032:1, so a roughly 1 MB ObjStm inside an otherwise-capped file still inflates to roughly 1 GB at load time. This exposure had been disclosed-and-deferred in every prior engine slice (redaction, scrub, detector, surgery, secure, generate) because it belonged to none of them — it is a shared seam across the whole crate.

**Decision:** bound memory with one parser-agnostic mechanism — `guard_input`, a raw-bytes pre-flight called once at the start of every public `pdf-core` operation, before either parser sees the bytes. It (1) rejects input over `max_input_bytes`, then (2) walks the raw file for each `stream` keyword and runs a bounded inflate of the following bytes (zlib per RFC 1950, then raw-deflate per RFC 1951) into a counting sink that discards the decompressed bytes, aborting the moment one stream exceeds `max_stream_inflated` or the running cumulative total crosses `max_total_inflated`. Operating on raw bytes rather than parsed xref structure means one pass covers both lopdf and hayro, and it closes the ObjStm load-time vector **for unencrypted documents** — an unencrypted object stream is itself a top-level `stream` object the pre-flight reads (objects cannot nest inside a nested ObjStm per the PDF spec). No fork of either parser's internals is needed, matching the engine's charter of composing pure-Rust crates and building only the gaps. (Encrypted stream bodies are opaque to the pre-flight; see the disclosed residual below.)

**Caps and basis:** `max_input_bytes` = 256 MiB, `max_stream_inflated` = 256 MiB, `max_total_inflated` = 1 GiB — evidence-based, not guessed. The input cap is bracketed by what the field accepts: US federal e-filing (CM/ECF) caps per district at 35–75 MB with a 200 MB outlier, and commercial PDF services (Adobe PDF Services, Smallpdf) cap at 100 MB; a legitimate legal PDF essentially never exceeds ~200 MB, so 256 MiB clears that ceiling with margin while staying inside the wasm32 memory envelope (roughly 2 GiB practical before allocations start failing). The stream and total caps are grounded by measuring the committed corpus (the W-9 AcroForm, the API/image samples, the fixtures): the largest single inflated stream observed was 0.24 MiB and the largest per-document total 0.43 MiB. The reasoned legitimate worst case — a full-page 300-DPI RGB image stored as Flate, roughly 25 MiB/page inflated — sits roughly 10× under the per-stream cap and the 1 GiB total bounds a multi-image document; both caps sit roughly 1000× above the measured floor, so false positives are not a concern and the gap to the memory envelope is the safety margin.

**Considered and rejected:** forking lopdf or hayro to add a native decode-size limit (rejected — two codebases to fork and track upstream, against the engine's compose-don't-fork charter); bounding every amplifying filter including LZWDecode and RunLengthDecode (rejected for v1 — zlib/raw-deflate reject non-deflate input on the first header/block-type check, so attempting them on every blob is cheap and clean, but LZW and RunLength have no header and would "decode" arbitrary image bytes into same-size garbage, adding cost on image-heavy documents and a false-positive risk on the cumulative cap, for two rare, low-ratio vectors); detecting `stream`/`endstream` boundaries to bound the inflate (unnecessary — deflate and raw-deflate are self-terminating on an end-of-block marker or Adler-32 trailer, so the decoder stops at the true stream end and a bomb hits the cap long before then; `endstream` is used only to advance the scan cursor).

**Threat model:** `pdf-core` has no production consumer wired yet; the Tool UIs are deferred and, per the engine's design, run client-side in WASM. There a bomb crashes only the user's own browser tab on a document they chose to open — a self-inflicted denial of service, not a server or tenant compromise. Inputs are firm-trusted or received-and-handled documents, not arbitrary internet uploads. Severity is therefore moderate; the guard is defense-in-depth that also protects any future server-side host.

**Disclosed residual:** a bomb using an amplifying filter the pre-flight does not decode — LZWDecode (roughly 9-bit table, modest ratio) and RunLengthDecode (at most 128×), plus image codecs (JBIG2/CCITT can expand bilevel rasters) — falls back to the plain input cap rather than the tighter per-stream cap; deflate, the dominant high-ratio vector, is bounded rigorously. Render/raster bombs (a tiny page with a huge MediaBox rendered at high DPI) are a separate attack class, out of scope here. `GuardLimits` is not yet caller-configurable through the WASM/TS API; v1 ships fixed defaults, with the struct available to native callers. For an **encrypted** document, the pre-flight reads ciphertext, so an encrypted object stream (or any encrypted stream) that decrypts to a deflate bomb is inflated by lopdf's decrypt-and-load (`decrypt` / `load_protected` / `inspect_security`) beyond the guard's reach; encrypted documents get the input cap only, and fully closing this needs a bounded loader (a follow-up — forking the parser stays out of scope). Separately, the raw-byte scanner keys off the literal `stream` keyword position, so a non-conformant file whose real deflate body sits at a different offset could evade the inflate while remaining parser-loadable — a theoretical residual under trusted input.

**Consequences:** every public operation (`redact`, `scrub`, `secure`, `generate::{merge, split, rotate}`, `watermark`, `bates::stamp_*`, `forms::{read_form, fill_form, flatten_form}`, `decrypt`, `detect`, and the public `Document::load`/`load_protected`) calls `guard_input` as its first statement and fails closed with a typed error and zero output bytes on rejection; internal loads use an unguarded path so each call pre-flights exactly once. Each module's error enum gains a bomb variant; `wasm.rs` maps it to the stable token `"decompression-bomb"` (matching `packages/metadata`'s `BombError` vocabulary), and `packages/pdf/src/index.ts` re-throws a typed `DecompressionBombError`, mirroring the existing `WrongPasswordError` pattern.
