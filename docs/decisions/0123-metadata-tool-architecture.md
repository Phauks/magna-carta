**The Metadata Inspector & Scrubber is all-TypeScript, behind engine interfaces that make a heavier runtime a measured-trigger swap; the tool is ephemeral, stateless, and record-less.**

**Context:** a law firm's most common metadata hazard is inadvertent disclosure — sending a `.docx` that still carries tracked changes, comments, or author and firm names can leak privileged work product; sending a photo may expose GPS coordinates. The design cycle evaluated three implementation approaches: (A) a single monolithic function, (B) a Rust → WASM image engine to share a native core with a future forensics tool, and (C) a port seam with TypeScript engines behind interfaces. The language decision (settled 2026-06-22, recorded in the design spec) evaluated Approach B and rejected it: the scrubber's image work is metadata-segment surgery (walking JPEG APPn markers, PNG ancillary chunks, TIFF IFDs and dropping the metadata-bearing ones) — that is well within TypeScript's reach and does not require pixel decoding. The only genuinely JS-hard image format is HEIC, and it is the rarest scrub target (an iPhone capture format, usually converted before use). The reuse argument for Rust depended on an undesigned, uncommitted forensics tool whose real Rust value (pixel analysis) is a distinct build; a Wasm toolchain is better introduced by the PDF engine and doc-discovery core already on the roadmap. Approach C is adopted.

**Decision:** (1) **All-TypeScript.** The `@magna-carta/metadata` package is a pure TypeScript package with no Rust, no WASM, no Cloudflare Container binding, and no network dependency — fully unit-testable in the Vitest worker pool. (2) **Engine interface seam.** Document work sits behind `DocumentMetadataEngine`; image work sits behind `ImageMetadataEngine`. Each interface exposes `inspect` and `scrub`. The interfaces are the swap points: a Container engine for large files or a Rust → WASM image engine can replace an in-process implementation without touching `MetadataPort`, the worker routes, or the UI. (3) **`MetadataPort` — stateless inspect + scrub.** `inspect(bytes, filename) → MetadataReport` and `scrub(bytes, filename, options) → { bytes, report }` (the report is a re-inspection of the cleaned output). Nothing is written to D1 or R2; there is no audit row, no stored copy, no session state. (4) **Size cap.** The port refuses files above a configured threshold with a clear error rather than doing heavy work on the hot path. A Container engine variant behind the same interface is the named measured-trigger seam for large files. (5) **v1 formats.** OOXML (`.docx`, `.xlsx`, `.pptx`) via fflate + XML surgery; JPEG, PNG, TIFF via segment/chunk/IFD walking. (6) **Named measured-trigger seams.** HEIC (deferred — route through the conversion tool first); PDF info-dictionary/XMP + annotations (deferred pending the in-house PDF engine); large-file Container engine (built only if the in-worker size cap is measured to be limiting); Rust → WASM image engine (built only if the forensics tool is greenlit or JS HEIC handling proves too fragile — never as speculative infrastructure). (7) **Scrub semantics.** One-click "Make safe to send" accepts all tracked changes, deletes comments, removes hidden text, strips identifying document properties and custom properties, and strips all image metadata. Granular toggles are derived from the findings. The input is never mutated; a fresh cleaned copy is returned. (8) **Security.** Decompression-bomb guards on OOXML unzip (cap inflated size, entry count, and per-entry ratio); real-format validation by magic bytes (not extension); file contents and extracted metadata values are never logged (golden rule 4 — redact by default).

**Consequences:** the tool ships in a single language with a single toolchain, is fast to iterate on (real bindings in the Vitest pool, no Container gap), and leaves clean swap points for heavier runtimes if measurement ever justifies them. The forensics tool, if built, can reuse the `ImageMetadataEngine` interface for its metadata-signal reads without inheriting the scrubber's scrub logic. The WASM toolchain is introduced by a better first candidate (the PDF engine or doc-discovery core) rather than by this tool. Load profile is not applicable — the tool adds no per-firm data surface and is stateless. Spec: [`docs/specs/2026-06-22-metadata-tool-design.md`](../specs/2026-06-22-metadata-tool-design.md).
