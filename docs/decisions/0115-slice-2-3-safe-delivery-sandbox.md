**Safe delivery of untrusted bytes for inline preview (slice 2·3), concretizing and extending ADR-0029.** The video-first inline-preview feature must serve untrusted file bytes to a viewer's browser without reopening the stored-XSS boundary (`security.md` _Untrusted file handling_ threat #3 — a malicious SVG/HTML/scripted-PDF running script in the viewer's origin). The decision, in five parts:

**(1) Consumption model — a media SUBRESOURCE on the trusted origin, not a sandboxed-iframe document.** The deferred player UI lives on the app origin and loads the file as a native `<video src="files.*/api/files-preview/<token>">` **subresource**. The untrusted bytes therefore reach **only the browser's media decoder**, never an HTML/script parser — a verdict false-positive (an active format mislabeled `playable`) is merely an undecodable video, not a rendered document. This makes delivery safety independent of the verdict being correct: the verdict gates feature **quality**, the delivery shape gates **safety**. The rejected alternative — an `<iframe sandbox>` navigating to the bare media URL as a document — forces `Content-Disposition: inline`, routes bytes through the document/media viewer, and leans on the sandbox CSP to contain a false-positive; it is a genuine deviation and strictly weaker on a direct navigation. The `<iframe sandbox>` (bare `sandbox`, never `allow-scripts`) remains the only sanctioned mechanism for the deferred document-rendition path, not for media.

**(2) `Content-Disposition: attachment` is KEPT verbatim; `security.md` is amended ADDITIVELY.** `Content-Disposition` has no effect on a subresource fetch (so the media plays) but is honored for a top-level navigation (so a direct hit on the raw bytes downloads — safe even on a false-positive). So every preview-route response carries `attachment` on all formats, `inline` is never emitted, and the `security.md` attachment rule is unweakened. The convention change is purely additive: it adds a **second** permitted inline-render mechanism (a native media subresource for verdict-confirmed inert media) alongside `<iframe sandbox>`, leaving the "never hand active formats raw — derived safe rendition" clause untouched. The load-bearing browser-behavior justification recorded here: `Content-Disposition` is honored for navigations but ignored for subresources; `X-Content-Type-Options: nosniff` request-blocking applies only to `script`/`style` destinations (so it does not block or re-type media — it is a belt, not the neutralizer); a bare `sandbox` disables scripts for any loaded document regardless of Content-Type; the navigation/subresource split is current convergent UA behavior (WHATWG Fetch #875), not a spec guarantee, and **fails safe** to download-only if a UA changes.

**(3) Cookieless origin via the same Worker on a second hostname, outside the chokepoint.** Untrusted bytes are served from a separate cookieless `files.*` host (never `app.magnacarta.esq`), realized as the existing Worker answering a second custom-domain route under the `/api/files-preview/{token}` path (the `/api/*` worker-first prefix is mandatory — anything else is intercepted by Workers Static Assets at the edge). The handler is host-guarded (`hostname === FILES_ORIGIN`), terminal, and sits **outside** the ADR-0067 chokepoint (no session exists on `files.*`); it honors a capability-bearing signed token, not a session. It carries its own standing fitness guard because the conformance chokepoint gate inspects only `/api/v1` paths. Every `200`/`206` carries an identical header set: `Content-Disposition: attachment`, `nosniff`, server-fixed sniffed `Content-Type` (never the attacker-declared type), `Content-Security-Policy: sandbox; default-src 'none'; frame-ancestors <app-origin>`, `Cache-Control: private, no-store`.

**(4) Inline bytes flow through the Worker under a first-party HMAC token, not an R2 presign.** A presigned R2 GET signs only `host`, targets the R2 S3 endpoint, and cannot carry `Content-Disposition`/`nosniff`/CSP — so it cannot satisfy the header contract for inline rendering. Inline bytes instead stream through the Worker under a token HMAC-signed over a key derived from `AUTH_SECRET`, carrying `{ r2Key, bucket, sniffedContentType, verdict, exp }`; the host verifies it constant-time and derives every header + bucket + key only from the verified payload. Signing with `AUTH_SECRET` (not behind the R2-presigner adapter) means dev/test and production share one sign/verify path, so the negative tests exercise real signature rejection. The download-only/attachment path keeps the existing 302-to-R2-presigned-GET unchanged. Seekable HTTP **Range/206** (with `ETag`+`If-Range`) is the slice's primary acceptance criterion and is served over real HTTP on web and desktop alike — never a `tauri://` custom scheme, which does not honor Range. CORS is ungranted at launch (a native `<video>` subresource needs none); `crossorigin` + scoped `Access-Control-*` is a later player-slice seam.

**(5) The grant is `audited:false`, and media-decoder RCE is a knowingly-accepted residual.** Per the white paper's "no per-view logging" for inline preview, the preview-grant route writes no audit row; the existing **audited** `/download` route still records every full-file pull. The one risk this design does not remove is browser **media-decoder RCE** (a malformed-but-decodable file fed to the native decoder) — a platform-level risk present identically in any native-inline-playback model (including the white paper's own), out of scope for `security.md`'s Container-only native-parser rule (which governs our FFmpeg/libvips/ghostscript, not the browser's decoder), and accepted for 2·3; its genuine eventual mitigation is the deferred Container-produced derived rendition.

**Context.** The feature is video-first inline preview (ADR-0029); the question was how to deliver untrusted bytes for inline playback without reopening threat #3, and whether the apparent need to deviate from the literal `Content-Disposition: attachment` rule was real. In-cycle browser-mechanics analysis showed the deviation was an artifact of the iframe-document consumption model; the subresource model dissolves it, keeps the rule verbatim, and is strictly safer on a direct-navigation false-positive.

**Considered & rejected.** `<iframe sandbox>` + `Content-Disposition: inline` (a real deviation; bytes reach a document context; safety rests on the sandbox containing a wrong verdict) — rejected as weaker and convention-violating. A presigned R2 GET for inline (cannot carry CSP/disposition/nosniff) — rejected; kept only for the deliberate-download path. Omitting `Content-Disposition` entirely (a direct navigation then renders top-level — the exact threat-#3 surface — for zero benefit since the subresource plays regardless) — rejected. A second, independently-deployed Worker for `files.*` (duplicates the R2 binding + secret set for no browser-origin-isolation gain) — rejected in favor of one Worker on two hostnames. `audited:true` per-view logging (floods the trail; contradicts the white paper) — rejected.

**Consequences.** Seekable inline video ships with the strongest containment (untrusted bytes reach only a media decoder; the cookieless host + attachment-on-navigation + server-fixed Content-Type carry safety independent of verdict correctness) and **no** weakening of the `security.md` attachment rule — only an additive mechanism, with the UA-behavior dependency named and fail-safe. The accepted media-decoder-RCE residual and the deferred derived-rendition mitigation are recorded. Builds on **ADR-0029** (inline preview, video-first), **ADR-0067** (chokepoint — the cookieless host is a named exception with its own guard), **ADR-0090** (cookieless-preview-origin posture). Pairs with **ADR-`inline-playable-verdict-seam`** (the verdict the delivery gate reads). Spec: [`docs/specs/2026-06-19-slice-2-3-inline-preview-safe-delivery-design.md`](specs/2026-06-19-slice-2-3-inline-preview-safe-delivery-design.md).

**Desktop transport invariant (a contract the deferred player slice inherits).** The preview route is served over real HTTP(S) on both web and desktop. When the Tauri desktop shell is built (0·7a/0·7b), the `files.*` preview origin MUST be bound to a real HTTPS (or localhost HTTP) URL — it MUST NOT be routed through a `tauri://` custom-scheme proxy. The `tauri://` scheme does not honor HTTP Range, so routing through it would silently kill scrubbing and seeking in the `<video>` player. This is not a future design question; it is a constraint fixed by the Range/206 delivery contract above.
