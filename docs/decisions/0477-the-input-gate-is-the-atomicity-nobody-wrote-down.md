**A Durable Object hands you atomicity you did not ask for and cannot see, and one ordinary-looking await gives it back.**

**Context:** the read-then-write in a Durable Object method is safe by default. workerd closes the input gate while a storage operation is outstanding, so a second call is not delivered until the first has finished writing — which is why `markRunning`, `markDone`, `start` and their siblings across eleven coordinator classes are correct without a lock between them.

The property is invisible. It is not in a type, a name, or a comment; it is in the runtime. And it holds only for **storage** awaits. Await an R2 HEAD to decide whether a cached artifact still exists, or a queue send, or a service binding, and the gate opens mid-decision: two callers both read the old state, both decide, and both act.

That is what had happened. `BundleBuildCoordinator.requestBundle` is the single-flight coordinator for bulk downloads, and its own comment says so. Its reaped-artifact branch — a `ready` job whose R2 object the lifecycle rule has expired is rebuildable, which is what makes the artifact a cache rather than a one-shot — decides by HEADing R2. Two requests for the same expired bundle therefore both read `ready`, both find the object gone, and both enqueue a full rebuild.

**Decision:** the decision is wrapped in `ctx.blockConcurrencyWhile`, and a scan keeps the shape from coming back.

**The enqueue stays outside the gate.** Deciding is what has to be atomic; sending the message is the consequence of having decided. Holding the gate across a queue send would stall every status poll on that job behind a network round trip for no benefit — a request delivered after the gate reopens reads `building` and shares, which is the outcome wanted.

**The verifier drives the two calls ungated, and says why.** The local pool serializes two RPCs to one object, so the race cannot be reproduced through the path a real request takes; calling the method twice directly interleaves at every await, which is what an open gate is. That over-approximates production gating, so it proves the window exists in the logic rather than proving a schedule the runtime will pick. The fix rests on the runtime's documented semantics — a non-storage await opens the gate — and `blockConcurrencyWhile` costs nothing on the happy path, so the asymmetry is entirely in favour of gating.

**Two property-based verifiers land beside it, for questions a pair cannot ask.** Two callers never lose five races in a row, so no two-caller test can see a bound that bites only at higher concurrency. Driving N number draws at once found one: correctness is absolute at every N — the numbers that commit are distinct and gapless — while convergence is bounded by the draw's retry budget, so beyond five simultaneous draws the excess is refused. That is a deliberate refusal rather than corruption, and the measured ceiling is now pinned so moving the budget is a decision somebody makes rather than one a test absorbs. The ledger's equivalent checks N concurrent postings against the invariants the domain already owns as fitness queries: a materialized balance equals the recomputed sum of its lines, every entry balances, and a parent's stored balance stays zero. Both are seeded rather than sampled, so a failure names a seed, and neither adds a dependency to run a loop.
