The second intake slice, from the owner's direction of 2026-09-05: the sidebar's Intake destination ships as the desk — every consultation in flight, firm-wide, with the client, the responsible member, where it stands against the procedure binding its kind, and whether the consultation is on the calendar — plus starting an intake from it (the New Matter window in intake purpose), resuming one on the matter's Intake section, and scheduling the consultation once every required step is answered. `@magna-carta/intake` gains `desk.ts` and `GET /api/v1/intake/consultations`; the step-kind vocabulary gains `client-forms` and `payment` through a per-firm table rebuild (migration `20260905T195543`, snapshot `0095`), so a stream adding its own per-firm migration will need to re-sequence the journal, and a stream regenerating the OpenAPI snapshot or the API client will collide on those files.

The design system's `EntityPicker` gains a top-level New control and a per-kind add row (`onCreate` now takes the kind), and `apps/web/src/lib/directory/directory-entity-picker.svelte` wraps it with the New Person and New Organization windows for every surface that picks a person: the matter window, the cost payee, the conflicts subject and consenting party, the directory's edges and organizations, and the calendar's participants. A stream touching any of those pickers should take the wrapper rather than the bare component.

**Second ruling, same day.** The stored matter status vocabulary is now `intake`, `consultation`, `open`, `closed` (migration `20260906T013304`, a reviewed rebuild of `matter`, snapshot `0096`; `prospective` is gone from the schema, every statement, every contract and every test). `graduateMatter` and `POST /api/v1/matters/{id}/graduate` (+ `graduate-readiness`) are new lifecycle routes; the intake procedure gates graduation, not opening. A stream that filters on `status = 'prospective'` anywhere — a query, a fixture, a test — will break on rebase and should take `consultation` (or `IN ('intake', 'consultation')` where it meant "not yet open").

**Third ruling, 2026-09-06.** A `hold` rung beside `open` (migration `20260906T030014`, a second reviewed rebuild of `matter` adding `held_at` and `hold_reason`, snapshot `0097`; permission `matters:hold` seeded in the same migration and added to the access-control registry, so a stream pinning the permission roster or the matters namespace order will need the new key). `holdMatter` / `releaseMatter`, `POST /api/v1/matters/{id}/hold` and `/release`, two more outbox topics (`matter.held`, `matter.released`) with notification types and timeline keys. A stream that enumerates the status vocabulary — a filter, a count, a `z.enum`, a status union in a test — takes five values now, and a stream that treats `status = 'open'` as "the live matters" should decide whether a held matter is live for it (the conflicts corpus and auto-file rules say yes; the active lists say no).

**Third stream, 2026-09-06, after #528 merged.** The numbering framework: `Settings · Matter Numbering` replaces its Soon stub with one editor per purpose over `GET`/`PUT /api/v1/numbering-scheme` and the preview route (model in `numbering-scheme.ts`, calls in `numbering-api.ts`, the editor in `numbering-scheme-editor.svelte`); the status window gains a Number block with Set Number over the renumber route; `renumberMatter` refuses an intake or a consultation. A stream touching the status window or the renumber service should expect both.
