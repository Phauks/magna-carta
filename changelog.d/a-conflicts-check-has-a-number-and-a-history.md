**A conflicts check is a numbered record with runs under it, opened at once and searched after the response; the walk goes to closure and nothing a firm sets limits it.** `conflicts_numbered_check` and `conflicts_check_run` (per-firm lineage, `20260911T120000_conflicts-check-numbers-and-runs.sql`, with a backfill so every existing `conflicts_check` row becomes run 1 of a numbered check) sit beside the append-only log; `packages/conflicts/src/check-run.ts` draws the number (`CC-` and four digits, `MAX + 1` under a unique index), opens runs and settles stale ones, and `apps/api-worker/src/conflicts/check-run-executor.ts` executes a run after the response through `runInBackground`, reporting its stage and counts on the run row. `POST /api/v1/conflicts/checks` answers 202 with the id, number, run id and ordinal; `GET .../checks/{checkId}?run=` carries the runs and the selected run's record; `POST .../checks/{checkId}/runs` re-runs; `PUT .../checks/{checkId}/matter` files; `GET .../checks/next-number` previews. The hop budgets, default depth, closure cap and candidate cap are gone from `ScopeRequest`, `ConflictsPolicy`, the draft and the settings page — `expandGraph` walks to closure under `WALK_CEILING`, and `CANDIDATE_WRITE_CEILING` is the most one batch can carry, both stated on the record when reached; stored JSON keeps its key names so old rows read under the budgets they ran with. The web surface: the New Check panel's right pane is two tabs (Locations by place over `SEARCH_LOCATIONS`; Advanced Settings with name matching as a `ChoicePicker`), the matter field offers a chosen party's matters through `matter-choice.svelte`, the check screen is titled by its number with input and output in separate cards, a `ProgressSteps` reading of a run in flight (`run-progress.ts`), the run history, Run Again, File on a Matter, and exactly Print Report and Download Report (`report-download.ts` projects the sheet through the export renderer). The seam left behind: execution rides the request's background allowance with a two-minute stale rule; the executor is queue-ready once the per-firm dispatch table can take it.

## Public

**Every conflicts check now has a number — CC-0001, CC-0002 — and keeps its history.** The number is drawn the moment you open a check and is how it is referred to on its own screen, in the log and on anything printed. **Run Again** on the check's screen searches again as a further run under the same number; an automatic re-check lands under the matter's own check; and the screen lists every run with when it ran and what it came to, showing whichever one you open. While a run is under way the screen says where the search is and what it has counted so far, stage by stage. A check run before there was a matter can be filed on one from its screen, and the report's two controls are now exactly **Print Report** and **Download Report**, the second handing you the same sheet as a PDF.

**The New Check panel says less and asks by place.** Its right side is two tabs: **Locations** lists where a check searches — Directory, Files, Messaging, Magnus — with what the Directory search does beneath it behind a caret, and a place that cannot be searched yet is shown disabled, marked Soon, saying what it waits on. **Advanced Settings** holds name matching, now a dropdown whose rows show a name each choice would catch. Once you have chosen a party, the matter field offers the matters that party is on first, with the rest of the docket searchable beneath.

**Nothing limits a check any more.** "How far to follow relationships" and the two limits are gone from the panel and from **Settings, Conflicts**: every check follows every recorded relationship as far as the chain goes. The one bound left is the platform's own ceiling on a single search, far above any real corporate group, and a run that reaches it says so on its record.
