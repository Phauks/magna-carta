**A migration lineage now defends its own apply order, its own bundle and its own history — three tools, all running on every pull request.** Apply order is by TAG, and a branch cut before another one lands keeps its earlier timestamp while drizzle renumbers its `idx` to the end. A fresh database then applies it before the migration it was written on top of, building its schema in an order no existing firm ever used. Nothing about the merge looks wrong afterwards and every firm that already exists keeps working, which is why two of them reached `main` in September 2026.

**The worker's tag-to-SQL bundle is generated from the journal** (`tooling/migration-bundles`). `apps/api-worker/src/per-firm-migrations.ts` and its control-plane sibling were a hand-kept map of forty lines that had to gain an entry every time the journal did, and it lost one three times — a merge resolves the journal cleanly, because its entries are adjacent lines, and drops one branch's import in the same conflict. `migrationsFromJournal` throws on that, but only inside a Durable Object on wake, so it surfaced as a twenty-second route timeout rather than as a missing import. `pnpm run lint:migration-bundles` now fails when a module and its journal disagree. The emitted text is a fixed point of the repo formatter, so the generator and `vp check --fix` cannot undo each other.

**A conflicted `_journal.json` is resolved by a command** (`node tooling/resolve-journal/index.mjs`), not by hand. What decides the answer is not "ours" and "theirs" — which of those is the branch depends on which direction the merge ran — it is `main`, which is production here, so a tag on `main` has deployed and is immutable and a tag that is not can still move for free. Trunk entries keep their tags and their order; everything else is appended in the order it was integrated and re-stamped above the head, its `.sql` renamed to match and the bundles regenerated. It reads git's conflict stages during a merge and the journal on disk otherwise, so it repairs an inversion that already landed as readily as it resolves a live one. `timestamp-latest-migration.mjs` shares its tag arithmetic: two implementations of "a tag that sorts above the head" is the shape of the bug both exist to prevent.

**A migration that has deployed can no longer be changed** (`pnpm run lint:migration-immutability`). The applied-ledger in every database records the tag, not the SQL behind it, so an edit to a deployed migration is never seen by the databases that already ran it, and a rename leaves them holding a tag the runner cannot recognise — which blocks every later migration for the life of that database. Neither is fixed by deploying again. The check measures from where the branch left `main`, not from `main`'s tip, so a migration that landed while the branch was open is not mistaken for one the branch deleted. Deliberate exceptions are recorded with the reason no database could have applied them; a baseline collapse is not one, because `LEGACY_BASELINES` reconciles those at runtime and the gate reads that list rather than asking for the same fact twice.
