**The matter status seal is the control that changes it, and the program answers what closing requires.** Pressing the seal on a matter's masthead opens the status window; the lifecycle action left the overflow menu, which held nothing else and is gone with it. The window is short by design: the status, what closing requires with each requirement already answered, where the firm's paper file is kept, and the one step the status allows. One step per status, never a status picker, because none of the three operations takes a status on the wire.

`GET /api/v1/matters/{id}/close-readiness` is new. The close hook's rules are pure reads with a separate commit guard, so running them read-only is the same question the close asks and none of the write — which means the window can list what closing requires with each one marked met or unmet, rather than handing somebody boxes to tick or a button to press to find out. One reply answers every requirement, because the route runs every rule and reports every failure, so a rule it does not name is a rule that passed; a refusal naming a rule this build has never heard of becomes its own unmet row rather than disappearing. An unmet requirement disables the press, per the rule that a control does not offer a press whose refusal is predictable — but an unanswered one never does, because nothing has been predicted there and the close is the authority either way. The route reports an already-closed matter as not closable with that as its blocker, so one definition of the word survives. A close refused at the last moment answers in the same shape and re-answers the requirements already on screen rather than arriving beside them. Those sentences reach the screen through a new `errors` array on the shared problem envelope, which until now dropped everything a refusal said beyond its one summary line.

**The window has two sides, and the division is the point.** Left: the status and the step it offers. Right: the firm's own paper file. They are apart because the paper file is a STANDING fact and not a consequence of the step — a firm keeps a matter's folder in a box, commonly with other matters' folders and commonly at a remote store, and closing the matter moves none of that. Laid out under the requirements it would read as what closing does to the file, which is the one thing it must not say, so the panel says the opposite in as many words.

**Location**, **Box** and **Destroy after** render and say what they wait on. None of it is modelled: the platform has no register of the firm's OWN paper files, and no retention policy anywhere to derive a destruction date from — the custody register is explicit that it runs no timer at all, destroying an original on a written basis by two people rather than because a date arrived. Custodian is client property left with the firm to guard, which outlives the matter that brought it in, and is not the firm's file for a matter; conflating them would put a client's will where a paper file belongs. The gap is now a ledger node (`matters.physical-file`) rather than an absence.

**`StatusMark` is a new design-system component** (`@magna-carta/design-system/status-mark`): the affirmative mark, a disc filled in the success tone with the check knocked out of it. It existed as a recipe class three surfaces reached for with their own icon import, and they had already drifted onto two different Lucide glyphs — `circle-check` in the file manager, the larger-tick `circle-check-big` in the catalog and the record-window gallery. One mark that reads the same everywhere is the whole point of a register, so the glyph is decided in one place now and `statusMarkClasses()` is retired; a met requirement in the status window looks exactly like a clean file in the file manager, because it is the same component. It carries an accessible name by default and takes `decorative` where words beside it already say the word.

The masthead also gained the way back, as a bare arrow at the head of the ledger line — the labelled `BackLink` rule earns its label above a masthead, where "back" is ambiguous; on a matter's own ledger line the docket is the only place up.

## Public

**Change a matter's status by clicking its status badge, and see what closing requires before you try.** The badge at the top of a matter opens a short window: the matter's status, what closing requires, and where the firm's paper file is kept. Magna Carta checks the firm's own rules for you when the window opens and marks each requirement met or not — nothing there is yours to tick. Where one is not met, it names what is in the way, the account it sits on, and the ways to clear it, and the Close button stays disabled until it is. Beside it, the firm's own physical file: the box it is filed in, where that box is kept, and when the file may be destroyed. None of the three is recorded yet, and it says so rather than leaving the questions off the screen. It sits beside the status rather than under the close because closing a matter does not move its file. There is also a back arrow to the matters list at the top left of every matter.
