**The file manager's details panel renames what it is showing, in the panel.** Pressing the name called `onRename` back into `file-manager.svelte`, which set `manager.renamingKey` — so the field opened on the ROW, which may be scrolled out of view or in another folder. The reader pressed a name and watched a selection happen somewhere else. The panel now hosts the field itself: `file-inspector.svelte` keeps its own editing state, seeds the draft through `renameFieldValue`/`renameSelectionEnd` so only the stem is selected, commits through `committedRename` so a hidden extension reattaches, and takes one seam from the host — `onRenameCommit(name)`, answering null or the sentence that refuses. The behaviour is Magnus's `conversation-name.svelte`, which had already settled it: Enter commits, Escape abandons, blur commits, and a refusal keeps the field open holding what was typed with the reason beneath it, because a name that collides is fixed where it was written. The field takes the resting control's own height (`mc-input-sm` and `mc-button-sm` are the same `--mc-density-control-sm`), so opening it moves nothing else in the header. Six mounted tests in `apps/web/test/file-inspector-rename.test.ts` — the claim is about a rendered panel, so a source scan could not make it.

**A safety check says what it ran under, and a request that never ran says so.** Three facts the platform already recorded and did not show. The re-scan route audits `enqueued` on every request, and nothing read it back: a request that reached no queue — no engine recorded, or none bound — showed as "Check requested" and the reader waited for a verdict that was never coming. It now reads **Not queued** in the warning register with the reason beside it, derived from the second unread fact, the engine recorded at the moment of asking (`currentEngineVersion` in the same metadata, which `scanFactsFromMetadata` dropped). Third, the firm's own scan settings: the history response carries the four the File Safety page writes, so the Safety tab states the engine decomposed into its three parts beside the depth, the threshold, the treatment and the re-authentication choice — and says, in its own last row, that only the ENGINE is recorded per check. What a check ran under, when somebody has since changed the depth or the threshold, is recorded nowhere; stating that is more useful than a number that might describe a different configuration.

`FileScanEvent` gains `queued`, `FileScanHistory` gains `scanSettings`, and the reading of the policy on this route is deliberately open to any member who can read the file — reading a verdict means reading what it was looked for with, where CHANGING the policy stays behind `firm:manageScanPolicy`. The four settings' words moved into `scan-policy-words.ts` so the settings page that writes them and the Safety tab that reads them cannot name one setting two ways.

## Public

**Renaming from the details panel now opens the field in the panel.** Press the name at the top of the panel, type, and press Enter to keep it or Escape to leave it as it was; clicking away keeps it. It used to put the cursor on the row in the list instead, which is no help when that row has scrolled away. If the name is already taken, the field stays open with what you typed and the reason beneath it, and the document keeps the name it had.

**A document's Safety tab now shows what its checks ran under.** Beneath the history of checks, the tab states the three parts of the engine the firm uses and the firm's four file-safety settings, and says plainly which of them is recorded against each check and which is only true of today. A request for a fresh check that could not be sent to the engine now reads "Not queued" and says why, instead of looking like a check on its way.
