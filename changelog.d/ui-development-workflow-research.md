Research on how UI screens should be developed and reviewed on this stack, and specifically how the sign-in screen gets from a standalone mockup into the product. Research only — nothing built, no tool adopted, no dependency added.

**The finding is mostly that the toolchain is already right.** The component catalog in use is current and maintained on the versions this stack runs, story files already double as behaviour tests and accessibility checks, and the screenshot-comparison harness is correctly designed. Nothing there needs replacing. What is missing is narrower than a tool: the screens have nowhere to be seen in all their states at once, and the owner has no address to open on his phone.

**The mockup has done its job and should be retired for this screen.** Iterating a screen as a self-contained mockup file is the right way to work while the building blocks it needs do not exist yet. For sign-in they now all exist, and the screen is live in the product, so there are two copies of one screen and only one of them ships — every further mockup round is work that has to be redone. The rule proposed for the future states when to stop: iterate in a mockup while a round is inventing shapes the design system cannot yet express, and move into the real screen the moment every part of it names a building block that already exists.

**What replaces it costs nothing.** A single developer-only page showing the sign-in screen in every step, every error, and every theme and colour mode at once, edited with live reload — which is the one thing the mockup genuinely did better. Alongside it, a small preview site carrying the built application and the component catalog, reachable from a phone at a stable address per branch. Both are free to run: requests to files served this way are not billed, and publishing happens from a developer's machine, so nothing is spent from the automated-build budget that is currently exhausted.

Also settled by the research: no design tool is worth introducing here, because it would create a second, drifting source of design truth alongside the one the platform already generates and enforces, and because feedback given in words applies to code faster than to a design file; no screenshot-comparison service is worth buying yet, because the free allowance does not cover this catalog's size and there is nothing to review until the first reference images are recorded; and the automated accessibility checks that exist at the component level should be joined by a whole-page check on the real sign-in route, with the parts no machine can judge — where focus lands between steps, whether a screen reader announces a failure clearly, whether the wording leaves a person able to act — staying a human pass.
