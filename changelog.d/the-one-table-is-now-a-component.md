**`DataTable.Grid` — the platform's one table, as a design-system component.** The one-table ruling (`docs/conventions/time-tab-rulings.md`, TB2 — binding cross-surface) says any behavior gap between two matter tables is a defect by definition; until now the settled machinery lived only in the mockups. The design system's `data-table` now carries it as a composed component driven by a declarative column model: type-aware stable sorting (empties last in both directions), the one per-column filter mechanism living inside the header cell (flush at its end edge, one hover unit, space always reserved; contains-text, checkbox set with counts and select-all, numeric range, date range; active funnels unmistakable, clear affordances present only while a filter is in play), column show/hide with pinning at measured sticky offsets, drag-reorder with the anchored column immovable, resize grips with double-click fit, the Docket's selection model (click / Ctrl / Shift / Ctrl+A scoped to the table / arrows / click-empty-clears) with selection emitted as state — never presented, double-click activation as its own event with no select/deselect churn, the scope-honest totals row (voids excludable), zebra, and the "n of m · filtered" footer with one-click clear. Cells render through a consumer snippet, so status chips stay each surface's business.

The pure machinery (`grid-columns` / `grid-filters` / `grid-selection`) is unit-tested; the behaviors run as story play tests in the catalog. The owner's review surface is the developer console's new Table states page (`/developer-console/table-states`), which renders the real component over a litigation fixture in every state — the mockups' polish carried into the product, where it can no longer drift. Existing tanstack-adapter consumers are untouched; migrating the matter surfaces onto the grid is the pipeline's next slices.
