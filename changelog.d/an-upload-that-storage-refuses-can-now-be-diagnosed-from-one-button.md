**The deploy gate requires the Cloudflare provisioning credentials, and a firm's upload path can be checked from the server.** `wrangler.jsonc` adds `CLOUDFLARE_API_TOKEN_FIRM_PROVISIONER` and `CLOUDFLARE_ACCOUNT_ID` to `secrets.required`, so a deployment can no longer run the development provisioner (which records a bucket name and creates no bucket) or the development presigner against real firms. `apps/api-worker/src/files/upload-readiness.ts` verifies the six preconditions of the browser's direct-to-storage write in order — bucket recorded, bucket exists, ingest notification, expiry rules and CORS policy (each re-applied as a whole-set PUT), and a signed HEAD proving the S3 credential is honoured by the bucket (a 403 names the token scoped to one bucket and the re-mint) — and `POST /api/v1/firm/upload-readiness` runs it for the session's firm, audited, on `firm:manageScanPolicy`; the version panel runs it with its other reads for a member holding that key and opens the report as a copyable modal (`versions/upload-readiness-dialog.svelte`, model in `versions/upload-readiness-model.ts`). The provider interface carries `kind` and `bucketExists` so the report states which adapter ran rather than inferring it. The first real run of the check also exposed that `configureBucketNotifications` was never idempotent — R2 refuses a rule that overlaps one already configured (11020), so a resumed provisioning, and the check, failed on a bucket whose rule was in place; a refused overlap is now read back from the bucket's configuration and passes when the rule it meant to add is already there for the same queue. `GET /api/v1/meta/database-health` gains a `fileStorage` block — the upload path, the provisioning adapter, and the last readiness check read back from its audit row, never run — and the version overlay's Database section shows it as a fifth row. The first draft's deployment-mode object, startup refusal, daily sweep and firm-row cache were cut on the owner's ruling that best means easy to diagnose and not overcomplicated.

## Public

**When an upload says storage did not answer, an administrator can now find out why by opening the version chip.** Its Database section checks each thing an upload depends on, from the server's side, puts right the settings it can, and shows the verdict on a File storage line; an Upload readiness report button opens the full report, with Copy Report to paste it into a message. The report reads top down: the first line that fails is the cause, and it says what to do. The upload dialog's failure message now points there.
