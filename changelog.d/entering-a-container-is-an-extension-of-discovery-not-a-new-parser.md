**A design for entering a zip from the File Manager and extracting its entries into a matter — and the finding that the platform is not, in fact, write-only about archives.** `docs/specs/2026-08-22-archive-reader-design.md`, gated on nine owner flags (`AR1`–`AR9`) and not started.

The premise the work began from was that the platform's zip machinery is write-only. It is not. Five readers already parse archives in production paths — `crates/discovery-core/src/archive.rs` (full enumeration plus guarded recursive expansion under five named guards), `containers/scan`'s structural heuristics (which open every uploaded file's central directory unconditionally, not on offset-0 magic), `crates/decryption-core/src/zip_adapter.rs`, and the `fflate` readers in `@magna-carta/metadata` and `@magna-carta/document-assembly`. **Discovery already unpacks containers end to end**, with a container-family chain of custody and every entry re-entering the ordinary ingest gate. The File Manager is the one place that deliberately cannot, and that deliberateness is ADR-0027. So the design is an extension of a shipped capability rather than a new parser, and it argues for extracting `crates/archive-core` out of `discovery-core` rather than growing a sixth reader.

**Three things genuinely do not exist, and they are the build.** Every reader in the tree takes the whole archive as one buffer; nothing locates the end-of-central-directory record from a tail slice, which is what makes browsing a 40 GiB container cost the same two-to-four ranged reads as a 40 KiB one. There is no File Manager surface of any kind. And there is no write path from a container back into a matter — discovery's writes land in a review-set corpus, not the matter's folder tree.

**The two halves are separated on risk.** Browsing is a synchronous read with no write path, and ships first: it builds the ranged directory reader, the WASM target, and the server-minted entry-id contract that makes extraction's plan un-forgeable, and it produces the evidence the ceilings should be set against instead of guessed at. Extraction is a job on the `BundleBuildCoordinator` pattern where each entry goes through `initiateUpload` → `put` with the minted dimensions → `completeUploadSession` → the ingest event, exactly as `discovery/archive-expansion.ts` and `emails/attachment-extraction.ts` already do. There is no second way to put bytes in a firm's bucket and the design adds none.

**Fifteen attack rows, each with a bound and the one place it is enforced** — Zip Slip and absolute paths (unconditional, and structurally moot besides, since the R2 key is server-minted), symlink entries, ratio and absolute-size bombs (checked on declared sizes before inflating and on real produced bytes after, correcting for a lying header), nested containers, entry-count explosion, filename encoding tricks, and the central-directory/local-header disagreement, which refuses the whole container rather than the entry on PyPI's reasoning. Sources cited per class.

**It earns no new deployable.** Applying the extraction rubric in `docs/conventions/operations.md` section 18: no heavy native runtime, no independent deploy cadence, contention already answered by the queue consumer, containment satisfied in the isolate on the same terms `packages/pdf` and `packages/decryption` already parse untrusted privileged bytes there — so in-process WebAssembly, with the job coordination app-side per the compute-vs-coordination seam. Riding the discovery or bundle Workers was considered and rejected with reasons.

**Two flags are memory-safety and confidentiality postures rather than numbers.** `AR2` asks whether the inflate is the Workers runtime's `DecompressionStream` (memory-flat at any size, but zlib underneath — a platform primitive, surfaced rather than adopted, because golden rule 14 exists for untrusted privileged bytes specifically) or pure-Rust `miniz_oxide` in WebAssembly (memory-safe, but it buffers, so an oversized entry is recorded rather than extracted). `AR5` asks whether an encrypted container is refused or prompts for a password, and the answer reaches further than it looks: `/decryption/unlock` runs in-process today, so **no member-typed password crosses a service binding anywhere in the platform** — a property verified from the code rather than written down anywhere — and prompting keeps it only if `AR2` also stays in-process.

**Two pieces of drift recorded and deliberately not fixed here**, both belonging to files this stream does not own: the `documents.upload.archive-opacity` ledger node still claims "no server-side extraction code in the tree", which stopped being true when discovery slice 5·1·3 landed, and `fileManager.archiveCaps` is a declared per-firm setting that nothing reads — this design would be its first consumer.
