**A file the firm already holds is still filed, and a taken name is the reader's decision.** The
upload's hash check used to answer "the matter already holds these bytes" by filing nothing —
`already`, "Nothing was sent" — which turned an economy (do not send bytes the firm has) into a
policy (do not file what the reader chose). Owner ruling: the check is for storage and speed, never
a substitute for the upload. A match on the matter now takes the same path a match elsewhere did —
`uploads.duplicate` makes the new file server-side from the held version, `copiedFrom: "matter"` —
and the `already` outcome and stage are gone. What a duplicate does ask about is its NAME: a file
whose name is taken in the landing folder is filed under a numbered name by default, or, as the
reader chooses for the batch or per file, as the next version of the file that has the name
(`fileId` on the reserve, no hash question) or skipped (a `skipped` stage; nothing read, nothing
sent). The intake table gains a Name Taken column and menu, mirroring the document-type ones;
the queue resolves the clash against the destination's files before the digest is read.

## Public

**Uploading a file your firm already has now files it.** Two identical files you chose both
arrive; a file uploaded twice is there twice — the copy is made without sending the bytes again,
and the row says where it came from. **A taken name is your call:** by default the new file is kept
beside the other under a numbered name; under Advanced Settings you can have such files filed as
the next version of the file that has the name, or skipped. The Name Taken column shows which files
are asking, and the Name Taken menu above the list answers for the files you select.
