# @magna-carta/directory — CLAUDE.md

**Purpose.** The Directory domain module — the firm's single source of truth for the people and organizations it deals with. Models the firm as a graph: two equal-depth node tables (`directory_person` / `directory_organization`), a typed-edge table, append-only name history with phonetic + trigram search substrate, protected sensitive identifiers behind the 1·2 `protected()` machinery, per-firm category labels, entry-time duplicate-candidate generation, non-destructive merge, and the `matter_party` bridge. Validates in memory and composes statements into `@magna-carta/data-access`'s `composeEffectBatch`; never runs logic mid-transaction and never calls external services.

## Key files / entry points

- `src/types.ts` — domain types: branded identifier re-exports (`dpe_`/`dor_`/`dnm_`/`did_`/`ded_`/`dct_`/`dpr_`/`mtp_`/`eme_`), `EntityKind`, `NameRole`, `PhoneticScheme`, `EdgeType`, `IdentifierType`
- `src/entity-kind.ts` — `entityKindFromId` / `nodeTableForEntityId` / `assertEntityExists` shared utilities (derive `EntityKind` and the node table from the handle prefix, and assert an entity exists AND is live — not soft-deleted, not merged away — before a referencing write; used by edges, party, categories, name-history, identifiers, merge, and search)
- `src/normalize-name.ts` — frozen name normalization: NFC, case-fold, diacritic/punctuation strip, suffix/title parse — produces the `normalized_display` stored at write time
- `src/phonetics.ts` — scheme-keyed Double Metaphone computation (seam over `words/double-metaphone`); produces `directory_name_phonetic_code` rows for both primary and secondary codes
- `src/match-key.ts` — `normalizedMatchKey` / `normalizedMatchKeyBare`, two derived keys layered ON TOP OF the frozen `normalizeName` output and never replacing it. The first canonicalizes connector words and legal-entity spellings while KEEPING the legal form (`Smith & Jones LLP` == `Smith and Jones, L.L.P.`); the second removes the form, so a partnership and a limited company under one name meet one rung weaker. `LEGAL_ENTITY_FORMS` is the single table; adding a form is one entry
- `src/honorifics.ts` — the prefix and suffix SUGGESTIONS (`NAME_PREFIXES` / `NAME_SUFFIXES` / `honorificSuggestions`). Deliberately not a catalog like the rest: `prefix` and `suffix` are free-text columns and stay free text, because the set of things people are called has no edge. Nothing validates against these arrays and nothing should start; every surface offering them offers a "type your own" row beside them (`apps/web/src/lib/names/honorific-field.svelte` is the one control that does)
- `src/nickname.ts` — the nickname equivalence catalogue, registered and SHIPPED EMPTY. `Bob`/`Robert` is curated data with a licensing question attached, and shipping the empty table is what lets a conflicts check record the dimension as one it could not search rather than omitting it
- `src/types.ts` — the catalogs. `EDGE_TYPES` carries the membership family (`officer_of` … `point_of_contact_for`) beside the legacy `affiliation`, which stays for the rows already recorded and is no longer offered for new ones. **A new edge type is classed in `packages/conflicts/src/edge-classes.ts` in the same change** — the traversal budgets by class, and an unclassed type is walked at the widest allowance rather than refused, which is safe and silent. The tighter `constituent` class the entity-model design describes is deferred to the conflicts pass; until then every constituent is classed `control`.
- `src/name-index-backfill.ts` — the resumable, budgeted sweep that fills the match keys on names written before the columns existed. No stored cursor: the selection predicate IS the outstanding work
- `src/statements.ts` — SQL statement builders (insert/update/repoint) for the atomic batch; the `directoryAuditStatement` helper
- `src/topics.ts` — the six outbox topics this package publishes, as one frozen set (`directory.entity.created`/`.renamed`/`.merged`, `directory.edge.created`, `directory.identifier.added`, `matter_party.linked`). A subscriber that spells a topic itself can spell it differently, and the failure is silent: an unrecognized topic on the per-firm bus is acked and ignored by design
- `src/person.ts` — `createPerson` / `readPerson` / `updatePerson` / `setPersonPronouns`
- `src/pronouns.ts` — the pronoun set: the five grammatical forms plus verb agreement, the all-or-nothing column projection, and the validation the write path runs
- `src/organization.ts` — `createOrganization` / `readOrganization` (an organization's name changes through `name-history.ts`, so there is deliberately no `updateOrganization` twin of `updatePerson`)
- `src/name-history.ts` — `addName` / `changeName` (append-and-flip); inserts the new `directory_name` row + phonetic codes + flips `is_current` on the prior in the same batch
- `src/search.ts` — FTS5 trigram name search (`searchNames`) + `findDuplicateCandidates` (phonetic-block union trigram union blind-index, signal-count ranked). The blind-index channel takes plaintext `identifiers` (entry-time duplicate detection) **or** a `subjectEntityId` (conflicts): the latter self-joins an already-persisted entity's sealed blind indexes, so the exact-identifier channel runs with no plaintext in hand. `findDuplicateCandidatesBatch` answers the same question for a SET of subjects with each channel run once over the set — the conflicts graph traversal asks it of hundreds of entities, and one call each is a query count proportional to entities times channels. It is additive: `findDuplicateCandidates` keeps its exact SQL and behaviour, and the two are held to the same hit set by `packages/conflicts/test/matcher-equivalence.test.ts`.
- `src/identifier-shape.ts` — what each identifier kind is made of and whether a typed value fits it (`IDENTIFIER_SHAPES`, `checkIdentifier`, the as-you-type formatters, the paired account value). Pure; imported by the API's request check and the web's live refusal so the two never disagree
- `src/person-record.ts` — `createPersonRecord`: a whole person (names, pronouns, dates, contact points, sealed identifiers, organization edges) composed into ONE effect batch from each owning module's `compose*` function, so a person is never half-recorded
- `src/identifiers.ts` — `protectedField` declarations for all identifier types + `addIdentifier` / `composeIdentifierWrite` / `readIdentifier` / `findByIdentifier` (via `composeProtectedWrite` / `readProtected` / `blindIndexValue`); `findEntitiesSharingIdentifiers` and `findEntitiesSharingIdentifiersBatch` — the conflicts blind-index self-join for one subject and for a set (other live entities sharing a subject's `value_blind_index`, no decrypt/permission/audit). Both live HERE and not at the call site because `value_blind_index` may be named in this module and nowhere else in the package: a blind index is a stable fingerprint of the plaintext, so a query naming it elsewhere is a correlation surface, and `test/no-plaintext-escape.test.ts` refuses one
- `src/edges.ts` — `createEdge` / `readEdges` (typed, temporal, directional; `ReadEdgesOptions` optionally pins the instant expiry is judged against and admits already-expired edges — the conflicts traversal wants both, ordinary reads want neither) / `readEdgesForEntities` (the same read over a whole frontier in one query per chunk)
- `src/categories.ts` — `createCategory` / `assignCategory` / `readCategories`
- `src/merge.ts` — `mergeEntities` (non-destructive, atomic batch, full repoint set, `entity_merge` event + `audit_log` row)
- `src/party.ts` — `linkMatterParty` / `readMatterParties` / `createPartyRole` / `listPartyRoles`
- `src/contact-email.ts` — `addEmail` / `updateEmail` / `removeEmail` / `readEmails` (temporal `directory_email` rows, at-most-one-primary enforced in the write path) + `findEntitiesByEmailAddress` (the address → entity reverse lookup: normalized match key, soft-delete-aware, resolves a merged-away owner to its surviving master)
- `src/contact-phone.ts` — `addPhone` / `updatePhone` / `removePhone` / `readPhones`. The technology and the context are two columns (`contact_system` / `contact_use`), so a work fax is expressible and a delivery path can ask whether a number takes a fax. `number` is the number AS ENTERED and is never rewritten
- `src/contact-address.ts` — `addAddress` / `updateAddress` / `removeAddress` / `readAddresses`, over the international address field set. No field is required beyond one of them being present
- `src/contact-points.ts` — `readContactPoints`, the one read a record screen makes: all three channels, one round trip. Unlike the write paths it admits a MERGED entity, because a folded-away record still has to open
- `src/contact-preference.ts` — the permission/preference/verification block the three tables share, and `resolveContactFields`, which folds a caller's input over the row's current values
- `src/phone-number.ts` — `structurePhoneNumber`: the E.164 assignment rule, not a metadata library
- `src/postal-address.ts` — the address field set, and `normalizedAddressKey` (a DUPLICATE key, deliberately not a canonical postal form). What a country CALLS each field and what order it reads them in is presentation and lives with the form (`packages/design-system/src/lib/components/address-fields/address-format.ts`); nothing here may grow a second opinion about it
- `src/entity-listing.ts` — the INDEX: every live record in name order, cursor-paged, with the count of the whole record. A row carries display identity, the parts a person's name was assembled from, and the record's DEFAULT way to reach it — one email, one number, one place, read for the PAGE in a second bounded query rather than joined into the union (a correlated subquery there would make the count and the walk pay for contact rows on every record the firm holds). A sealed identifier is never on this row: reading one is a permission-gated, audited decrypt. Given a `search`, the same read answers a NAME in the same rows: `searchNames` chooses the records, the listing query says what each one is, and the answer comes back in the firm's own relevance order with `nextCursor` null and `capped` set — because the screen showing the answer is the screen showing the index, and a second row shape there is a second table for the reader to learn. One entity yields one row however many of its names the query landed on
- `src/audit.ts` — `directoryAuditStatement` (shared write-options type, audit-row builder used by all write paths)
- `src/run-directory-effect.ts` — `runDirectoryEffect` top-level executor (threads the idempotency context + crypto context + actor for routes)
- `src/fitness.ts` — `assertDirectoryFitness` + the per-invariant probe queries it runs (`findDanglingToSubordinate`, `assertNoDanglingToSubordinate`, `findNamesMissingPhonetics`, `findEdgesToDeletedEntities`)
- `src/index.ts` — public barrel

## Invariants that apply here

- **All writes compose the atomic batch.** Every mutation goes through `composeEffectBatch` (never raw D1 outside a statement builder). Mirror the pattern in `packages/matters/src/matter-service.ts`.
- **Names are append-and-flip, never edited in place.** A name change inserts the new `directory_name` row (with phonetic codes) and flips `is_current = 0` + sets `valid_to` on the prior row in the same batch. The FTS5 external-content index (triggers) and phonetic-code rows travel with each name row. Editing the name text directly breaks the conflicts corpus and history.
- **Phonetic codes on every name write.** Every insert of a `directory_name` row must be accompanied by `directory_name_phonetic_code` rows for both Double Metaphone schemes (`double_metaphone_primary` and `double_metaphone_secondary`) in the same batch statement set. The fitness probe `findNamesMissingPhonetics` enforces this.
- **A contact point's PERMISSION and its PREFERENCE are two facts, and `is_primary` is a third.**
  `contact_permitted` (default 1) is whether the firm may use the contact point at all — the standing
  instruction a person gave. `contact_preferred` is the route they asked to be reached by, and **at
  most one exists per entity across `directory_email`, `directory_phone` and `directory_address`
  together**, because "write to me" is a single answer about every channel; a write that sets it
  composes `demoteEntityPreferredContactStatements`, which is three UPDATEs in the one batch.
  `is_primary` is neither: it is the CHANNEL's default row, and the email reverse lookup already
  depends on it. None of the three is a Rule 4.2 no-contact flag — that is matter-scoped and derived,
  and putting it on an entity states the rule wrongly.
- **A failed verification is recorded and surfaced and gates nothing.** Owner ruling: a failed address
  verification does not block a send, it notifies. `verification_status` / `verified_at` /
  `verified_by` / `verification_detail` exist so returned mail, a bounced message and a disconnected
  line have somewhere to live; no code path may read them as a refusal. `verified_at` and `verified_by`
  move ONLY when the status moves — an unrelated edit must never read back later as a confirmation the
  firm never made.
- **A date of birth is an attribute, not an identifier, and it is stored in the clear.** It was filed
  in `directory_identifier`, which matches only by exact blind index; a date of birth is too
  low-entropy to index safely, so the code refused, and a firm could store one and ask it nothing.
  `date_of_birth` / `date_of_death` / `deceased` are plain nullable columns on `directory_person`,
  written only through `setPersonLifeDates`, registered in `packages/data-access/src/pii-registry.ts`,
  and covered by the standing redaction default. `deceased` is separate from the date because "known
  dead, date unknown" is real, and the date-implies-the-flag rule lives in the write path because a
  cross-column CHECK cannot be added to a populated table under expand-contract. The `dob` identifier
  type is never dropped — existing sealed values stay readable — and is closed to new writes.
- **The address field set is the international one.** Which fields a country uses, what they are
  called and what order they read in are properties of the COUNTRY. The columns are named for their
  position (`recipient`, `organization_name`, `street`, `street_two`, `dependent_locality`, `city`,
  `region`, `postal`, `sorting_code`, `country`); nothing assumes a state and a five-digit postal code,
  and no field is required. `normalized_key` is a duplicate-detection key and NOT a canonical postal
  form: it folds case, accents and punctuation and stops there. Canonicalization is a provider's job,
  and a key whose meaning changes later silently invalidates every comparison made under the old one.
- **Sensitive identifiers only via `protectedField`.** SSN, EIN, accounts, driver's licence numbers, bar numbers, and SSN-last-four are stored encrypted; the plaintext `label` column beside the seal (the issuing region, the jurisdiction, who an account is held with) is the one part a list may show, and never any part of the value. An account is sealed as one value holding its number, username and secret (`identifier-shape.ts`), and blind-indexed on the number alone. Write them only through `composeProtectedWrite`; read them only through `readProtected` (permission check → audit row → AAD decrypt, inseparable) or `blindIndexValue` (no permission, no audit — matching reveals nothing). Blind-index policy: SSN digit-strip standalone-indexed (L=16); EIN digit-strip standalone-indexed (L=16); account number strip-spaces-dashes-uppercase standalone-indexed (L=24); driver's licence state-prefixed standalone-indexed (L=16); bar number and SSN-last-four protected but **never** standalone-indexed — decrypt-and-compare on a candidate set. The policy lives in `@magna-carta/data-access`.
- **Uniform `directory_identifier` model.** ALL sensitive identifiers live in `directory_identifier` rows — there are no plaintext `dob` or `ein` columns on the node tables. The design's §5 uniform model was adopted; the plan's §2 table columns were dropped.
- **Soft-delete only.** No `DELETE` ever targets directory tables; set `deleted_at` instead. Merged subordinates carry `status = 'merged_into'` + `merged_into_id`; they remain in the corpus so merged-away aliases still surface in search and conflicts. The single exception is a colliding `directory_entity_category` link during a merge: the composite primary key leaves no room for a second row under the master, and the row's entire content (the entity/category pair) is written into the `entity_merge` event, so nothing is lost that the event does not carry.
- **Merge is non-destructive and atomic.** `mergeEntities` runs a single `composeEffectBatch`: archive the subordinate, repoint ALL inbound references (matter_party, edges, categories, custom-field values) to the master, write an append-only `entity_merge` event recording the exact repoint list + survivorship choices, and write an `audit_log` row. A reference that cannot be repointed live — a duplicate the master already holds, or a would-be self-loop — is **absorbed**, not destroyed: it still moves to the master but lands archived (soft-deleted for `matter_party`/`directory_edge`, flipped out of currency for a custom-field value), so the record that the subordinate held that relationship stays queryable. The subordinate's OWN child rows — names, phonetic codes, `directory_identifier`, contact rows — are deliberately **left in place**, not repointed: they stay in the search and conflicts corpus under the subordinate and resolve to the master through `merged_into_id`, so a merged-away alias or identifier still surfaces a hit. `REPOINT_REFERENCE_COLUMNS` in `src/merge.ts` is the exported list of what does get repointed (the PII/erasure registry is pinned as a superset of it). The repoint set must stay complete — `assertNoDanglingToSubordinate` enforces no inbound reference pointing at a `merged_into` subordinate.
- **Merge chains are flattened, never followed.** Resolution is one hop (`COALESCE(merged_into_id, id)` in the search channels, and the in-code twins in `search.ts` / `contact-email.ts`), so a merge repoints the `merged_into_id` of every entity previously merged into the subordinate onto the new master, in the same batch. `merged_into_id` therefore always names a live entity; no read path walks a chain and none needs a cycle guard. The two node-table probes in `fitness.ts` enforce it.
- **Writes never land on a merged-away entity.** `assertEntityExists` treats status as part of existence: a merged subordinate throws `MergedEntityError` (409, naming the master), while a missing or soft-deleted row throws `UnknownEntityError` (404). Reads are unchanged — a merged entity is still readable and carries `mergedIntoId` for a client to follow.
- **Idempotency on all write routes.** All directory create/update/merge operations thread the idempotency context (the matters pattern) — a same-key retry returns the committed result without re-executing the batch. Merge replay is proven not to double-repoint.
- **Match a phonetic table to the encoder's SHAPE, not to the open CHECK.** `directory_name_phonetic_code.scheme` carries an open `length > 0` CHECK, but the table's PRIMARY KEY is `(name_id, scheme)` — it holds at most ONE code per name per scheme. That fits an encoder returning a fixed, small number of codes (Soundex one, Double Metaphone two) and nothing whose output is a variable SET: Beider-Morse returns tens of phonemes for one surname and would need a table keyed by the CODE. Reaching for a scheme suffix (`beider_morse_00`, `_01`) fits under the CHECK and is refused — the column would stop naming a scheme and `WHERE scheme = 'beider_morse'` would silently find nothing.
- **A second phonetic encoder cannot run in a Worker request today, and the number is why.** Beider-Morse was built against `bmpm` (MIT, pure TypeScript, zero runtime dependencies, so golden rule 14 never applied) and removed: the library compiles its whole rule set into regular expressions at module load, which Node does in 16 ms and workerd does in 20,377 ms — measured on the first `POST /api/v1/directory/persons` with the channel wired. A lazy dynamic import is worse, because Workers forbid runtime module loading and the request hangs instead. Before reaching for another encoder, measure its module-load cost INSIDE workerd rather than in Node; the two are four orders of magnitude apart here.
- **Every name write derives every index, at the statement builder.** A `directory_name` insert carries its two Double Metaphone rows and its two match keys in the same batch. Eight write paths insert a name row, so the derivation that CAN live inside the builder does: `insertNameStatement` computes both match keys from the row's own `normalized_display`. A key a caller has to remember to compute is a key some caller eventually does not compute, which is a name silently missing from a blocking channel a conflicts check will nonetheless report as having run. `findNamesMissingPhonetics` and `findNamesMissingDerivedMatchingData` in `fitness.ts` are the audit; on a database the backfill has finished, anything they report is a forgotten write path.
- **Pronouns are RECORDED, never inferred, and whole or absent.** A person's pronoun set is what
  that person stated. Nothing derives it — not from `name_given`, not from `name_prefix`, not from any
  other column — and nothing derives anything else from it; the platform holds no gender field, and a
  pronoun set must never become a proxy for one. The set is the WHOLE declension (subject, object,
  possessive determiner, possessive pronoun, reflexive) plus a verb-agreement number, because a
  two-form label determines none of the last three for a set the platform has not seen and any
  label-to-forms table is a closed enum in disguise. All six columns are recorded together or none is:
  the table CHECK refuses a partial row, `updatePersonPronounsStatement` is the only write and writes
  all six, and `pronounSetFromColumns` returns null for anything short of a whole set — three layers
  for one invariant, because "she" in one clause and "them" in the next is invisible to a proofreader
  and lands on a real person. Rendering, including what an unrecorded set becomes, is
  `@magna-carta/document-assembly`'s business, not this package's.
- **Every mutation audited.** An `audit_log` row rides in the same batch as each mutation (the `directoryAuditStatement` helper).
- **A write path that can invalidate an answered conflicts check announces itself with EXACTLY ONE outbox row, in the batch it was already composing.** `linkMatterParty`, `mergeEntities`, `createEdge`, `addIdentifier`, `changeName`, `createPerson`, and `createOrganization` each add one row and add **no query** — resolving which matters a change affects is a queue consumer's work, and doing it here would put an unbounded fan-out inside a request. Two rows would double the write amplification of every party link and merge; none would silently stop the automatic re-check path, because an unrecognized (or absent) topic is acked and ignored rather than throwing. Topic constants live in `src/topics.ts`; `test/topics.test.ts` holds the one-row rule and the "no announcement when the write fails" rule.
- **A relayed payload carries handles, never values.** `directory.identifier.added` names the entity, the identifier ROW, and its TYPE — never the plaintext and never `value_blind_index`. A blind index is a stable fingerprint of the plaintext, so putting one on a message would let anything reading the bus correlate a person without ever decrypting. `directory.entity.merged` names master AND subordinate, because a matter that knew only the archived record is precisely the one the merge could have changed.

## Dependencies & contracts

- Depends on: `@magna-carta/data-access` (effect batches, `composeProtectedWrite`/`readProtected`/`blindIndexValue`, `protectedField` registry), `@magna-carta/database` (per-firm schema), `@magna-carta/identifiers`, `words/double-metaphone` (pinned).
- Pure and synchronous per operation: produces statements for the caller to run via the data-access layer; holds no D1 binding and performs no I/O of its own.
- The worker routes (`apps/api-worker/src/routes/directory/directory.ts`) are the only callers of `runDirectoryEffect` — they own threading `env`, the actor, and the crypto context.

## Gotchas

- D1 has no interactive transactions — everything an operation needs must be read before composing the batch; never plan logic "between" statements. Use `assertEntityExists` (from `entity-kind.ts`) before any write that references an entity handle.
- `directory_name` must NOT be WITHOUT ROWID — the implicit SQLite rowid backs the FTS5 external-content table (`content_rowid='rowid'`). Removing or altering the rowid breaks the trigram index.
- The FTS5 trigram table is kept in sync by triggers on `directory_name` (insert/update/soft-delete). The migration `0008_directory` creates these triggers via raw SQL — drizzle-kit cannot model FTS5 or triggers, so they live in the hand-written `.sql` file and are verified by the migration test.
- `NameRole`, `EdgeType`, `IdentifierType`, `ContactSystem`, `ContactUse`, `AddressUse`, `AddressType` and `ContactVerificationStatus` are application-level open catalogs (the schema enforces only `length > 0`, or nothing at all). Add new catalog values to the `as const` union in `src/types.ts` before using them in write paths. The CHECK is open at rest **on purpose**: a committed migration is immutable, so a closed `IN (...)` would turn every catalog addition into a migration against every firm and would make a firm mid-upgrade reject a value the code already emits. The route's `z.enum` and the domain modules' `assertClassification` are where the catalog is actually enforced.
- **The phone splitter holds no per-country knowledge, and that is the point.** `structurePhoneNumber` applies the E.164 assignment rule (zones 1 and 7 are one digit, a fixed set is two, everything else is three) and nothing else. A number in national form yields a null calling code rather than a guessed one, and a national trunk prefix inside an international number is NOT stripped — knowing that a leading zero is a trunk code is per-country knowledge, and editing a client's digits on a guess is worse than keeping them. Reaching for a metadata library means hundreds of kilobytes that go stale monthly; if per-region validation is ever wanted it goes behind this same shape.
- FTS5 trigrams treat SQL keywords (`and`, `not`, `or`) as query operators, not literals — `searchNames` wraps each trigram as a phrase literal (`"<term>"`) to prevent keyword collisions. Do not change this without adding regression coverage for the collision cases.
- `findDuplicateCandidates` orders candidates by signal count descending, then entity id ascending (the final sort in `src/search.ts` — cited by function, not line, so the note does not rot as the file moves) — stable across database row orders, never insertion-order. `channels` (which of the phonetic/trigram/identifier channels fired) and `identifierTypes` (which identifier types matched) travel with each candidate, not only `signalCount`.
