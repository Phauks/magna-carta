# Magna Carta — CLAUDE.md

Magna Carta is a legal practice-management platform the firm controls — matters, time, trust, billing, costs, conflicts, discovery, custodian, documents & automation, a client portal, payments, and reporting — built on Cloudflare, multi-tenant from day one.

This is the **entry point** for anyone working in this repo: the golden rules and where everything lives. Read it, then follow the links — detail lives in the linked homes, not here.

**Cross-reference rule:** `§N` is navigation _inside_ the white paper only. From any other file, reference the white paper by **document + topic name** (or a stable **`ADR-NNNN`**), never a section number — they shift on reorganization.

**Developer docs vs. user docs — not duplication.** The white paper / conventions / specs / ADRs serve _builders_; [`docs/user/`](docs/user/) serves _people using the product_. Different facts for different readers (no shared sentences to drift), hard boundary: no internal architecture in user docs, no task walkthroughs in developer docs. `docs/user/` is additive — the only home for user-facing help, which is itself a shipped product feature.

## Stack at a glance

- **Languages:** TypeScript (primary); **Rust** surgically (Tauri shell, Tantivy, a shared doc/discovery core → WASM for web + native for desktop).
- **Frontend:** Svelte 5 / SvelteKit (SPA, `adapter-cloudflare`); Tailwind v4 + the in-house **`@magna-carta/design-system`** (styled directly on headless **Bits UI**); DTCG tokens via Terrazzo; **Lucide icons**.
- **Backend:** Cloudflare **Workers** + **Hono**; REST as **OpenAPI 3.1 code-as-contract** (zod).
- **Data/platform:** control-plane **D1**; a per-firm **SQLite-backed Durable Object** (`FirmDatabase`, addressed by firm id, self-migrating on wake — it replaced per-firm D1, which capped the fleet at the ~5,000-bindings-per-Worker ceiling and needed a redeploy per firm: ADR-0140); per-firm **R2**; **Queues**, **Durable Objects**, **KV**; **Containers** (Collabora, Tantivy, OCR, LibreOffice).
- **Auth:** Better Auth (control-plane D1). **Desktop:** Tauri 2 (after web MVP). **Tooling:** **Vite+** (CLI `vp`; manages pnpm + dev/build/pack/test + `vp check` for fmt/lint/typecheck — Oxc) · rustfmt/clippy. **Source control:** GitHub (repos, branch protection, PRs, review). **CI/CD:** **Cloudflare Workers Builds** (`vp run build-all` → `wrangler deploy`), not GitHub Actions. **`main` IS production** — the owner moved `magna-carta` and `magna-carta-web` onto it on 2026-08-29 to shorten the UI review loop, superseding the deliberate `git push origin main:release` model this file described before. So **a merge to `main` deploys, within minutes, with no second gesture.** Treat every merge accordingly: a migration, a contract change or a binding change reaches real users on the strength of whatever verification ran before it landed — and that verification is the pull-request tier of the gate of record. `release` no longer gates anything; it survives as history. Runbook: [`docs/conventions/operations.md`](docs/conventions/operations.md).

Architecture detail: the [white paper](docs/Magna-Carta-White-Paper.md) — _Delivery model_, _Authentication & encryption_, _Core domain_.

## Golden rules

Broad principles for how we build — they apply across the work, not just one subsystem.

1. **Reuse before building.** Check for an existing component, utility, or pattern before creating a new one; compose and extend rather than reinvent.
2. **All UI through the design system.** Style only with Tailwind + the `@magna-carta/design-system` components and design tokens — no raw CSS, no off-token values, no direct `bits-ui` imports outside the design-system package (CI rejects all three). Lucide icons; **no emojis** anywhere (UI, docs, commits). (_Design system_; ADR-0076)
3. **Data access through the firm-scoped DAL.** All business data goes through the firm-scoped data-access layer — no query crosses firms; bulk content to R2, never D1. (_Tenancy & data isolation_; ADR-0003)
4. **Standardized error & bug logging.** Report every error/bug through the one standard in-house pipeline; **redact by default** (never log privileged content), correlate by ID, surface a user-facing Error ID, and never use a third-party error SaaS. Standard: [`docs/conventions/error-logging.md`](docs/conventions/error-logging.md). (_Observability & diagnostics_; ADR-0017, ADR-0038)
5. **Keep documentation current.** No feature is done until its docs (developer _and_ user) and [`ROADMAP.md`](ROADMAP.md) + [`CHANGELOG.md`](CHANGELOG.md) are updated — same commit. For the changelog and ADRs this is met by committing a **fragment** (`changelog.d/<slug>.md`, `docs/decisions/pending/<slug>.md`); the rendered `CHANGELOG.md` and the Decision-Log register are build outputs assembled on `main` by `vp run changelog-build` / `vp run decisions-build`, never hand-edited on a branch. Standard: [`documentation.md`](docs/conventions/documentation.md); language: [`documentation-style.md`](docs/conventions/documentation-style.md).
6. **Feature parity.** Web and desktop stay at parity; no platform-exclusive features (desktop only adds optional local accelerations with a server fallback). (_Delivery model_; ADR-0023)
7. **No shell for file operations; Bash is the shell.** Dedicated file tools only — the shell is for git, pnpm, cargo, rustup, and process management. Of the two shells this machine offers, **Bash (Git Bash) is canonical**; reach for PowerShell only for genuinely Windows-native work (process/service management, ACLs). Mixing them is not a style preference: the two take opposite multi-line-string syntax (heredoc vs here-string) and opposite path/redirect idioms, and PowerShell invocations here fail about four times as often as the same work in Bash. Write paths in one canonical form — `C:/dev/magna-carta-worktrees/<branch>`, forward slashes, unquoted — and pass absolute paths rather than prefixing `cd <dir> &&`, so a permission allow-list entry can actually match twice.
8. **Design before code.** White paper → brainstorm → spec ([`docs/specs/`](docs/specs/)) → plan → build; record decisions as ADRs in [`docs/Decision-Log.md`](docs/Decision-Log.md), same commit.
9. **One home per fact.** Follow existing conventions; reference the white paper by topic name or `ADR-NNNN`, never a `§` number.
10. **Measure before optimizing; keep work off the hot path.** No heavy work in a request handler or on the UI main thread — offload to Containers/Queues/Web Workers; stream, don't buffer; no N+1. Optimize against the load-profile harness, not guesses. (_Performance & concurrency model_; ADR-0039)
11. **Implement on the latest — verify library docs first.** Before using or upgrading any library, look up its **current** documentation and build against the latest stable API/patterns (e.g. Svelte 5 **runes**, Tailwind v4, Vite+ `vp`) — never older idioms from memory. Web-search the docs when unsure. Getting it current up front avoids retrofitting the codebase later. (_Development guidelines_)
12. **Fully write out names — no shorthand.** Spell every name out in full across packages, code, and docs: `@magna-carta/identifiers` not `ids`, `@magna-carta/database` not `db`, `@magna-carta/data-access` not `dal`; `newIdentifier()` not `newId()`; "the data-access layer", never "the DAL". Clarity imposed now is cheap; decoding shorthand later is not, and it compounds across the codebase. Only exception: documented storage-encoding suffixes from an accepted spec (e.g. `amount_minor`, `rate_e4`) and universal external terms (`id`, `URL`, `JSON`, `SQL`). Standard: [`docs/conventions/code-style.md`](docs/conventions/code-style.md).
13. **Code explains itself; cite files, not process docs.** Source, tests, config, and consumer-facing strings (e.g. OpenAPI `description`s) carry **no references to process artifacts** — no `ADR-NNNN`, no "design spec" / "spec §N", no white-paper section citation, no "slice 0·N" / "Phase N", no "decided #N" / plan "Task N", no "spike". State the _reasoning_ inline, or point to a concrete file (another module, or a living standard in [`docs/conventions/`](docs/conventions/) **by path**). ADRs, specs, and plans are point-in-time process records that move, renumber, and get superseded; a comment that explains _why_ outlives them. Decisions are still recorded as ADRs (golden rule 8) — the [Decision Log](docs/Decision-Log.md) is their home, never the code. **One exception:** a _forward-looking_ slice/phase reference that names **when** an interim or seam gets replaced, or a feature gets built (e.g. "slice 0·6 swaps in the real email adapter", "built in Phase 2·3") — that states a real schedule, not a process-doc citation, and is allowed. Enforced in CI by a source-scan fitness function (`pnpm run lint:process-refs`). Standard: [`docs/conventions/code-style.md`](docs/conventions/code-style.md).
14. **Memory-safe languages by default — Rust, TypeScript, Svelte.** Build in Rust, TypeScript, and Svelte. A **C/C++ dependency or tool** — including transitive native libraries and C-compiled-to-WASM — is used **only when there is no legitimate Rust/TypeScript alternative**, and even then **only with explicit owner consent**. Memory-unsafe code parsing untrusted, privileged bytes is a confidentiality risk even inside a sandbox, so prefer the memory-safe library even at some cost in performance or format breadth, and record the trade. When an existing or proposed dependency pulls in C/C++, surface it and ask rather than adopting it silently. (e.g. the raster conversion engine uses the pure-Rust `image` crate, not native libvips; where a C engine is genuinely unavoidable — clamd in the malware-scan Container — it is consented, contained in a network-isolated sandbox, and documented.)

**Domain invariants (scoped).** Subsystem-specific correctness rules — the financial & trust ledger rules, and secrets/encryption — are hard but bind only in their area: see [`docs/conventions/invariants.md`](docs/conventions/invariants.md) and the local `CLAUDE.md` of the area you are working in.

## How we work

- **Build in vertical slices:** each feature complete through every layer (schema → firm-scoped data-access layer → API → UI → tests → docs), not horizontal layers — each slice ships working and is perf-tested against the load-profile fixtures as built.
- **Build when in the area:** when a slice is open, include the cheap-from-the-getgo / expensive-to-retrofit parts up front — seams, schema columns, instrumentation. "Build when measured" gates are for heavy machinery only (golden rule 10 governs optimization, not foundations). This includes **build-time performance**: anything that builds repeatedly in CI or the cloud is made fast by default (caching, path-filtering, slow inputs baked at build time) — fast feedback compounds, and a cache is a foundation you add up front, not a measure-first optimization. Home: [`docs/conventions/build-performance.md`](docs/conventions/build-performance.md). (ADR-0078)
- **UI is built in the repository, and reviewed on the deployed site.** The owner's standing
  direction from 2026-08-29: a screen under review is real Svelte in `apps/web` or a real component
  in `packages/design-system`, so a correction lands in the code that ships instead of in a
  disposable copy of it. `magna-carta-web` builds from `main`, so a merge is visible within
  minutes. The self-contained HTML mockup — the route the file manager and the financial surfaces
  took through 2026-08 — is **superseded for new work**: it cost every screen twice and lost the
  owner's own polish in translation. What survives from it is the part worth keeping: the ruling
  ledgers in [`docs/conventions/`](docs/conventions/), which are the regression memory, and the
  browser harnesses that pin them. Where a screen needs a reviewable state that real data cannot
  reach, build the dev-only gallery beside it (`/developer-console/*`, the sign-in-screens
  precedent), never a second implementation.
- **Implementation:** autonomous and terse; comprehensive fixes over incremental patches. Design and brainstorming stay collaborative.
- **Install, then bootstrap, then check what changed.** A fresh worktree starts with **no `node_modules` at all** and without its generated artefacts (the Rust→WASM output under `packages/{pdf,decryption,email,seven-zip}/src/pkg/` is git-ignored), so anything importing them fails until they exist. Two commands, in this order: **`pnpm install`**, then **`pnpm exec vp run bootstrap`** (which rebuilds only what is stale and is a no-op otherwise). Plain `pnpm install` is the first one on purpose — **`vp` is a `devDependency`, so it does not exist until something has installed it**, and `pnpm exec vp install` in a fresh worktree exits 254 with `Command "vp" not found`. Reaching for the parent checkout's binary instead is worse than it looks: `vp` then takes _that_ checkout as its root and operates on the wrong tree. While working, run **`pnpm check:scoped`** (fmt + lint on the diff, incremental `tsc -b`, and svelte-check/Rust only when you touched them), not the full `pnpm check`. The pre-push hook runs that same scoped gate for fast local feedback; the exhaustive whole-repo gate is **`pnpm gate`** (`tooling/gate/`), the **gate of record, run on the machine that made the change before it merges** — format, governance, the pinned osv-scanner audit, the WASM artefacts, the type-check, the contract-drift checks, the type-aware lint over the affected closure, the Rust and container gates where the change reaches them, and the full `pnpm test`, each dimension run only when the change can reach it and named when skipped. The same command also runs hosted as the required `gate` check (`.github/workflows/ci.yml`, restored 2026-11-09 on a capped Actions budget), so a pull request still pastes the local gate's summary block into its description, `pnpm gate --plan` says what a change will run, and `pnpm gate --all` is the sweep after a batch of merges. **The repo-wide fitness sweep** (the Vitest checks that self-register with `@repo-wide-fitness` — the encryption chokepoint, the console ban, the off-token and `bits-ui` scans) runs unconditionally in the gate's `governance` dimension, because a whole-repo scan that only the test battery looks at is one the merge is the first to report. Home: [`docs/conventions/build-performance.md`](docs/conventions/build-performance.md).
- **A merge that adds a package or an export path needs `pnpm install` before typecheck means anything.** Workspace links are resolved at install time, so after merging `main` a `tsc -b` can fail with `Cannot find module '@magna-carta/<something>'` for code that is perfectly correct. It reads exactly like a real break and it is not one — run `pnpm install`, then re-run. Three separate cycles were spent diagnosing this in one day. `node tooling/tsconfig-refs/index.mjs --check` tells the two apart: if the build refs are in sync, the missing module is a stale link rather than a missing reference.
- **Never run two test suites at once, in any worktree.** The `pnpm test` single-flight lock is **per-worktree, not per-machine**, so nothing stops a second run — and it will not fail cleanly, it will produce phantom failures in files neither run touched. Timeouts are the usual shape, because a starved test looks exactly like a slow one. This also covers running `check:scoped` or a doc build in one worktree while a suite runs in another. Before believing any test failure, re-run it with the machine idle.
- **Land a pull request the way parallel threads need it to land** (owner ruling 2026-11-09, carried over from the Grim-Games repository). Several threads open pull requests at once against a `main` that deploys on merge, so:
  - **Merge `main` into your branch right before every push**, and again whenever `main` moves while your pull request is open. A merge commit, never a rebase or force-push of a branch others may have read. Check with **`git fetch origin main && git merge-tree --write-tree origin/main HEAD`** (non-zero exit, or conflict lines in its output, means it conflicts): GitHub's own conflict check lags the push by minutes.
  - **A pull request that conflicts with `main` gets no CI at all**, so its `gate` check never reports and auto-merge never fires, and nothing tells you. The PR upkeep workflow (`.github/workflows/pr-upkeep.yml`) labels it `merge conflict` and comments once per head commit: fix it on that wake, by merging `main` in and re-running `pnpm gate`.
  - **Turn on auto-merge (squash) once the pull request is ready**, so it lands the moment `gate` is green, with nobody polling. A green pull request with auto-merge on that has not merged 30 minutes later gets a "stuck" comment from the upkeep workflow: merge it through the merge API. Where the owner has asked to review a change before it ships (anything in the template's _Reaches production as_ list counts), leave auto-merge off and say so in the pull request.
- **"Has this branch landed?" is a question about the past, and neither ancestry nor a merge into today's `main` answers it.** This repository squash-merges, so a landed branch is never an ancestor of `main` — `git branch --merged` and `git merge-base --is-ancestor` report only branches with **no commits of their own**, which is a live or abandoned workspace, not a delivery. Merging the branch into `origin/main` in memory (`git merge-tree --write-tree`) and checking the tree is unchanged is right **only on the day it merges**: once `main` touches any file the branch also touched, re-merging is no longer a no-op and the same test answers "not landed" for a branch that provably landed, permanently. Ask instead **where** the content landed — walk `main` forward from the merge base and find the first commit the branch merges into without changing it. That commit never moves, so the answer never expires. Worked implementation: [`tooling/branch-landing/`](tooling/branch-landing/), shared by the artifact cleaner and the active-work registry.
- **Read a file immediately before you edit it, and give every file one owner.** Most failed edits are stale-context edits: the file was read long ago, or a second agent rewrote it in between. When work is split across concurrent agents, each file belongs to exactly one of them — overlapping ownership turns a fast parallel pass into a serial repair job.
- **Per-area `CLAUDE.md`:** each code area carries its own (template in [`docs/conventions/`](docs/conventions/)) for local rules and the domain invariants that apply there — keep cross-cutting rules in `docs/conventions/`, not duplicated locally. Held by **`pnpm run lint:area-notes`**: every workspace package has a note, and each note opens by naming its own area and saying what it is. 55 of 85 do today, so the 30 without are a register that only shrinks — among them `packages/data-access`, the home of the firm-scoping golden rule, and `apps/web`. A NEW package arrives with its note.

### Parallel worktrees & branches

Several worktrees run at once, so streams must stay aware of each other and keep merges cheap.

- **Make your stream visible.** When you start work, add a note at [`docs/active-work/<branch>.md`](docs/active-work/) — **the path mirrors the branch exactly, slashes included** (`claude/fix-thing` gets `docs/active-work/claude/fix-thing.md`), and it needs the frontmatter block from [`docs/active-work/README.md`](docs/active-work/README.md) (`worktree`, `area`, `status`, `touches`). A note at a flattened path, or with no frontmatter, is invisible to the registry and warns nobody — `vp run worktrees` names both cases, so run it before you push. Before starting a stream — and **before editing any cross-cutting file** (`CLAUDE.md`, `STATUS.md`, `ROADMAP.md`, the white paper, `docs/conventions/`) — run **`vp run worktrees`** to see what else is in flight and where it overlaps. One note per stream (never a shared list), so the registry never collides.
- **Append-don't-collide on shared files — but STATUS is not one of them.** CHANGELOG, ADRs, and STATUS all go through fragments (`changelog.d/`, `docs/decisions/pending/`, `status.d/`), and that is where your edit goes. Where they differ is who renders them, and getting this backwards costs a round trip: **branches never edit `CHANGELOG.md`, the Decision-Log register, or the build register (`docs/now.md`, `docs/now.html`, `docs/decisions-open.html`)** — those are assembled on `main`, and a branch that writes them collides with every other branch. A branch flips its `roadmap.d/` node and stops; `pnpm run lint:roadmap` fails a branch that carries the rendered register, and `vp run register-build` refuses to write it there. **`STATUS.md`/`STATUS.json` are rendered on the branch and committed with the fragment**: write `status.d/<slice>.md`, run **`vp run status-build`**, and commit all three. `pnpm run lint:status` fails otherwise ("STATUS.md does not match a fresh render of status.d/"), so a branch that adds a fragment and stops cannot pass its own gate.
- **Sync `main` on a cadence.** Long-lived branches merge/rebase `main` regularly, and **always before touching a shared or generated file** — merge cost scales with drift. If `main` is more than a handful of merges ahead (`vp run worktrees` shows the gap), sync before continuing.
- **Worktree lifecycle — `vp run retire-note <branch>`, not four edits by hand.** Feature worktrees live at `C:/dev/magna-carta-worktrees/<branch>`; transient agent worktrees under `.claude/worktrees/`. Retiring a stream is **one command**: it clears every `status.d/` fragment whose `active-work:` names the note, re-renders `STATUS.md`/`STATUS.json`, deletes `docs/active-work/<branch>.md`, and removes the worktree and branch. That fragment pointer is the part that gets forgotten — the note deletion looks like one file, and `pnpm run lint:status` then fails with "active-work points at a missing file" long after the fact — so the parts are not separable here and the pointer cannot outlive the note. **Run it with `--with-merge`, on the branch, in the pull request that lands the work** — `main` is production, so retiring in a second pull request afterwards is a production deploy whose only content is deleting one file. The deletion is a commit on the branch, so it reaches `main` exactly when the work does and `main` keeps the note for as long as the pull request is open; nothing is hidden from another worktree early. That is also why `--with-merge` skips the landing check and checks instead that you are on the branch: a branch cannot have landed while the pull request landing it is still open. It does the **paperwork only** — removing a worktree and deleting a branch cannot happen from inside that branch, so run a plain `vp run retire-note <branch>` locally afterwards for that half, which keeps its landing check. Without `--with-merge` the command refuses a branch that has not landed unless you pass `--force`; `--dry-run` prints the plan, `--keep-workspace` retires the paperwork only. `vp run worktrees` names every dead note **with its dependent fragments and this command**, so discovery and remedy arrive together. Periodically `git worktree prune` and clear `[gone]` branches. A tracked `post-merge` hook runs `vp run clean` on every merge to `main`, sweeping regenerable build artifacts (`target/`, `.svelte-kit/`, `.wrangler/`, `.vite/`, `dist/`, `build/`, `coverage/`) from worktrees whose branch has landed — pruning dangling Docker cache, and sweeping load-profile working copies abandoned in the system temp directory by a killed run (its own `mkdtemp` name shape only, and only when older than 24 h — the snapshotter reaps its own, so this is the backstop) — so dead build output never accumulates. The hook is git-ignored-only and never removes a worktree, branch, or `node_modules`. `pnpm install` activates the tracked hooks through its `postinstall` step (**`vp run setup-hooks`** is the same step, runnable by hand if it warned); `vp run clean` is also runnable by hand (preview with `node tooling/clean/index.mjs --dry-run`).

## Commands

```
pnpm install                                                            # FIRST in a new worktree: vp is a devDependency, so it does not exist until this has run (`pnpm exec vp install` there exits 254)
vp install                                                              # deps thereafter (vp manages pnpm + Node version)
vp run bootstrap                                                        # SECOND in a new worktree: build the git-ignored Rust->WASM artefacts; rebuilds only what is stale, no-op when current
vp run setup-hooks                                                      # activate the tracked git hooks (pre-push quality gate + auto-clean on merge to main); pnpm install already runs this as its postinstall step
vp dev                                                                  # web SPA dev server only (Vite HMR, no Worker)
vp run worker-dev                                                       # full local app: builds the SPA, then runs wrangler dev (Miniflare: local D1/R2/Queues)
vp run build-all                                                        # build all apps in dependency order
vp run worktrees                                                        # print the active-work registry (concurrent streams + touch-overlaps + drift from main) — and every dead note with the command that retires it
vp run retire-note <branch> --with-merge                                # ROUTINE: retire the note in the PR that lands the work (paperwork only: clears every status.d/ pointer at it, re-renders STATUS, deletes the note) — run ON the branch
vp run retire-note <branch>                                             # afterwards, locally: the same, plus removing the worktree + branch (--dry-run / --force / --keep-workspace)
vp run register-build                                                   # re-render docs/now.md (the build register) from the roadmap.d/ feature ledger — on main only (the assembly workflow or the docs-sync routine); on a branch it refuses, because a branch's change is its roadmap.d/ edit alone (--preview shows the render without committing it)
pnpm test                                                               # unit + integration (Vitest, single-run; includes the Miniflare worker integration test). Wraps `vp test` with a per-worktree single-flight lock — two runs in one worktree wedge each other at 0% CPU, so a second one is refused. Args pass straight through; filter by PATH, not by test name
pnpm check:scoped                                                       # INNER LOOP: fmt+lint on the diff, incremental tsc -b, svelte-check/Rust only if touched
pnpm fix:scoped                                                         # apply fmt + lint autofixes to that SAME diff (markdown included) — never a bare repo-wide `vp check --fix`. Autofixes known to be wrong here (sort()->toSorted(), `=== false`->`!x`) still WARN but are never applied
pnpm gate                                                               # THE GATE OF RECORD, before a merge: every dimension the change can reach (format, governance, audit, wasm, typecheck, contracts, lint over the affected closure, rust, containers, test-collection, the full pnpm test). --plan prints what would run; --all is the sweep; --checks-only skips the battery; --only/--skip name dimensions
pnpm check                                                              # full quality gate (slow, exhaustive): every pass over the whole repo — the whole-repo half of `pnpm gate`; run it by hand only when you want that answer on its own
pnpm --filter @magna-carta/api-worker exec wrangler deploy --dry-run        # validate deploy without pushing
cargo test  /  cargo clippy                                             # Rust
```
