# Magna Carta — CLAUDE.md

Magna Carta is a legal practice-management platform the firm controls — matters, time, trust, billing, costs, conflicts, discovery, custodian, documents & automation, a client portal, payments, and reporting — built on Cloudflare, multi-tenant from day one.

This is the **entry point** for anyone working in this repo: the golden rules and where everything lives. Read it, then follow the links — detail lives in the linked homes, not here.

**Cross-reference rule:** `§N` is navigation _inside_ the white paper only. From any other file, reference the white paper by **document + topic name** (or a stable **`ADR-NNNN`**), never a section number — they shift on reorganization.

**Developer docs vs. user docs — not duplication.** The white paper / conventions / specs / ADRs serve _builders_; [`docs/user/`](docs/user/) serves _people using the product_. Different facts for different readers (no shared sentences to drift), hard boundary: no internal architecture in user docs, no task walkthroughs in developer docs. `docs/user/` is additive — the only home for user-facing help, which is itself a shipped product feature.

## Stack at a glance

- **Languages:** TypeScript (primary); **Rust** surgically (Tauri shell, Tantivy, a shared doc/discovery core → WASM for web + native for desktop).
- **Frontend:** Svelte 5 / SvelteKit (SPA, `adapter-cloudflare`); Tailwind v4 + the in-house **`@magna-carta/design-system`** (styled directly on headless **Bits UI**); DTCG tokens via Terrazzo; **Lucide icons**.
- **Backend:** Cloudflare **Workers** + **Hono**; REST as **OpenAPI 3.1 code-as-contract** (zod).
- **Data/platform:** control-plane **D1**; a per-firm **SQLite-backed Durable Object** (`FirmDatabase`, addressed by firm id, self-migrating on wake — it replaced per-firm D1, which capped the fleet at the ~5,000-bindings-per-Worker ceiling and needed a redeploy per firm: ADR-0140); per-firm **R2**; **Queues**, **Durable Objects**, **KV**; **Containers** (Collabora, Tantivy, OCR, LibreOffice).
- **Auth:** Better Auth (control-plane D1). **Desktop:** Tauri 2 (after web MVP). **Tooling:** **Vite+** (CLI `vp`; manages pnpm + dev/build/pack/test + `vp check` for fmt/lint/typecheck — Oxc) · rustfmt/clippy. **Source control:** GitHub (repos, branch protection, PRs, review). **CI/CD:** **Cloudflare Workers Builds** deploys (`vp run build-all` → `wrangler deploy`); GitHub Actions runs the pull-request `gate` check. **`main` IS production** — the owner moved `magna-carta` and `magna-carta-web` onto it on 2026-08-29 to shorten the UI review loop, superseding the deliberate `git push origin main:release` model this file described before. So **a merge to `main` deploys, within minutes, with no second gesture.** Treat every merge accordingly: a migration, a contract change or a binding change reaches real users on the strength of whatever verification ran before it landed — and that verification is whatever ran on the pull request (see _Merge bar_ below). `release` no longer gates anything; it survives as history. Runbook: [`docs/conventions/operations.md`](docs/conventions/operations.md).

Architecture detail: the [white paper](docs/Magna-Carta-White-Paper.md) — _Delivery model_, _Authentication & encryption_, _Core domain_.

## Golden rules

Broad principles for how we build — they apply across the work, not just one subsystem.

1. **Reuse before building.** Check for an existing component, utility, or pattern before creating a new one; compose and extend rather than reinvent.
2. **All UI through the design system.** Style only with Tailwind + the `@magna-carta/design-system` components and design tokens — no raw CSS, no off-token values, no direct `bits-ui` imports outside the design-system package (CI rejects all three). Lucide icons; **no emojis** anywhere (UI, docs, commits). (_Design system_; ADR-0076)
3. **Data access through the firm-scoped data-access layer.** All business data goes through the firm-scoped data-access layer — no query crosses firms; bulk content to R2, never D1. (_Tenancy & data isolation_; ADR-0003)
4. **Standardized error & bug logging.** Report every error/bug through the one standard in-house pipeline; **redact by default** (never log privileged content), correlate by ID, surface a user-facing Error ID, and never use a third-party error SaaS. Standard: [`docs/conventions/error-logging.md`](docs/conventions/error-logging.md). (_Observability & diagnostics_; ADR-0017, ADR-0038)
5. **Keep documentation current.** No feature is done until its docs (developer _and_ user), `ROADMAP.md` and the changelog are updated in the same pull request, through fragments (see _Shared files and fragments_). Standard: [`documentation.md`](docs/conventions/documentation.md); language: [`documentation-style.md`](docs/conventions/documentation-style.md).
6. **Feature parity.** Web and desktop stay at parity; no platform-exclusive features (desktop only adds optional local accelerations with a server fallback). (_Delivery model_; ADR-0023)
7. **Prefer the dedicated file tools; the shell is Bash.** Read, search and edit files with the dedicated tools where they fit; use the shell for git, pnpm, cargo, process management, and for searches or mechanical edits that are clearer as a command.
8. **Design before code.** White paper → brainstorm → spec ([`docs/specs/`](docs/specs/)) → plan → build; record decisions as ADRs in [`docs/Decision-Log.md`](docs/Decision-Log.md), same commit.
9. **One home per fact.** Follow existing conventions; reference the white paper by topic name or `ADR-NNNN`, never a `§` number.
10. **Measure before optimizing; keep work off the hot path.** No heavy work in a request handler or on the UI main thread — offload to Containers/Queues/Web Workers; stream, don't buffer; no N+1. Optimize against the load-profile harness, not guesses. (_Performance & concurrency model_; ADR-0039)
11. **Implement on the latest — verify library docs first.** Training data lags releases, so before using or upgrading a library, check its current documentation and build on the latest stable API (Svelte 5 runes, Tailwind v4, Vite+ `vp`). (_Development guidelines_)
12. **Fully write out names — no shorthand.** Spell every name out in full across packages, code, and docs: `@magna-carta/identifiers` not `ids`, `@magna-carta/database` not `db`, `@magna-carta/data-access` not `dal`; `newIdentifier()` not `newId()`; "the data-access layer", never "the DAL". Clarity imposed now is cheap; decoding shorthand later is not, and it compounds across the codebase. Only exception: documented storage-encoding suffixes from an accepted spec (e.g. `amount_minor`, `rate_e4`) and universal external terms (`id`, `URL`, `JSON`, `SQL`). Standard: [`docs/conventions/code-style.md`](docs/conventions/code-style.md).
13. **Code explains itself; cite files, not process docs.** Source, tests, config and consumer-facing strings carry no references to process artifacts (no `ADR-NNNN`, spec sections, "slice 0·N", plan task numbers, "spike"): state the reasoning inline or point at a concrete file by path. ADRs and specs move and get superseded; a comment that explains _why_ outlives them. The one exception is a forward-looking reference that says when an interim gets replaced ("slice 0·6 swaps in the real email adapter"). Enforced by `pnpm run lint:process-refs`; standard: [`docs/conventions/code-style.md`](docs/conventions/code-style.md).
14. **Memory-safe languages by default — Rust, TypeScript, Svelte.** Build in Rust, TypeScript, and Svelte. A **C/C++ dependency or tool** — including transitive native libraries and C-compiled-to-WASM — is used **only when there is no legitimate Rust/TypeScript alternative**, and even then **only with explicit owner consent**. Memory-unsafe code parsing untrusted, privileged bytes is a confidentiality risk even inside a sandbox, so prefer the memory-safe library even at some cost in performance or format breadth, and record the trade. When an existing or proposed dependency pulls in C/C++, surface it and ask rather than adopting it silently. (e.g. the raster conversion engine uses the pure-Rust `image` crate, not native libvips; where a C engine is genuinely unavoidable — clamd in the malware-scan Container — it is consented, contained in a network-isolated sandbox, and documented.)

**Domain invariants (scoped).** Subsystem-specific correctness rules — the financial & trust ledger rules, and secrets/encryption — are hard but bind only in their area: see [`docs/conventions/invariants.md`](docs/conventions/invariants.md) and the local `CLAUDE.md` of the area you are working in.

## How we work

All work runs in Claude Code cloud sessions: each project thread gets a fresh container, one branch (`claude/<thread>`), and a pull request. The project coordinator tracks which threads are in flight. A merge to `main` deploys.

- **Build in vertical slices:** each feature complete through every layer (schema → firm-scoped data-access layer → API → UI → tests → docs), not horizontal layers — each slice ships working and is perf-tested against the load-profile fixtures as built.
- **Build when in the area:** when a slice is open, include the cheap-from-the-getgo / expensive-to-retrofit parts up front — seams, schema columns, instrumentation. "Build when measured" gates are for heavy machinery only (golden rule 10 governs optimization, not foundations). That includes build-time performance: anything that builds repeatedly in CI is fast by default (caching, path-filtering). Home: [`docs/conventions/build-performance.md`](docs/conventions/build-performance.md). (ADR-0078)
- **New screens start as mockups the owner picks from; corrections land in the code.** For a new screen or a redesign, show two or three options as screenshots in the project files and build the one the owner picks as real Svelte in `apps/web` or `packages/design-system`. A correction to a built screen goes straight into the code and is reviewed on the deployed site (`magna-carta-web` builds from `main`). Never build a second implementation to review: for a state real data cannot reach, add a dev-only gallery beside the screen (`/developer-console/*`). The ruling ledgers in [`docs/conventions/`](docs/conventions/) are the regression memory.
- **Implementation:** autonomous and terse; comprehensive fixes over incremental patches. Design and brainstorming stay collaborative.
- **Set up a fresh container in this order.** The Rust→WASM output under `packages/{pdf,decryption,email,seven-zip}/src/pkg/` is git-ignored and `vp` is a devDependency, so: `cargo install wasm-pack --locked` if `wasm-pack` is missing (the SessionStart hook in `.claude/hooks/session-start.sh` does this when it runs, but it does not always run), then `pnpm install`, then `pnpm exec vp run bootstrap` (rebuilds only what is stale). Set `NODE_OPTIONS=--max-old-space-size=8192` before `tsc -b` or `pnpm gate`; the container's default Node heap of about 2 GB runs out. A Rust build in `crates/` can write about 18 GB to `crates/target` and fill the container's disk; set `CARGO_TARGET_DIR` outside the repository when a change reaches Rust.
- **Check what changed, then gate it.** While working, run `pnpm check:scoped` (fmt + lint on the diff, incremental `tsc -b`, svelte-check/Rust only when touched). Before a pull request is ready, run `pnpm gate --checks-only --skip containers,audit,rust` and paste its summary into the pull request: the container has no Docker and its proxy refuses `api.osv.dev` and `cdn.pyke.io`, so those three dimensions cannot run here. The hosted `gate` check (`.github/workflows/ci.yml`) runs the rest, including the full test battery; `pnpm gate --plan` says what a change will run. The repo-wide fitness sweep (the `@repo-wide-fitness` Vitest checks: encryption chokepoint, console ban, off-token and `bits-ui` scans) runs in the gate's `governance` dimension. Push with `--no-verify`, because the pre-push hook's Rust step needs `cdn.pyke.io`.
- **A merge that adds a package or an export path needs `pnpm install` before typecheck means anything.** A `tsc -b` after merging `main` can fail with `Cannot find module '@magna-carta/<something>'` for correct code. Run `pnpm install` and re-run; `node tooling/tsconfig-refs/index.mjs --check` tells a stale link from a missing reference. Recurring fixes after a `main` merge are listed in [`docs/conventions/build-performance.md`](docs/conventions/build-performance.md) under _Merging main_.
- **Run one test suite at a time.** Two concurrent runs (or `check:scoped` beside a suite) starve each other and produce phantom timeouts in files neither touched. Before believing a test failure, re-run it alone.
- **Merge bar** (owner ruling 2026-11-09): **speed of landing beats green tests.** Merge a feature-complete, non-draft pull request on the checks a cloud session can run, without waiting for the full battery or an all-green hosted run, and list in the pull request any failing check you merged past so the owner can clean it up later. Never merge past a failure that breaks the build, the deploy, or a migration. When the owner asked to review a change first, wait for their word.
- **Land a pull request the way parallel threads need it to land:**
  - **Merge `main` into your branch right before every push**, and again whenever `main` moves while the pull request is open. A merge commit, never a rebase or force-push (the cloud push proxy refuses force pushes anyway). Check with `git fetch origin main && git merge-tree --write-tree origin/main HEAD`; GitHub's own conflict check lags by minutes.
  - **A pull request that conflicts with `main` gets no CI at all.** The PR upkeep workflow (`.github/workflows/pr-upkeep.yml`) labels it `merge conflict`; fix it by merging `main` in.
  - **Land with a squash merge through the merge API.** Auto-merge cannot be turned on for this repository from a cloud session.
  - **If every hosted job fails in seconds with no steps run,** read the check-run annotations before debugging (`gh api repos/Phauks/magna-carta/check-runs/<id>/annotations`): it is usually the Actions spending limit, not the code. Land on the cloud checks and say so in the pull request.
- **"Has this branch landed?"** This repository squash-merges, so ancestry never answers it. Use [`tooling/branch-landing/`](tooling/branch-landing/), which finds the commit on `main` where the branch's content landed.
- **Give every file one owner.** When work is split across concurrent agents, each file belongs to exactly one of them. Re-read a file another agent may have touched before you edit it.
- **Per-area `CLAUDE.md`:** each code area carries its own ([template](docs/conventions/area-claude-template.md)) for local rules and the invariants that apply there — cross-cutting rules stay in `docs/conventions/`. Keep a note to what an agent needs before editing that area: purpose, key files, local rules, invariants, gotchas. Rulings history and design narrative belong in `docs/conventions/` ledgers or `docs/specs/`. A large package splits its note by subdirectory, so a family's rules load only when you work on it (`packages/design-system` is the precedent). Held by `pnpm run lint:area-notes`; a new package arrives with its note, and the packages still without one are a register in `tooling/lint-area-notes/baseline.json` that only shrinks.
- **The repository is public** (since 2026-11-13; all rights reserved). Never commit a personal email address, an IP address, or a secret. See [`docs/conventions/security.md`](docs/conventions/security.md).

### Shared files and fragments

- **Branches write fragments, `main` renders.** CHANGELOG, ADRs, and the build register go through fragments (`changelog.d/`, `docs/decisions/pending/`, `roadmap.d/`). A branch never edits `CHANGELOG.md`, the Decision-Log register, or `docs/now.md` / `docs/now.html` / `docs/decisions-open.html`; `pnpm run lint:roadmap` fails a branch that carries the rendered register.
- **STATUS is the exception: it renders on the branch.** Write `status.d/<slice>.md`, run `vp run status-build`, and commit the fragment with `STATUS.md` and `STATUS.json`; `pnpm run lint:status` fails otherwise.
- **Active-work notes are only for work other files point at.** A cloud thread does not need a `docs/active-work/<branch>.md` note: the coordinator tracks threads. Write one (path mirrors the branch, frontmatter from [`docs/active-work/README.md`](docs/active-work/README.md)) only when a `status.d/` fragment's `active-work:` or a `roadmap.d/` node marked `in-build` must name it, because `lint:status` and `lint:ledger-staleness` check those pointers. Retire it in the pull request that lands the work with `vp run retire-note <branch> --with-merge`. The weekly docs-sync pass deletes notes whose branch is gone.

## Commands

```
pnpm install                                   # first in a fresh container (vp is a devDependency)
pnpm exec vp run bootstrap                     # second: build the git-ignored Rust->WASM artefacts; no-op when current
vp dev                                         # web SPA dev server only (Vite HMR, no Worker)
vp run worker-dev                              # full local app: builds the SPA, then runs wrangler dev (Miniflare)
vp run build-all                               # build all apps in dependency order
pnpm check:scoped                              # inner loop: fmt+lint on the diff, incremental tsc -b, svelte-check/Rust only if touched
pnpm fix:scoped                                # apply fmt + lint autofixes to that same diff; never a bare repo-wide `vp check --fix`
pnpm gate                                      # the gate: every dimension the change can reach. --plan / --checks-only / --only / --skip / --all
pnpm test <path>                               # Vitest, single run; filter by PATH, not by test name
vp run status-build                            # re-render STATUS.md/STATUS.json from status.d/
vp run retire-note <branch> --with-merge       # retire an active-work note in the PR that lands the work
pnpm --filter @magna-carta/api-worker exec wrangler deploy --dry-run   # validate a deploy without pushing
cargo test  /  cargo clippy                    # Rust
```
