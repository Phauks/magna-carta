## 1. Token architecture — needs-attention

**Tier layering is real and disciplined.** Primitives (`packages/design-tokens/tokens/primitives/*.json`) → semantic aliases only (`tokens/semantic.json:5` — every `$value` is a `{color.*}` reference) → component tier deliberately deferred (design spec §2.2, `docs/specs/2026-06-10-design-system-foundation-design.md:40`). The resolver (`resolver.json:51-57`) stacks primitives → semantic → theme → mode → contrast. This is the correct factoring and the five gates (purity/completeness/contrast/golden/drift) make it enforceable rather than aspirational.

**Semantic completeness for coming surfaces — mostly there, with named holes:**

- Strong: the subtle status trios (`tokens/semantic.json:59-81`), the `chrome.*` edge register (`semantic.json:49-58`), the gold `accent.*` set (`semantic.json:41-48`), all AA-gated in every theme×mode (`src/contrast-pairs.ts:27-151`).
- **Selection is not a semantic role.** DataTable overloads `action.secondary` for both row hover and row selection (`packages/design-system/src/lib/components/data-table/data-table.css:66-71`). Billing/trust screens are selection-heavy; when the owner wants selected ≠ hover (or a different selection tint in one theme), there is no token to turn. Add `surface.selected` (or `interaction.hover`/`interaction.selected`) while the consumers number one.
- **No field-surface token.** Inputs sit on `surface.default`; dense forms at scale (intake wizards, portal) commonly want a distinct field background. Cheap to alias now (`surface.field: {color.neutral.0}`), expensive to sweep later.
- **Legal-domain statuses (trust/hold/conflict)** are named in the design language (`docs/specs/2026-06-12-design-language.md:74`) but absent from `semantic.json` — acceptable (register-as-slices-land is the stated plan), but reserve the _pattern_ now: each will need the full solid-pair + subtle-trio shape and a `contrast-pairs.ts` entry, and Badge should take variants as data so registration is additive.
- **Namespace collision:** semantic text _colors_ (`--mc-text-default`, `semantic.json:11-17`) and primitive type _sizes_ (`--mc-text-sm`, `tokens/primitives/typography.json:33-41`) share the `--mc-text-*` prefix in generated output. A size var in a `color:` slot passes the purity gate and fails silently. Decide now (rename to `--mc-color-text-*` / `--mc-font-size-*` while consumers are one package) or document and accept; renaming at 80 components is a breaking sweep.

**The four unwired axes — the "genuinely additive" claim is half true:**

- **Typeface — genuinely additive.** Every recipe consumes `var(--mc-font-sans)` (44 references); a `:root[data-typeface="lexend"] { --mc-font-sans: … }` overlay re-points one variable with zero recipe edits. Note the overlay must be imported _after_ `tokens.css` (specificity ties with `:root[data-theme="…"]`), and Lexend/OpenDyslexic faces are not yet in `fonts.css` — additive, but not free.
- **Density — NOT proven, and the design language's claim is currently unmet.** `docs/specs/2026-06-12-design-language.md:108` states "A real second density is defined now so the axis is _proven_, not theoretical." In fact: (a) there is no density modifier in `resolver.json:22-49` (only theme/mode/contrast) and no compact values anywhere; (b) only DataTable consumes the `density.*` aliases — 4 references (`data-table.css:41-42,77-78`) — against **264** raw `--mc-space-*` references and 17 direct `--mc-control-*` heights across every other recipe (`button.css:93-108`, `input.css:10`, `select.css:16`, …). Flipping a future `data-density="compact"` overlay would change table geometry and nothing else. The retrofit is exactly the pain the aliases were meant to prevent: re-plumbing every control recipe's height/padding onto density-responsive aliases. Do it now (or formally re-scope the axis to "data surfaces only" and amend the design language — that is a legitimate owner decision, but make it deliberately).
- **Naming collision inside density:** DataTable's per-table View-menu option uses `data-density="compact"` _on the table element_ (`data-table.css:119-124`) — the same attribute name the global `<html>` axis will use. Rename the table-local one (e.g. `data-row-density`) before the axis lands, or descendant selectors will read a user's global preference as a table option and vice versa.
- **Motion — the specced mechanism was never built.** Design spec §2.2 (`2026-06-10-design-system-foundation-design.md:38`) and design language §7 (`2026-06-12-design-language.md:133`) mandate a `motion.reduced-scalar` every animation multiplies by. `tokens/primitives/motion.json` has only duration/easing — no scalar; reduced motion today is per-recipe `@media (prefers-reduced-motion: reduce)` blocks (`styles/recipes/presence.css:38-43`, `tabs.css:69-73`) plus the JS gate in `internal/view-transition.ts:20-26`. A binary media query cannot express the three-level axis (full/reduced/off). Important constraint: the purity gate bans `calc()`, so recipes _cannot_ multiply by a scalar. The clean in-architecture fix is to model **motion as a resolver modifier** (contexts `full`/`reduced`/`off` re-pointing the `duration.*` primitives, `off` → `0ms`), emitted as `:root[data-motion="…"]` overlays — recipes stay untouched, the `@media` blocks become redundant-but-harmless defaults, and compliance becomes structural as designed. Additive _if done now_; retrofitting after more animation accretes means re-auditing every `animation-duration` site.
- **High-contrast — structurally reserved (`resolver.json:43-49`), genuinely additive at the token level.** But recipes already draw structure with devices that die under forced-colors/WHCM: the selected-row gilt bar is a transparent border that gets colored (`data-table.css:84-90` — survives), the sidebar active bar is an inset `box-shadow` (`sidebar.css:138` — box-shadows are removed in forced-colors), and collapsed labels hide via `color: transparent` (`sidebar.css:169` — forced-colors overrides color). No `@media (forced-colors: active)` exists anywhere. Not urgent, but audit before first client — legal/government buyers disproportionately include WHCM users.

**px tracking — unsound as designed; there is an in-spec fix.** `tracking.caps` is `1px` "≈0.09em at the xs size" (`typography.json:54-62`). The type scale is rem-based precisely so OS/browser text-size scaling grows the UI (`design-language.md:84`), but px tracking does not scale with it: at 200% text size the caps voice's letterspacing _halves_ relative to the glyphs (0.09em → 0.045em) — the register visibly tightens for exactly the low-vision users the rem decision serves. `em` would be ideal but DTCG 2025.10 dimensions are limited to `px|rem` — so use **rem**: `0.0675rem` (≈0.09em at the 0.75rem size the voice is pinned to) scales with root text size for free. Same for `tracking.wordmark` and `tracking.tight` (`-0.16px` → `-0.01rem`). Two-line token edit + golden re-pin now; a multi-size problem never materializes because each voice already gets its own token (the "multiple sizes" objection to px is solved by the one-token-per-voice pattern, not by unit choice — but the _scaling_ defect only rem/em solve).

## 2. Recipe layer — sound

**The grammar demonstrably works at 36 components** (`src/lib/styles/components.css:12-48` imports; the gate at `test/fitness/boundaries.test.ts:203-460` scans every recipe file with a real parser, no escape valve). The workarounds it has forced are documented and bounded:

- **Indicator child elements instead of pseudos** (`tabs.css:55-62` + `tabs-trigger.svelte`) — the cost is one extra DOM node per trigger and every future ornament (gilt bars, engraved rules, corner ticks) being markup. At ~80 components this stays workable, but the Engraved Ledger register is ornament-forward; recommend a **single deliberate widening: allow `content: ""` (empty string only) as a structural keyword** — it carries no design value, is trivially gateable (exact-match), and removes the most common contortion. The area CLAUDE.md already anticipates exactly this ("bare `0`, `calc(…)`, and `content: ""` … need tokens or a deliberate, reviewed gate widening", `packages/design-system/CLAUDE.md:99-102`).
- **The `calc()` ban** produced the per-side-border date-range ring instead of box-shadow offsets (`CLAUDE.md:156`) — a genuinely better outcome, as it happens. Keep the ban.
- **Good precedents already in the grammar:** `fr` track factors admitted with rationale (`boundaries.test.ts:245-252`), the `flex-grow`/`flex-shrink` trap closed with its own scanner (`boundaries.test.ts:332-350`), keyframes with structural literals exiled to `animations.css:1-22` with a written justification. The grammar is being tended, not just enforced.
- **`--mc-space-0` as universal zero** (72 uses) is semantic noise ("space" meaning "outline-width") but harmless; a dedicated `--mc-length-0` would read better and costs one token if it ever grates.

**@layer + Tailwind v4 layering — robust, one documented dependency.** Recipes slot into Tailwind's own `components` layer so utilities always win consumer overrides (`components.css:5-7`; `apps/web/src/app.css:10-15` import order). This holds **only when the consuming stylesheet imports `tailwindcss` first to declare layer order** — true today in both entries (`app.css`, `.storybook/preview.css:14`). The future portal shell and any Tauri webview entry must repeat this exact import contract; it is stated in a comment, not tested. The preview/app mirror has _already drifted once_ (fonts, below) — add a mirror test like the existing `boot-script-mirror.test.ts`.

**App-level composition:** apps consume components + layout utilities only; "no styled raw HTML outside the design system" is a review rule (`docs/conventions/ui-design.md:62`), not yet a gate. That is the right call for now — the recipe grammar should not extend to app CSS because app CSS should not exist.

## 3. Composition boundary — needs-attention

The line is clean below the component level and undrawn above it, and 0·7b lands exactly on the undrawn part. Recommended placements:

- **App Shell.** Parts in the design system, assembly in the app. `Sidebar` is already a design-system component (`components/sidebar/`); the shell composition exists only as a story (`src/stories/app-shell.stories.svelte`). Keep: **design-system owns the chrome parts** (Sidebar, TopBar, BrandMark, the timer/alert _slots_) because desktop parity (golden rule 6) and the portal shell both re-consume them; **apps/web owns the assembled AppShell**, the nav _registry_ (data-driven, role-filtered — `docs/specs/2026-06-12-page-archetypes.md:37-52`), and route wiring, because permissions and module flags are domain knowledge that must never enter the design system.
- **Page mastheads: design-system component, and it is the missing register keystone.** `font.display` (Fraunces) is tokenized (`typography.json:18-22`) and loaded, but has **zero recipe consumers** — the serif-masthead half of the approved register is unbuilt. The masthead is a system voice (identical everywhere, ceremonial edge), so it must be a component (`Masthead`/`PageHeader`) — and note `font.display` is deliberately _not_ mapped to a Tailwind utility (`terrazzo.config.mjs:48-51`), which is correct: it structurally prevents apps from sprinkling serif anywhere except through the component. Build it before 0·7b (auth is a ceremonial surface).
- **Ledger voice: split it.** Money _formatting_ (minor-units → string, muted cents) belongs to `@magna-carta/money` + a design-system `MoneyText`/`MoneyCell` that applies `font-variant-numeric: tabular-nums` (the `data-align="end"` pattern already exists, `data-table.css:93-97`). The **double-rule total is a recipe**, and pleasingly the grammar already permits it: `border-block-start-style: double` is a structural keyword — `mc-ledger-total` needs no gate change. Domain meaning ("this row is a trust balance") stays in the app.
- **Status pills for domain states:** three homes — the _colors_ in design-tokens (`status.trust/hold/conflict` when their slices land), the _pill_ in design-system (Badge, variants as data), the _state→variant mapping_ in apps/web feature code. Never let the design system know what a "conflict" is.
- **Page archetypes: specs, not components — harvest on the rule of two.** First List/Detail screens are built in apps/web against the archetype doc; when the second screen repeats the skeleton, extract the layout grammar (grid + state-set slots) into design-system blocks. Extracting before a second consumer exists would freeze guesses. The state-set requirement (empty/loading/error/dense) stays a review gate (`ui-design.md:63`).

## 4. Dark mode + theming — sound

**The two-layer factoring (mode re-points ramp _positions_, themes swap ramp _values_) is correct and mechanically enforced.** Themes swap only neutral+brand ramps (`tokens/themes/verdigris.json:2` — "Status mini-ramps stay shared"); gold and status hues are theme-invariant; dark is one shared overlay (`tokens/modes/dark.json`). Because the Engraved Ledger register is built entirely from semantic roles — hairlines = `border.default` (a _tinted_ neutral step in every theme, so "ink-tinted hairlines, never gray" holds automatically per theme), gold = shared accent ramp, pale-tint status = shared mini-ramps — it survives 6 themes × 2 modes **without per-theme special-casing by construction**, and the contrast gate proves the declared pairs in all 12 contexts. This is the strongest part of the architecture.

Three specific gaps (design-pass items, not re-architecture):

1. **`surface.sunken` collapses into `surface.default` in dark** (`dark.json:3,5` — both `neutral.1000`): the table header fill (`data-table.css:43`) and any sunken well disappear, leaving hairlines alone to carry structure. Possibly intended (flatter dark), but it is an _accidental_ property of one overlay line, and the owner's own notes flag "Dark mode pass for the A register (not yet mocked)" (`design-lab/NOTES.md:63`). Decide deliberately.
2. **Elevation is invisible in dark**: shadows are fixed near-black at 6–14% alpha (`tokens/primitives/shadow.json`), unoverridden in dark; floating surfaces rely on `overlay` (900) vs `default` (1000) plus a hairline. The wiring for a per-mode override exists (`tailwind.template.css:19` comment) — populate it (dark-mode elevation is usually a lighter surface tint or a stronger border, which the high-contrast axis machinery could also serve).
3. **Gold-on-dark is un-re-pointed**: `dark.json:37-41` overrides `accent.default/subtle/subtle-foreground` but not `accent.strong/strong-foreground`, so the gilt CTA (`button.css:58-65`) keeps its light-mode pairing in dark. It passes the AA gate in all contexts (`contrast-pairs.ts:88-92`) and bright-gold-on-dark is arguably the signature — but confirm it is a decision, not an omission, in the dark pass.

Also note the status-subtle tints being theme-invariant means a shared pale blue sits on Parchment's cream and Verdigris's stone-green surfaces — contrast is gated (foreground-on-tint is theme-invariant) but _harmony_ is only covered by the VRT×12 walk. That is what the owner review gate is for; no code change.

## 5. Motion architecture — sound; anime.js seam proposal

**Current state is coherent:** compositor-only keyframes (all of `animations.css:24-159` is transform/opacity), IN/OUT name-swap presence (`recipes/presence.css`), View Transitions for unavoidable layout (`internal/view-transition.ts`, the sidebar precedent `sidebar.css:9-15`), tokens for duration/easing. Two register reconciliations owed at the craft pass: the approved easing pair (out `0.23,1,0.32,1`, in-out `0.77,0,0.175,1` — `design-lab/NOTES.md:33-35`) does not match the token trio (`motion.json:9-14`), and the 500ms+ signature rung (`design-language.md:126`) is missing from the ladder (`motion.json:2-8` tops at 300ms).

**Where anime.js v4 slots in — the integration seam:**

1. **One module, one boundary.** `packages/design-system/src/lib/internal/signature-motion.ts` is the _only_ import site of `animejs` — the same discipline as `floating.ts` for z-index. Add a fitness gate cloning the bits-ui scanner (`test/fitness/boundaries.test.ts:80-100` pattern): any `"animejs"` module reference outside `internal/` fails CI. Components and apps call the wrapper; nothing imports the library.
2. **Lazy by construction.** The wrapper `await import("animejs")`s inside itself — signature moments only, never the hot path (golden rule 10; the same rule the GSAP plan carried, design spec `2026-06-10…design.md:113`). Functional motion stays CSS/View Transitions — anime.js is the _third lane_ (complex choreography), not a replacement for lanes one and two.
3. **CSP: verify empirically before adopting, using the harness you already own.** anime.js v4's WAAPI module drives `element.animate()` and its core engine writes `element.style` via CSSOM — both are the CSP-clean channels the spike verdict blessed (the banned channel is `setAttribute("style", …)` / injected `<style>`; `packages/design-system/CLAUDE.md:87-92`). Extend `test/csp-spike/` with one anime.js animation under strict `style-src` and assert the verdict, exactly as it asserts the bits-ui patch. Prefer the WAAPI module as the default engine.
4. **Compositor-only law, typed in.** The wrapper's API accepts only `transform`/`opacity` keyframe properties (a typed record, not pass-through), plus one documented exception: SVG `stroke-dashoffset` for the written-live wordmark (`svg.createDrawable` — v4 ships the DrawSVG-equivalent _and_ a text splitter, meaning MIT anime.js can fully supersede the design language's GSAP+DrawSVG+SplitText plan at `design-language.md:135`; record the supersession as the ADR when the first consumer lands, per the owner's note `design-lab/NOTES.md:41-51`). Stroke draw is paint-only on a ceremonial surface where nothing reflows — acceptable, but name it as the exception.
5. **Reduced motion is the wrapper's job — and this is the mandated first JS gate.** `CLAUDE.md:46-48`: "The first JS-driven animation must add the JS `prefersReducedMotion` gate — it does not exist yet." Extract the predicate from `view-transition.ts:20-26` into a shared `internal/motion-preference.ts` returning the three-level value — `matchMedia` OR the future `data-motion` html attribute (the 0·7b axis seam, read the DOM attribute so the wrapper needs no settings plumbing). `reduced`/`off` → jump to the end state (`seek(duration)`/complete callbacks), never "skip the callback" (end-state correctness is the structural guarantee). `runViewTransition` consumes the same predicate — one source of truth for all three motion lanes.
6. **Tokens stay authoritative.** The wrapper reads durations/easings at runtime via `getComputedStyle(document.documentElement).getPropertyValue("--mc-duration-…")` — JS choreography is token-fed like CSS. Add the signature rung + register easings to `motion.json` first so there is something to read.

## 6. Risks / debt

- **MUST-FIX: the app never loads its fonts.** `apps/web/src/app.css:10-15` imports tokens/animations/components but **not** `@magna-carta/design-system/styles/fonts.css`; only the Storybook preview does (`.storybook/preview.css:13`). The export exists (`design-system/package.json:50`), the fontsource deps are design-system-side (`package.json:63-65` — apps/web has none). The product currently renders the entire register in Segoe UI. The mirror comment in `fonts.css:3-4` claims app.css imports it — it doesn't. One-line fix + a preview/app mirror test.
- **Font loading strategy is undecided beyond "fallback until load."** Fontsource defaults to `font-display: swap` → FOUT on every cold load, and the fonts are `@import`ed (discovered late, after CSS parse). Before first client: `<link rel="preload">` the two critical latin woff2 in `app.html`, and add a metric-compatible fallback (`@font-face` override with `size-adjust`/`ascent-override` against Arial) so the swap doesn't reflow — cheap now, fiddly after screens multiply.
- **rem/px mixing under text-only scaling.** Type is rem (the stated WCAG 1.4.4 rationale) but control heights are fixed px (`button.css:93-108 block-size`, `input.css:10`). Full-page zoom is fine; OS/browser _text-size_ scaling grows glyphs inside non-growing 36px controls → clipping at large settings. Sidebar already uses `min-block-size` (`sidebar.css:42,105`) — make that the recipe-wide rule for control heights. (Whether the _space_ scale should be rem is a bigger judgment call; the min-height change captures most of the value.)
- **Sidebar view-transition at app scale — measure before generalizing.** Only one ViewTransition can run per document: a route-level `onNavigate` transition (the natural next adopter) and a collapse will preempt each other, and the full work-canvas snapshot (`mc-app-canvas`) on every collapse could jank on data-heavy billing tables. Keep the pattern, profile it on the load-profile harness before making it the platform-wide idiom (`ui-design.md:61` already anoints it).
- **Virtualization gap on the DataTable.** virtua wraps Combobox (`internal/virtual-list.svelte`) but the table is unvirtualized; trust/billing screens are the 10k-row surfaces. Table virtualization fights table semantics (role=row / display:contents) — plan it before the Phase-3 money screens, not during.
- **RTL: in excellent shape — lock it in.** Recipes are near-uniformly logical-property based; the only physical properties in the entire recipe set are the scrollbar's `width`/`height` (`styles/recipes/scrollbar.css:13-14`, fine). Add a cheap fitness rule banning physical box properties in recipes so the discipline survives 50 more components.
- **Print: nothing exists.** Zero `@media print` in the repo; the design language sells "print-clean." Decide the boundary deliberately: document/letterhead output belongs to the PDF engine (already a program), but browser-printed _screens_ (a ledger, a pre-bill review) will happen at a law firm whether you design for it or not. A minimal print stylesheet for table/ledger surfaces before first client.
- **Smaller items:** z-order `dropdown(1000) < sticky(1100)` decision still open (`z-index.json`, flagged `CLAUDE.md:195-196`) — settle before the shell ships sticky headers; the `--mc-text-*` color/size namespace collision (§1); the DataTable `data-density` attribute collision (§1); fractional-DPR hairline weight is a known accepted-or-snap decision for this review (`CLAUDE.md:197-209`).

## Prioritized recommendations

**Now (this craft pass — cheap while the surface is small):**

1. Import `fonts.css` in `apps/web/src/app.css` + preload critical woff2 in `app.html`; add the preview/app mirror test. (must-fix)
2. Convert tracking tokens px → rem (`tracking.caps` ≈ `0.0675rem`, `wordmark`, `tight`); regen + re-pin goldens.
3. Build the motion axis as a **resolver modifier** (`full`/`reduced`/`off` re-pointing `duration.*`), add the signature duration rung + the two register easings; extend the boot script/`theme-preference.ts` seam to carry `data-motion` (and `data-density`/`data-typeface`) alongside theme/mode.
4. Prove the density axis or re-scope it: add compact values + the `data-density` overlay and route control-recipe geometry through `density.*` aliases — or amend the design language to scope density to data surfaces. Rename DataTable's local `data-density`.
5. Add `surface.selected` (and `surface.field`) semantic tokens; stop overloading `action.secondary` for selection.
6. Grammar widening: admit `content: ""` as structural; add the physical-property (RTL) recipe gate.
7. anime.js adoption kit: `internal/signature-motion.ts` seam + shared `motion-preference.ts` (extracted from `view-transition.ts`) + `animejs` import-boundary gate + csp-spike extension. Record the GSAP-supersession ADR with the first consumer.

**Before 0·7b:** 8. Build `Masthead`/`PageHeader` as the first `font.display` consumer (auth is ceremonial); settle the shell split — parts in design-system, assembly + nav registry in apps/web. 9. Dark design pass: `surface.sunken` vs `default` in dark, dark elevation values, gilt-CTA-in-dark confirmation; VRT the register in dark across the gallery. 10. `min-block-size` sweep for control recipes (text-scaling resilience). 11. Settle the z-order `dropdown`/`sticky` decision before the shell ships.

**Before first client:** 12. forced-colors / `prefers-contrast` audit; populate (or partially populate) the reserved contrast axis; fix shadow-drawn and `color: transparent` structure under WHCM. 13. Print boundary decision + a minimal print stylesheet for ledger/table surfaces. 14. DataTable virtualization plan ahead of the Phase-3 money screens; profile the view-transition pattern at app scale. 15. Ledger-voice components (`MoneyText`/`MoneyCell`, `mc-ledger-total` double rule — grammar-legal today via `border-style: double`) paired with `@magna-carta/money`; `status.trust/hold/conflict` tokens as their slices land.

The foundation is genuinely strong — the token/gate machinery, the theming factoring, and the recipe discipline are better than most mature systems. The debt is concentrated where the spec's claims outran the build (density, the motion scalar) and at the composition seam the next slice needs.
