Scan engine performance: where the time goes

A 1 GiB file today scans in ~110 s. The engine itself could do it in ~16 s. Here is the entire gap, what we have already closed, and what's left — measured, not guessed.

All numbers measured inside the container (no host network), on random data, single scan. Throughput = MiB / s.

2 Where 256 MiB of scan time actually goes

Same scan, three configurations. The strategy is to peel off the overhead layers until only the irreducible work — clamd's actual scan — remains. Shorter is faster; the green floor is the real work.

Nagle / delayed-ACK stalls — fixed INSTREAM structural cost (temp-spool + 1 KiB reads) — next target clamd scan — irreducible (the 63 MiB/s work)

Decomposition is approximate but grounded: clamd's real scan of 256 MiB ≈ 4 s (from the 63 MiB/s direct measurement); the rest is delivery overhead, split by the before/after-NODELAY delta (~26 s of that was Nagle stalls, 256 chunks × ~200 ms).

A file's journey through the scanner. Two stages add almost all the overhead. We've eliminated the first; the second is structural to INSTREAM and only a direct file scan removes it.

clamd reads the socket 1 KiB at a time and spools the whole stream to a temp file, then scans that. INSTREAM = receive + temp-write + scan.

The actual signature + heuristic pass over the bytes. One thread, one core.

Stage 4 is the whole story now: a direct SCAN <path> lets clamd open and read the file itself — no socket copy, no spool — collapsing stage 4 to ~0 and landing on the stage 5 floor.

4 How we get faster

In priority order. The first is done; the second is the big remaining win.

DONE TCP_NODELAY + 1 MiB chunks

Drive INSTREAM directly and disable Nagle so each frame ships immediately. Removed the ~200 ms per-chunk stalls.

4.7 → ~9–10 MiB/s · ~2×

NEXT File-based SCAN

Write the buffered body to a tmpfs file, send clamd zSCAN <path> over the existing socket, delete after. clamd reads it directly — no INSTREAM copy or spool. The path to the engine's native rate.

~10 → ~63 MiB/s · ~6× → 1 GiB in ~16 s

WITH YARA Concurrent engines

Today clamd → yara → heuristics run in series, but yara is rule-less (free). Once the YARA-Forge corpus is baked, run them in parallel (spawn_blocking) so the total is max(clamd, yara), not the sum.

~halves large-file latency once yara is a real cost

5 Legitimate limits — the walls we can't move

Honesty about the floor. After file-based SCAN, these are what's left, and most are fundamental.

WALL One file = one core

A single scan is single-threaded inside libclamav. ~63 MiB/s is one core's rate with the full signature DB on this CPU. You cannot safely split one file across cores — malware signatures span chunk boundaries, so a split scan can miss a threat straddling the cut.

≈ 16 s / GiB is the realistic single-file floor

OFF-LIMITS Don't scan less

You could go faster by lowering MaxScanSize, skipping archives, or shortening recursion — but every one of those speeds the scan up by scanning less, i.e. weakening detection. For a legal-docs platform that's not on the table.

speed that costs coverage isn't speed we want

COMING YARA-X is a real cost

YARA scans the whole file in one linear pass. With a YARA-Forge-scale corpus, expect ~10–30 MiB/s over a large buffer — co-equal with clamd. Concurrency hides it behind clamd's time but doesn't make it free.

plan for it; overlap it; can't erase it

6 Future avenues — and their ceilings

Beyond single-file latency, the real scaling lever is throughput across files, which the async design is already built for.

  • File-based SCAN → the next ~6×, lands at clamd's native ~63 MiB/s. Ceiling: stage-5 single-core scan.
  • Concurrent engines (clamd ∥ yara) → folds yara's future cost under clamd's wall-time. Ceiling: max(clamd, yara), not lower.
  • tmpfs for clamd's temp dir → a marginal extra on top of SCAN (RAM-speed spill). Mostly moot once SCAN removes the spool.
  • Horizontal scale-out → more container instances scan different files in parallel. This is how you raise throughput (files/sec) without limit. Ceiling: $ per instance, and the per-instance memory needed for a 2 GiB scan.
  • The architecture already hides latency → scanning is asynchronous: an upload returns instantly, the file becomes usable when its background scan finishes. So a 16-second scan is never a user-blocking wait — it's queue-drain latency, which scale-out addresses.

The honest summary: we can take a single 1 GiB file from ~110 s → ~16 s (file-based SCAN), and that ~16 s is the wall for one file on one core. Everything past that is scale-out for throughput, not making one file scan faster — and because scanning is background work, throughput is what actually matters at volume.

7 The recommendation

Ship file-based SCAN next — it's the single change that closes most of the remaining gap (~10 → ~63 MiB/s), works over the socket we already have, and is roughly memory-neutral vs INSTREAM. The two things to get right: bulletproof temp-file cleanup (a leaked 2 GiB blob is a RAM-exhaustion DoS) and a small instance-size note for full-size scans. Bake the YARA corpus and add engine concurrency together, as one unit, when that lands.
