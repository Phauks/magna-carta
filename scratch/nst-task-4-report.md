## What `speedtest.d.ts` actually declares

Read from `apps/web/node_modules/@cloudflare/speedtest/dist/speedtest.d.ts` after `vp install`.

- **Default export**: `SpeedTestEngine` (aliased `SpeedTest` on import), extending `MeasurementEngine`.
- **Constructor**: `constructor(userConfig?: ConfigOptions)` where `ConfigOptions = Partial<Config>`;
  `Config.autoStart: boolean` — matches the plan's `new SpeedTest({ autoStart: false })`.
- **Callbacks**: `onRunningChange: (running: boolean) => void` (unused here); `onResultsChange:
(payload: { type: MeasurementType }) => void` — takes a payload argument (the plan's zero-arg
  `() => {...}` is still a valid assignment under TS's function-parameter-count variance); `set
onFinish(f: (results: Results) => void)` and `set onError(f: (message: string) => void)` are
  **setter-only accessors**, not plain fields — assignment syntax (`instance.onFinish = ...`) is
  identical either way, but a variable typed to include `onFinish`/`onError` as _readable_ fields
  would not structurally match. I sidestepped this by keeping the local `engine` variable's type to
  only `{ play(): void; pause(): void; restart(): void }` — the callbacks are wired once directly on
  `instance` at construction, before it is ever narrowed to `engine`.
- **`Results` methods used**: `getDownloadBandwidth(): number | undefined`,
  `getUploadBandwidth(): number | undefined`, `getUnloadedLatency(): number | undefined`,
  `getUnloadedJitter(): number | null | undefined` (the plan's structural type omitted `null`),
  `getDownLoadedLatency(): number | undefined`, `getUpLoadedLatency(): number | undefined`,
  `getDownloadBandwidthPoints(): BandwidthPoint[]`, `getUploadBandwidthPoints(): BandwidthPoint[]`,
  `getUnloadedLatencyPoints(): number[]`, `getDownLoadedLatencyPoints(): number[]`,
  `getUpLoadedLatencyPoints(): number[]`, `getPacketLoss(): number | undefined` (not called — packet
  loss is deliberately not measured per the module's own comment), `getSummary(): MeasurementSummary`
  (not used by this page), `getScores(): Scores`.
- **`getScores()` return type, exactly**: `Scores = Record<string, ExperienceScore>` where
  `ExperienceScore = { points: number; classificationIdx: number; classificationName:
'bad' | 'poor' | 'average' | 'good' | 'great' }`. Keys are experience names (e.g. streaming,
  gaming, RTC) defined by the library's internal `aimExperiencesDefs`.

## Other deviations from the plan's literal code, and why

1. **Token substitution**: `text-status-critical-subtle-foreground` does not exist. Checked
   `packages/design-tokens/generated/tailwind-theme.css` — there is no `critical` status tier, only
   `--color-status-{info,success,warning,danger}-*`. Used `text-status-danger-subtle-foreground`
   instead (the real token for this severity).
2. **`border-border-strong` and `--mc-tracking-caps`**: both verified present (`--color-border-strong`
   in `tailwind-theme.css`; `--mc-tracking-caps: 0.0675rem` in `packages/design-tokens/generated/
tokens.css`, already consumed the same way in `apps/web/src/lib/matters/section-stub.svelte` and
   `apps/web/src/routes/(app)/tools/+page.svelte`). Used as written.
3. **Spacing**: kept `mb-24`/`mb-16`/`mt-16`/`gap-16` (all on the closed 0/4/8/12/16/20/24/32/40/48/64/96
   scale) rather than the plan's `mb-12`/`mt-4`/`mt-8`/`gap-8` — both sets are valid scale values; I
   matched the sibling `/tools/+page.svelte`'s actual rhythm (`Masthead.Root class="mb-24"`, section
   headers `mb-16`/`pb-8`) rather than the plan's slightly different numbers, for visual consistency
   with the page it's a sibling of. Not a token-validity fix, a consistency choice — flagging in case
   the coordinator wants it to match the plan's numbers exactly instead.
4. **`Card.Content` wrapper in `metric-tile.svelte`**: `.mc-card` (Card.Root) only carries block
   (vertical) padding; inline (horizontal) padding lives on `.mc-card-header`/`.mc-card-content`/
   `.mc-card-footer`. The plan's literal code put the label/value/note divs directly inside
   `Card.Root` with no horizontal padding, which would touch the card's border. Wrapped them in
   `Card.Content` (which the design system exports and other pages use) to get the `padding-inline`
   rule.
5. **Engine store — reactivity fix (the significant deviation)**: the plan's `speed-test-engine.svelte.ts`
   reassigns `results = instance.results as unknown as SpeedTestResults` on every `onResultsChange`/
   `onFinish`. Per `Results`'s own doc comment, the engine mutates one `Results` instance's `raw` field
   in place rather than replacing it — `instance.results` returns the **same object reference** every
   time. I confirmed via the Svelte `$state` docs ("If the new value ... is referentially identical to
   its previous value, downstream updates will be skipped" — the general push-pull/reference-equality
   rule, and separately "Class instances are not proxied", so a `Results` instance never becomes a deep
   reactive proxy either) that reassigning the same reference to a `$state` variable is a no-op for
   reactivity: the template would never repaint mid-run, and might not even repaint on `onFinish` if the
   finished-results object is the same instance passed throughout. I replaced the direct
   `as unknown as` cast with a `snapshotResults(source: Results): SpeedTestResults` helper that returns
   a **fresh plain object** on every call, each of whose methods delegates live to the real instance
   (`() => source.getDownloadBandwidth()`, etc.) — so every publish gets a new reference (state update
   never skipped) while every read stays live off the one real engine instance. Also folded the
   duplicated probe-kickoff code (present twice in the plan: once in `start()`, once in `restart()`)
   into one `runProbe()` helper — a minor simplification, not a correctness fix.
6. **`getUnloadedJitter()` null handling**: real return type is `number | null | undefined` (null when
   fewer than 2 samples), not `number | undefined` as the plan's structural interface had it. Widened
   the interface's honesty by coercing at the snapshot boundary — `getUnloadedJitter: () =>
source.getUnloadedJitter() ?? undefined` — so the public `SpeedTestResults` interface stays
   `number | undefined` (compatible with `formatMilliseconds`) and "not enough samples yet" reads the
   same as "not measured yet", which is honest (both are "no number to show").
7. **`formatRatio`**: the plan's Task 4 "Consumes" line lists `formatRatio` from Task 3, but Task 3's
   actual shipped `speed-test-format.ts` (already on this branch) only exports `formatBandwidth` and
   `formatMilliseconds` — no `formatRatio` exists, and Task 4's literal page code never calls one
   (Packet loss renders as a static "Unavailable" + reason note, not a formatted ratio). Did not
   fabricate it; this looks like a stale mention from an earlier draft before packet loss was
   descoped to a static statement.
